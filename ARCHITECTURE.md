# Whoopsy Architecture Guide: Clean Architecture & Local-First Design

## 1. Architectural Philosophy

**Whoopsy** is designed from the ground up as a **100% offline-first, subscription-free, privacy-preserving** iOS companion application for WHOOP® straps (Gen 4 and Gen 5).

To guarantee scalability, testability, and clear separation of concerns, Whoopsy strictly enforces **Clean Architecture** (Robert C. Martin / Uncle Bob) combined with **Domain-Driven Design (DDD)** and modern Swift Concurrency (`async`/`await`, `AsyncStream`, `Sendable`).

```
+-----------------------------------------------------------------------+
|                         PRESENTATION LAYER                            |
|  - SwiftUI Views (Glassmorphism, Neon Gauges, Hypnograms)             |
|  - ViewModels (@Observable, Unidirectional Data Flow, UI State)       |
|  - 1:1 Official WHOOP Layout (Tabs: Home, Strain, Sleep, Recovery...) |
+-----------------------------------+-----------------------------------+
                                    |
                                    v (Uses)
+-----------------------------------------------------------------------+
|                           DOMAIN LAYER                                |
|  - Entities (BiometricSample, RecoveryMetric, StrainScore, Sleep,     |
|    StressScore)                                                       |

|    AnalyzeSleep, AnalyzeStress, ...)                                  |
|  - Repository Interfaces (Inversion of Control Contracts)             |
+-----------------------------------+-----------------------------------+
                                    ^
                                    | (Implements Contracts)
+-----------------------------------+-----------------------------------+
```

## 2. Layer Definitions & Boundaries

### A. Domain Layer (The Core)
* **Zero External Dependencies**: Does not import `UIKit`, `SwiftUI`, `CoreBluetooth`, `HealthKit`, or `GRDB`.
* **Entities**: Pure immutable Swift structs representing core physiological models (`BiometricSample`, `RecoveryMetric`, `HRVMetric`, `HealthImportSummary`, `WhoopImportSummary`, `StrainScore`, `StressScore`, `StressDay`, `StressWindow`, `MetricWeek`, `MetricDay`, `SleepSession`, `UserProfile`, `WhoopDevice`). `StressScore`, `StressDay` and `StressWindow` are derived on read and never stored — they are a function of `biometric_samples` and nothing else, so a persisted copy could only disagree with the samples it came from. None has a placeholder instance or a zero value: a day with no eligible window has no score and no series at all. `StressDay` is the aggregate *and* the series in one value, and it computes its `StressScore` from the windows it was handed rather than accepting one beside them — so a score describing a different day than the line beneath it is not a bug to guard against, it is unconstructible. `MetricWeek` and `MetricDay` are the same bargain for a *week*: the seven-day join behind Home's Strain & Recovery chart and its four metric panels, derived on read from three stored histories plus one per-week scalar (the profile's maximal heart rate, which the VO₂ estimate is computed from) and stored nowhere. The VO₂ estimate is the one field on a slot that comes off another field of *the same slot* rather than off a row — `makeDay` hoists the day's gated resting heart rate into one local and both the RESTING HEART RATE panel and the estimate read it — so the two can never describe different days. `MetricWeek` builds its slots from the **date sequence**, not from the rows, so a day with no data is an empty slot and never a shortened array — which is what stops a gap from sliding every later point one day to the left — and it computes each panel's rolling baseline as a plain mean over the measured slots only, `nil` below `minimumBaselineDays`. It deliberately takes no `calendar:` parameter: the database snaps day keys with `Calendar.current`, so a caller passing another zone would fail to match the rows rather than shift the week.

**A metric's absence is the same shape in all four: no row, and the optional is the answer.** `CalculateRecoveryUseCase` and `CalculateStrainUseCase` return an optional and write nothing for a day they could not measure, exactly as `AnalyzeSleepUseCase` and `AnalyzeStressUseCase` do, so a day with no data is absent from its table rather than present as a reserved zero — and a reader that forgets the rule sees an empty day rather than a fabricated one. `RecoveryMetric.hasMeasurement` and `StrainScore.hasMeasurement` remain, as **reader tolerance** for placeholder rows written before this rule: they keep those rows off the screens, out of the baselines and off the charts. `MetricWeek` is the one place that encodes all four rules side by side.
* **Use Cases (Interactors)**: Single-responsibility business logic units (e.g., `CalculateRecoveryUseCase`, `CalculateStrainUseCase`, `AnalyzeSleepUseCase`, `AnalyzeStressUseCase`, `StreamBiometricsUseCase`). `RecoveryScoring` is a pure scoring helper rather than a use case, shared by the strap path, the HealthKit import and the WHOOP export import so the weights exist in exactly one place. `AnalyzeStressUseCase` is the one Analyze use case that **never writes at all** — it reads samples and returns a value, with no repository to store it in — so unlike its siblings it cannot damage a stored day, and it is safe to point at any date. It has two entry points and one evaluation: `executeDay(for:) -> StressDay?` and `execute(for:) -> StressScore?`, the latter a forwarder returning `executeDay(for:)?.score` rather than a second implementation, so the two can never disagree about whether a day has a measurement.
* **Repository Interfaces**: Abstract Swift protocols defining data operations (e.g., `BiometricRepository`, `RecoveryRepository`, `WorkoutRepository`, `WhoopBLEDeviceRepository`, `HealthKitSyncing`, `WhoopExportImporting`).

### B. Data Layer (Infrastructure & Adapters)
* **BLE Engine**:
  - `WhoopBLEManager`: Direct interface with Apple's `CoreBluetooth`. Discovers peripherals, negotiates MTU, manages reconnects and bonding.
  - `WhoopPacketDecoder`: Decodes raw byte frames starting with `0xAA`, verifying CRC8 header integrity and CRC32 payload checksums, extracting HR, R-R intervals, accelerometer, SpO2, and skin temperature.
  - `WhoopMockBLEManager`: High-fidelity hardware simulator generating realistic physiological variations for UI development and unit testing without requiring physical hardware.
* **Persistence**:
  - `LocalDatabaseManager`: GRDB/SQLite store running entirely on-device in the app sandbox, migrated by `DatabaseMigrator` (currently `v1` … `v8`; `v5` adds the nullable `source` column to `recoveries`, `sleeps` and `strains`, `v6` adds `workouts`, `workout_route_points` and `workout_splits`, `v7` adds `strains.hasMeasurement` and backfills it, and `v8` adds the nullable `biometric_samples.rrIntervalsMs` holding the full per-notification R-R series as JSON text). **Column naming is per-table and decided by `CodingKeys`**: `RecoveryRecord` declares them and its columns are snake_case, while `StrainRecord` declares none so `strains`' columns are camelCase — a migration that assumes one convention for both dies at launch. **Migration identifiers are recorded but bodies are not checksummed, so a registered migration is frozen once shipped** — schema changes go in a new `registerMigration` block. A failing migration calls `fatalError` in `init`, so it crashes at launch rather than at the query.
  - `source` records which writer produced a row: `whoop_export` for a bulk import, `NULL` for a row the app measured itself through the strap or HealthKit. Nothing reads it yet; it exists so hundreds of imported rows stay distinguishable from local measurements if they ever need re-running or backing out.
  - `workouts` deliberately **breaks the day-key rule** the other metric tables follow. `recoveries`, `sleeps` and `strains` are primary-keyed on `date` snapped to `startOfDay`, because a day holds one of each; a day can hold several workouts, so `workouts` is keyed on `id` (a UUID string) with `date` as an ordinary indexed lookup column. `WorkoutRoutePointRecord` and `WorkoutSplitRecord` are separate tables keyed on their own `id` and bound to the session by a `workout_id` foreign key, fetched per workout rather than joined — a join would multiply the session row by its route points. The records live in `Data/Persistence/Models/WorkoutRecord.swift` as one file because the three are one aggregate.
  - `GRDBWorkoutRepository` is what makes a recorded workout survive the launch that recorded it. It replaced `LocalWorkoutRepository`, an actor wrapping an array that lost every session at the next launch.
  - Repositories implement domain protocols to convert GRDB records into immutable domain models, and they **answer from local storage only** — there are no fallback sources. A stored row maps to a model without inventing values: a column the strap never filled in becomes `nil` on the model, never a plausible constant, so "not measured" stays distinguishable from a measurement all the way to the screen.
  - History reads state the day their window **ends** on: `getRecoveryHistory(days:endingOn:)` and its `sleeps`/`strains` siblings, with `endingOn` defaulting to now for the scoring baselines and the JSON exporter. The end is a parameter rather than an assumption of `Date()` because the metric screens show a day the user picked, and a window anchored on *now* cannot describe it. The reads bound the top of the window too (`<= endingOn.endOfDay`) — without it, a window anchored on an old day runs on to the present.
* **Health**:
  - `HealthKitBridge`: The app's one HealthKit entry point, injected as `HealthKitSyncing`. Availability is a **runtime** question (`HKHealthStore.isHealthDataAvailable()`); `#if canImport(HealthKit)` is true on macOS and guards nothing.
  - `HealthStoreClient` / `HealthKitStoreClient`: A protocol over the health store plus its real implementation. The protocol's value types are plain `Sendable` structs with no HealthKit import, so the import mapping is testable with no device and no entitlement. It has two read shapes, and the difference matters: `quantitySamples(_:from:to:)` returns the individual readings a window holds, while `dailyTotal(_:from:to:)` returns one **sum** over it (`HKStatisticsQuery` with `.cumulativeSum`). Steps are the only quantity read through the second, because a step count is a cumulative daily total rather than a reading the app can file under a day key.
  - `HealthKitSyncing.stepCount(on:)` is now its **only** member that does **not** throw. HealthKit never discloses read-permission status, so a denial, an empty day, a device with no source for the quantity and an unavailable store are indistinguishable from the caller — and all of them are honestly the same dash. It is read through to the store on demand and never stored, so there is no table and no column for it and no copy to go stale. Its read shape is `dailyTotal`'s `.cumulativeSum`, because a step count is a cumulative daily total rather than a reading the app can file under a day key.
  - **The VO₂ MAX panel is no longer a read-through, and this is the second shape it has had.** It used to take `quantitySamples` for `HKQuantityTypeIdentifierVO2Max` — a per-sample read reduced to a day's *newest*, not its highest — and that path is **deleted at every layer**: no `vo2MaxReadings(days:endingOn:)` on `HealthKitSyncing`, no `.vo2Max` case on `HealthQuantityMetric`, and therefore no VO₂ max in `readTypes`, so the consent prompt no longer asks for it. The panel now prints an estimate this app computes — see §2.D `Vo2MaxMath` — which is why `HomeViewModel` takes a `userProfileRepository` it did not previously need. Do not "restore" the read-through on the assumption that a stored-derived value is a downgrade: two estimates of one quantity on one panel, on different days, with nothing to say which was which, is the outcome `ALGORITHMS.md` §6 rejects.
  - `HealthKitImporter`: Maps a window of HealthKit readings onto `recoveries` rows through the domain repositories. One row per day, SDNN only, and a day with no reading produces no row at all.
* **Import**:
  - `WhoopExportParser`: Reads WHOOP's `physiological_cycles.csv` into `WhoopExportRow` values — a plain `Sendable` struct of optionals, with no GRDB types and no decisions. Nothing about what an empty cell *means* is decided here, and a row whose date or timezone cannot be parsed **throws** rather than being skipped silently.
  - `WhoopExportImporter`: Walks the parsed rows in chronological order and writes day-keyed rows through the same domain repositories the strap uses. It day-keys on `startOfDay(Wake onset)`, scores each night through `RecoveryScoring` against the preceding 30 imported days — the window is `RecoveryScoring.baselineWindow(before:in:)`, shared with every other reader rather than owned here, because the Recovery detail screen prints the same baseline its score was computed from — and takes Strain verbatim because the export holds no heart-rate series. Days with an existing measurement are skipped, so the import is idempotent.
  - Injected as `WhoopExportImporting`, and triggered only from Settings. It is deliberately not a launch-time sync: ~900 days of history should not be written behind the user's back.
* **Exporters**:
  - `LocalDataExporter`: Generates standard JSON and CSV files for user-controlled backup and external analysis.

### C. Presentation Layer (SwiftUI + MVVM + Design System)
* **Declarative SwiftUI**: Optimized for iOS 17+ with smooth 120Hz ProMotion animations, dark-mode-first aesthetic, glowing gauges, and live ECG-style sparklines.
* **ViewModels**: Annotated with `@Observable`, accepting Use Cases via constructor injection. They emit discrete UI states (`Idle`, `Connecting`, `Streaming`, `Error`).
* **1:1 Official WHOOP App Layout Structure**:
  - `MainContainerView.swift`: Bottom navigation tab bar routing container. It builds **one** `ActiveWorkoutViewModel` and hands it to both Home and the Workout tab, so the `+` on Home and the Workout tab are two views of a single live session rather than two that could each believe they were recording.
  - `Home/`: Overview dashboard. A day stepper with a strap status badge, the three metric rings (`MetricRingView`), a **My Day** section holding the ACTIVITIES card (the day's sleep session and every recorded workout, each with its time range), and a **My Dashboard** tile grid (STEPS, RESTORATIVE SLEEP, then the full-width RESTING HEART RATE, SLEEP NEEDED, HEART RATE VARIABILITY and VO₂ MAX panels, the STRESS MONITOR tile and the STRAIN & RECOVERY chart tile). Every figure is measured, derived-on-read, or a dash — see the no-fabrication rules in `CLAUDE.md`. `HomeViewModel.load(for:)` is the reference implementation of day selection: it **reads** each day through the repositories and never touches a calculate use case, which would overwrite whatever the day already holds.
    - **The collapsing rings header.** Scrolled past, the three rings reappear as a compact sticky row (`collapsedHeader`, `MetricRingView` at `size: 40` with `showsLabel: false`) pinned to the top of the scroll view. iOS 17 has **no scroll-geometry API** — `onScrollGeometryChange` is iOS 18 — so the mechanism is a `PreferenceKey` (`RingsBottomKey`) publishing the rings row's `maxY` in a named coordinate space, read back through `overlayPreferenceValue`. The preference reports where the rings *are*, not a scroll offset, so there is no threshold constant to go stale when the top bar changes height; the ramp is `(52 − ringsBottom) / 52`, clamped. The overlay writes **no** `@State` — its transform runs every scroll frame, and a state write per frame would invalidate the whole screen. The `VStack` must stay a `VStack`: a `LazyVStack` may release the rings row once it is scrolled past, taking the preference publisher with it. The second half of this used to be a caveat: Home's content did not overflow its viewport, so the header was latent and unreachable. **The Strain & Recovery chart, the two panels and the five tiles now overflow it** — verified on device — so the collapsed header is live, not latent.
    - **The Stress Monitor chart** (`StressMonitorChartView`) draws the day's `StressWindow` series in the STRESS MONITOR tile: a full-day x-axis with the unscored hours shaded, a fixed 0–3 y-axis, band-coloured fill, and breaks where the record is not continuous. It draws nothing at all when the day has no series. The rules and their reasoning are in `ALGORITHMS.md` §5.
    - **The Strain & Recovery chart** (`StrainRecoveryChartView`) is the codebase's first **two-series, two-axis** chart: strain 0–21 on the left axis in `Theme.strainRing`, recovery 0–100% on the right axis with its four tick labels coloured by `RecoveryState(score:)`. Both axes are ticked at **thirds of their own range** (0/7/14/21 and 0/33/66/100) so one set of gridlines is honest for both. One column per `MetricWeek` slot — always seven, whether or not a slot holds anything — with the line **breaking** at an unmeasured slot rather than joining across days nobody measured, and **nothing drawn at all** when the whole week is empty. Only the highlighted day's two values are labelled. It is built on `StressMonitorChartView`'s idiom (private `Scale`, `Shape`s, data-space separated from screen-space, and the gradient/stop rules that go with it) rather than a shared chart component, because two charts is not yet a pattern worth extracting.
    - **The four metric panels — RHR, Sleep Needed, HRV and VO₂ Max** — share one `metricPanel(label:symbol:value:baselineText:change:changeColor:)` builder, and each prints a **7-day rolling mean of its own metric** as the small figure — not the previous day, and not `UserProfile.targetSleepHours`. The first two invert the tile grid's up-is-good rule: a resting heart rate or a sleep need *above* the baseline is the body asking for something, so it renders in `Theme.strainPrimary` rather than green; HRV follows the grid's own direction, because `RecoveryScoring` scores it upward. VO₂ Max prints **no change marker at all** and carries an **`(EST.)` label** — it is the one panel whose value is a model's output rather than a measurement, and it is the only one whose error bar is this app's to quote. The quantity moves over years and the estimate's own error is quoted in whole mL/(kg·min) — 4.7 for the method this app uses — so a day-to-day arrow would report the noise floor as a reading (see `ALGORITHMS.md` §6). The HRV mean is narrowed to a **single `HRVMetric`** before it is averaged, which is the never-mix rule reaching a second screen. The means and the two series come from **one** `MetricWeek`, so the chart and the panels cannot describe different days. Each panel's icon is drawn in `Theme.textMuted` with **no chip behind it**, and its label in `Theme.textPrimary` — the builder used to take a `tint:` that coloured both a glyph and a rounded tile of that same tint at 18%, which made four colours the only thing distinguishing one panel from another; the glyphs (a heart, a moon, a waveform, a pair of lungs) already do that, so the parameter is gone rather than left unused. The 38pt frame that sized the chip stays, because it is what keeps the four labels in the column at one x.
  - `Strain/`: Dedicated view for 0–21 scores, cardiovascular load, HR Zones 1–5, and strain target builder. A day with nothing stored renders `—` with no ring, and the zone card says "No zone data recorded." — imported days have no zone breakdown to show.
  - `Sleep/`: Hypnogram stages (Awake, Light, Deep, REM), performance %, and sleep debt calculations.
  - `Recovery/`: Z-score baseline algorithms, RMSSD HRV trends, resting heart rate, and respiratory tracking. The figures are `RecoveryDetailView`, which is deliberately **not** a tab: it carries no `NavigationStack` and is seeded with the day it opens on, so the Recovery tab (`RecoveryDashboardView`, now only the stack around it) and a tap on Home's recovery ring render one definition of the tier colour, the dash gates and the never-mix trend filter rather than two that drift. **The screen is a ring and a breakdown, and the breakdown is the point**: beneath the score is one row per input — HEART RATE VARIABILITY, RESTING HEART RATE, RESPIRATORY RATE, SLEEP PERFORMANCE — each printing the day's figure, a `MetricChange` triangle, and the trailing mean it was read against, so a reader can see *why* the ring says what it says. The means come from `RecoveryScoring.baselines(...)`, which `score(_:)` is itself built on, so the row and the ring cannot describe different windows (`ALGORITHMS.md` §3). The four rows do **not** share an absence rule and must not be given one: HRV and RHR gate on `hasMeasurement` (with RHR additionally on `> 0`), while respiratory rate and sleep performance are optionals with no reserved zero to gate — the strap has no respiratory sensor, and an unclassifiable night has no row at all. The 14-day trend card beneath them is kept from the previous layout, because it carries the never-mix caption and is the only place the day's HRV quantity is named. **The page carries no chrome above the ring at all**: no `DashboardHeader`, and no `DayNavigationBar`. Both were removed for the same reason — the page is one night's reading against one trailing window, and a title or a stepper above it is furniture that either restates what the reader just tapped or invites them to page the day out from under the figures. The no-data state survives the header's removal in the gauge's own label, which reads "No data" on a day with no measurement. **`RecoveryDetailView`'s day is handed in and fixed** — `private let date`, a plain `let` rather than a `@State`, because nothing can change it: the Recovery tab passes `Date()` and Home's ring pushes the day on screen. It is the one day-keyed screen without a stepper, and the consequence is worth stating plainly: on an install whose history is all imported, the Recovery *tab* opens on today, which is past the export's end, and shows a dash with no way to page back. Every past day is still reachable through the ring, which is the route that exists for this. Two things in the app this was modelled on are deliberately not drawn, and the reason is in the view's own doc comment: the WHOOP wordmark (another company's brand, in the one position on a screen that says whose app it is — which is now simply empty rather than holding a substitute) and the `i` button beside the ring (no destination — the affordance rule below).
  - `Coach/`: Local/API AI insights and Voice of Whoop conversational review cards.
  - `Device/`: BLE hardware pairing, battery status, firmware details, and live HR broadcast modes.
  - `Settings/`: Data privacy toggles, local SQLite backup exports, and UI configuration options. Hosts the one-shot WHOOP-export import button — the only entry point to `WhoopExportImporter`.
* **Day selection**: `DayNavigationBar` (in `Presentation/DesignSystem/`) is the one day stepper, shared by **Home, Strain and Sleep** — and deliberately not by Recovery, which is handed a fixed day instead (see the `Recovery/` row above; its four rows describe one night against one trailing window, and paging away would leave the window explaining a day no longer on screen). Each of the three owns a **private** `selectedDate` — deliberately independent, so paging one tab does not move another — and each loads that day by **reading** it through its repositories. The calculate use cases those three screens used to call are now unreachable for a past day, because they write without checking what is already stored. Two of the bar's three behaviours are rules about the **date** rather than about data, so they hold wherever it is drawn and live in `DayBarRules`: the centre reads `TODAY` when the day is today, and the forward chevron stops there — a day that has not happened is empty everywhere, and leaving the clamp to the screens that happen to pass a calendar would give the app two day steppers that disagree about the future. `DayBarRules` also takes `now` as a parameter, which is what lets the runner assert both rules without a renderer and without a clock (`Domain`, and therefore a `Color`-free helper, cannot be where they live — they are a `Presentation` rule about a label).
* **DesignSystem**: Reusable design tokens, glassmorphic card containers, the shared `DayNavigationBar` day stepper, the month calendar (`MonthGrid` + `Components/MonthCalendarView`), and signature neon color palettes (Recovery Green/Yellow/Red, Strain orange-red scales). All colours are tokens in `Theme.swift` — including the Home surfaces (`homeBackground`, `homeCard`, `ringTrack`, `sleepPerformance`, `strainRing`), which were literals inside `HomeDashboardView` until the Home rebuild and are what `DayNavigationBar` used to carry a private copy of. `Components/MetricChange.swift` is the one definition of a **comparison between a figure and the value it is read against** — which way it moved, and whether that direction is good news — shared by Home's four metric panels and the Recovery breakdown's four rows. It was Home's private `TileChange` until a second screen drew the same thing; the lift is the one-rule-one-definition discipline applied to a component, and the two decisions it holds are exactly the two a copy drifts on. **Direction and verdict are separate by construction**: the triangle always points the way the number went, and `higherIsBetter` alone decides whether that is `Theme.recoveryGreen` or `Theme.strainPrimary` — so an HRV rise is green while a resting-heart-rate rise is orange, from one call. Two further rules are worth knowing because both produce a wrong arrow that looks plausible: the comparison is made on the **formatted** pair, not the raw one (a resting rate of 52 against a mean of 52.4 is genuinely below it, but both print as `52`, and a row reading `52 ▼ 52` contradicts itself), and `nil` — no triangle, just the mean — covers a missing day, a missing baseline, and a day that *is* its own mean.
* **The month calendar is Home's, and it is opt-in on the shared bar.** `DayNavigationBar` takes an optional `onTitleTap`, and Home is the only caller that passes one; where it is `nil` the centre stays the plain `Text` it always was, because a title that looks tappable and has nowhere to go reads as broken — the same rule that keeps `CUSTOMIZE` and the ACTIVITIES expand icon off the screen. Opening it is an **overlay**, not a `.sheet`: a sheet is a full-height card the system centres, which left the grid floating in a dark slab with the app's own screen invisible behind it, whereas the calendar is a small bounded thing that reads as one only when it hangs from the top of the safe area with the day it is choosing between still legible under a partial (`0.45` black) scrim. Home hides the tab bar while it is up — an overlay inside a tab cannot cover the bar, and a live row of tabs under a modal both looks wrong and lets a tab switch strand the calendar open. `MonthGrid` is a pure value that derives the weekday header and the leading blanks from **one** `firstWeekday` rotation so the two cannot drift, and `MonthCalendarView` is dumb: values in, closures out.
* **Two ring components, deliberately.** `GaugeRingView` draws an angular gradient, an outer glow, and its label *inside* the ring; Strain, Sleep, Recovery and the workout HUD depend on that look. `MetricRingView` is the flat counterpart Home's mockup calls for — neutral track, value centred, label beneath — and is a sibling rather than a mode of `GaugeRingView`, so restyling one screen does not move four. `MetricRingView` takes its value as an **optional** `String?`: a caller passing a dash cannot also pass a fill, so the ring cannot contradict itself. It also takes `showsLabel` (defaulted `true`, so the three existing call sites do not move), which Home's collapsed header sets to `false` — its label font is fixed at 10pt rather than scaled from `size`, so at 40pt the words would be wider than the rings and would decide the header's height.
* **The Recovery ring's colour is the day's tier**, not a fixed green — green 67–100, yellow 34–66, red 0–33, so a 20% morning reads red on Home exactly as it does on the Recovery tab. The boundaries live in one place, `RecoveryMetric.RecoveryState`'s three `Range<Int>` constants (`greenRange`, `yellowRange`, `redRange`), which `init(score:)` is built from; `RecoveryMetric.state` forwards to it and `GenerateCoachInsightsUseCase` reads it rather than comparing against `67` itself. Those constants are `public` because a **view** now has to print them: the calendar's key reads `<34%`, `34% - 66%` and `>66%` off the ranges (`RecoveryTierLegend.entries`) instead of typing the numbers a second time. Note the two ends are different bounds — `<34%` is yellow's *lower* bound and `>66%` is its *upper*, `greenRange.lowerBound - 1` — which is the off-by-one a hardcoded key would have shipped. `RecoveryState.color` (`Presentation/DesignSystem/RecoveryState+Extensions.swift`) is the single mapping from tier to token, used by Home's ring and by the Recovery tab's gauge, HRV card and trend chart. It is a `Presentation` extension rather than a property on the enum because `Domain` imports only `Foundation` and cannot name a `Color`. No fill is drawn for an unmeasured day, so a legacy `score: 0` placeholder never reaches the screen as a red 0%. `StressMath.Band.color` (`StressBand+Extensions.swift`) is the same shape for the Stress Monitor's three bands, and exists for the same reason Home's private `stressBandColor(_:)` was deleted: the tile's label and the chart's fill need one mapping, not two.
* **Two things on Home navigate now, and both are pushes on Home's own `NavigationStack`** — the day bar's title, which opens the month calendar, and the **recovery ring**, which pushes `RecoveryDetailView` seeded with the day on screen. Everything else the mockup draws is still omitted: `CUSTOMIZE`, the pencil, the ACTIVITIES expand icon, the chevrons beside the rings and the STRESS MONITOR tile. A control that looks tappable and is not reads as broken; the day-bar title is honest because it has somewhere to go, and on the other three screens `onTitleTap` is `nil` so its label is not a button at all. **The ring pushes rather than switching to the Recovery tab, and that is a data decision rather than a styling one**: `RecoveryDashboardView` keeps a private `selectedDate` seeded to `Date()`, so a tab switch would show *today*, and today is past the export's end — the reader would tap an 87% ring on an imported day and land on "No data recorded". The pushed copy is seeded with Home's own `selectedDate` and owns its day from there, so Home's day does not move underneath it, which is the same independence the four tabs already have. **Strain, Sleep and the STRESS MONITOR tile stay inert for that same reason**: each of those screens keeps a private day seeded to today, so each needs the same push-shaped fix rather than a tab switch, and `RecoveryDetailView` — the day's figures with no `NavigationStack`, wrapped by the tab and pushed by Home — is the shape to copy when they get one. The one part of it **not** to copy is the missing stepper: Strain and Sleep keep theirs, so their pushed copies must still page. The chevrons stay omitted: a chevron on one of three otherwise identical rings would say the other two are broken. Two `RecoveryViewModel`s exist for the same reason two days exist — sharing one would let paging the pushed copy move the tab's day.

### D. Core Layer (Cross-Cutting Utilities)
* **Math & Signal Processing**: Robust mathematical engines for Heart Rate Variability (RMSSD/SDNN), Borg-scale exponential Strain integration, rolling baseline statistics, the Sleep Need model, daytime Stress activation, and the VO₂ max estimate.
  - `SleepNeedMath`: the sleep a night required, as `baseline + 6.40 min × the previous day's Strain`. The coefficient is **fitted to the bundled export** rather than cited, because WHOOP publishes this model's shape and none of its constants; the type's own doc comment carries the fit, the 5-fold cross-validation, and the three WHOOP inputs the model deliberately omits. Accumulated Sleep Debt, naps and Sleep Stress are named WHOOP inputs that are *not* implemented — each with its basis in `ALGORITHMS.md` §4.
  - `StressMath`: daytime physiological activation on WHOOP's published 0–3 scale. WHOOP publishes this model's inputs, its 14-day baseline window and its band edges, and **not** the mapping between them — so every constant in the type is this app's own, calibrated to reproduce the described behaviour, and this app's number will not agree with the WHOOP app's. Same bargain as `SleepNeedMath`; the whole model is in `ALGORITHMS.md` §5. It also owns `wakingWindow(on:calendar:)`, because the window is no longer one consumer's private detail: the chart has to know which hours the model *can* score, so it can shade them rather than draw them as calm.
  - `Vo2MaxMath`: the one model here whose constant is **cited rather than fitted** — the Heart Rate Ratio Method, `15.3 × HRmax / HRrest` (Uth, Sørensen, Overgaard & Pedersen 2004), called `heartRateRatioEstimate(maxHeartRate:restingHeartRate:)`. That makes it the mirror image of the two above: they reproduce a model whose constants WHOOP withholds, and this one implements a published constant against a proprietary model it declines to reimplement. Its caller is `Domain/Entities/MetricWeek.swift`, **not** a screen: the estimate is computed per day inside `makeDay` from that day's already-gated resting heart rate, so it is derived on read, stored nowhere, and cannot disagree with the RESTING HEART RATE panel beside it. That `Domain/Entities/ → Core/Math` edge is not new and `MetricWeek`'s own `minimumBaselineDays` doc already says why it costs nothing — `StressScore` and `StressWindow` name `StressMath` the same way, and `Domain` importing only `Foundation` is a rule about *frameworks*, not about the module's own layers. `ALGORITHMS.md` §6 carries the citation, the constant's derivation, the error bar that applies because this app's `HRmax` is assumed rather than measured, and the measurement that rejected the day's own observed peak as the anchor.
* **Dependency Injection**: `DIContainer` for clean, modular wiring and testing overrides.

## 3. Unidirectional Data Flow

```
[WHOOP Strap (BLE)]                     [Apple HealthKit]              [WHOOP data export (CSV)]
        | (Raw Bytes: 0xAA Framing)              | (HKQuantitySample)             | (physiological_cycles.csv, bundled)
        v                                        v                                v
[WhoopPacketDecoder]                    [HealthKitStoreClient]          [WhoopExportParser]
        | (BiometricSample)                      | (HealthQuantitySample)         | (WhoopExportRow)
        v                                        v                                v
[BiometricRepository] ---> [Local GRDB Database] <--- [HealthKitImporter] <--- [WhoopExportImporter]
        | (AsyncStream<BiometricSample>)         | (RecoveryMetric, SDNN)         | (RecoveryMetric, SleepSession, StrainScore)
        |                                        |                                |
        |                                        | (dailyTotal: steps — the one
        |                                        |  display-time read-through left)
        |                                        |                                |
        +------------> [AnalyzeStressUseCase]     |                                |
        |              reads the day's samples    |                                |
        |              and its 14-day baseline    |                                |
        v                                        |                                |
[StreamBiometricsUseCase] / [CalculateStrainUseCase]                             |
        | (Domain Models: StrainScore, RecoveryMetric, StressScore)                v
        +----------------> [RecoveryScoring] <------------------------------------+
                                 |
                                 v
        [MetricWeek] — joins the week; the VO2 estimate is derived HERE, on read,
        from a stored resting heart rate and the profile's assumed maximum
                                 |
                                 v
                   [@Observable ViewModels]
                                 |
                                 v
                   [MainContainerView (SwiftUI)]
```

All three sources write the **same** day-keyed rows through the same repositories, so a day has one
recovery row regardless of which source produced it. `RecoveryScoring` is the meeting point: it owns
the z-score weights, and the metric filter that keeps an SDNN day and an RMSSD day out of each
other's baselines. Each importer only fills days that have no local measurement, so a strap-recorded
day is never overwritten by an imported one.

The third input is unlike the other two in two ways that the diagram does not show. It is **not a
sync**: it reads a file that shipped inside the app and runs once, when the user asks (Settings), so
there is no availability question and no background path. And it is the only source whose Strain is
not computed here — the export holds one row per day and no heart-rate series, so
`WhoopExportImporter` stores WHOOP's finished score rather than integrating one. See `ALGORITHMS.md`
§2.

Three paths in the diagram deliberately **do not** touch the database. Steps are read through
`HealthKitSyncing.stepCount(on:)` straight from the store at display time — a daily sum is not a
reading that can be filed under a day key, and a stored copy would go stale the moment the phone
logged more. The VO₂ estimate is derived on read from two values that *are* stored — the day's
resting heart rate on its `recoveries` row and the profile's maximal heart rate — so it needs no
column of its own and a persisted copy could only ever be a second number that disagrees with its own
inputs (see `ALGORITHMS.md` §6, which carries the model, its citation and its error bar; WHOOP's own
three-tier model is still the one this app declines to implement). And `AnalyzeStressUseCase` is
derived on read from `biometric_samples`: it answers from a table but writes nothing, which is what
makes it safe to point at any date — the calculate use cases are not, because they overwrite. All
three keep the day-keyed tables holding only what was measured once.

## 4. Testing & Verification Strategy

1. **Domain Tests**: Test business rules, Recovery z-score computations, and Strain algorithms in complete isolation with zero mocks.
2. **Decoder Tests**: Verify binary packet parsing against raw hex fixture dumps with various CRC edge cases and corrupted frames.
3. **Repository Tests**: Validate GRDB persistence and query operations against `LocalDatabaseManager(inMemory: true)`.
4. **Import Tests**: Drive `HealthKitImporter` with a fixture `HealthStoreClient` and an in-memory database, asserting day attribution, that a day without a reading stores no row, and that a repeated import does not duplicate rows. No device and no HealthKit entitlement are needed. `WhoopExportImporter` is driven the same way against the **real** bundled CSV read by path, asserting the day keys it derives (recomputed independently from the parsed rows), the minutes-to-seconds conversions, and that a second run writes nothing.
5. **ViewModel Tests**: Ensure state transitions and UI updates respond predictably to use case streams.
