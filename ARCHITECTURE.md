# Whoopsy Architecture Guide: Clean Architecture & Local-First Design

## 1. Architectural Philosophy

**Whoopsy** is designed from the ground up as a **100% offline-first, subscription-free, privacy-preserving** iOS companion application for WHOOP® straps (Gen 4, Gen 5 and Gen 5 MG — three models, two wire formats, and the app must be told which one it is holding).

To guarantee scalability, testability, and clear separation of concerns, Whoopsy strictly enforces **Clean Architecture** (Robert C. Martin / Uncle Bob) combined with **Domain-Driven Design (DDD)** and modern Swift Concurrency (`async`/`await`, `AsyncStream`, `Sendable`).

```
+-----------------------------------------------------------------------+
|                         PRESENTATION LAYER                            |
|  - SwiftUI Views (Glassmorphism, Neon Gauges, Hypnograms)             |
|  - ViewModels (@Observable, Unidirectional Data Flow, UI State)       |
|  - 1:1 Official WHOOP Layout (Tabs: Home, Strain, Sleep, Recovery...) |
+-----------------------------------+-----------------------------------+
                                    |
                                    v (Uses)
+-----------------------------------------------------------------------+
|                           DOMAIN LAYER                                |
|  - Entities (BiometricSample, RecoveryMetric, StrainScore, Sleep,     |
|    StressScore)                                                       |
|  - Use Cases / Interactors (CalculateRecovery, CalculateStrain,        |
|    AnalyzeSleep, AnalyzeStress, ...)                                  |
|  - Repository Interfaces (Inversion of Control Contracts)             |
+-----------------------------------+-----------------------------------+
                                    ^
                                    | (Implements Contracts)
+-----------------------------------+-----------------------------------+
|                            DATA LAYER                                 |
|  - BLE Hardware Engine (CoreBluetooth, Custom 0xAA Framing, Decoders) |
|  - Persistence (Local-First GRDB / SQLite Sandbox)                    |
|  - Mock Data Engine (Hardware-free Simulator Mode for Previews/Tests) |
|  - Adapters (HealthKit Read/Import, WHOOP Export Import, JSON/CSV Out) |
+-----------------------------------------------------------------------+
|                            CORE LAYER                                 |
|  - Signal Processing (RMSSD, SDNN, Exponential Strain Integrator,      |
|    Stress activation)                                                 |
|  - Dependency Injection Container & Logging Subsystem                 |
+-----------------------------------------------------------------------+
```

## 2. Layer Definitions & Boundaries

### A. Domain Layer (The Core)
* **Zero External Dependencies**: Does not import `UIKit`, `SwiftUI`, `CoreBluetooth`, `HealthKit`, or `GRDB`.
* **Entities**: Pure immutable Swift structs representing core physiological models (`BiometricSample`, `RecoveryMetric`, `HRVMetric`, `HealthImportSummary`, `WhoopImportSummary`, `StrainScore`, `StressScore`, `StressDay`, `StressWindow`, `SleepStressNight`, `MetricWeek`, `MetricDay`, `SleepSession`, `SleepNap`, `UserProfile`, `WhoopDevice`, `WhoopHardwareGeneration`). `WhoopHardwareGeneration` is the one entity here that describes the *hardware* rather than the body, and it carries a deliberate shape: **five cases** — three WHOOP models plus `standardBleHR` and `simulator`, which are also real answers a discovered device can have — and a derived `selectableModels` returning the three a user may *choose* — derived rather than listed, the rule `SleepStageType.allCases` follows. A single `whoop5` case covering both the 5.0 and the 5.0 MG would collapse the one distinction that matters most, since `BLE_PROTOCOL.md` §6 records that the pair may not agree with each other on the wire. `WhoopDevice` lives only in memory, so the model choice is persisted separately and per device — see `StrapModelRepository` below. `StressScore`, `StressDay` and `StressWindow` are derived on read and never stored — they are a function of `biometric_samples` and nothing else, so a persisted copy could only disagree with the samples it came from. None has a placeholder instance or a zero value: a day with no eligible window has no score and no series at all. `StressDay` is the aggregate *and* the series in one value, and it computes its `StressScore` from the windows it was handed rather than accepting one beside them — so a score describing a different day than the line beneath it is not a bug to guard against, it is unconstructible. `SleepStressNight` is that same bargain for a **night** rather than a day, and it differs in three ways worth naming: it carries its own `span` (the session's in-bed bounds, which cross midnight and are therefore not expressible as a `StressMath.wakingWindow` range within one calendar day), so a chart can never draw its windows against the day's 24-hour axis; it carries a `bands` array where **`0%` is a reading rather than a reserved placeholder**, because a night that spent none of itself highly activated really did spend none of it highly; and its `init` is **failable**, refusing an empty window list and a zero-length span, because its shares are a division and a night with nothing scored has no card rather than three zeroes over an unnamed total. `MetricWeek` and `MetricDay` are the same bargain for a *week*: the seven-day join behind Home's Strain & Recovery chart and its four metric panels, derived on read from three stored histories plus one per-week scalar (the profile's maximal heart rate, which the VO₂ estimate is computed from) and stored nowhere. The VO₂ estimate is the one field on a slot that comes off another field of *the same slot* rather than off a row — `makeDay` hoists the day's gated resting heart rate into one local and both the RHR panel and the estimate read it — so the two can never describe different days. `MetricWeek` builds its slots from the **date sequence**, not from the rows, so a day with no data is an empty slot and never a shortened array — which is what stops a gap from sliding every later point one day to the left — and it computes each panel's rolling baseline as a plain mean over the measured slots only, `nil` below `minimumBaselineDays`. It deliberately takes no `calendar:` parameter: the database snaps day keys with `Calendar.current`, so a caller passing another zone would fail to match the rows rather than shift the week. `MetricDay.deepSleepSeconds` and `.remSleepSeconds` are the type's one pair carried as a **split**, for the one chart in this app that draws a stack, and their total is left underived rather than stored beside them for the reason every duplicated quantity here is: three numbers can disagree where two parts cannot. `SleepNap` is the second entity keyed on an instant rather than a day, and the one that is deliberately **not** a `SleepSession` with a flag: a session has a need, a performance and an efficiency, all three ratios against what a *night* requires, and a nap is by definition a fraction of one — WHOOP's own eight nap rows score 6–43% on that denominator. So it carries its window and its asleep duration and nothing derived from a need it does not have. Its `id` is a `String` where `SleepSession.id` is a `UUID`, and that one difference is what makes an import idempotent: a session's fresh-per-init `UUID` means two reads of one night never compare equal, while a nap's identity comes from the row. `SleepSession.hasWhoopSleepNeed` is the entity's one field that records **provenance rather than a measurement**, and it exists because `sleeps.target_sleep_need_seconds` is a two-producer column: WHOOP's own figure on an imported night, `SleepNeedMath`'s on a strap night, indistinguishable by value. It is set on read from `sleeps.source` and it defaults to `false` — an unknown provenance may not be spent as a known one — which is what lets a caller withhold a claim about a stored pair rather than make one.

**A metric's absence is the same shape in all four: no row, and the optional is the answer.** `CalculateRecoveryUseCase` and `CalculateStrainUseCase` return an optional and write nothing for a day they could not measure, exactly as `AnalyzeSleepUseCase` and `AnalyzeStressUseCase` do, so a day with no data is absent from its table rather than present as a reserved zero — and a reader that forgets the rule sees an empty day rather than a fabricated one. `RecoveryMetric.hasMeasurement` and `StrainScore.hasMeasurement` remain, as **reader tolerance** for placeholder rows written before this rule: they keep those rows off the screens, out of the baselines and off the charts. `MetricWeek` is the one place that encodes all four rules side by side.
* **Use Cases (Interactors)**: Single-responsibility business logic units (e.g., `CalculateRecoveryUseCase`, `CalculateStrainUseCase`, `AnalyzeSleepUseCase`, `AnalyzeStressUseCase`, `StreamBiometricsUseCase`). `RecoveryScoring` is a pure scoring helper rather than a use case, shared by the strap path, the HealthKit import and the WHOOP export import so the weights exist in exactly one place. `AnalyzeStressUseCase` is the one Analyze use case that **never writes at all** — it reads samples and returns a value, with no repository to store it in — so unlike its siblings it cannot damage a stored day, and it is safe to point at any date. It has two entry points and one evaluation: `executeDay(for:) -> StressDay?` and `execute(for:) -> StressScore?`, the latter a forwarder returning `executeDay(for:)?.score` rather than a second implementation, so the two can never disagree about whether a day has a measurement. **`AnalyzeSleepStressUseCase` is the second such use case** and follows the same rule for the same reason: it scores the window `StressMath.wakingWindow` deliberately excludes, reads `biometric_samples` and writes nothing, so it is safe on any night including every imported one. Two things about its signature are decisions. Its **prior nights are handed in** rather than fetched — `execute(for:priorNights:)` takes the same night array the page's other cards were built from, so every figure on that screen describes one set of nights and the use case cannot select a different history from the screen above it, the failure `SleepViewModel.resolveWindow` exists to prevent. And it takes **no `SleepRepository`**, which is what makes that structural rather than a convention. The span it scores is the session's own in-bed bounds, guarded by `maximumNightSpanSeconds` (16 h) and skipped rather than clamped past it — the guard is a bound on the *read*, because one export row's `Sleep onset` is literally `00:00:00`. Its baseline is drawn from prior **nights**, one bounded read per night, collapsed to one point each, below `StressMath.minimumBaselineDays` returning `nil`. Four more types live beside the use cases without being interactors, and all four are the same move — a rule lifted out of a `View`'s body because this repo's runner has no renderer and a rule written into a `body` is a rule nothing can assert. `SleepStageRangeScoring` computes a night's four stage shares against the nights before it, `SleepNeedBreakdown` splits a night's need into the parts the stored row can source, and `SleepConsistencyScoring` assembles the consistency card: the five nights as spans on the model's own clock, the two rules their average draws, and the figure over its window mean. `SleepEfficiencyScoring` takes the window mean of `SleepSession.sleepEfficiencyPercentage` for the efficiency card's comparison, and it **filters out a night with no sleep period before applying its count floor** — `SleepSession.sleepEfficiencyPercentage` guards a zero denominator by returning `100`, so a window mean that counted one would be averaging a fabricated perfect night. All four are pure, all four are `enum` namespaces over free functions, and all four are **statics rather than instance methods** for the same reason: there is no state to hold and the caller has none to give. `SleepConsistencyScoring` also owns the `SleepSession` → `SleepConsistencyMath.Night` mapping (`night(from:)`), because both the score reader and the chart need one answer to "which field is the onset" — see §2.D. Its `typicalScore(in:history:)` carries the card's one absence rule that a fixture could get wrong: a window night that neither a stored figure nor the model can score is **left out of the mean** rather than counted as a zero, since a `0%` consistency is a claim about a night and no night was measured there.
* **Repository Interfaces**: Abstract Swift protocols defining data operations (e.g., `BiometricRepository`, `RecoveryRepository`, `SleepRepository`, `NapRepository`, `WorkoutRepository`, `WhoopBLEDeviceRepository`, `StrapModelRepository`, `WhoopProtocolProviding`, `HealthKitSyncing`, `WhoopExportImporting`). `NapRepository` is deliberately **not** a member of `SleepRepository`: the two answer different questions about a day — one night or `nil`, against an array that is legitimately empty — and merging them would make "no nap today" and "no night recorded" the same return value.
* **`StrapModelRepository` is a preference about the user's hardware, not measured data.** It maps a peripheral identifier to the `WhoopHardwareGeneration` the user picked for that strap, and it is the app's first stored fact about the *device* rather than about a day. `WhoopProtocolProviding` is the Domain-side question the UI asks — can this build frame this generation's packets — and it is a protocol rather than a property on the enum for the reason `HealthKitSyncing` is one: whether an envelope has been implemented is a fact about the code that changes with every release, and a case on an entity would go stale in the one direction that matters (a generation claiming support it does not have). The concrete answer lives in `Data/BLE/Constants/WhoopProtocolProfile.swift`, where the byte-level table belongs.

### B. Data Layer (Infrastructure & Adapters)
* **BLE Engine**:
  - **Which strap is connected is a stored choice, and the guess is only a fallback.** `WhoopHardwareGeneration` has five cases — `whoop4`, `whoop5`, `whoop5MG`, `standardBleHR`, `simulator` — and `selectableModels` derives the three a user may choose. The choice is read from `StrapModelRepository` and wins over the name heuristic; the heuristic (`advertisedName.contains("5")`) survives only for a strap the user has never been asked about, because such a strap still has to be described as something. The precedence rule is `WhoopBLEManager.resolvedGeneration(stored:advertisedName:)`, a **static** taking both inputs so it is assertable without constructing a `CBCentralManager` — which the suite has no way to do, since constructing one raises a system Bluetooth prompt.
  - `WhoopBLEManager`: Direct interface with Apple's `CoreBluetooth`. Discovers peripherals, negotiates MTU, manages reconnects and bonding. Three things about the generation-aware path are load-bearing. `refreshStrapModels()` runs **before** `startScanning()`, because `didDiscover` is a synchronous CoreBluetooth callback and cannot `await` the store. `didConnect`/`didDisconnect` go through `resolvedDevice(for:)` rather than building a bare `WhoopDevice` — whose `hardwareGeneration` defaults to `.whoop4` — so the discovery-time resolution is not replaced by a literal the moment the strap connects. And `sendCommand` is the **choke point**: it refuses to write when there is no profile for the connected generation, because the packet-type numberings do not overlap, so a 4.0-framed command written to a 5.0 strap is a *different message* rather than a rejected one.
  - `WhoopProtocolProfile`: the value describing how to frame and parse for one generation — envelope, header-checksum algorithm and **its input**, the inner record's origin, and the packet-type numbering. `profile(for:)` answers `nil` for every generation this build has not implemented, which today is `.whoop5`, `.whoop5MG`, `.standardBleHR` and `.simulator`. It is the single point at which "we do not speak that strap" is decided, and both the encoder and the decoder return `nil` rather than a frame when handed one.
  - `WhoopPacketEncoder`: builds the four transmitted frames (`pingCommand`, `hapticAlarmCommand`, `enableLiveTelemetry`, `requestHistoricalSync`), each a function of a profile and each returning `nil` for an absent one. The 4.0 envelope it writes is `SOF | len u16 LE | crc8 | type | seq | cmd | payload | crc32`, with the CRC8 over **the two length bytes only** and the CRC32 over the inner record. Both of those were wrong until recently, and the wrongness is worth remembering: the encoder and decoder were consistent with each other, so they round-tripped, and the suite's assertions were self-referential — which is why a wrong polynomial, byte order *and* input all passed. `WhoopCommandSequence` supplies the inner `seq`, which the old three-byte-header builder never had to produce.
  - `WhoopPacketDecoder`: validates a proprietary frame and hands it up **undecoded** as a `WhoopRawFrame` (generation, type, seq, cmd, payload). Four checks, in order: start of frame, declared length, header checksum over the format's own bytes, and CRC32 over `frame[innerOrigin ..< length]`. A frame that fails any of them produces nothing and logs why — **a rejected frame is silence, not an error the caller can act on**. The three payload decoders that used to live here are **deleted rather than fixed**: they decoded packet types this app invented (there is no live-telemetry and no battery proprietary type in the spec), and the one that mattered — the historical record — walked 16-byte chunks through a layout `BLE_PROTOCOL.md` §4 gives a **96-byte** header, so on a real drain it would have read a byte of the record counter as a heart rate. Raw frames are also the shape the pending capture needs. `decodeStandardHeartRate` is untouched: the SIG `0x2A37` profile is not a WHOOP envelope and remains the one heart-rate producer on this path that is implemented end to end.
  - `WhoopMockBLEManager`: High-fidelity hardware simulator generating realistic physiological variations for UI development and unit testing without requiring physical hardware.
* **Persistence**:
  - `LocalDatabaseManager`: GRDB/SQLite store running entirely on-device in the app sandbox, migrated by `DatabaseMigrator` (currently `v1` … `v12`; `v5` adds the nullable `source` column to `recoveries`, `sleeps` and `strains`, `v6` adds `workouts`, `workout_route_points` and `workout_splits`, `v7` adds `strains.hasMeasurement` and backfills it, `v8` adds the nullable `biometric_samples.rrIntervalsMs` holding the full per-notification R-R series as JSON text, `v9` adds the nullable `sleeps.sleep_consistency`, deliberately **not** backfilled — that column holds WHOOP's own figure on an imported row, and a migration that filled it from `SleepConsistencyMath` would write a computed number into the column the importer uses for a measured one, `v10` adds the nullable `sleeps.sleep_debt` holding WHOOP's accumulated deficit in **seconds**, not minutes — every duration column on that table is seconds, and this is the one where a raw minutes value would still look plausible on screen — and `v11` creates `naps`, the second `id`-keyed table after `workouts` and for the same reason, since a day holds one night but can hold several naps, and `v12` adds the nullable `sleeps.sleep_stages`, holding the night's 30-second epochs as a JSON array of segments in a `.text` column — the second JSON-encoded array in this schema after `biometric_samples.rrIntervalsMs` and for the same reason, that `Array` is not a `DatabaseValueConvertible`). **`v12` is what makes a recorded timeline survive storage at all**: `AnalyzeSleepUseCase` has always built the epochs, but the four stage *totals* were all `SleepRecord` carried, so the array was dropped at the write and the read path's `[]` default filled it back in — a night the strap staged perfectly came back indistinguishable from one that was never staged, and the sleep-efficiency card's timeline could only ever have drawn on the night being computed live. **Column naming is per-table and decided by `CodingKeys`**: `RecoveryRecord` declares them and its columns are snake_case, while `StrainRecord` declares none so `strains`' columns are camelCase — a migration that assumes one convention for both dies at launch. **Migration identifiers are recorded but bodies are not checksummed, so a registered migration is frozen once shipped** — schema changes go in a new `registerMigration` block. A failing migration calls `fatalError` in `init`, so it crashes at launch rather than at the query.
  - `UserDefaultsStrapModelRepository` is the one repository in `Data/Persistence/` that is **not** GRDB, and the choice is deliberate rather than lazy: it stores the per-device model choice as a `[peripheralUUID: rawValue]` dictionary under a single `UserDefaults` key, beside `UserDefaultsAppPreferencesRepository`, which is the shape this repo already keeps its non-measured settings in. Two reasons not to make it a migrated table. A failing migration `fatalError`s the app at launch, so a migration is a large hammer for a preference; and the value is a statement about the user's *hardware* rather than a measurement, which is exactly the distinction that puts everything else in this file on the `source` column's side of the line. The consequence to accept knowingly: a peripheral identifier survives launches but not a reinstall, so a reinstall loses the mapping and falls back to the heuristic until the picker is used again.
  - `source` records which writer produced a row: `whoop_export` for a bulk import, `NULL` for a row the app measured itself through the strap or HealthKit. It has one reader, and it is `GRDBSleepRepository.makeSession`, which resolves it into `SleepSession.hasWhoopSleepNeed` — the fact that separates WHOOP's own `Sleep need (min)` from one `SleepNeedMath` computed, since both are stored on the same column and nothing in the two numbers tells them apart. The mapper is where it is resolved because the mapper is where the column exists at all, and every value that is not the importer's own label (a strap night's `NULL`, a row written before the column) resolves to *not known to be WHOOP's*: the answer that withholds a claim rather than making one.
  - `workouts` deliberately **breaks the day-key rule** the other metric tables follow. `recoveries`, `sleeps` and `strains` are primary-keyed on `date` snapped to `startOfDay`, because a day holds one of each; a day can hold several workouts, so `workouts` is keyed on `id` (a UUID string) with `date` as an ordinary indexed lookup column. `WorkoutRoutePointRecord` and `WorkoutSplitRecord` are separate tables keyed on their own `id` and bound to the session by a `workout_id` foreign key, fetched per workout rather than joined — a join would multiply the session row by its route points. The records live in `Data/Persistence/Models/WorkoutRecord.swift` as one file because the three are one aggregate.
  - `GRDBWorkoutRepository` is what makes a recorded workout survive the launch that recorded it. It replaced `LocalWorkoutRepository`, an actor wrapping an array that lost every session at the next launch.
  - Repositories implement domain protocols to convert GRDB records into immutable domain models, and they **answer from local storage only** — there are no fallback sources. A stored row maps to a model without inventing values: a column the strap never filled in becomes `nil` on the model, never a plausible constant, so "not measured" stays distinguishable from a measurement all the way to the screen.
  - History reads state the day their window **ends** on: `getRecoveryHistory(days:endingOn:)` and its `sleeps`/`strains` siblings, with `endingOn` defaulting to now for the scoring baselines and the JSON exporter. The end is a parameter rather than an assumption of `Date()` because the metric screens show a day the user picked, and a window anchored on *now* cannot describe it. The reads bound the top of the window too (`<= endingOn.endOfDay`) — without it, a window anchored on an old day runs on to the present.
* **Health**:
  - `HealthKitBridge`: The app's one HealthKit entry point, injected as `HealthKitSyncing`. Availability is a **runtime** question (`HKHealthStore.isHealthDataAvailable()`); `#if canImport(HealthKit)` is true on macOS and guards nothing.
  - `HealthStoreClient` / `HealthKitStoreClient`: A protocol over the health store plus its real implementation. The protocol's value types are plain `Sendable` structs with no HealthKit import, so the import mapping is testable with no device and no entitlement. It has two read shapes, and the difference matters: `quantitySamples(_:from:to:)` returns the individual readings a window holds, while `dailyTotal(_:from:to:)` returns one **sum** over it (`HKStatisticsQuery` with `.cumulativeSum`). Steps are the only quantity read through the second, because a step count is a cumulative daily total rather than a reading the app can file under a day key.
  - `HealthKitSyncing.stepCount(on:)` is now its **only** member that does **not** throw. HealthKit never discloses read-permission status, so a denial, an empty day, a device with no source for the quantity and an unavailable store are indistinguishable from the caller — and all of them are honestly the same dash. It is read through to the store on demand and never stored, so there is no table and no column for it and no copy to go stale. Its read shape is `dailyTotal`'s `.cumulativeSum`, because a step count is a cumulative daily total rather than a reading the app can file under a day key.
  - **The VO₂ MAX panel is no longer a read-through, and this is the second shape it has had.** It used to take `quantitySamples` for `HKQuantityTypeIdentifierVO2Max` — a per-sample read reduced to a day's *newest*, not its highest — and that path is **deleted at every layer**: no `vo2MaxReadings(days:endingOn:)` on `HealthKitSyncing`, no `.vo2Max` case on `HealthQuantityMetric`, and therefore no VO₂ max in `readTypes`, so the consent prompt no longer asks for it. The panel now prints an estimate this app computes — see §2.D `Vo2MaxMath` — which is why `HomeViewModel` takes a `userProfileRepository` it did not previously need. Do not "restore" the read-through on the assumption that a stored-derived value is a downgrade: two estimates of one quantity on one panel, on different days, with nothing to say which was which, is the outcome `ALGORITHMS.md` §6 rejects.
  - `HealthKitImporter`: Maps a window of HealthKit readings onto `recoveries` rows through the domain repositories. One row per day, SDNN only, and a day with no reading produces no row at all.
* **Import**:
  - `WhoopExportParser`: Reads WHOOP's `physiological_cycles.csv` into `WhoopExportRow` values — a plain `Sendable` struct of optionals, with no GRDB types and no decisions. Nothing about what an empty cell *means* is decided here, and a row whose date or timezone cannot be parsed **throws** rather than being skipped silently.
  - `WhoopExportImporter`: Walks the parsed rows in chronological order and writes day-keyed rows through the same domain repositories the strap uses. It day-keys on `startOfDay(Wake onset)`, scores each night through `RecoveryScoring` against the preceding 30 imported days — the window is `RecoveryScoring.baselineWindow(before:in:)`, shared with every other reader rather than owned here, because the Recovery detail screen prints the same baseline its score was computed from — and takes Strain verbatim because the export holds no heart-rate series. Days with an existing measurement are skipped, so the import is idempotent. **It reads two files through one button.** `importBundledExport()` imports the naps out of `sleeps.csv` first and folds that count into the same summary, so More → Settings' import is one action over one export; a build whose bundle lacks the side file imports no naps and reports `0` for them rather than failing, because the cycle file is the one the app asked for and the naps are a side file. The nap path keys, writes and reports separately — `napsWritten` is deliberately **not** added to `daysWritten`, since a nap is not a day and adding it would make the summary claim history it did not import. **Three columns are stored verbatim rather than recomputed**, and they are the ones this app can also derive or model for a strap night: `Sleep need (min)` → `sleeps.target_sleep_need_seconds`, `Sleep consistency %` → `sleeps.sleep_consistency`, and `Sleep debt (min)` → `sleeps.sleep_debt` (× 60). WHOOP derived all three from the same inputs with its own constants, so recomputing any would put two models on one chart — and because a stored row and a computed one are the same number on the same column, the suite's guard for each is a *property* rather than a count (`ALGORITHMS.md` §4). Sleep debt is the one it could not recompute even if it wanted to: the deficit is a running total across nights, so there is no per-night expression to recompute it from.
  - Injected as `WhoopExportImporting`, and triggered only from Settings. It is deliberately not a launch-time sync: ~900 days of history should not be written behind the user's back.

### C. Presentation Layer (SwiftUI + MVVM + Design System)
* **Declarative SwiftUI**: Optimized for iOS 17+ with smooth 120Hz ProMotion animations, dark-mode-first aesthetic, glowing gauges, and live ECG-style sparklines.
* **ViewModels**: Annotated with `@Observable`, accepting Use Cases via constructor injection. They emit discrete UI states (`Idle`, `Connecting`, `Streaming`, `Error`).
* **1:1 Official WHOOP App Layout Structure**:

  The five week charts share a **frame** and nothing else, and the split is `WeekChartAxis`: the seven-column geometry (`columnWidth`, `x(slot:columnWidth:)`), the highlighted anchor column filled with `Theme.ringTrack` at `anchorFillOpacity`, and the weekday-over-day-of-month date strip with its chipped bold anchor day. It exists because five copies of a date label are five chances to label a column with the wrong day, and the charts sit directly above and below each other so a disagreement would be visible. Everything that differs stays in the chart: bars against a line, a fixed scale against a fitted one, a tier colour against a flat one, gridlines against none. `StrainRecoveryChartView` deliberately does **not** use it — its geometry has gutters for two labelled axes and its private `Scale` honours `rect.minX`, so it is a genuinely different frame rather than a copy, and it is documented as such inside `WeekChartAxis` rather than left implicit.

  `WeekLineChartView` draws the page's three **auto-fitted y-axes**, and the trade is explicit. `FittedAxis` rounds a set of values out to bounds that are multiples of a step chosen from a fixed ladder (1, 2, 5, 10, 20, 25, 50, 100, …) so the gridlines land on values a reader can name — an HRV week of 32…67 becomes 30…70 at step 10 with lines at 40/50/60, the reference resting-heart-rate week of 49…66 becomes 45…70 at step 5 with lines at 50/55/60/65, and the reference respiratory-rate week of 14.8…16.5 becomes 14…17 at step 1 with lines at 15/16 — and it widens a zero-span range rather than dividing by it. The doctrine it bends is the **fixed-scale** one (`CLAUDE.md`, the Stress Monitor): an auto-scaled axis draws a calm day and a wired day as the same picture. The distinction is that the rule is about *unlabelled* shapes, where height is the whole of the evidence; this chart labels **every** point with its value, so the axis is a guide and the reading is stated. None of the three quantities has a usable fixed scale, from opposite directions: HRV's absolute magnitude is meaningless without the person's own baseline and has no natural ceiling, and a resting heart rate and a respiratory rate *do* have physiological floors and ceilings but a week of either spans a couple of units, so any fixed axis wide enough to hold every person flattens every week into a straight line. So the alternatives are a fabricated ceiling or a fitted axis, and the labels are what make the fitted one honest. **The resolution those labels print at is not this type's business** — a ladder that rounds milliseconds out to tens must round breaths out to single units, and the type only ever sees numbers — so it lives on `WeekLineSeries.valueDecimals`, where the chart's labels and the card's spoken sentence both read it and cannot state the same day differently. Remove the labels and it becomes exactly the chart the fixed-scale rule forbids, which is why the two ship together and why a run of one point still draws its label.

  `WeekLineChartView` is **one view for all three series**, and `WeekLineSeries` is **one type with three named initialisers**, because the three cards are the same drawing around a different selection rule — and, for one of them, a different resolution. They differ in which days plot and how finely their numbers read, and both are the initialiser's business — the caller hands the series in already built, narrowed or not — so everything downstream is shared: the same fitted axis, the same hollow points, the same value labels over them, the same seven columns and date strip. Three copies of a chart would be three chances for one of them to drift, and neither difference would show up as a compile error. The two whole-number quantities (`hrvWeek`, `restingHeartRateWeek`) print at `valueDecimals == 0`, because that is the resolution their columns are stored at; `respiratoryRateWeek` prints at 1, because a week of breaths spans about two units and a whole-number label would render the reference week's six distinct days as six `15`s. The selection rules differ too: the HRV initialiser is the only one that narrows, since it is the only one whose column holds two incomparable quantities. The series is a type rather than code in the view's body for the reason `DayBarRules` is one: the runner has no renderer, so a rule written into a `View` is a rule nothing can assert.

  The three initialisers answer "which days plot" differently, and that is the whole of the difference between the cards bar one resolution. `init?(restingHeartRateWeek:)` and `init?(respiratoryRateWeek:)` take **every** day carrying a reading: each of those is one quantity in one unit, so nothing is narrowed, and the assertion that keeps this honest is that a week giving the HRV line three points gives the resting-rate one five. `init?(hrvWeek:)` cannot, and applies the **never-mix rule** to the chart — it narrows to `MetricWeek.hrvBaselineMetric`, the newest measured slot's quantity, so a week holding both SDNN and RMSSD plots only one of them and *fewer than seven points* even though the dropped days were measured. All three then split the points into `runs` of adjacent slots so the line **breaks** at a gap. A gap is either an unmeasured day or — for HRV — a day measured in the other quantity, and a segment drawn across either would be read as a value for days this line has no reading in; a run of one draws its dot and no segment. That is the rule `StrainRecoveryChartView` and `StressMonitorChartView` already follow. The resolver that differs is `valueDecimals`, on the same type and for the same reason as the selection rule: `restingHeartRateWeek` and `hrvWeek` print whole because their columns are stored whole, and `respiratoryRateWeek` prints to a tenth because a week of breaths spans about two units — the reference week's six distinct days all render as `15` at zero decimals. All three lines and their hollow points are drawn in `Theme.weekLine`, one token for the three of them: every other blue in `Theme` already means a sleep stage, a ring or a tier, and borrowing one would invite a reader to compare two things this app has decided not to put on one axis. The shared token is also a deliberate statement that here the **colour does not carry quantity identity** — on the bars above it does, since the bar's colour *is* the recovery tier, but on these three the card's own label and its own axis say which quantity is plotted, so colouring them apart would imply a relationship between a millisecond count, a beat rate and a breathing rate that does not exist. **The page carries no chrome above the ring at all**: no `DashboardHeader`, and no `DayNavigationBar`. The no-data state survives the header's removal in the gauge's own label, which reads "No data" on a day with no measurement. **`RecoveryDetailView`'s day is handed in and fixed** — `private let date`, a plain `let` rather than a `@State`, because nothing can change it: the Recovery tab passes `Date()` and Home's ring pushes the day on screen. The three `bandPoor`/`bandSufficient`/`bandOptimal` tokens are the **sleep** band scale, not the recovery tiers: this scale's middle colour is a neutral grey rather than a warning yellow, because "Sufficient" is not a caution — and `Components/SleepBandBar.swift` draws the three-segment position bar that lights one of them, over `SleepBand.allCases` so a fourth band could not be drawn without appearing there. Unlike `HeartRateZoneBar` and `HypnogramChartView` it deliberately carries **no `GeometryReader`**: those two draw a distribution whose segments are proportional to a quantity, while this one draws a *position* on a fixed three-step scale, so its segments are equal by definition. `Components/MetricChange.swift` is the one definition of a **comparison between a figure and the value it is read against** — which way it moved, and whether that movement is good news — shared by Home's four metric panels, Home's two tiles, and the Recovery breakdown's four rows. It was Home's private `TileChange` until a second screen drew the same thing; the lift is the one-rule-one-definition discipline applied to a component, and the two decisions it holds are exactly the two a copy drifts on. **Direction and verdict are separate by construction**: the triangle always points the way the number went, while `higherIsBetter` turns that direction into a verdict and the verdict alone picks the colour — so an HRV rise is green while a resting-heart-rate rise is red, from one call. Three further rules are worth knowing because each produces a wrong marker that looks plausible. The verdict has **three states**, not two: green better, yellow the same, red worse — and the middle one is why the colour is not derivable from the direction, since a figure equal to its average has no direction at all. `direction` is therefore optional, and `nil` there means *unchanged* and draws `circle.fill` rather than a triangle. The comparison is made on the **formatted** pair, not the raw one (a resting rate of 52 against a mean of 52.4 is genuinely below it, but both print as `52`, and a row reading `52 ▼ 52` contradicts itself). And a `nil` **`MetricChange`** — no marker at all, just the mean — is reserved for a missing side: a day with no measurement, or a window too thin for a baseline. That is a different absence from `.same`, and one the screen renders differently. Two more components live here for the same reason `MetricChange` does, and both were lifted out of the sleep detail screen one card later. `Components/MetricHeadline.swift` is the big figure over its comparison — the night's hours of sleep, or the need card's percentage, against the window's mean — and `Components/CardNotch.swift` is the caret drawn on a card's top edge to point it at whatever it explains. Both were `private` inside `SleepDetailView` while one card was their only user, and both gained a second caller with the need card. The notch in particular is a `Shape` rather than an `Image` so it takes the fill of the surface it is attached to and cannot come to be drawn in a colour that surface is not; its two callers fill it differently, which is exactly what a shape buys.
* **The month calendar is Home's, and it is opt-in on the shared bar.** `DayNavigationBar` takes an optional `onTitleTap`, and Home is the only caller that passes one; where it is `nil` the centre stays the plain `Text` it always was, because a title that looks tappable and has nowhere to go reads as broken — the same rule that keeps `CUSTOMIZE` and the ACTIVITIES expand icon off the screen. Opening it is an **overlay**, not a `.sheet`: a sheet is a full-height card the system centres, which left the grid floating in a dark slab with the app's own screen invisible behind it, whereas the calendar is a small bounded thing that reads as one only when it hangs from the top of the safe area with the day it is choosing between still legible under a partial (`0.45` black) scrim. Home hides the tab bar while it is up — an overlay inside a tab cannot cover the bar, and a live row of tabs under a modal both looks wrong and lets a tab switch strand the calendar open. `MonthGrid` is a pure value that derives the weekday header and the leading blanks from **one** `firstWeekday` rotation so the two cannot drift, and `MonthCalendarView` is dumb: values in, closures out.
* **Two ring components, deliberately.** `GaugeRingView` draws an angular gradient, an outer glow, and its label *inside* the ring; Strain, Sleep, Recovery and the workout HUD depend on that look. Its per-caller styling is a set of **defaulted** parameters — `ringColor`, `lineWidth`, `size`, and since the sleep detail page a `labelColor` — so a screen can restyle its own ring without the other four moving; that page is the one caller that passes a label colour, and the one whose label carries a line break. `MetricRingView` is the flat counterpart Home's mockup calls for — neutral track, value centred, label beneath — and is a sibling rather than a mode of `GaugeRingView`, so restyling one screen does not move four. `MetricRingView` takes its value as an **optional** `String?`: a caller passing a dash cannot also pass a fill, so the ring cannot contradict itself. It also takes `showsLabel` (defaulted `true`, so the three existing call sites do not move), which Home's collapsed header sets to `false` — its label font is fixed at 10pt rather than scaled from `size`, so at 40pt the words would be wider than the rings and would decide the header's height.
* **The Recovery ring's colour is the day's tier**, not a fixed green — green 67–100, yellow 34–66, red 0–33, so a 20% morning reads red on Home exactly as it does on the Recovery tab. The boundaries live in one place, `RecoveryMetric.RecoveryState`'s three `Range<Int>` constants (`greenRange`, `yellowRange`, `redRange`), which `init(score:)` is built from; `RecoveryMetric.state` forwards to it and `GenerateCoachInsightsUseCase` reads it rather than comparing against `67` itself. Those constants are `public` because a **view** now has to print them: the calendar's key reads `<34%`, `34% - 66%` and `>66%` off the ranges (`RecoveryTierLegend.entries`) instead of typing the numbers a second time. Note the two ends are different bounds — `<34%` is yellow's *lower* bound and `>66%` is its *upper*, `greenRange.lowerBound - 1` — which is the off-by-one a hardcoded key would have shipped. `RecoveryState.color` (`Presentation/DesignSystem/RecoveryState+Extensions.swift`) is the single mapping from tier to token, used by Home's ring and by the Recovery tab's gauge, HRV card and trend chart. It is a `Presentation` extension rather than a property on the enum because `Domain` imports only `Foundation` and cannot name a `Color`. No fill is drawn for an unmeasured day, so a legacy `score: 0` placeholder never reaches the screen as a red 0%. `StressMath.Band.color` (`StressBand+Extensions.swift`) is the same shape for the Stress Monitor's three bands, and exists for the same reason Home's private `stressBandColor(_:)` was deleted: the tile's label and the chart's fill need one mapping, not two. `StressMath.Band.gradient` is that file's second export and the third instance of the same rule — two charts now fill under a stress trace, the day's `StressMonitorChartView` and the night's `SleepStressChartView`, and a divergence between their fills would not be a styling difference: it would put "high" at a different score on two screens that both label their axis 0–3. It is on `Band` rather than on `Theme` because its stops are `StressMath`'s band edges divided by `StressMath.maximumScore` — the same two numbers `band(forScore:)` branches at — so neither chart types `1.0` or `2.0`.
* **Three things on Home navigate now, and all three are pushes on Home's own `NavigationStack`** — the day bar's title, which opens the month calendar; the **recovery ring**, which pushes `RecoveryDetailView` seeded with the day on screen; and the **status badge**, which pushes `DeviceDetailView`. The badge is the only element on Home that is about the *strap* rather than about the day, which is what makes it the honest way in — and wrapping it in a link required care in two places that a screenshot would not reveal: the `batteryText` dash gate had to survive untouched, and the accessibility label had to move onto the link with a hint rather than being left on the inner `HStack`, which would have announced a battery percentage as a button with no indication of where it leads. Everything else the mockup draws is still omitted: `CUSTOMIZE`, the pencil, the ACTIVITIES expand icon, the chevrons beside the rings and the STRESS MONITOR tile. A control that looks tappable and is not reads as broken; the day-bar title is honest because it has somewhere to go, and on the other three screens `onTitleTap` is `nil` so its label is not a button at all. **The ring pushes rather than switching to the Recovery tab, and that is a data decision rather than a styling one**: `RecoveryDashboardView` keeps a private `selectedDate` seeded to `Date()`, so a tab switch would show *today*, and today is past the export's end — the reader would tap an 87% ring on an imported day and land on "No data recorded". The pushed copy is seeded with Home's own `selectedDate` and owns its day from there, so Home's day does not move underneath it, which is the same independence the four tabs already have. **Strain, Sleep and the STRESS MONITOR tile stay inert for that same reason**: each of those screens keeps a private day seeded to today, so each needs the same push-shaped fix rather than a tab switch, and `RecoveryDetailView` — the day's figures with no `NavigationStack`, wrapped by the tab and pushed by Home — is the shape to copy when they get one. The one part of it **not** to copy is the missing stepper: Strain and Sleep keep theirs, so their pushed copies must still page. The chevrons stay omitted: a chevron on one of three otherwise identical rings would say the other two are broken. Two `RecoveryViewModel`s exist for the same reason two days exist — sharing one would let paging the pushed copy move the tab's day.

### D. Core Layer (Cross-Cutting Utilities)
* **Math & Signal Processing**: Robust mathematical engines for Heart Rate Variability (RMSSD/SDNN), Borg-scale exponential Strain integration, rolling baseline statistics, the Sleep Need model, daytime Stress activation, and the VO₂ max estimate.
  - `SleepNeedMath`: the sleep a night required, as `baseline + 6.40 min × the previous day's Strain`. The coefficient is **fitted to the bundled export** rather than cited, because WHOOP publishes this model's shape and none of its constants; the type's own doc comment carries the fit, the 5-fold cross-validation, and the three WHOOP inputs the model deliberately omits. Accumulated Sleep Debt, naps and Sleep Stress are named WHOOP inputs that are *not* implemented — each with its basis in `ALGORITHMS.md` §4.
  - `StressMath`: daytime physiological activation on WHOOP's published 0–3 scale. WHOOP publishes this model's inputs, its 14-day baseline window and its band edges, and **not** the mapping between them — so every constant in the type is this app's own, calibrated to reproduce the described behaviour, and this app's number will not agree with the WHOOP app's. Same bargain as `SleepNeedMath`; the whole model is in `ALGORITHMS.md` §5. It also owns `wakingWindow(on:calendar:)`, because the window is no longer one consumer's private detail: the chart has to know which hours the model *can* score, so it can shade them rather than draw them as calm. It has **two consumers over two different windows** — `AnalyzeStressUseCase` over the waking day and `AnalyzeSleepStressUseCase` over a night's in-bed span — which is why every constant it owns is read by name from both rather than restated, including the band edges the two charts' shared `Band.gradient` is stopped on.
  - `WholePercentMath`: how a set of durations becomes a column of whole percents, by **largest remainder**. It exists because a printed column that sums to 101 is a column a reader can catch by adding it up, while the same column printed by naive rounding looks entirely ordinary — the export stores whole minutes and the exact shares land on fractions, so an eight-hour night split `4.2 / 1.8 / 1.6 / 0.4` hours rounds to `53 + 23 + 20 + 5 = 101`. Two cards now print such a column — the sleep detail screen's typical-range bars and its within-sleep stress rows — so this is the second thing lifted to `Core/Math` for that screen's benefit, after `StressMath` itself.
  - `SleepConsistencyMath`: how closely a night's **timing** matches the nights before it, on a 0–100% scale, from the recency-weighted circular boundary shift against the four prior records. Like `SleepNeedMath` its constants are **fitted to the bundled export** rather than cited, and like it the fit and its error are carried in the type's own doc comment. Three things about it are decisions rather than details: it defines its own nested `Night` value type instead of taking a `SleepSession`, because `Core/Math` does not name `Domain` entities (`StressMath` takes a `Double` and returns its own `Band` for the same reason) — so the `SleepSession` → `Night` mapping lives in `SleepConsistencyScoring.night(from:)`, one definition shared by the score reader and the chart; it returns `nil` below four priors rather than rendering a partial score, which is the gate `SleepNeedMath` and `BaselineStatisticsMath` apply to insufficient history; and it carries **two** model outputs rather than one — `consistency(for:history:)` is the figure, and `typicalBoundaries(for:history:)` is the recency-weighted **circular** mean of the same four priors' onsets and wakes, which the consistency card draws as its two dashed rules. `circularMean` is where that clock arithmetic lives, and its degenerate-input guard is on the resultant's length rather than on the components being zero, because a true cancellation is not zero in floating point. `clockMinutes(fromNightClock:)` is the inverse of `nightClockMinutes`, for the three callers that print a night-clock minute as a time of day. The model is in `ALGORITHMS.md` §4.
  - `RespiratoryRateMath`: the breathing rate a night's own beats carry, by respiratory sinus arrhythmia — respiration modulates the R-R interval, so a peak in the tachogram's 0.1–0.4 Hz band **is** the rate. This is the first signal processing in the repo (no FFT, no vDSP, no resampling anywhere else) and the only `Core/Math` type whose input is a **time series** rather than values: it takes `[BiometricSample]`, which is why it also owns `usablePackets`/`contiguousRuns`/`isContiguous` — the rule that decides whether two BLE notifications' beats may be chained at all, built on the SIG characteristic's own meaning (a packet's R-R field carries the intervals since the previous notification, so the seam is `dt − span` of the *later* packet). It returns `Double?` and never `0.0`, and unlike the fitted models above it has **no ground truth in this app at all** — the export carries no R-R series — so its constants are derived from published window lengths and its threshold from a synthetic noise measurement. `ALGORITHMS.md` §4 carries the contiguity rule, every constant with its basis, and what it cannot be validated against.
  - `SleepDebtMath`: the running sleep deficit WHOOP names, as a **lagged** accumulation — the export's own column correlates 0.891 with the *prior* night's shortfall against 0.506 with its own, so a night's debt sums the shortfalls strictly before it and never its own. Fitted to the bundled export like `SleepNeedMath` and `SleepConsistencyMath`, and carrying its fit table in the type's own doc comment. Three things about it are decisions rather than details: it defines its own nested `Night`, for the same `Core/Math`-does-not-name-`Domain` reason `SleepConsistencyMath` does; it is written as a **closed form over an explicit sort rather than as a walk**, because a recurrence has loop-carried state and reading the export in its own newest-first file order moves MAE from 8.31 to 22.69; and it **may legitimately return `0`**, uniquely among the numbers this app computes, since WHOOP's own column bottoms out at zero — `nil` is the word for *not scored*. `ALGORITHMS.md` §4 carries the formula, the constants, the fit table and the recorded negative result on a repayment term.
  - `SleepOnsetMath`: where a night begins and ends, from the classified epochs themselves — onset is the start of the first run of consecutive non-`awake` epochs whose own **wall-clock** span reaches ten minutes, wake the end of the last such run, and no qualifying run means no night at all. It exists because the strap path had no onset detector: a session's boundaries used to be its first and last sample, which are the edges of the read window (9 PM → 10 AM, *when the strap might have been worn*) rather than of the night, so a strap put on at 7 PM reported a night beginning at 7 PM. It follows the `Core/Math` convention exactly — a locally-defined nested `Epoch` rather than a `SleepStageSegment`, for the same reason `SleepDebtMath.Night` and `RespiratoryRateMath.BeatPacket` exist — and its one constant is **cited** (`SO1`/`SO5`/`SO10`, the actigraphy convention, with Busa et al. 2022 finding the choice moves no sleep variable) rather than fitted. `ALGORITHMS.md` §4 carries the rule, the citation, and the quiet-wakefulness blind spot that no run length can fix.
  - `Vo2MaxMath`: the one model here whose constant is **cited rather than fitted** — the Heart Rate Ratio Method, `15.3 × HRmax / HRrest` (Uth, Sørensen, Overgaard & Pedersen 2004), called `heartRateRatioEstimate(maxHeartRate:restingHeartRate:)`. That makes it the mirror image of the two above: they reproduce a model whose constants WHOOP withholds, and this one implements a published constant against a proprietary model it declines to reimplement. Its caller is `Domain/Entities/MetricWeek.swift`, **not** a screen: the estimate is computed per day inside `makeDay` from that day's already-gated resting heart rate, so it is derived on read, stored nowhere, and cannot disagree with the RHR panel beside it. That `Domain/Entities/ → Core/Math` edge is not new and `MetricWeek`'s own `minimumBaselineDays` doc already says why it costs nothing — `StressScore` and `StressWindow` name `StressMath` the same way, and `Domain` importing only `Foundation` is a rule about *frameworks*, not about the module's own layers. `ALGORITHMS.md` §6 carries the citation, the constant's derivation, the error bar that applies because this app's `HRmax` is assumed rather than measured, and the measurement that rejected the day's own observed peak as the anchor.
* **Formatting and Logging**: `Core/Extensions/` holds the two files that turn stored values into the strings the screens print, and they are here rather than on the views because a duration is printed on more than one screen and two formatters that agree today are a bug that fires later. `Double+Extensions` carries `formattedOneDecimal`, `formattedHoursMinutes`, `formattedCompactHoursMinutes` and `formattedSignedCompactHoursMinutes` — the last is the compact form with a leading `+`, which exists because a comparison column needs the sign shown rather than left to the sign of the number, and `rounded(toPlaces:)` beside them. `Date+Extensions` carries the time, short-date and weekday abbreviations the day bars and chart strips print, plus `formattedClock(minutesOfDay:)` — the one place minutes past midnight become a clock string. It prints a whole hour as `"7 PM"` and a minute as `"7:56 AM"`, and that asymmetry is a rule rather than an accident: a **tick** on a whole-hour axis is a time of night and three characters of `:00` five times down a gutter is noise, while a **mean** lands on a minute and dropping its minutes would print a figure the model did not produce. Midnight is `"12 AM"` rather than `"0 AM"`, and a negative or past-a-day count wraps rather than printing a negative hour. `Core/Logging/AppLogger.swift` is the app's `os.log` wrapper and the sole reason `Core` imports anything beyond `Foundation`.
* **Dependency Injection**: `DIContainer` for clean, modular wiring and testing overrides. The strap-model work added two wires and both are constructor-injected like everything else below the container: `strapModelRepository` (`UserDefaultsStrapModelRepository`) goes into `WhoopBLEManager`, because resolution happens inside a synchronous CoreBluetooth callback, and `protocolCatalog` (the `WhoopProtocolProviding` conformance over `WhoopProtocolProfile`) goes into `DeviceDetailViewModel`, which is the only thing that has to answer "can this build speak that strap" before the user picks. `DIContainer.preview` and `DIContainer(useMockBLE: true)` take the same two; there is no mock variant of either, because neither has anything to fake — one is a `UserDefaults` dictionary and the other is a pure function of the generation. `analyzeSleepStressUseCase` is wired the same way and takes one dependency for a reason worth naming: `biometricRepository` only. It is deliberately given **no `sleepRepository`**, because the prior nights it scores against are handed in by the caller, and leaving the repository out is what makes that structural rather than a convention — a use case that could fetch its own history could describe a different night set from the cards above it.
* **`DeviceDetailViewModel` is built in `MainContainerView`, not inside the `NavigationLink`'s destination closure.** That closure is re-evaluated on every push, so a view model constructed in it would be a fresh one every time — losing the device subscription each push and starting another. It is the same rule that makes `MainContainerView` build **one** `ActiveWorkoutViewModel` for two screens.

```
[WHOOP Strap (BLE)]                     [Apple HealthKit]              [WHOOP data export (CSV)]
        | (Raw Bytes: 0xAA Framing)              | (HKQuantitySample)             | (physiological_cycles.csv, bundled)
        v                                        v                                v
[WhoopPacketDecoder]                    [HealthKitStoreClient]          [WhoopExportParser]
        | (BiometricSample)                      | (HealthQuantitySample)         | (WhoopExportRow)
        v                                        v                                v
[BiometricRepository] ---> [Local GRDB Database] <--- [HealthKitImporter] <--- [WhoopExportImporter]
        | (AsyncStream<BiometricSample>)         | (RecoveryMetric, SDNN)         | (RecoveryMetric, SleepSession, StrainScore)
        |                                        |                                |
        |                                        | (dailyTotal: steps — the one
        |                                        |  display-time read-through left)
        |                                        |                                |
        +------------> [AnalyzeStressUseCase]     |                                |
        |              reads the day's samples    |                                |
        |              and its 14-day baseline    |                                |
        |                                        |                                |
        +------------> [AnalyzeSleepStressUseCase]|                                |
        |              reads the same table over  |                                |
        |              a night, with its baseline |                                |
        |              from prior NIGHTS' spans   |                                |
        v                                        |                                |
[StreamBiometricsUseCase] / [CalculateStrainUseCase]                             |
        | (Domain Models: StrainScore, RecoveryMetric, StressScore)                v
        +----------------> [RecoveryScoring] <------------------------------------+
                                 |
                                 v
        [MetricWeek] — joins the week; the VO2 estimate is derived HERE, on read,
        from a stored resting heart rate and the profile's assumed maximum
                                 |
                                 v
                   [@Observable ViewModels]
                                 |
                                 v
                   [MainContainerView (SwiftUI)]
```

All three sources write the **same** day-keyed rows through the same repositories, so a day has one
recovery row regardless of which source produced it. `RecoveryScoring` is the meeting point: it owns
the z-score weights, and the metric filter that keeps an SDNN day and an RMSSD day out of each
other's baselines. Each importer only fills days that have no local measurement, so a strap-recorded
day is never overwritten by an imported one.

The two stress branches are the diagram's two **read-only** producers of a derived value, and they
are the only ones: each reads `biometric_samples` on demand and returns a value with no repository to
store it in, which is why neither can damage a stored day and both are safe to point at any date. They
differ in exactly one input — `AnalyzeStressUseCase` reads the day's waking window
(`StressMath.wakingWindow`, 06:00–22:00) and `AnalyzeSleepStressUseCase` the night's own in-bed span,
which crosses midnight and is not a range within any calendar day. The night model's baseline comes
from prior **nights**, one bounded read per night, because a night's beats are not a day's.

The third input is unlike the other two in two ways that the diagram does not show. It is **not a
sync**: it reads a file that shipped inside the app and runs once, when the user asks (Settings), so
there is no availability question and no background path. And it is the only source whose Strain is
not computed here — the export holds one row per day and no heart-rate series, so
`WhoopExportImporter` stores WHOOP's finished score rather than integrating one. See `ALGORITHMS.md`
§2.

One edge in the diagram is now narrower than it reads. `[WhoopPacketDecoder]` emits a `BiometricSample` only on the **standard** `0x2A37` heart-rate characteristic, which is the one producer on the strap path implemented end to end. Its proprietary branch validates the envelope and hands up a `WhoopRawFrame` and **nothing consumes that yet** — no record parser, no writer — so the strap input currently reaches `biometric_samples` through the SIG characteristic alone, and the historical drain is work in `TODO.md` §5 rather than a path on this diagram.

Three paths in the diagram deliberately **do not** touch the database. Steps are read through
`HealthKitSyncing.stepCount(on:)` straight from the store at display time — a daily sum is not a
reading that can be filed under a day key, and a stored copy would go stale the moment the phone
logged more. The VO₂ estimate is derived on read from two values that *are* stored — the day's
resting heart rate on its `recoveries` row and the profile's maximal heart rate — so it needs no
column of its own and a persisted copy could only ever be a second number that disagrees with its own
inputs (see `ALGORITHMS.md` §6, which carries the model, its citation and its error bar; WHOOP's own
three-tier model is still the one this app declines to implement). And `AnalyzeStressUseCase` is
derived on read from `biometric_samples`: it answers from a table but writes nothing, which is what
makes it safe to point at any date — the calculate use cases are not, because they overwrite. All
three keep the day-keyed tables holding only what was measured once.

## 4. Testing & Verification Strategy

1. **Domain Tests**: Test business rules, Recovery z-score computations, and Strain algorithms in complete isolation with zero mocks.
2. **Decoder Tests**: Verify binary packet parsing against raw hex fixture dumps with various CRC edge cases and corrupted frames. The assertions that carry the weight are the **published known-answer vectors** from `BLE_PROTOCOL.md` §2.1 — a CRC checked against its own implementation is not a check, and four tautologies of exactly that shape are what let a wrong polynomial, byte order *and* input all pass. The corruption cases are built by mutating a **well-formed frame the encoder produced** (a bad SOF, a bad header checksum, a bad payload checksum, a truncated frame, a frame that lies about its length), so each rejection is a one-byte difference from a frame that was accepted. The generation-resolution rule is asserted as a pure function of its two inputs, `WhoopBLEManager.resolvedGeneration(stored:advertisedName:)`, because a `CBCentralManager` cannot be constructed in a test run — doing so raises a system Bluetooth prompt.
3. **Repository Tests**: Validate GRDB persistence and query operations against `LocalDatabaseManager(inMemory: true)`.
4. **Import Tests**: Drive `HealthKitImporter` with a fixture `HealthStoreClient` and an in-memory database, asserting day attribution, that a day without a reading stores no row, and that a repeated import does not duplicate rows. No device and no HealthKit entitlement are needed. `WhoopExportImporter` is driven the same way against the **real** bundled CSV read by path, asserting the day keys it derives (recomputed independently from the parsed rows), the minutes-to-seconds conversions, and that a second run writes nothing.
5. **ViewModel Tests**: Ensure state transitions and UI updates respond predictably to use case streams.
