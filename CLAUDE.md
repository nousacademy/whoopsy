# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Whoopsy** — a 100% offline, subscription-free iOS companion app for WHOOP 4.0/5.0 straps. Reads biometrics over BLE, decodes a reverse-engineered packet protocol, stores everything locally, and computes Recovery/Strain/Sleep metrics on-device.

Written in Swift 6 with strict concurrency (`async`/`await`, `AsyncStream`, `Sendable`), structured as Clean Architecture + DDD. Single dependency: GRDB.swift (SQLite).

## Commands

```bash
swift build                      # builds WhoopsyCore library + WhoopsyApp executable (host/macOS)
swift build 2>&1 | grep warning  # build emits known resource warnings — see Gotchas
xed Whoopsy.xcodeproj            # the real iOS build path (iOS 17+, target WhoopsyApp, bundle org.whoopsy.app)
```

`swift build` is the fast edit/compile loop. The iOS app itself is built from `Whoopsy.xcodeproj`, which consumes the `WhoopsyCore` package product. There is no linter configured.

### Building for iOS

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  xcodebuild -project Whoopsy.xcodeproj -scheme WhoopsyApp \
  -destination 'generic/platform=iOS' build
```

Two things to know. **`xcode-select` points at CommandLineTools**, so bare `xcodebuild` errors out and `xcrun --sdk iphoneos` cannot find the SDK; the `DEVELOPER_DIR` prefix above sidesteps that without a `sudo xcode-select -s`. And the legacy `-target` form **cannot resolve SwiftPM dependencies** (it fails with `Unable to resolve module dependency: 'GRDB'`), so use `-scheme` — `WhoopsyApp.xcscheme` is checked in under `xcshareddata` precisely because Xcode only auto-generates schemes when the GUI opens the project.

Signing is not yet functional: `DEVELOPMENT_TEAM` is empty in both configurations and there is no certificate (`security find-identity -v -p codesigning` → 0). `App/iOS/Whoopsy.entitlements` (`com.apple.developer.healthkit`) is wired up via `CODE_SIGN_ENTITLEMENTS` on both configs, and Xcode now rejects the target with *"has entitlements that require signing with a development certificate"* — which is the expected state until a team is set. Adding `CODE_SIGNING_ALLOWED=NO` builds everything up to signing, which is how to check iOS compilation without a team. Note the entitlement requires the HealthKit capability enabled on the App ID server-side; a free Personal Team is very unlikely to support it.

### Tests

```bash
swift test                       # FAILS: "no tests found" — Package.swift declares no test target
./scripts/run_tests.sh           # FAILS at the link step — see below
```

The real suite is `Tests/WhoopsyTestRunner/main.swift` (a hand-rolled assert runner, not XCTest). To build and run it against a clean build:

```bash
swift build --scratch-path /tmp/whoopsy-verify
swiftc -I /tmp/whoopsy-verify/arm64-apple-macosx/debug/Modules \
  -Xcc -fmodule-map-file=.build/checkouts/GRDB.swift/Sources/CSQLite/module.modulemap \
  /tmp/whoopsy-verify/arm64-apple-macosx/debug/Whoopsy.build/*.o \
  /tmp/whoopsy-verify/arm64-apple-macosx/debug/GRDB.build/*.o \
  Tests/WhoopsyTestRunner/main.swift -o /tmp/whoopsy-verify/WhoopsyTestRunner
/tmp/whoopsy-verify/WhoopsyTestRunner
```

Why the scratch path: `scripts/run_tests.sh` globs `.build/.../Whoopsy.build/*.o`, which includes stale object files left behind by since-deleted sources (`MainTabView`, `SettingsView`, `TodayDashboardView`, `SwiftData*Repository`, …), so the link fails with `symbol(s) not found`. It also omits the `-fmodule-map-file` flag and dies earlier with `missing required module 'CSQLite'`.

There is no way to run a single test — the runner is a linear `main.swift`. Trim it or comment out sections for focused runs.

The runner has 15 sections and all 15 now execute. Keep it that way: an uncaught throw inside its `Task` does **not** print a failure — the process idles out the `RunLoop` and exits **0**, so exit code is not a reliable pass signal. Check the section headers (they are numbered `[n/15]`) and the `✅ ALL WHOOPSY TESTS PASSED` banner. All new sections go inside the existing single `Task` in that order; adding one means renumbering every header.

**Run the binary from the repo root.** `whoopExportURL()` climbs three levels from `#filePath`, and the compile recipe above passes `Tests/WhoopsyTestRunner/main.swift` as a **relative** path — so the "repo root" it computes is whatever directory the process was started in. Started anywhere else, §11, §13 and §15 each fail with *"The bundled export is missing at &lt;cwd&gt;/Sources/…"*, which reads like a broken import and is only a wrong working directory.

It prints **757** `✓` lines as of the timeline lanes' absence, merge and scale rules plus the `v12` round trip that keeps them, the efficiency card's two notes, the consistency chart's circular mean, the night heading's `Today` rules, the heart-rate chart series and the hours-vs-needed card's split — including its provenance gate, which is asserted from both producers' sides — on top of `MetricChange`'s three-state verdict, the instant-anchor `baselineWindow` guard, the recovery-detail sleep-performance week chart, the `WeekBarSeries` palette/gridline assertions and the two bar initialisers' independent absences, the `WeekLineSeries` gap assertions, the per-quantity `valueDecimals` rule, `SleepConsistencyMath`'s pinned constants, recency weighting, midnight wraparound and four-record window, `RespiratoryRateMath`'s contiguity pair and band-edge guards, and the nap and sleep-debt paths — the export's eight naps importing, their day key being their own onset rather than their wake, the import being idempotent through an id derived from that instant, and `sleep_debt` round-tripping as a `Double?` whose `nil` and `0` are different answers. There is no test discovery, so a section that stops running looks exactly like one that passed — record the count before you edit and treat a drop as a deleted guarantee.

§11 drives the real WHOOP export. It locates the CSV from `#filePath` rather than the working directory, and it derives its expected day keys from the parsed rows instead of hardcoding counts — the device time zone decides `startOfDay`, and two 23:30 fragments sit on a date boundary. Prefer that shape for new assertions here: a hardcoded count that only holds in one zone is a test that fails on someone else's machine.

§12 is the day-selection guard. It imports the export into its own in-memory database, then drives the real `RecoveryViewModel`/`StrainViewModel`/`SleepViewModel` `load(for:)` over an imported day and asserts every row comes back byte-identical — score, HRV, and `source` — with the use cases built on `EmptyBiometricStore`, which is the true shape of an imported day. That is the assertion that fails if anyone re-wires a calculate use case into the day-selection path. Its window assertions move the `endingOn:` anchor rather than comparing against `Date()`, so they hold on whatever day the suite runs — keep that shape.

§13 is the Sleep Need and Sleep Consistency guard, and it is the only section whose fixture strap recorded a night: `OvernightBiometricStore` returns real samples where `EmptyBiometricStore` returns `[]`, because a need is only computed for a night the classifier could read. It pins the fitted coefficient with its fit basis in the assertion message, drives the real `AnalyzeSleepUseCase` against a strain row on the previous day, and — the part that matters — re-imports the export and asserts all 910 imported nights still carry WHOOP's own need. Do not assert the imported night *count* there: §11 owns the day keys. Assert the properties instead (whole minutes; 53 nights below the 8-hour baseline, which the formula cannot produce), because a hardcoded count that holds in one device time zone is a test that fails on someone else's machine.

The same section now owns the two strap-side models, and its RSA block is built the way the models' unvalidatability requires: **synthetic tachograms, never the export**, because the export carries no R-R series to test against. It pins the contiguity pair (a seam the later packet's own span accounts for chains; the same beats 90 s apart do not, and the night is `nil` rather than a series stitched across the gap) — that pair is the one that fails if anyone sums intervals across a notification boundary, which is the defect `CLAUDE.md` already records against the two RMSSD consumers. Both halves use **twelve packets, not six**: ten intervals of 600 ms is 6 s of beats, so six packets span 36 s — one window at a 5 s step, below `minimumWindows`, and the night would come back `nil` for a reason unrelated to contiguity. The band-edge pair pins both ends of `edgeGuardBins`, and the 30 bpm half is the assertion that would fail if anyone narrowed the guard back to one bin on the assumption that leakage peaks *on* the edge — it peaks one bin inside it, at 5.61× the mean. The two-tone case asserts a **`nil`**, deliberately: it is what keeps "declined" from reading as "broken", with a single 18 bpm tone and a single 9 bpm tone beside it to show the estimator reads each of them plainly. The debt block pins hand-computed accumulations against literals rather than against the model, asserts `nil` at no priors and a value at one, and covers the one quantity in this app that may legitimately be `0`. **The end-to-end block anchors its synthetic beats inside the use case's own window** — `AnalyzeSleepUseCase` reads `[morning − 11 h, morning + 10 h]`, so a series pinned at the reference date is filtered away before it is classified and the night is `nil` for a reason that has nothing to do with the R-R series under test; that is what `syntheticPackets`' `anchor:` parameter is for.

The consistency block is built on **fixed clock times rather than elapsed offsets**, and that is not incidental: `date(byAdding: .minute,)` adds elapsed time, so on a spring-forward day "420 minutes after midnight" is 08:00 on the wall and every pinned literal would move. Its hours (22:00–23:59, 06:00–07:59) sit outside both the 02:00 gap and the 01:00 fold, so the wall clock is unambiguous all year. Four assertions carry the weight. The **recency pair** — the same total drift, recent against old, scoring 88 and 92 — fails if the weights are dropped or the sort is reversed, which a single case cannot see because a flat mean scores both arrangements alike. The **midnight assertion** (a 23:50 onset against 00:10 priors scores 91) separates circular distance from a naive minute-of-day subtraction by 91 points, since the naive form reads the pair as 1420 minutes apart and clips to the floor. The **gap assertion** — a night whose fourth prior is 10 days back is still scored — is the one that fails if anyone re-derives the four-record window by subtracting calendar days. And the **strict-before assertion** passes a night dated *after* the target alongside three real priors and requires `nil`, which is what keeps a forward-dated row from taking the heaviest weight.

Its export guard is a *property* in the same spirit as the need's, and it needs one for the same reason: a stored WHOOP consistency and a computed one are the same `Int` on the same column, so nothing but an assertion keeps either producer off the other's rows. The property that separates them is **disagreement** — the model reproduces WHOOP's figure closely but not exactly, so a column that had been recomputed rather than read would agree on every night. The suite counts the nights where the two differ by more than the model's own error bar (167 of 906 at the time of writing) and requires it to be large; a fixed count of nights would break on a device time zone that merges two day keys.

§14 is the Home screen's sources, and it is the only section that touches all four of them. It asserts the `v6` tables exist and that a `WorkoutSession` round-trips through `GRDBWorkoutRepository` with its route and splits — including that a session saved at a raw 17:33 is found on its own day and **not** on a neighbouring one, which is the day-snap rule this suite exists to guard. It drives the steps path through `FixtureHealthStore` → `HealthKitBridge` and asserts a day with no samples is `nil` rather than `0`. `DaytimeBiometricStore` is the fixture strap for the stress model — `OvernightBiometricStore`'s counterpart for daytime samples, and needed for the same reason: `AnalyzeStressUseCase` returns `nil` the moment its store is empty, so only a store that holds samples can prove the measured path. One block asserts that a day with nothing stored yields `nil` from every one of `HomeViewModel`'s sources, which is what the screen's dashes follow from — and the block after it is that one's counterpart, because **the dashes are the only thing this suite used to prove**: a fresh install has no strap data, so the first day Home can show a number for is an *imported* one, and nothing asserted Home populates from it at all. It imports the real export into its own in-memory database, loads Home with the most recent day that carries a recovery **and** a night **and** a strain (not simply the last day of any one of them — the export's tail has a night with no strain, and demanding all three from one arbitrary day asserts a fact about the file rather than about Home), and asserts the rings and the RESTORATIVE SLEEP tile populate while STEPS and STRESS MONITOR stay dashes, since the export carries neither step counts nor an R-R series. That gap is what a user reporting "data isn't populating" was actually seeing.

The section's last block is the seven-day `MetricWeek` join behind the Strain & Recovery chart and the four metric panels, and it is where the **alignment invariant** is pinned: seven slots oldest-first ending on the anchor, a day with no rows as an *empty slot* rather than a missing one, and the baselines as the mean of the measured slots only — `nil` at two measured days and non-`nil` at three, asserted at both edges of `minimumBaselineDays`. Two assertions there are the ones that fail if anyone plots a legacy placeholder as a reading: a `recoveries` row with `hasMeasurement == false` yields a `nil` `recoveryScore` slot, and the same for `strains` — plus the same row yielding no HRV *and no metric*, so the pair can never disagree. The HRV baseline's **never-mix** narrowing is asserted on a week built so the two answers differ: three RMSSD days and two SDNN days, where the SDNN days are lower, so an unfiltered mean (56.4) and the correct one (63.33) are distinguishable — and again in the other direction, where the newest metric is the minority and the answer is still its own mean, not a blend. The VO₂ MAX block is the **estimate**, not a read-through, and its guards are the ones that keep a derivation from becoming a fabrication: the arithmetic pinned to a literal (`15.3 × 190/50` at 58.14, compared with a tolerance, so a changed constant fails rather than agreeing with itself), the two `0`-anchor cases (`?? 0` writes both columns, so a `0` resting rate and a `0` maximal rate must each be an absence rather than a division), and a `nil` anchor on either side. The discriminating one is in the week: a fixture day holding `hrvValueMs: 0` beside a **plausible `55` bpm** yields no estimate, because the estimate reads the slot's gated value and not the raw row. That case is what a mutation test confirmed — pointing `makeDay` at `recovery?.restingHeartRate` passes a `0` straight to the model, whose own `> 0` guard catches *that* but not a real-looking rate, and the assertion fails. `hasAnyMeasurement` still excludes VO₂ max, though that exclusion is now provably redundant (an estimate requires a non-`nil` resting rate, already in the list) rather than load-bearing as it was when the value could arrive from HealthKit on a day with no stored row at all. The block also drives `CalculateStrainUseCase` against `EmptyBiometricStore` and asserts it returns `nil` **and writes no row** — the contract that replaced the reserved-zero placeholder. The placeholder shape itself is no longer produced by any writer, so it is covered by constructing one directly through `GRDBStrainRepository` and asserting it reads back unmeasured while a `0.1` row reads back measured. That is measured, not assumed: three assertions over the imported export assert all 931 strain rows read back measured, that every one carries a heart rate, and that the 2 days WHOOP itself scored exactly `0.0` are among them — the pair that keeps the `v7` backfill's predicate honest, since a backfill keyed on the score alone would have marked those two as absences. **What it cannot cover is the `v7` backfill `UPDATE` itself** — the migrator runs it before any row can exist — so the suite tests the write/read path instead and does not claim the backfill is covered.

The Stress Monitor block is also where the day's **series** is asserted, not just its aggregate. `StressDay` computes its `StressScore` from the windows it was handed rather than accepting one, so `windows.count == score.windowCount` is structural; the assertions pin that, that the windows are sorted and inside `StressMath.wakingWindow`, that the average really is their mean, and — the one that matters most — that `executeDay(for:)` and `execute(for:)` return the same figure, since `execute` is a forwarder rather than a second implementation. The **anti-flat-line** pair is there too: a day with no eligible window returns `nil` from both entry points, because a `StressDay` with an empty series would draw a flat line at zero, which is the strongest possible claim of calm. What none of this proves is the chart's *drawing* — that is a `Shape`, and the runner has no renderer. It proves the series the drawing is made of.

It also pins the recovery tier boundaries at all six edges (100/67 green, 66/34 yellow, 33/0 red), because the colour of Home's recovery ring is decided there and an off-by-one at 66/67 is invisible on screen — the two colours are adjacent either way — and then asserts `RecoveryMetric.state` agrees with `RecoveryState(score:)` across the range, since the coach message path holds a bare score and reads the initialiser while the ring reads the property. The pair next to them is what keeps a placeholder off the screen: an unmeasured day's `score: 0` row reports `.red` **and** `hasMeasurement == false`, so a view that drew the tier colour without checking the latter would show an unworn night as a hard 0% red recovery.

The month calendar's blocks sit beside those tier assertions, and they are shaped by what a runner with no renderer can and cannot see. `DayBarRules` is a separate type rather than logic in the bar's body for exactly this reason — a rule written into a `View` is a rule nothing here can assert — and it takes `now` as a parameter so the assertions do not say something different tomorrow; one of them pins that `TODAY` is decided by the **calendar day** and not the instant, which a raw `Date` comparison gets wrong. `MonthGrid` is swept across all 60 months of 2023–2027 and the per-month failures are accumulated into single assertions rather than one assertion per day, so the coverage is exhaustive without the count exploding. **The sweep alone cannot see the bug `MonthGrid` exists to prevent**: this machine's `Calendar.current` is Sunday-first, so `firstWeekday - 1` is 0 and the wrong `blanks = weekdayOfFirst - 1` agrees with the right answer — that was confirmed by mutating `MonthGrid` to it and watching all six sweep assertions still pass. The block that catches it drives a **Monday-first** calendar (the parameter `MonthGrid.make` takes for precisely this) through the same invariant, and the mutation fails there with `Thu, Jan 1 sits under Fri but is a Thu`. The month read is then driven through the real `HomeViewModel.loadMonth(containing:)` against an in-memory database holding a row inside the displayed month and one in the month either side, and it asserts **both neighbours absent** — the window is `days: <the span between the month's own bounds>, endingOn: <the month's last day>`, and a window one day too wide would tint a day nothing measured, which is invisible on screen. The measurement gate is asserted the same way it is everywhere else: a `hasMeasurement == false` row is absent from the map rather than `.red`. The last block is the one that fails if anyone decides a load is "still running" from `monthTiers.isEmpty` — a month the export never covered returns an empty map, no error, and `isLoadingMonth == false`.

One assertion there is a deliberate documentation of a trap rather than a behaviour: it asserts that a `WhoopDevice` constructed `.disconnected` reports `batteryPercentage == 100`. That is the *reason* the Home readout gates on connection state, so the assertion fails loudly if anyone "fixes" the default without fixing the readout.

§15 is the sleep detail screen's four cards — the typical range, the hours-vs-needed breakdown, the consistency chart and the sleep-efficiency card that closes the page — and it is split into the three kinds of thing a card there is made of: the arithmetic its percent column comes from, the layout rule its bars are drawn from, and the absence rules that decide when there is no card, no markers and no comparison. It is the section that would otherwise not exist, because **the card is almost entirely a drawing** — four coloured bars, two dashed marks each — and the runner has no renderer. That is why `SleepStageRangeScoring` and `TypicalRangeBarLayout` are values rather than bodies, and why the spoken strings are `nonisolated` statics on the card instead of text built inside a `body`. The percentile is pinned against hand-computed literals (1.75/2.5/3.25 on 1…4) rather than against a second implementation, and the numbers are the ones R's `quantile(type = 7)` and NumPy's default produce, so they are reproducible outside this codebase. **The whole-percent block is the one that would silently pass a wrong rule**: 3h/3h/1h/1h is 37.5/37.5/12.5/12.5, floors sum to 98, and the assertion distinguishes the correct `[38, 38, 12, 12]` from naive rounding's 102 — and the general property (every percent within one of its exact share) is asserted over five fixtures and then over all 910 imported nights, which is what catches a rule that only works on the shapes someone thought to build. Its summary fixtures are chosen so the quartiles are **exact in binary** (deep shares 20/25/30/35% of an eight-hour night give 23.75 and 31.25), which is what lets them be pinned as literals rather than to a tolerance. Two blocks are worth keeping for the bug they encode: a stored night with no sleep period is filtered out of the window **before** the count floor is applied, asserted in both directions (five nights with one empty still bands; three with one empty do not), and the window itself is `RecoveryScoring.baselineWindow(before:in:)` handed the target's own day and a later night to prove neither lands inside it. The export block at the end re-verifies on real data the three identities the design was evaluated against — the four shares sum to 100, each is within one of its exact share, and DURATION equals the night's own sleep period — as properties, so a device time zone that merges two day keys narrows them without breaking them. The **hours-of-sleep headline** sits inside the same section, because it is the same card: the night's three sleep stages (`asleepSeconds`), the window's mean of them, and the comparison between the two. Its assertion that matters is the **identity** — `asleepSeconds + awakeSeconds == durationSeconds` — which is not a restatement of the entity's own arithmetic but the thing the card prints two separate figures for, so a reader adding the column up on the screen reaches the `DURATION` in the header. Both halves are then re-run over all 910 imported nights as properties: every night carries a *positive* headline (the card is never titled over a dash) and every night's headline agrees with its awake row. **The hours-vs-needed card closes the section and is built the same way**, its fixtures the mockup's own numbers (7:33 asleep against a 9:17 need is 81%, with 1:44 of debt) so the literals are figures a reader can check against the reference: the two parts sum to the need printed above them on every imported night, and the bar's split is drawn on the need's own scale rather than an arbitrary fraction of the track. **Its provenance gate is the one assertion here that no fixture could have caught**, and it is asserted from both sides: all 910 imported nights read back with `hasWhoopSleepNeed == true` and split, while the strap night §13 classifies reads back `false` and produces no split even when handed an hour of debt. That pair is the check on a defect the card shipped with — `AnalyzeSleepUseCase` stores a debt on the strap path too, so the split's original `debt != nil` gate admitted both producers, and the box's first row would have been labelled `Healthy Minimum + Recent Strain` over a need containing neither term. Deleting the `hasWhoopNeed` guard makes the §13 half fail; the runner halts on the first failure, so that half is the one to run when this gate is in doubt. **The consistency card closes the page and adds five blocks to the same section**, all of them about a chart with no renderer. Its arithmetic is pinned against hand-computed literals rather than a second implementation: the opposed pair (`circularMean([1410, 30])` is **midnight**, where the naive mean of the same two is noon — the one fixture where the two rules are twelve hours apart), the flat/weighted pair (the same four onsets average 720 flat and 715.9979 weighted 4:3:2:1, so a dropped weight shows up as a moved literal), and the degeneracies. **The degeneracy guard is on the resultant's length rather than the weight sum**, because `sin(π)` is `1.2e-16` and not `0` — an exactly opposed pair would otherwise return a direction computed from floating-point noise, which is an arbitrary time presented as an average. The frame conversion gets a block of its own because it is where two minute scales meet (see the gotcha below): a 24-hour round trip, plus the naive-vs-circular pair that prints `"12 PM"` from one path and `"12 AM"` from the other. The five-night block drives the real layout over fixed clock times and pins the default axis labels (`["7 PM", "11 PM", "3 AM", "7 AM", "11 AM"]`), the anchor fractions, the two callout strings, the two-prior absence, the widening fixture (a 17:30 onset moves the axis to 300 and the labels to `"5 PM"` / `"9:30 PM"`), and the refusal of an interval containing noon. Its window-mean block is the one that would silently pass a wrong rule: three stored figures average to 92, and adding two unscoreable nights to those three must leave it at 92 — counting them as zeroes prints 55.2. The card's own words come last, because the legend *is* the correction: the block asserts `SleepConsistencyCard.legendLabel` is `Avg Bed/Waketime` and that it does **not** contain `optimal`. **The efficiency card closes the section**, and its block is shaped by the fact that two of its three elements have no producer on any night this app can show: the middle is a timeline the export cannot supply (it reports stage totals and no timeline, permanently), and the `WAKE EVENTS` count is `disturbanceCount`, which no imported night carries — so both slots draw a note and the assertion is on the card's own words rather than on a screenshot. **The lane blocks are the arithmetic that picture is made of**, resolved into `SleepTimelineLanes` rather than drawn, and three properties carry them. The **absence rule**: no segments, or no duration, is `nil` — an instance with two empty lanes would be a drawn timeline of a night with neither sleep nor wakefulness in it, and a zero duration is the guard that keeps `make` from dividing into two `NaN` lanes, which is a mark taking the whole bar with it rather than one drawn in the wrong place. The **merge**: three abutting epochs are one run covering the whole period, because an unmerged lane is hundreds of abutting rectangles and anti-aliasing draws a hairline of track between each pair, so eight hours of unbroken sleep come out looking striped; and only `.awake` is awake, so all three sleep stages fill the other lane as a single run. The **scale**: the awake run sits at the middle third of the sleep period — a fraction of the *night*, not of the day — and a segment reaching outside that period is clamped into the lane rather than drawn past its end, since a mark outside the scale reads as a different scale. **The `v12` round trip is the assertion that fails if the column, the record property or the mapper is removed** — four segments written through `GRDBSleepRepository` and read back with their stages in order — and it is the whole reason the card can draw a timeline on a night the app was not running for; beside it an imported night is asserted to come back with **no** timeline, so the note on every night this app can show is a fact about the producer rather than about a missing column. What none of this can see is the **drawing**: the marks are placed by `SleepTimelineView`, and the runner has no renderer — see the layout gotcha below for the defect that hid there. Its arithmetic block is the one that would silently pass a wrong rule: `SleepEfficiencyScoring` must **filter out a night with no sleep period before applying its count floor**, because `SleepSession.sleepEfficiencyPercentage` guards a zero denominator by returning `100`, and a mean that counted one prints 87.5 where the correct answer is 83.33 — asserted beside the pair that makes the floor itself discriminating (two scored nights beside an empty one is still below `minimumBaselineDays`). The efficiency/performance distinction is pinned on one fixture where the two read 100 and 50, and then re-run over the export as a *disagreement* property, since a card reading one figure for the other would agree on every night: measured, the two differ on **904 of 910** nights.

The three XCTest files in `Tests/WhoopsyTests/` are dead: no test target references them, so they are never compiled or run.

## Architecture

Four layers under `Sources/Whoopsy/`, with a strict one-way dependency rule (verified: `Domain/` imports only `Foundation`; `Core/` adds only `os.log`; `Presentation/` imports no GRDB or CoreBluetooth):

```
Presentation  (SwiftUI + @Observable ViewModels)   →  depends on DIContainer
Domain        (Entities, UseCases, Repository protocols)  ←  implemented by Data
Data          (BLE, GRDB persistence, HealthKit adapter, exporters)
Core          (HRV/Strain/Stress math, logging, extensions)
```

- **`Domain/Repositories/*`** are protocols only. Concrete implementations live in `Data/Persistence/Repositories/`.
- **`App/DependencyInjection/DIContainer.swift`** is the single wiring point. `DIContainer.shared` uses real BLE; `DIContainer.preview` uses `WhoopMockBLEManager`. `app/iOS/WhoopsyApp.swift` picks `preview` when `XCODE_RUNNING_FOR_PREVIEWS=1`. Use cases are constructor-injected; there are no singletons below the container except `LocalDatabaseManager.shared`.
- **Data flow**: `WhoopBLEManager` → `WhoopPacketDecoder` (0xAA framing) → `BiometricRepository` → `LocalDatabaseManager` (GRDB) → `StreamBiometricsUseCase` / `Calculate*UseCase` → `@Observable` ViewModel → SwiftUI. Two further inputs write into the same tables through the same repositories: `HealthKitStoreClient` → `HealthKitImporter`, and `WhoopExportParser` → `WhoopExportImporter` for a bundled WHOOP data export.
- **`Data/Import/*` is the only WHOOP-export seam**, and it is not a sync. It reads a CSV that shipped inside the app bundle, it runs only when the user taps the button in Settings, and it exists so a fresh install can show history that predates it. `WhoopExportParser` produces a plain `Sendable` row of optionals and decides nothing; `WhoopExportImporter` does the day-keying and the scoring. Unlike the other two inputs, it does not compute Strain — see the gotcha below.
- **`Data/Health/*` is the only HealthKit seam.** `HealthStoreClient` is the protocol the importer depends on; its value types are plain `Sendable` structs and it deliberately does **not** `import HealthKit`, which is what lets the import be tested with a fixture store and no device. `HealthKitStoreClient` is the real actor behind it. It has two read shapes and the difference is load-bearing: `quantitySamples(_:from:to:)` for individual readings (HRV, resting heart rate) and `dailyTotal(_:from:to:)` for a cumulative sum over a window (steps only). Adding a case to `HealthQuantityMetric` also adds it to `readTypes`, so the consent prompt grows with it — and **removing one shrinks it**, which is how the VO₂ max read-through left the prompt when its case was deleted. `FixtureHealthStore` in the runner answers **per metric in a `switch`**, deliberately — its old two-way ternary sent everything that was not HRV to the resting-heart-rate array, so a new case would have silently answered one quantity's query with another's readings, which is a fixture inventing a measurement of the wrong kind.
- **Views get their ViewModel built in `MainContainerView`** — tabs are Home, Strain, Workout, Sleep, Recovery, and a "More" stack holding Coach/Device/Settings. Adding a screen means wiring its use cases through `DIContainer` and `MainContainerView`, not reaching for a global. `MainContainerView` builds **one** `ActiveWorkoutViewModel` and passes it to both Home's `+` and the Workout tab, so those are two views of one live session.
- **`Presentation/DesignSystem/Theme.swift`** holds all color tokens (recovery green/yellow/red, strain gradient, sleep stage colors, and the Home surfaces `homeBackground`/`homeCard`/`ringTrack`/`sleepPerformance`/`strainRing`). Don't hardcode colors in views.
- **There are two ring components and they are not interchangeable.** `GaugeRingView` (gradient, glow, label inside) is what Strain, Sleep, Recovery and the workout HUD use. `MetricRingView` is Home's flat counterpart and takes its value as an **optional** `String?` so a dash cannot arrive with a fill attached. Changing one must not move the other.
- **The Recovery ring is drawn in the day's tier colour, and there is exactly one definition of the tiers and one mapping to colour.** The boundaries (green 67–100, yellow 34–66, red 0–33; spec in `ALGORITHMS.md` §"Recovery Tiers") are written down once, in `RecoveryState.init(score:)` — `RecoveryMetric.state` forwards to it, and `GenerateCoachInsightsUseCase` reads it rather than holding its own `>= 67`. `RecoveryState.color` in `Presentation/DesignSystem/RecoveryState+Extensions.swift` is the only place a tier becomes a `Color`; Home's ring and the Recovery tab's gauge, HRV card and trend chart all read through it. It cannot be a property on the enum (Domain imports only `Foundation`) and it must not be re-written per screen: the copies had already diverged twice, with Home drawing `recoveryGreen` unconditionally while the Recovery tab tiered it (a 20% morning green on one screen and red on the other) and the coach message holding a second green boundary. A tier is computed from the **score**, so a `score: 0` placeholder reports `.red` — which is why the drawing gates on `hasMeasurement` and an unmeasured day renders `—` with no fill rather than as a hard 0% red ring. The rule is general and the repo now holds a second instance of it: `SleepStageType.color` in `Presentation/DesignSystem/SleepStageType+Extensions.swift` is the one stage-to-`Color` mapping, lifted out of `HypnogramChartView` when the sleep detail screen's typical-range card needed the same four answers. A fourth stage added to the enum, or a screen that wants "a slightly different deep purple", goes through that file or not at all.

### Persistent gotchas

- **A shipped migration is frozen.** GRDB records applied migration *identifiers* and does not checksum bodies, so editing `v1`'s body changes nothing on any database that already ran it — and the schema silently stays wrong. Schema changes always go in a new `registerMigration` block. The per-version inventory — what `v2`…`v11` each added — is `ARCHITECTURE.md` §2.B and is not repeated here. Note `addMissingColumns(to:columns:in:)` adds **nullable, undefaulted** columns only; a NOT NULL column needs an explicit `db.alter`, which is why `source` is nullable: NULL is the honest value for a row written before the column existed.
- **A `[Double]` property on a `Codable` record is a JSON-encoded `.text` column, and `Array` is not a `DatabaseValueConvertible`.** `biometric_samples.rrIntervalsMs` is `[Double]?` and GRDB stores it as a String, which is why `v8` declares the column `.text`. The array can therefore only ever be a *record property* — using it as a query binding is a compile error, and `BiometricSampleRecord.rrSeries` exists as the computed `[Double]` that is safe to pass around. Computed properties are invisible to `Codable` synthesis, so adding one to a record adds no column. The same record has **no `CodingKeys`**, so its property names *are* its column names — `rrIntervalsMs`, camelCase. `v12`'s `sleeps.sleep_stages` is `[SleepStageSegment]?` in the same shape, and one detail of that encoding is worth knowing before writing a fixture or a backfill by hand: **the `Date`s inside the JSON are unix milliseconds** (`1787372263000`), not seconds and not an Apple reference date, so a plausible-looking value in the wrong unit decodes to a year far away and the night silently loses its timeline.
- **The test suite is not hermetic, but only in the migration sense — §6 opens the developer's real database, and does not write rows to it.** `Tests/WhoopsyTestRunner` §6 builds `DIContainer(useMockBLE: true)`, and `DIContainer.init` takes `LocalDatabaseManager.shared` — the actual `~/Library/Application Support/whoopsy.sqlite` — whose `init` runs the migrator. So **running the suite applies any pending migration to that file**, which is how `v8`, `v9`, `v10` and `v11` land on a developer's database before the app is ever launched, and it is the one thing here that mutates real state. It does **not** leave §6's rows behind: measured, a full run leaves that file byte-identical (same mtime, same size, no `-wal`), because every section that writes builds its own `LocalDatabaseManager(inMemory: true)` — that is the shape to copy, and there is no path-injecting initialiser to reach the real one with on purpose (see the gotcha below). The practical consequence is narrow and worth stating exactly: a migration added in a turn is exercised against real data by the next suite run, so a failing one `fatalError`s there rather than at app launch — and a passing run tells you nothing about whether the rows you *expect* were written, since nothing was.
- **The BLE streams are multicast.** `liveTelemetryStream` and `deviceStream` each hold a dictionary of continuations keyed by `UUID`, pruned in `onTermination` and guarded by a lock (the class is `@unchecked Sendable`, and these are written from caller threads and read from the BLE queue). A second subscriber must never orphan the first: the failure is silent — no error, no gap, just a `for await` that stops receiving, which is indistinguishable from a strap that went quiet. Both streams genuinely have two consumers: `StreamBiometricsUseCase` is driven from `HomeViewModel.load(for:)` and from `MainContainerView`'s workout HUD, and `deviceStream` is read by `HomeViewModel.observeDevice()` and `DeviceViewModel.load()`. A new subscriber is safe to add, but anything that *yields* must go through `yieldTelemetry`/`yieldDevice` rather than touching the dictionary.
- **A sample row's `timestamp` is an arrival instant, not a beat time.** `WhoopBLEManager` stamps `Date()` when the notification is decoded, so the column records when the app heard about the beats, not when they happened. Within a notification the intervals in `rrIntervalsMs` are adjacent beats in exact order; **across** notifications they are not, and no column distinguishes them. Anything building a beat-to-beat tachogram must therefore reconstruct beat times by cumulative sum from the intervals themselves and must not trust `timestamp` as a per-beat time. `getSamples` orders by `timestamp` with `id` as the secondary key, which recovers insertion order for ties — that is arrival order, and it is the best the schema has.
- **The proprietary BLE path has never been validated against hardware, and no part of it should be described as working.** The framing now matches `BLE_PROTOCOL.md` §2 — the 4.0 envelope's header CRC8 is over the two length bytes only, `length` is the inner record plus four, and the inner record is `[type][seq][cmd][payload…]` with the CRC32 over the whole record — and the decoder verifies both checksums on inbound frames. Both of those were wrong until recently, and **the way they were wrong is the part worth remembering**: the encoder and decoder were self-consistent with each other, so they round-tripped, and the suite's CRC assertions were self-referential (`crc8Val >= 0` on a `UInt8`, `!= 0` for the other two, and a layout check against the encoder's own constant), so a wrong polynomial, byte order and *input* all passed. **An assertion whose expected value is computed by the code under test is not an assertion**; §1 of the runner now pins the four published vectors from `BLE_PROTOCOL.md` §2.1 plus layout assertions derived from the format. Two things this did *not* buy: length-based reassembly across BLE fragments is still absent (a false `0xAA` boundary now fails its checksum rather than parsing as garbage, but reassembly is not length-driven), and **nothing here has been captured on this project's own hardware** — `biometric_samples` holds **0 rows** in both the dev and seeded databases, so nothing on this machine was ever written by this path.
- **The history drain is unimplemented, and the reason it is unimplemented rather than half-built is that half of it is dangerous.** Four gaps remain, all open: request opcode `0x30` where 4.0 uses `0x16`; no ACK/token loop at all; no record walk (the decoder hands up a validated `WhoopRawFrame` and decodes no payload); and an unimplemented 5.0/MG envelope. **The `0x30` opcode is deliberately not corrected yet** — the drain is a loop that needs the per-batch `0x17` ACK, and without a correct ACK **the strap re-sends the same batch forever**, so starting a drain this app cannot acknowledge is worse than sending a command a strap ignores. A related deletion: the old `decodeHistoricalSyncPayload` walk is gone rather than fixed, because it walked 16-byte chunks through the *live* layout where the record header is 96 bytes, so on a real drain it read a record-counter byte as a heart rate and wrote it to `biometric_samples` — a fabricated reading of exactly the kind the absence rule forbids. The capture plan that would settle all of it, in cheapest-first order, is `BLE_PROTOCOL.md` §6. **The 4.0 base UUID is itself unresolved** between the doc (`…82b8-614a-1c8cb0f8dcc6`) and `WhoopGATTConstants` (`…82A5-4E40-1CA360B95B30`), which presents as *no device found* rather than as a decode error — so a capture may fail before it reaches any of the above. **The timestamp that would place a drained batch on a timeline is verified as a field and unverified as a value** — `[7:11]` of the 96-byte type-24 record is a u32 unix time, but the strap's RTC is set by `0x0A SET_CLOCK`, which this app never sends, and the 4.0 reference's event enum carries type 13 `RTC_LOST` ("battery fully died — clock reset"), so a battery-flat strap stamps every record with a wrong offset and nothing in the record shows it. That failure is silent in the worst way: it files history onto a **wrong day** rather than onto no day. Check `[7:11]` against wall time per strap before trusting it; `BLE_PROTOCOL.md` §6 lists that as the capture's most consequential question. **Two opcodes must never be sent**: `0x19 FORCE_TRIM` is a flash erase (destructive — the drain is non-destructive by design and needs no trim; issuing one to "clear the backlog" destroys history including what has not been drained), and `0x9A TOGGLE_PERSISTENT_R21` forces the optical engine on across reboots, burning battery until a `REBOOT_STRAP`.
- **Which strap is connected is a stored choice, and a guess must never override it.** `WhoopHardwareGeneration` has five cases — `whoop4`, `whoop5`, `whoop5MG`, `standardBleHR`, `simulator` — and `selectableModels` derives the three a user may pick. The choice is kept per **peripheral identifier** in `UserDefaults` (`UserDefaultsStrapModelRepository`), because a strap advertising no name arrives as `"WHOOP Strap"` and the old name heuristic — `advertisedName.contains("5") ? .whoop5 : .whoop4` — cannot tell a 5.0 from a 5.0 MG and calls an unnamed 5.0 a 4.0. The precedence rule is `WhoopBLEManager.resolvedGeneration(stored:advertisedName:)`, a **public static** taking both inputs so the suite can assert it without a `CBCentralManager` (constructing one raises a system Bluetooth prompt mid-run). Three things about the wiring are load-bearing. `refreshStrapModels()` must run **before** `startScanning()`, because `didDiscover` is a synchronous CoreBluetooth callback and cannot `await` the store. `didConnect`/`didDisconnect` go through `resolvedDevice(for:)` rather than building a bare `WhoopDevice` — whose `hardwareGeneration` defaults to `.whoop4` — so the discovery-time resolution is not silently replaced by a literal the moment the strap connects. And `WhoopBLEManager.sendCommand` is the **choke point**: it refuses to write when `currentProfile` is `nil`, because the packet-type numberings do not overlap between generations, so a 4.0-framed command written to a 5.0 strap is a *different message* rather than a rejected one. `WhoopProtocolProfile.profile(for:)` answers `nil` for every envelope this build has not implemented, and the encoder returns `nil` rather than a frame for one — so a 5.0 or 5.0 MG strap gets **no command at all**, and the device screen says so in as many words. Do not "fall back" to the 4.0 path for an unimplemented generation; that is the single mistake this whole arrangement exists to prevent.
- **Column naming differs per table, and `CodingKeys` is the only thing that decides it.** `RecoveryRecord` declares `CodingKeys` mapping its properties to **snake_case** columns (`recovery_score`, `hrv_value_ms`), so a new property needs a matching case there. `StrainRecord` has **no** `CodingKeys`, so its property names *are* its column names and `strains`' columns are **camelCase** (`strainScore`, `averageHeartRate`, `hasMeasurement`). Writing `hasMeasurement` as `has_measurement` in `v7` produced `SQLite error 1: no such column` at launch — and because a failing migration `fatalError`s, the whole app went with it. Check `pragma_table_info(<table>)` or the record's `CodingKeys` before naming a column in a migration.
- **`naps` follows `workouts`, not `sleeps`, and a nap's day is its onset while a night's is its wake.** A day holds one night and can hold several naps, so `naps` is keyed on `id` with `date` an ordinary indexed column, exactly as `workouts` is — a `date` primary key would make the second nap overwrite the first. The day key is still snapped centrally by `LocalDatabaseManager.saveNap`, so a nap written at a raw 17:33 is found on its day and not on a neighbouring one. **The key itself is the opposite of the night table's**: a night is filed under the morning it ended on, a nap under the day it was *taken* on, and the difference is a whole day — measured against the bundled export, keying the eight naps on their wake onset moves the two that cross midnight (2024-02-05 22:13 → 02:34, 2024-08-26 23:48 → 02:36) onto a day nothing reads, so only six are reachable. **The `id` is the nap's own start instant as a string, never a `UUID()`** — this is the one place `SleepNap` deliberately differs from `SleepSession`, whose fresh-per-init `UUID` is why two reads of one night never compare equal. A `UUID()` here would write eight more rows on every press of the import button, since GRDB's `save` is INSERT-or-UPDATE *by primary key*. **A nap is not a night and carries no performance**: WHOOP's own `Sleep performance %` for the export's eight naps is 6–43 because its denominator is a full night's need (526–617 min) against 33–237 min of actual nap, so reading it as a performance would file a deliberate 33-minute nap as a 6% night. `SleepNap` therefore holds only its window and its asleep duration. **The three rows the sleep-performance screen gained are all ungated readings, and that is the point of them**: sleep debt and respiratory rate are optional on the row *and* on the value, and neither joins `SleepBand` — WHOOP publishes no anchor for a respiratory rate, and a running deficit is not monotone in the direction the banded rows share — so both render as plain figures in `Theme.textPrimary`. A nap is drawn as an **absent row, not a dash**, when the day has none: not napping is an ordinary answer rather than an unmeasured one.
- **`workouts` deliberately breaks the day-key rule, and that is not a bug to fix.** `recoveries`, `sleeps` and `strains` are primary-keyed on `date` snapped to `startOfDay` because a day holds one of each. A day can hold **several** workouts, so `workouts` is keyed on `id` (a UUID string) with `date` as an ordinary indexed lookup column, and `getWorkouts(for:)` returns an array rather than an optional. The snap still applies — `LocalDatabaseManager.saveWorkout` snaps `date` centrally like its `saveRecovery`/`saveSleep`/`saveStrain` siblings — so a session started at 17:33 is filed under that day. Do not "normalise" this table onto a `date` primary key; that would make a second session on one day overwrite the first. `DIContainer` wires `GRDBWorkoutRepository`; there is no in-memory workout store.
- **`WhoopDevice.batteryPercentage` is not optional and defaults to `100`.** `WhoopBLEManager` writes a literal `100` at discovery, so a percentage read off a strap that is not connected is a constant this app wrote down rather than a measurement it took. Any battery readout must therefore gate on `connectionState == .connected` and render `—` otherwise — `HomeDashboardView`'s status badge is the reference. The real fix (making the field optional the way `SleepSession.respiratoryRate` is) is still open and is a wider change than a view.
- **Steps is the only value on Home still read through HealthKit, and the VO₂ MAX panel no longer is.** Steps are a daily *sum* — the one HealthKit quantity that is not a reading the app can file under a day key — so `HealthStoreClient.dailyTotal` uses `HKStatisticsQuery(.cumulativeSum)` rather than the per-sample path, and `HealthKitBridge.stepCount(on:)` reads the store on demand; there is no table and no column. It is a `HealthKitSyncing` member that does **not** throw, deliberately: HealthKit never discloses read-permission status, so a denial, an empty day, a device with no source and an unavailable store are indistinguishable from the caller, and all of them are honestly the same dash. A `0` for steps would be a different claim — a day the user did not walk. **The VO₂ MAX panel is not a HealthKit read and must not become one again** — there is no `.vo2Max` case on `HealthQuantityMetric` and no member on `HealthKitSyncing`, so VO₂ max is absent from the consent prompt's `readTypes`. It prints an estimate this app computes instead: `Vo2MaxMath.heartRateRatioEstimate` (`15.3 × HRmax / HRrest`, Uth et al. 2004), derived on read inside `MetricWeek.makeDay` from the slot's own gated resting heart rate and `UserProfile.maxHeartRate`, stored nowhere. Two things about it are not negotiable: the label says `(EST.)` because it is a model's output beside three measurements, and a day that cannot produce one is `—` and never `0`. `ALGORITHMS.md` §6 carries the model, the citation, the 4.7 mL·kg⁻¹·min⁻¹ (~7.8%) error bar that applies when `HRmax` is *not* measured, the measurement that rejected the day's own peak as an anchor, and why WHOOP's three-tier model is still unimplemented.
- **The scoring window is the last 30 days that *have rows*, and a mean is not a baseline until the window held some.** `RecoveryScoring.baselineWindow(before:in:)` filters to the days strictly before the day and *then* takes the trailing `baselineWindowDays` (30) — slicing first takes the wrong thirty, and the input must be **oldest-first**, which is what the repositories return. **The `before:` comparison is made on the calendar day, and that is not a detail**: every row is keyed on `startOfDay`, but the two callers hand different kinds of anchor — `WhoopExportImporter` passes a snapped day key while `RecoveryViewModel.loadBaselines` passes the `Date` the screen is displaying, which is an instant and on every day this app runs is hours after midnight. Compared raw, that instant is later than the day's own midnight row, so the day fell inside its own baseline and the printed mean was taken over a different set of days than the score above it — measured on the simulator, 2026-08-17 printed an HRV baseline of 53 and a sleep-performance baseline of 80 where the strictly-before window gives 52 and 78. Both anchors are snapped inside the helper rather than at the call sites, so the contract holds for whatever a caller passes; every fixture in the suite used a snapped anchor, which is how it survived until a screenshot of a real day was read against the database. The two definitions are not nearly the same number: measured over the bundled export, 391 of 907 comparable days have a calendar-30 window that differs from the last-30-rows window, by up to **18.03 ms**, and the worst case reaches back **172 calendar days** to fill thirty rows. A reader must fetch `baselineWindowLookbackDays` (180) back or it silently prints a baseline built from fewer days than the score above it used. It lives here rather than in the importer because the Recovery detail screen prints the same baseline its ring was scored against. **`BaselineStatisticsMath.baseline` substitutes a cold-start constant on an empty window** (65 ms RMSSD, 40 ms SDNN, 54 bpm) — right for scoring a first day, wrong to print, since a screen showing `65 ms` as "your HRV baseline" would present a constant as a measurement. `RecoveryScoring.baselines(...)` therefore returns each mean *with the count it was taken over*, and `Baselines.displayed` withholds one below `minimumBaselineDays` (3). `score(_:)` is built on `baselines(...)`, so a screen that prints `displayed` cannot disagree with the ring above it.
- **`MetricChange` draws a comparison on the *formatted* pair, not the raw one, and its verdict is three states rather than two.** A resting heart rate of 52 against a mean of 52.4 is genuinely below it, but a row printing `52` over `52` renders as `52 ▼ 52` — a row contradicting itself. The digits on screen are the whole of the evidence a reader has, so the comparison is made on the **formatted** pair: two figures that print alike *are* the same as far as the screen is concerned. That case is `.same` — `direction` is `nil` and the glyph is `circle.fill`, because a figure sitting on its average has not moved and there is no direction to point. **The middle state is the whole reason the colour cannot be read off the direction**, and `nil` is now reserved for a *missing side* — a day with no measurement, a window with no baseline — rather than for "unchanged", which conflated two answers the screen renders differently. Direction and verdict are separate by construction: the triangle always points the way the number went, while `higherIsBetter` turns that direction into the verdict and the verdict alone picks the colour — `Theme.recoveryGreen` / `Theme.recoveryYellow` / `Theme.recoveryRed`, so an HRV rise is green while a resting-heart-rate rise is red from one call. The type is shared by Home's four metric panels, Home's two tiles, and the four breakdown rows, so a change here moves all three.
- **A week's baseline is a mean over measured slots, and HRV's is narrowed to one metric first.** `MetricWeek` computes four baselines from the same seven slots. Three are plain means over the slots carrying that figure, `nil` below `minimumBaselineDays` (3). HRV's is not: SDNN and RMSSD are different quantities on different scales, so it takes the **newest measured slot's metric**, averages only the days matching it, and can therefore come back `nil` in a week that has readings in it — which is the honest answer, not a baseline over a mixture. **`hrvBaselineMetric` and `hrvBaselineMs != nil` are two different conditions**, and picking the wrong one is silent: the metric names which quantity the week is *in* and is set as soon as one slot has a reading, while the mean additionally needs `minimumBaselineDays` days in it — so a two-day week is `hrvBaselineMetric == .rmssd` with `hrvBaselineMs == nil`. Anything selecting days to plot wants the metric; anything printing a mean wants the mean. `MetricDay.hrvMetric` is non-`nil` only when `hrvValueMs` is, so a slot can never name a quantity it has no reading in. VO₂ max joins the week through `MetricWeek.init`'s `maxHeartRate:` parameter instead — the one input that is not a per-day row, being the profile's assumed maximal heart rate, which is also what `CalculateStrainUseCase` builds its Karvonen zones from so the app has one definition of `HRmax` rather than two. The estimate itself is computed **inside** `makeDay` from that slot's already-gated `restingHeartRate`, which is the whole reason for the placement: the day's absence rule for a resting rate is applied once, and the VO₂ field inherits it. A caller assembling the estimate itself would have to restate the `hasMeasurement && > 0` gate, and an unmeasured row carrying a plausible `55` bpm — which is constructible, since `hasMeasurement` is `hrvValueMs > 0` — would then produce a confident estimate on a day this app calls unmeasured. **A `MetricWeek` built from one history is not a week with the other two unmeasured.** `MetricWeek.init`'s three history parameters all default to `[]`, so a caller that passes only `recovery:` gets `nil` for `strain` and `sleepNeedSeconds` on every slot — and on this type `nil` is the documented word for *nothing was measured*. `RecoveryViewModel.week` is that build one history short (the Recovery page draws five charts and the five read two histories between them: the recovery-performance bars and all three lines come out of `recovery`, since HRV, resting rate and respiratory rate are all columns on a `recoveries` row, and the sleep-performance bars need a `sleeps` row, which no column of a `recoveries` row carries), so its `strain` is "not asked for" and **a strain-plotted view handed that week would report every day of it as unmeasured**. The narrowing is per-caller, so it is carried in that property's doc comment rather than here; the fix if a view ever needs a second series is to pass the second history, not to read through the `nil`.
- **Stress Monitor is a calibration, not a recovery of WHOOP's function.** WHOOP publishes the model's shape (HRV + heart rate + motion, a 14-day personal baseline, a 0–3 scale banded 1.0/2.0) and none of its constants, so every threshold in `StressMath` is this app's own and **this app's number will not agree with the WHOOP app's** — the same bargain `SleepNeedMath` documents. Two things about it will otherwise read as bugs: `minimumRRIntervals` is **load-bearing**, because `HeartRateVariabilityMath.calculateRMSSD` returns `0.0` on insufficient data and a zero RMSSD scores as *maximum* stress; and the tile renders `—` far more often than a number, because samples exist only for days the app was running with the strap connected and the export carries no R-R series at all. The full model is in `ALGORITHMS.md` §5.
- **The Stress Monitor chart follows three rules that are not styling choices.** The y-axis is **fixed at 0–3** and never auto-scaled (auto-scaling draws a calm day and a wired day as the same picture); a gap longer than `windowSeconds × 1.5` **breaks the line** rather than interpolating, because an ineligible window is unmeasured and joining across it draws a reading nobody took; and **no windows means no chart at all** — not an empty frame, not a zero line, since a flat line at zero is the strongest possible claim of calm. The fill's gradient stops come from `StressMath.lowMediumBandEdge`/`.mediumHighBandEdge` divided by the scale, so it must not type `1.0`/`2.0` itself. The fill is a `Shape` and not a `Path` built in the view: `path(in:)` receives the frame, so the stops land on the score scale — a `Path` in a `ZStack` is graded over its own bounding box and the band colours move with the data.
- **Home's collapsing rings header is a `PreferenceKey`, and it writes no `@State`.** iOS 17 has **no scroll-geometry API** — `onScrollGeometryChange` is iOS 18 and the deployment target is 17.0 — so the mechanism is `GeometryReader` → `RingsBottomKey` (the rings row's `maxY` in a named coordinate space) → `.overlayPreferenceValue`. Four things about it are load-bearing: `PreferenceKey.defaultValue` must be `static let`, not `static var` (a mutable static is a Swift 6 concurrency error), and its value is deliberately out of any real range so an unpublished frame resolves to *hidden*; the preference reports where the rings **are**, not a scroll offset, so there is no threshold constant to go stale when the top bar changes height; the transform must not write `@State`, because it runs on every scroll frame and a state write per frame invalidates the whole screen; and the `VStack` must **not** become a `LazyVStack` — a lazy stack may release the rings row once it is scrolled past, taking the preference publisher with it and hiding the header permanently. Home's content is currently **shorter than its viewport on every day this app can show** (an empty day is ~576pt against ~741pt of scroll space, and an imported day adds only a sleep row), so the page does not scroll and the header is latent (verified once by forcing overflow with a temporary bottom padding, since reverted). Do not conclude from a screenshot that it is broken; conclude that Home needs more content before it is reachable.
- **A failing migration crashes the app at launch.** `LocalDatabaseManager.init` calls `fatalError` on a migration error. Test a migration against the real dev database before trusting it; the reset is `rm ~/Library/Application\ Support/whoopsy.sqlite`. **`LocalDatabaseManager` has no path-injecting initialiser** — `init(inMemory:)` or the `~/Library/Application Support` default are the only two — and on macOS `FileManager.url(for: .applicationSupportDirectory,…)` does **not** follow a `HOME` override, so a host-side tool that writes through it lands in the developer's own dev database however the process is launched. The simulator app is unaffected (its container is separate); a host tool that must not touch the dev database has to be given one by *temporarily moving that file aside*, not by re-pointing `HOME`.
- **Day-keyed writes must be snapped to `date.startOfDay`.** `recoveries`, `sleeps` and `strains` are read back with `startOfDay` as the lookup key, and GRDB's `save` is INSERT-or-UPDATE *by primary key* — so a row written at a raw timestamp is inserted, never updated, and no keyed read can find it. `LocalDatabaseManager`'s `saveRecovery`/`saveSleep`/`saveStrain` snap centrally for this reason; keep new writers going through them.
- **A day-keyed screen must READ.** Send day selection to the repositories (`getRecovery(for:)`, `getStrain(for:)`, `getSleepSession(for:)`), which is what `RecoveryViewModel`/`SleepViewModel`/`StrainViewModel`'s `load(for:)` do; they fall through to a calculate use case only for a day that **is today and holds no measurement**. `HomeViewModel.load(for:)` is the reference implementation. The read is the point: a stored day has no raw samples to recompute from (an imported day has none by construction), so a recompute would come back as *no row at all* and blank the day the user was looking at. `RecoveryViewModel.shouldCompute` is the gate, and it tests the measurement rather than `nil` so that a placeholder row left by an older build stays a legitimate candidate to fill.
- **`getXHistory(days:)` windows back from `Date()` unless you pass `endingOn:`.** The three metric screens show a day the user picked, so they call `getRecoveryHistory(days:endingOn:)` and its siblings. Those reads bound the window at **both** ends (`>= cutoff` and `<= endingOn.endOfDay`); the upper bound was added with `endingOn`, because a window anchored on an old day would otherwise run on to the present. Pulling the whole imported range in a test is still `days: 4000`.
- **The calendar's day colours are a map, and a day absent from it means no measurement.** `HomeViewModel.monthTiers` is keyed by `startOfDay` and built by gating each row on `hasMeasurement` — never on the row existing. A legacy placeholder holds `score: 0` and reports `.red`, so a map keyed on existence would paint an unworn night a hard red, which is the same fabrication the dash convention exists to prevent, drawn in a cell instead of a ring. Two consequences worth keeping: a day *missing* from the map is drawn grey and is still **selectable** (Home legitimately opens on an empty today, so most of a fresh install has to stay reachable), and the loading test is `isLoadingMonth`, never `monthTiers.isEmpty` — a month the export never covered is empty and finished, and testing emptiness would spin forever on it.
- **The month read's window is `days: <the span between the month's own bounds>, endingOn: <the month's last day>`.** Because the window is inclusive at both ends and runs from `endingOn - days`, that pair covers exactly the month. Neither of the obvious alternatives does: `days: 30` reaches back into the previous month on a 31-day one, and `days: dayCount` pulls in the 1st of the next — either would put a neighbouring month's row in `monthTiers`, where the grid is free to tint a day nothing measured. An assertion on one month cannot see this, which is why §14's version puts a row on each side.

This is the second member of the family that also holds `#if canImport(HealthKit)` being true on the host: **a green iOS build is not a green host build, and vice versa** — run both.

That caption has since been removed with the row it explained, so **there is no live instance of the mistake left to look at** and the rule now stands on its own: write emphasis as its own `Text`, an `AttributedString`, or `Text(LocalizedStringKey(…))`; never as `**…**` inside a string built with `+`.

- **SDNN and RMSSD are different quantities and never share a baseline.** Every `recovery` row carries `hrvMetric`; `RecoveryScoring` is the only place that filters history by it. Mixing them computes a z-score between two distributions and silently mis-scores every day.
- **The export's day key is `startOfDay(Wake onset)`, and that is the app's own convention.** `CalculateRecoveryUseCase` writes `date.startOfDay` and reads the sleep session *for that same date*, so a recovery row for day D comes from the night that ended on D's morning. The export's `physiological_cycles.csv` is one row per cycle, and keying those on `Cycle start` would collapse 935 rows onto 753 days — silently dropping a fifth of the history. `WhoopExportImporter` keys on the wake onset for every row that has one. Verified against the real file: 910 wake rows → 910 distinct days, zero collisions, and 933 `Day Strain` values → 931 distinct days.

- **24 export cycles have a `Day Strain` but no wake onset.** They are fragments that never closed, so they become `strains`-only rows. Two of them start at 23:30 and 23:48 on a day a closed cycle already claims (2024-02-11, 2024-03-20), and their day is genuinely unknowable — so the closed cycle takes the day and the fragment defers. That is why 933 `Day Strain` values produce 931 `strains` rows, and it depends on the device zone: a fragment near midnight lands on a different date in a different zone. `Tests/WhoopsyTestRunner` §11 recomputes the expected key set rather than hardcoding it. The three day-level counts in `WhoopImportSummary` (`daysWritten`, `strainOnlyDays`, `duplicateExportRows`) are accumulated from those key sets as the walk goes, because they cannot be recovered from the per-table row totals: on this export the arithmetic shortcut for strain-only days gives 21 where the truth is 22, since one scored day carries no strain. `duplicateExportRows` exists because a skipped row has two possible causes that look identical — a day that already held data *before* the import ran, and a day an *earlier row of the same import* claimed. Only the first is `daysAlreadyRecorded`; counting the collision rows there made a fresh install report "2 already recorded locally" when nothing was.

Three things about it are decisions, not oversights, each with its basis in `ALGORITHMS.md` §4: the coefficient is **fitted to the bundled export** (WHOOP publishes this model's shape and none of its constants — 6.40 is the pinned-intercept least-squares slope over the 909 nights carrying a preceding strain day, and the cross-validation curve is flat from 6.4 to 7.0, so the reproducible fit is shipped over the marginally luckier one), a **`nil` strain returns the baseline exactly** rather than a plausible strain, and the **accumulated Sleep Debt term WHOOP names is deliberately absent** — a judgement, not a measurement: a fitted 7-night deficit buys 0.35 of a point (3.77 → 3.41) for a second fitted constant and seven nights of history, and WHOOP's own `Sleep debt (min)` column does no better (3.43), so there is no hidden headroom. What *was* measured as harmful is the old documented `0.20` carryover: written out, it scores 18.44 against the flat 480's 10.06. - **The sleep detail screen's card is titled `HOURS OF SLEEP`, and that title is a figure the card prints rather than a label on the chart beneath it.** The reference's card carries the night's asleep total with the window's mean under it and draws the heart-rate trace *inside* the same card, so the screen's headline quantity is sleep and the trace is the recording sitting below it. The headline is `SleepStageRangeScoring.Summary.asleepSeconds` (`SleepSession.totalTimeAsleepSeconds`, the three sleep stages) read through `MetricChange` against `typicalAsleepSeconds`, the window's mean of it; the card prints `DURATION` further down, and the two are related by an identity a reader can check on the screen itself — **`asleep + awake = DURATION`**, the awake term being the fourth row. That identity is why the headline is the entity's own property and not a subtraction written on the view, and §15 of the suite asserts it. **The headline and the chart are gated apart, deliberately**: the figure is a *reading*, present on every imported night, while the trace is a *recording* that needs `biometric_samples` rows — so gating the figure on the chart would hide a real reading behind an absent one, which is the fabrication every absence rule in this app exists to prevent. Below the headline, `SleepTypicalRangeCard` draws the night's four stages as a share of the sleep period over a hatched remainder, with the band that share is normally in drawn as **one filled region with a dashed rule down each of its sides** — built by `SleepStageRangeScoring`, drawn by `TypicalRangeBar`, and the rules stroked by `BandEdges`, which traces two vertical lines and no closing segment. A region bounded by two rules rather than two marks because two lines say where a band's edges are while a region says the two edges bound *one span*, which is what a range is; the card's header carries a glyph of the same mark as its key to it. **The bar's own styling is measured off the reference rather than picked, and every constant that was wrong was wrong in a way a reader would report as "the bars don't match".** Three were. The hatch was **inverted**: `Theme.hatchStripe` was white over the track, which draws a shimmering dark band where the reference has a quiet light one — its track reads `(60,64,68)` and its stripes `(39,43,47)`, so the hatch is a *dark* texture on a light ground, and `Color.black.opacity(0.30)` over `ringTrack` reproduces the reference's stripe to within a unit. Its period and stripe width were a third of the reference's — `5` pt and `1` pt against `10.9` pt and `3.85` pt, quoted as the horizontal run a 45° stripe makes across the scan because that is the axis `HatchShape` walks, and the pair is a **1:1 duty cycle**. And the ends were **capsules** where the reference draws a small corner and a **square share**: a capsule's radius is half the bar's height (`9.8` pt at the default `20`), so the share's trailing edge was a semicircle bulging into the middle of the bar and the track's corners were over twice as round as the reference's. The share is now a plain rectangle clipped to the track's shape, which is what makes its leading end round and its trailing end flat in one move. **The corner radius was solved for rather than read off**, because an anti-aliased corner's last pixel or two fall below any threshold and its visible extent is therefore not its radius: the reference's profile (`3.42`, `1.71`, `0.85` pt of inset at `0`, `0.85`, `1.71` pt below the bar's top) was matched against this app's own render at a radius the file names, and the two agree at `4.5` pt. **Measure this bar on the share's leading edge** — the one edge with nothing hatched over it. The same scan across the remainder is confounded by the stripes, and in the reference the card background and its hatch stripe differ by one unit of luminance, so no threshold separates them; that image is also a 2× upscale of a ~1.17 px/pt source, so its rows quantise in pairs and one source pixel is `0.85` pt, which is the floor on every number above. **WHOOP publishes no stage boundaries**, so the window and the percentile are this app's own; only two halves are reused rather than invented, `RecoveryScoring.baselineWindowDays` and `.minimumBaselineDays`, so this card and the Recovery screen cannot come to disagree about how much history a baseline needs. **The band is in percentage points of the night, not in the minutes WHOOP quotes its own REM middle-50% in** — the bar's track is a 0–100% scale, so a band in minutes could not be drawn on it. `WholePercents` is largest-remainder because the card prints `DURATION` above the column those percentages divide, and the export stores whole minutes, so naive rounding produces a column summing to 101. The card is **absent, not empty**, on a night with no sleep period — four `0%` rows would be a picture of a night — but a *thin window* is a different state and is drawn: shares and durations are readings the night really has, so only the bands are withheld. **The heart-rate chart itself is built, and it reads a real table** — `HoursOfSleepChartSeries` off `biometric_samples` over the night's own window, drawn by `HoursOfSleepChartView`, with a gap longer than `HoursOfSleepChartSeries.maximumGapSeconds` (300 s) breaking the line rather than interpolating across it, and a sample whose `heartRate` is `0` refused as a point rather than plotted at the axis foot. **Those types are named for the card and not for the quantity, and the quantity was not renamed with them** — the series and its axis are `HoursOfSleepChart*` because they are drawn inside the `HOURS OF SLEEP` card and nowhere else, while their points stay `Point.bpm` and their labels stay `30/50/70/90`, because a `bpm` payload under a name that says hours is a name that lies about a quantity. Reaching for either half alone re-creates the mistake: `SleepHeartRateSeries` read at the call site said the card was *about* heart rate, and `Point.hours` would say a bpm is an hour. It is not a tachogram: one point per *notification*, not per beat, which is why `BiometricSample.timestamp`'s arrival-instant caveat does not bite here. The axis is **fixed at 30–110 bpm with its own gridlines** and widens in steps only to include a reading outside it, on `StressMonitorChartView`'s rule that an auto-scaled chart draws two different nights as the same picture. What is unchanged is that **no strap has ever filled that table**: `biometric_samples` holds 0 rows in every database on this machine, and the export carries no HR series at all (only a per-cycle daily average), so all 910 imported nights have none permanently and every one of them draws the chart's `No Data` state. That state sits in the chart's slot and speaks for the chart alone, because the headline above it is a real reading; a hypnogram is not a substitute for it either: `v12` now stores one for a strap night, but the export produces none (it reports stage totals and no timeline), so no night this app can show has stages to draw. So the chart is gated on strap sync, not on an algorithm, and `No Data` on an imported night is the correct output rather than a bug. **What makes it absent today is that no strap has ever been connected, not that the strap cannot produce one.** The live `0x2A37` path is implemented end to end (`WhoopBLEManager` → `BiometricSample` → `StreamBiometricsUseCase`) and yields instantaneous HR at each beat from `60000 / rr`, needing no sampling rate. - **A mark positioned by `.offset` inside an `overlay` must sit in an explicit `ZStack(alignment: .leading)` with an explicit full-width frame — a bare `ForEach` there is centred in a box sized to its widest sibling.** `.overlay(alignment: .leading) { ForEach { … .offset(x:) } }` lays the group out at the lane's leading edge but centres each mark *within* a box as wide as the widest one, so every narrower mark starts `(widest − thisOne) / 2` to the right of where its own offset puts it. WHOOP's word is a claim about what the user *should* do and this app cannot make it — the same judgement that labels Home's VO₂ figure `(EST.)`. Renaming the label to match the mockup would put a claim on the screen that no code makes.
- **`sleeps.respiratory_rate` and `sleeps.sleep_debt` are two-producer columns, and the model that computes one of the producers is unvalidatable.** Both are stored verbatim from the export for an imported night and computed for a strap night — `RespiratoryRateMath` and `SleepDebtMath` respectively, called from `AnalyzeSleepUseCase` and stored, not resolved on read. **Nothing but `source` distinguishes them**, exactly as `sleeps.sleep_consistency` already documents, and `nil` is the only marker for "not scored" — so a model must never be run over an imported row, and the suite re-imports the export and asserts all 910 nights still carry WHOOP's own pair. **The two producers' debts are not the same quantity, and only one of them is a term of the need printed above it.** WHOOP's need is a total that contains `need_from_sleep_debt` (the fit over the export recovers the debt at coefficient 0.98); `SleepNeedMath`'s deliberately omits any debt term (`ALGORITHMS.md` §4). The rule is one sentence: **a writer may persist a row only when it produced a measurement, and the test it uses must be the same test its readers use.** `RecoveryMetric.hasMeasurement` is `hrvValueMs > 0`, so the guard has to be that comparison made against the value *as it will be stored* — `CalculateRecoveryUseCase` rounds to one decimal **before** guarding, because an RMSSD below 0.05 ms passes on the raw value and is still written as `0.0`. Guarding on the interval count instead is a different test: `HeartRateVariabilityMath.calculateRMSSD` returns exactly `0.0` when `filterRRIntervals` leaves fewer than two beats, so one surviving interval used to write a `0.0` ms row that the type's own readers called unmeasured. On the reading side, `RecoveryScoring` filters placeholders out of every baseline, `HealthKitImporter` fills a day whose row is unmeasured instead of skipping it, and `RecoveryDashboardView`, `StrainDashboardView` and the Home rings render one as `—` rather than a red 0% or a confident `0.0`. A day with no *sleep* session contributes `BaselineStatisticsMath.sleepPerformancePivot` (0.70) to an otherwise-measured day — the value that shifts the score by zero. **`RecoveryMetric.hasMeasurement` and `StrainScore.hasMeasurement` are now reader tolerance, not a marker any writer sets**: rows written before this rule are still on disk holding zeros, and the gates are what keep them off the screens, the baselines and the charts. `StrainScore.hasMeasurement` is a **required** initialiser parameter with no default, deliberately: a default of `true` would let a construction site silently mark a placeholder measured, which is the exact bug the flag exists to prevent.
- **Absence is the same shape in all four metrics now, and that is the point.** Recovery, Strain, Sleep and Stress all report a day with no measurement as **no row**, with the optional as the answer. A reserved zero row is the weaker design — every reader has to remember to exclude it, and two did not (the export importer skipped a day whose strain row merely existed, so WHOOP's real `Day Strain` for it was never imported; `StrainViewModel` treated one as settled and never recomputed). An absent row cannot be mistaken for data by a reader that forgot the rule. Do not reintroduce a placeholder to make a keyed table "tell nothing from zero" — that is what the optional is for.
- **Sleep has no placeholder: an unclassifiable night is an absent row.** `AnalyzeSleepUseCase.execute(for:)` returns `SleepSession?` and returns `nil` — writing nothing — when the overnight window holds fewer than `minimumEpochSamples` (30). It previously built an eight-hour night out of literals and saved it, so a strap left on the charger was stored and scored as a full night's sleep; rows of exactly `4.2/1.8/1.6/0.4` hours in `sleeps` are that artefact. Every reader therefore takes an optional: `SleepDashboardView` and the Home ring render `—`, and `SleepViewModel.session` is `SleepSession?`. Recovery needs no special case — its sleep term falls back to the pivot above, which is a defined constant.
- **A channel the strap has no sensor for is `nil`, not a plausible constant.** `SleepSession.disturbanceCount` and `.respiratoryRate` are optional and `sleeps` stores both as nullable, and a disturbance count exists only for a night the classifier could read. A defaulted `respiratoryRate: 14.0` on every row a repository reads back, and a literal `14.4` written by `AnalyzeSleepUseCase`, are both fabrications this repo has shipped. When adding a field to a domain entity, ask which path actually produces it; a defaulted number on a stored row is a fabricated reading. (The strap does have a *derived* respiratory rate since `RespiratoryRateMath` — see the gotcha below — but it is derived from the R-R series, not read off a sensor, and it is `nil` for every night that series cannot support.) **`MetricDay.respiratoryRate` and `MetricDay.sleepPerformance` are the two fields in `MetricWeek.makeDay` passed through with no gate**, and the missing gate is the design rather than an omission to tidy: every other field there tests `hasMeasurement` (and RHR also `> 0`) because its column has a reserved zero, while respiratory rate is optional on the row *and* on the slot — so the optional already is the whole rule — and sleep performance is computed on read off a classified night, so there is no column and no zero to reserve. Adding either gate would let a week chart omit a mark the row directly above it prints — the same value, read through `RecoveryMetric` for respiratory rate and through `SleepSession.sleepPerformancePercentage` for sleep performance, both without a gate. The two are excluded from `hasAnyMeasurement` for opposite reasons: the sleep-performance exclusion is **redundant** (a day with a performance necessarily has a need, which is already in the list, the same as the VO₂ estimate), while the respiratory-rate one is **load-bearing** — a night can carry a respiratory rate with no HRV, so it is the field that could make an otherwise-empty day count as measured on a chart that draws neither quantity. Sleep performance's own fabrication risk is `SleepSession.sleepPerformancePercentage`'s `guard targetSleepNeedSeconds > 0 else { return 100 }`: unreachable on stored nights, because every imported row carrying a wake onset carries a need and the strap path computes one, but pinned by an assertion rather than left as a claim.
- `Package.swift` points the executable target at `path: "app"`, but the directory on disk is `App/`. These are the same directory on macOS's case-insensitive filesystem; be consistent with existing paths when adding files.

### Reference docs

Keep these in sync with the code — they are the spec for the non-obvious math and wire format:

- `ALGORITHMS.md` — RMSSD/SDNN and the never-mix rule, ectopic-beat rejection, the Borg-scale exponential Strain model (0–21) with HRR zone weights and `k ≈ 0.000045`, why HealthKit cannot feed Strain, the Recovery z-score formula with its guards and green/yellow/red tiers, sleep staging, and the Sleep Need model with the fitted strain coefficient and the three WHOOP inputs it deliberately omits. Implemented in `Core/Math/` and `Domain/UseCases/RecoveryScoring.swift`.
- `BLE_PROTOCOL.md` — the wire format for all three straps (4.0, 5.0, 5.0 MG), which do **not** share
  one: two envelopes, two header CRCs (CRC8 / CRC16-Modbus), and two non-overlapping packet-type
  numberings. Carries the GATT UUIDs, the historical flash-drain protocol including the record header
  that holds a real unix timestamp, the two heart-rate producers, and a tag on every claim saying
  whether it came from an open-source reference or from this codebase. **Nothing in it is captured on
  this project's own hardware.** It is a spec rather than a changelog, so where it and `Data/BLE/`
  stand in relation to each other is carried by its two implementation-status tables — §3's for the
  handshake and the transmitted opcode set, §4's for the drain — and not by the framing sections.
  Read both before touching the sync path. Its §2.1 carries the four published checksum vectors,
  which the suite now asserts in place; the 4.0 envelope in `Data/BLE/` matches §2, and the 5.0/MG
  envelope is **not implemented** and is refused rather than approximated.
- `PATENTS.md` — what WHOOP's filings actually disclose about the mathematics behind Recovery, Strain,
  Sleep, Stress and VO₂ max, tagged `[claimed]` / `[described]` / `[not disclosed]` / `[pending]` /
  `[app]`, because **a claimed range is not an implemented constant**. Its organising finding: for most
  metrics WHOOP publishes the shape *and anchors it to an input this app cannot measure* — the user's
  anaerobic and creatine-phosphate thresholds for Strain, the end of the last slow-wave episode for
  recovery HRV, a trained classifier for staging — so the app's substitutes are forced rather than
  lazy. It is also where the Recovery tier boundaries (WHOOP's 66/33) and the undisclosed sleep-need
  sigmoid are recorded. **It is a record, not a changelog** — §8 lists what it argues should change and
  none of it has been applied. Read it before claiming any constant in `ALGORITHMS.md` is WHOOP's.
- `ARCHITECTURE.md` — layer philosophy, folder layout, and the data-flow diagram covering both the strap and HealthKit inputs.
- `TODO.md` — one line per column of each bundled CSV: whether a named symbol consumes it, where it goes, and what the rest would take. Measured, and re-measured by `csv-field-coverage`. It is not a wish list — the uncovered lines carry the reason they are uncovered, and three of them (`Recovery score %`, `Sleep performance %`, `Sleep debt (min)`) are **decisions not to cover**, which is why the file says so in bold rather than leaving them to look like oversights.

Four skills under `.claude/skills/` route work that is easy to get wrong:

- **`architecture-doc-sync`** — when you change anything under `Sources/Whoopsy/`, it routes the
  change to the docs that must move with it.
- **`ui-regression-guard`** — when you add a screen, a UI component, or a new value to an existing
  view, or change anything shared (`GaugeRingView`, `MetricRingView`, `DayNavigationBar`, `Theme`).
  It carries the regression classes this app has actually hit — fabricated values, overwritten
  day-keyed history, unsnapped writes, frozen migrations, moved shared components — and the checks
  that catch them, including the ways a green build or a screenshot can lie.
- **`ui-data-provenance`** — before building any view that shows a number, chart, ring or tile, and
  whenever a mockup implies a figure this app should display. It establishes from the measured data
  whether that figure has a producer at all — the export carries no R-R series, no step counts, and
  ends 2026-08-22 — and lists the fabrication classes this repo has shipped, including a domain
  field that is scored but never persisted and is rendered as "At baseline" rather than a dash.
- **`csv-field-coverage`** — when an export column gains or loses a consumer: a field added to
  `WhoopExportRow`, a column on a record, a new model, a screen reading an imported value, or a CSV
  bundled or unbundled. It owns `TODO.md` and carries the command that re-measures it. Its one hard
  rule is that **a parsed column is not a covered column** — `asleepMinutes` and `inBedMinutes` sit
  on every imported row and are read by nothing.
