# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Whoopsy** — a 100% offline, subscription-free iOS companion app for WHOOP 4.0/5.0 straps. Reads biometrics over BLE, decodes a reverse-engineered packet protocol, stores everything locally, and computes Recovery/Strain/Sleep metrics on-device.

Written in Swift 6 with strict concurrency (`async`/`await`, `AsyncStream`, `Sendable`), structured as Clean Architecture + DDD. Single dependency: GRDB.swift (SQLite).

## Commands

```bash
swift build                      # builds WhoopsyCore library + WhoopsyApp executable (host/macOS)
swift build 2>&1 | grep warning  # build emits known resource warnings — see Gotchas
xed Whoopsy.xcodeproj            # the real iOS build path (iOS 17+, target WhoopsyApp, bundle org.whoopsy.app)
```

`swift build` is the fast edit/compile loop. The iOS app itself is built from `Whoopsy.xcodeproj`, which consumes the `WhoopsyCore` package product. There is no linter configured.

### Building for iOS

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  xcodebuild -project Whoopsy.xcodeproj -scheme WhoopsyApp \
  -destination 'generic/platform=iOS' build
```

Two things to know. **`xcode-select` points at CommandLineTools**, so bare `xcodebuild` errors out and `xcrun --sdk iphoneos` cannot find the SDK; the `DEVELOPER_DIR` prefix above sidesteps that without a `sudo xcode-select -s`. And the legacy `-target` form **cannot resolve SwiftPM dependencies** (it fails with `Unable to resolve module dependency: 'GRDB'`), so use `-scheme` — `WhoopsyApp.xcscheme` is checked in under `xcshareddata` precisely because Xcode only auto-generates schemes when the GUI opens the project.

Signing is not yet functional: `DEVELOPMENT_TEAM` is empty in both configurations and there is no certificate (`security find-identity -v -p codesigning` → 0). `App/iOS/Whoopsy.entitlements` (`com.apple.developer.healthkit`) is wired up via `CODE_SIGN_ENTITLEMENTS` on both configs, and Xcode now rejects the target with *"has entitlements that require signing with a development certificate"* — which is the expected state until a team is set. Adding `CODE_SIGNING_ALLOWED=NO` builds everything up to signing, which is how to check iOS compilation without a team. Note the entitlement requires the HealthKit capability enabled on the App ID server-side; a free Personal Team is very unlikely to support it.

### Tests

```bash
swift test                       # FAILS: "no tests found" — Package.swift declares no test target
./scripts/run_tests.sh           # FAILS at the link step — see below
```

The real suite is `Tests/WhoopsyTestRunner/main.swift` (a hand-rolled assert runner, not XCTest). To build and run it against a clean build:

```bash
swift build --scratch-path /tmp/whoopsy-verify
swiftc -I /tmp/whoopsy-verify/arm64-apple-macosx/debug/Modules \
  -Xcc -fmodule-map-file=.build/checkouts/GRDB.swift/Sources/CSQLite/module.modulemap \
  /tmp/whoopsy-verify/arm64-apple-macosx/debug/Whoopsy.build/*.o \
  /tmp/whoopsy-verify/arm64-apple-macosx/debug/GRDB.build/*.o \
  Tests/WhoopsyTestRunner/main.swift -o /tmp/whoopsy-verify/WhoopsyTestRunner
/tmp/whoopsy-verify/WhoopsyTestRunner
```

Why the scratch path: `scripts/run_tests.sh` globs `.build/.../Whoopsy.build/*.o`, which includes stale object files left behind by since-deleted sources (`MainTabView`, `SettingsView`, `TodayDashboardView`, `SwiftData*Repository`, …), so the link fails with `symbol(s) not found`. It also omits the `-fmodule-map-file` flag and dies earlier with `missing required module 'CSQLite'`.

There is no way to run a single test — the runner is a linear `main.swift`. Trim it or comment out sections for focused runs.

The runner has 14 sections and all 14 now execute. Keep it that way: an uncaught throw inside its `Task` does **not** print a failure — the process idles out the `RunLoop` and exits **0**, so exit code is not a reliable pass signal. Check the section headers (they are numbered `[n/14]`) and the `✅ ALL WHOOPSY TESTS PASSED` banner. All new sections go inside the existing single `Task` in that order; adding one means renumbering every header.

It prints **451** `✓` lines as of `MetricChange`'s three-state verdict, the instant-anchor `baselineWindow` guard, the recovery-detail sleep-performance week chart, the `WeekBarSeries` palette/gridline assertions and the two bar initialisers' independent absences, the `WeekLineSeries` gap assertions, and the per-quantity `valueDecimals` rule. There is no test discovery, so a section that stops running looks exactly like one that passed — record the count before you edit and treat a drop as a deleted guarantee.

§11 drives the real WHOOP export. It locates the CSV from `#filePath` rather than the working directory, and it derives its expected day keys from the parsed rows instead of hardcoding counts — the device time zone decides `startOfDay`, and two 23:30 fragments sit on a date boundary. Prefer that shape for new assertions here: a hardcoded count that only holds in one zone is a test that fails on someone else's machine.

§12 is the day-selection guard. It imports the export into its own in-memory database, then drives the real `RecoveryViewModel`/`StrainViewModel`/`SleepViewModel` `load(for:)` over an imported day and asserts every row comes back byte-identical — score, HRV, and `source` — with the use cases built on `EmptyBiometricStore`, which is the true shape of an imported day. That is the assertion that fails if anyone re-wires a calculate use case into the day-selection path. Its window assertions move the `endingOn:` anchor rather than comparing against `Date()`, so they hold on whatever day the suite runs — keep that shape.

§13 is the Sleep Need guard, and it is the only section whose fixture strap recorded a night: `OvernightBiometricStore` returns real samples where `EmptyBiometricStore` returns `[]`, because a need is only computed for a night the classifier could read. It pins the fitted coefficient with its fit basis in the assertion message, drives the real `AnalyzeSleepUseCase` against a strain row on the previous day, and — the part that matters — re-imports the export and asserts all 910 imported nights still carry WHOOP's own need. Do not assert the imported night *count* there: §11 owns the day keys. Assert the properties instead (whole minutes; 53 nights below the 8-hour baseline, which the formula cannot produce), because a hardcoded count that holds in one device time zone is a test that fails on someone else's machine.

§14 is the Home screen's sources, and it is the only section that touches all four of them. It asserts the `v6` tables exist and that a `WorkoutSession` round-trips through `GRDBWorkoutRepository` with its route and splits — including that a session saved at a raw 17:33 is found on its own day and **not** on a neighbouring one, which is the day-snap rule this suite exists to guard. It drives the steps path through `FixtureHealthStore` → `HealthKitBridge` and asserts a day with no samples is `nil` rather than `0`. `DaytimeBiometricStore` is the fixture strap for the stress model — `OvernightBiometricStore`'s counterpart for daytime samples, and needed for the same reason: `AnalyzeStressUseCase` returns `nil` the moment its store is empty, so only a store that holds samples can prove the measured path. One block asserts that a day with nothing stored yields `nil` from every one of `HomeViewModel`'s sources, which is what the screen's dashes follow from — and the block after it is that one's counterpart, because **the dashes are the only thing this suite used to prove**: a fresh install has no strap data, so the first day Home can show a number for is an *imported* one, and nothing asserted Home populates from it at all. It imports the real export into its own in-memory database, loads Home with the most recent day that carries a recovery **and** a night **and** a strain (not simply the last day of any one of them — the export's tail has a night with no strain, and demanding all three from one arbitrary day asserts a fact about the file rather than about Home), and asserts the rings and the RESTORATIVE SLEEP tile populate while STEPS and STRESS MONITOR stay dashes, since the export carries neither step counts nor an R-R series. That gap is what a user reporting "data isn't populating" was actually seeing.

The section's last block is the seven-day `MetricWeek` join behind the Strain & Recovery chart and the four metric panels, and it is where the **alignment invariant** is pinned: seven slots oldest-first ending on the anchor, a day with no rows as an *empty slot* rather than a missing one, and the baselines as the mean of the measured slots only — `nil` at two measured days and non-`nil` at three, asserted at both edges of `minimumBaselineDays`. Two assertions there are the ones that fail if anyone plots a legacy placeholder as a reading: a `recoveries` row with `hasMeasurement == false` yields a `nil` `recoveryScore` slot, and the same for `strains` — plus the same row yielding no HRV *and no metric*, so the pair can never disagree. The HRV baseline's **never-mix** narrowing is asserted on a week built so the two answers differ: three RMSSD days and two SDNN days, where the SDNN days are lower, so an unfiltered mean (56.4) and the correct one (63.33) are distinguishable — and again in the other direction, where the newest metric is the minority and the answer is still its own mean, not a blend. The VO₂ MAX block is the **estimate**, not a read-through, and its guards are the ones that keep a derivation from becoming a fabrication: the arithmetic pinned to a literal (`15.3 × 190/50` at 58.14, compared with a tolerance, so a changed constant fails rather than agreeing with itself), the two `0`-anchor cases (`?? 0` writes both columns, so a `0` resting rate and a `0` maximal rate must each be an absence rather than a division), and a `nil` anchor on either side. The discriminating one is in the week: a fixture day holding `hrvValueMs: 0` beside a **plausible `55` bpm** yields no estimate, because the estimate reads the slot's gated value and not the raw row. That case is what a mutation test confirmed — pointing `makeDay` at `recovery?.restingHeartRate` passes a `0` straight to the model, whose own `> 0` guard catches *that* but not a real-looking rate, and the assertion fails. `hasAnyMeasurement` still excludes VO₂ max, though that exclusion is now provably redundant (an estimate requires a non-`nil` resting rate, already in the list) rather than load-bearing as it was when the value could arrive from HealthKit on a day with no stored row at all. The block also drives `CalculateStrainUseCase` against `EmptyBiometricStore` and asserts it returns `nil` **and writes no row** — the contract that replaced the reserved-zero placeholder. The placeholder shape itself is no longer produced by any writer, so it is covered by constructing one directly through `GRDBStrainRepository` and asserting it reads back unmeasured while a `0.1` row reads back measured. That is measured, not assumed: three assertions over the imported export assert all 931 strain rows read back measured, that every one carries a heart rate, and that the 2 days WHOOP itself scored exactly `0.0` are among them — the pair that keeps the `v7` backfill's predicate honest, since a backfill keyed on the score alone would have marked those two as absences. **What it cannot cover is the `v7` backfill `UPDATE` itself** — the migrator runs it before any row can exist — so the suite tests the write/read path instead and does not claim the backfill is covered.

The Stress Monitor block is also where the day's **series** is asserted, not just its aggregate. `StressDay` computes its `StressScore` from the windows it was handed rather than accepting one, so `windows.count == score.windowCount` is structural; the assertions pin that, that the windows are sorted and inside `StressMath.wakingWindow`, that the average really is their mean, and — the one that matters most — that `executeDay(for:)` and `execute(for:)` return the same figure, since `execute` is a forwarder rather than a second implementation. The **anti-flat-line** pair is there too: a day with no eligible window returns `nil` from both entry points, because a `StressDay` with an empty series would draw a flat line at zero, which is the strongest possible claim of calm. What none of this proves is the chart's *drawing* — that is a `Shape`, and the runner has no renderer. It proves the series the drawing is made of.

It also pins the recovery tier boundaries at all six edges (100/67 green, 66/34 yellow, 33/0 red), because the colour of Home's recovery ring is decided there and an off-by-one at 66/67 is invisible on screen — the two colours are adjacent either way — and then asserts `RecoveryMetric.state` agrees with `RecoveryState(score:)` across the range, since the coach message path holds a bare score and reads the initialiser while the ring reads the property. The pair next to them is what keeps a placeholder off the screen: an unmeasured day's `score: 0` row reports `.red` **and** `hasMeasurement == false`, so a view that drew the tier colour without checking the latter would show an unworn night as a hard 0% red recovery.

The month calendar's blocks sit beside those tier assertions, and they are shaped by what a runner with no renderer can and cannot see. `DayBarRules` is a separate type rather than logic in the bar's body for exactly this reason — a rule written into a `View` is a rule nothing here can assert — and it takes `now` as a parameter so the assertions do not say something different tomorrow; one of them pins that `TODAY` is decided by the **calendar day** and not the instant, which a raw `Date` comparison gets wrong. `MonthGrid` is swept across all 60 months of 2023–2027 and the per-month failures are accumulated into single assertions rather than one assertion per day, so the coverage is exhaustive without the count exploding. **The sweep alone cannot see the bug `MonthGrid` exists to prevent**: this machine's `Calendar.current` is Sunday-first, so `firstWeekday - 1` is 0 and the wrong `blanks = weekdayOfFirst - 1` agrees with the right answer — that was confirmed by mutating `MonthGrid` to it and watching all six sweep assertions still pass. The block that catches it drives a **Monday-first** calendar (the parameter `MonthGrid.make` takes for precisely this) through the same invariant, and the mutation fails there with `Thu, Jan 1 sits under Fri but is a Thu`. The month read is then driven through the real `HomeViewModel.loadMonth(containing:)` against an in-memory database holding a row inside the displayed month and one in the month either side, and it asserts **both neighbours absent** — the window is `days: <the span between the month's own bounds>, endingOn: <the month's last day>`, and a window one day too wide would tint a day nothing measured, which is invisible on screen. The measurement gate is asserted the same way it is everywhere else: a `hasMeasurement == false` row is absent from the map rather than `.red`. The last block is the one that fails if anyone decides a load is "still running" from `monthTiers.isEmpty` — a month the export never covered returns an empty map, no error, and `isLoadingMonth == false`.

One assertion there is a deliberate documentation of a trap rather than a behaviour: it asserts that a `WhoopDevice` constructed `.disconnected` reports `batteryPercentage == 100`. That is the *reason* the Home readout gates on connection state, so the assertion fails loudly if anyone "fixes" the default without fixing the readout.

The three XCTest files in `Tests/WhoopsyTests/` are dead: no test target references them, so they are never compiled or run.

## Architecture

Four layers under `Sources/Whoopsy/`, with a strict one-way dependency rule (verified: `Domain/` imports only `Foundation`; `Core/` adds only `os.log`; `Presentation/` imports no GRDB or CoreBluetooth):

```
Presentation  (SwiftUI + @Observable ViewModels)   →  depends on DIContainer
Domain        (Entities, UseCases, Repository protocols)  ←  implemented by Data
Data          (BLE, GRDB persistence, HealthKit adapter, exporters)
Core          (HRV/Strain/Stress math, logging, extensions)
```

- **`Domain/Repositories/*`** are protocols only. Concrete implementations live in `Data/Persistence/Repositories/`.
- **`App/DependencyInjection/DIContainer.swift`** is the single wiring point. `DIContainer.shared` uses real BLE; `DIContainer.preview` uses `WhoopMockBLEManager`. `app/iOS/WhoopsyApp.swift` picks `preview` when `XCODE_RUNNING_FOR_PREVIEWS=1`. Use cases are constructor-injected; there are no singletons below the container except `LocalDatabaseManager.shared`.
- **Data flow**: `WhoopBLEManager` → `WhoopPacketDecoder` (0xAA framing) → `BiometricRepository` → `LocalDatabaseManager` (GRDB) → `StreamBiometricsUseCase` / `Calculate*UseCase` → `@Observable` ViewModel → SwiftUI. Two further inputs write into the same tables through the same repositories: `HealthKitStoreClient` → `HealthKitImporter`, and `WhoopExportParser` → `WhoopExportImporter` for a bundled WHOOP data export.
- **`Data/Import/*` is the only WHOOP-export seam**, and it is not a sync. It reads a CSV that shipped inside the app bundle, it runs only when the user taps the button in Settings, and it exists so a fresh install can show history that predates it. `WhoopExportParser` produces a plain `Sendable` row of optionals and decides nothing; `WhoopExportImporter` does the day-keying and the scoring. Unlike the other two inputs, it does not compute Strain — see the gotcha below.
- **`Data/Health/*` is the only HealthKit seam.** `HealthStoreClient` is the protocol the importer depends on; its value types are plain `Sendable` structs and it deliberately does **not** `import HealthKit`, which is what lets the import be tested with a fixture store and no device. `HealthKitStoreClient` is the real actor behind it. It has two read shapes and the difference is load-bearing: `quantitySamples(_:from:to:)` for individual readings (HRV, resting heart rate) and `dailyTotal(_:from:to:)` for a cumulative sum over a window (steps only). Adding a case to `HealthQuantityMetric` also adds it to `readTypes`, so the consent prompt grows with it — and **removing one shrinks it**, which is how the VO₂ max read-through left the prompt when its case was deleted. `FixtureHealthStore` in the runner answers **per metric in a `switch`**, deliberately — its old two-way ternary sent everything that was not HRV to the resting-heart-rate array, so a new case would have silently answered one quantity's query with another's readings, which is a fixture inventing a measurement of the wrong kind.
- **Views get their ViewModel built in `MainContainerView`** — tabs are Home, Strain, Workout, Sleep, Recovery, and a "More" stack holding Coach/Device/Settings. Adding a screen means wiring its use cases through `DIContainer` and `MainContainerView`, not reaching for a global. `MainContainerView` builds **one** `ActiveWorkoutViewModel` and passes it to both Home's `+` and the Workout tab, so those are two views of one live session.
- **`Presentation/DesignSystem/Theme.swift`** holds all color tokens (recovery green/yellow/red, strain gradient, sleep stage colors, and the Home surfaces `homeBackground`/`homeCard`/`ringTrack`/`sleepPerformance`/`strainRing`). Don't hardcode colors in views.
- **There are two ring components and they are not interchangeable.** `GaugeRingView` (gradient, glow, label inside) is what Strain, Sleep, Recovery and the workout HUD use. `MetricRingView` is Home's flat counterpart and takes its value as an **optional** `String?` so a dash cannot arrive with a fill attached. Changing one must not move the other.
- **The Recovery ring is drawn in the day's tier colour, and there is exactly one definition of the tiers and one mapping to colour.** The boundaries (green 67–100, yellow 34–66, red 0–33; spec in `ALGORITHMS.md` §"Recovery Tiers") are written down once, in `RecoveryState.init(score:)` — `RecoveryMetric.state` forwards to it, and `GenerateCoachInsightsUseCase` reads it rather than holding its own `>= 67`. `RecoveryState.color` in `Presentation/DesignSystem/RecoveryState+Extensions.swift` is the only place a tier becomes a `Color`; Home's ring and the Recovery tab's gauge, HRV card and trend chart all read through it. It cannot be a property on the enum (Domain imports only `Foundation`) and it must not be re-written per screen: the copies had already diverged twice, with Home drawing `recoveryGreen` unconditionally while the Recovery tab tiered it (a 20% morning green on one screen and red on the other) and the coach message holding a second green boundary. A tier is computed from the **score**, so a `score: 0` placeholder reports `.red` — which is why the drawing gates on `hasMeasurement` and an unmeasured day renders `—` with no fill rather than as a hard 0% red ring.

### Persistent gotchas

- **A shipped migration is frozen.** GRDB records applied migration *identifiers* and does not checksum bodies, so editing `v1`'s body changes nothing on any database that already ran it — and the schema silently stays wrong. Schema changes always go in a new `registerMigration` block. The per-version inventory — what `v2`…`v8` each added — is `ARCHITECTURE.md` §2.B and is not repeated here. Note `addMissingColumns(to:columns:in:)` adds **nullable, undefaulted** columns only; a NOT NULL column needs an explicit `db.alter`, which is why `source` is nullable: NULL is the honest value for a row written before the column existed.
- **A `[Double]` property on a `Codable` record is a JSON-encoded `.text` column, and `Array` is not a `DatabaseValueConvertible`.** `biometric_samples.rrIntervalsMs` is `[Double]?` and GRDB stores it as a String, which is why `v8` declares the column `.text`. The array can therefore only ever be a *record property* — using it as a query binding is a compile error, and `BiometricSampleRecord.rrSeries` exists as the computed `[Double]` that is safe to pass around. Computed properties are invisible to `Codable` synthesis, so adding one to a record adds no column. The same record has **no `CodingKeys`**, so its property names *are* its column names — `rrIntervalsMs`, camelCase.
- **The test suite is not hermetic: §6 writes to the developer's real database.** `Tests/WhoopsyTestRunner` §6 builds `DIContainer(useMockBLE: true)`, and `DIContainer.init` takes `LocalDatabaseManager.shared` — the actual `~/Library/Application Support/whoopsy.sqlite`. So running the suite applies any new migration to that file and leaves the rows §6 writes in it. That is how `v8` lands on a developer's database before the app is ever launched, and it means the suite's results depend on that file's state. There is no path-injecting initialiser to fix it with (see the gotcha below); the sections that need isolation build their own `LocalDatabaseManager(inMemory: true)` and that is the shape to copy.
- **The BLE streams are multicast.** `liveTelemetryStream` and `deviceStream` each hold a dictionary of continuations keyed by `UUID`, pruned in `onTermination` and guarded by a lock (the class is `@unchecked Sendable`, and these are written from caller threads and read from the BLE queue). A second subscriber must never orphan the first: the failure is silent — no error, no gap, just a `for await` that stops receiving, which is indistinguishable from a strap that went quiet. Both streams genuinely have two consumers: `StreamBiometricsUseCase` is driven from `HomeViewModel.load(for:)` and from `MainContainerView`'s workout HUD, and `deviceStream` is read by `HomeViewModel.observeDevice()` and `DeviceViewModel.load()`. A new subscriber is safe to add, but anything that *yields* must go through `yieldTelemetry`/`yieldDevice` rather than touching the dictionary.
- **A sample row's `timestamp` is an arrival instant, not a beat time.** `WhoopBLEManager` stamps `Date()` when the notification is decoded, so the column records when the app heard about the beats, not when they happened — and `decodeHistoricalSyncPayload` stamps every row of a historical batch with the same decode-time instant. Within a notification the intervals in `rrIntervalsMs` are adjacent beats in exact order; **across** notifications they are not, and no column distinguishes them. Anything building a beat-to-beat tachogram must therefore reconstruct beat times by cumulative sum from the intervals themselves and must not trust `timestamp` as a per-beat time. `getSamples` orders by `timestamp` with `id` as the secondary key, which recovers insertion order for ties — that is arrival order, and it is the best the schema has.
- **Column naming differs per table, and `CodingKeys` is the only thing that decides it.** `RecoveryRecord` declares `CodingKeys` mapping its properties to **snake_case** columns (`recovery_score`, `hrv_value_ms`), so a new property needs a matching case there. `StrainRecord` has **no** `CodingKeys`, so its property names *are* its column names and `strains`' columns are **camelCase** (`strainScore`, `averageHeartRate`, `hasMeasurement`). Writing `hasMeasurement` as `has_measurement` in `v7` produced `SQLite error 1: no such column` at launch — and because a failing migration `fatalError`s, the whole app went with it. Check `pragma_table_info(<table>)` or the record's `CodingKeys` before naming a column in a migration.
- **`workouts` deliberately breaks the day-key rule, and that is not a bug to fix.** `recoveries`, `sleeps` and `strains` are primary-keyed on `date` snapped to `startOfDay` because a day holds one of each. A day can hold **several** workouts, so `workouts` is keyed on `id` (a UUID string) with `date` as an ordinary indexed lookup column, and `getWorkouts(for:)` returns an array rather than an optional. The snap still applies — `LocalDatabaseManager.saveWorkout` snaps `date` centrally like its `saveRecovery`/`saveSleep`/`saveStrain` siblings — so a session started at 17:33 is filed under that day. Do not "normalise" this table onto a `date` primary key; that would make a second session on one day overwrite the first. `DIContainer` wires `GRDBWorkoutRepository`; there is no in-memory workout store.
- **`WhoopDevice.batteryPercentage` is not optional and defaults to `100`.** `WhoopBLEManager` writes a literal `100` at discovery, so a percentage read off a strap that is not connected is a constant this app wrote down rather than a measurement it took. Any battery readout must therefore gate on `connectionState == .connected` and render `—` otherwise — `HomeDashboardView`'s status badge is the reference. The real fix (making the field optional the way `SleepSession.respiratoryRate` is) is still open and is a wider change than a view.
- **Steps is the only value on Home still read through HealthKit, and the VO₂ MAX panel no longer is.** Steps are a daily *sum* — the one HealthKit quantity that is not a reading the app can file under a day key — so `HealthStoreClient.dailyTotal` uses `HKStatisticsQuery(.cumulativeSum)` rather than the per-sample path, and `HealthKitBridge.stepCount(on:)` reads the store on demand; there is no table and no column. It is a `HealthKitSyncing` member that does **not** throw, deliberately: HealthKit never discloses read-permission status, so a denial, an empty day, a device with no source and an unavailable store are indistinguishable from the caller, and all of them are honestly the same dash. A `0` for steps would be a different claim — a day the user did not walk. **The VO₂ MAX panel is not a HealthKit read and must not become one again** — there is no `.vo2Max` case on `HealthQuantityMetric` and no member on `HealthKitSyncing`, so VO₂ max is absent from the consent prompt's `readTypes`. It prints an estimate this app computes instead: `Vo2MaxMath.heartRateRatioEstimate` (`15.3 × HRmax / HRrest`, Uth et al. 2004), derived on read inside `MetricWeek.makeDay` from the slot's own gated resting heart rate and `UserProfile.maxHeartRate`, stored nowhere. Two things about it are not negotiable: the label says `(EST.)` because it is a model's output beside three measurements, and a day that cannot produce one is `—` and never `0`. `ALGORITHMS.md` §6 carries the model, the citation, the 4.7 mL·kg⁻¹·min⁻¹ (~7.8%) error bar that applies when `HRmax` is *not* measured, the measurement that rejected the day's own peak as an anchor, and why WHOOP's three-tier model is still unimplemented.
- **The scoring window is the last 30 days that *have rows*, and a mean is not a baseline until the window held some.** `RecoveryScoring.baselineWindow(before:in:)` filters to the days strictly before the day and *then* takes the trailing `baselineWindowDays` (30) — slicing first takes the wrong thirty, and the input must be **oldest-first**, which is what the repositories return. **The `before:` comparison is made on the calendar day, and that is not a detail**: every row is keyed on `startOfDay`, but the two callers hand different kinds of anchor — `WhoopExportImporter` passes a snapped day key while `RecoveryViewModel.loadBaselines` passes the `Date` the screen is displaying, which is an instant and on every day this app runs is hours after midnight. Compared raw, that instant is later than the day's own midnight row, so the day fell inside its own baseline and the printed mean was taken over a different set of days than the score above it — measured on the simulator, 2026-08-17 printed an HRV baseline of 53 and a sleep-performance baseline of 80 where the strictly-before window gives 52 and 78. Both anchors are snapped inside the helper rather than at the call sites, so the contract holds for whatever a caller passes; every fixture in the suite used a snapped anchor, which is how it survived until a screenshot of a real day was read against the database. The two definitions are not nearly the same number: measured over the bundled export, 391 of 907 comparable days have a calendar-30 window that differs from the last-30-rows window, by up to **18.03 ms**, and the worst case reaches back **172 calendar days** to fill thirty rows. A reader must fetch `baselineWindowLookbackDays` (180) back or it silently prints a baseline built from fewer days than the score above it used. It lives here rather than in the importer because the Recovery detail screen prints the same baseline its ring was scored against. **`BaselineStatisticsMath.baseline` substitutes a cold-start constant on an empty window** (65 ms RMSSD, 40 ms SDNN, 54 bpm) — right for scoring a first day, wrong to print, since a screen showing `65 ms` as "your HRV baseline" would present a constant as a measurement. `RecoveryScoring.baselines(...)` therefore returns each mean *with the count it was taken over*, and `Baselines.displayed` withholds one below `minimumBaselineDays` (3). `score(_:)` is built on `baselines(...)`, so a screen that prints `displayed` cannot disagree with the ring above it.
- **`MetricChange` draws a comparison on the *formatted* pair, not the raw one, and its verdict is three states rather than two.** A resting heart rate of 52 against a mean of 52.4 is genuinely below it, but a row printing `52` over `52` renders as `52 ▼ 52` — a row contradicting itself. The digits on screen are the whole of the evidence a reader has, so the comparison is made on the **formatted** pair: two figures that print alike *are* the same as far as the screen is concerned. That case is `.same` — `direction` is `nil` and the glyph is `circle.fill`, because a figure sitting on its average has not moved and there is no direction to point. **The middle state is the whole reason the colour cannot be read off the direction**, and `nil` is now reserved for a *missing side* — a day with no measurement, a window with no baseline — rather than for "unchanged", which conflated two answers the screen renders differently. Direction and verdict are separate by construction: the triangle always points the way the number went, while `higherIsBetter` turns that direction into the verdict and the verdict alone picks the colour — `Theme.recoveryGreen` / `Theme.recoveryYellow` / `Theme.recoveryRed`, so an HRV rise is green while a resting-heart-rate rise is red from one call. The type is shared by Home's four metric panels, Home's two tiles, and the four breakdown rows, so a change here moves all three.
- **A week's baseline is a mean over measured slots, and HRV's is narrowed to one metric first.** `MetricWeek` computes four baselines from the same seven slots. Three are plain means over the slots carrying that figure, `nil` below `minimumBaselineDays` (3). HRV's is not: SDNN and RMSSD are different quantities on different scales, so it takes the **newest measured slot's metric**, averages only the days matching it, and can therefore come back `nil` in a week that has readings in it — which is the honest answer, not a baseline over a mixture. **`hrvBaselineMetric` and `hrvBaselineMs != nil` are two different conditions**, and picking the wrong one is silent: the metric names which quantity the week is *in* and is set as soon as one slot has a reading, while the mean additionally needs `minimumBaselineDays` days in it — so a two-day week is `hrvBaselineMetric == .rmssd` with `hrvBaselineMs == nil`. Anything selecting days to plot wants the metric; anything printing a mean wants the mean. `MetricDay.hrvMetric` is non-`nil` only when `hrvValueMs` is, so a slot can never name a quantity it has no reading in. VO₂ max joins the week through `MetricWeek.init`'s `maxHeartRate:` parameter instead — the one input that is not a per-day row, being the profile's assumed maximal heart rate, which is also what `CalculateStrainUseCase` builds its Karvonen zones from so the app has one definition of `HRmax` rather than two. The estimate itself is computed **inside** `makeDay` from that slot's already-gated `restingHeartRate`, which is the whole reason for the placement: the day's absence rule for a resting rate is applied once, and the VO₂ field inherits it. A caller assembling the estimate itself would have to restate the `hasMeasurement && > 0` gate, and an unmeasured row carrying a plausible `55` bpm — which is constructible, since `hasMeasurement` is `hrvValueMs > 0` — would then produce a confident estimate on a day this app calls unmeasured. **A `MetricWeek` built from one history is not a week with the other two unmeasured.** `MetricWeek.init`'s three history parameters all default to `[]`, so a caller that passes only `recovery:` gets `nil` for `strain` and `sleepNeedSeconds` on every slot — and on this type `nil` is the documented word for *nothing was measured*. `RecoveryViewModel.week` is that build one history short (the Recovery page draws five charts and the five read two histories between them: the recovery-performance bars and all three lines come out of `recovery`, since HRV, resting rate and respiratory rate are all columns on a `recoveries` row, and the sleep-performance bars need a `sleeps` row, which no column of a `recoveries` row carries), so its `strain` is "not asked for" and **a strain-plotted view handed that week would report every day of it as unmeasured**. The narrowing is per-caller, so it is carried in that property's doc comment rather than here; the fix if a view ever needs a second series is to pass the second history, not to read through the `nil`.
- **Stress Monitor is a calibration, not a recovery of WHOOP's function.** WHOOP publishes the model's shape (HRV + heart rate + motion, a 14-day personal baseline, a 0–3 scale banded 1.0/2.0) and none of its constants, so every threshold in `StressMath` is this app's own and **this app's number will not agree with the WHOOP app's** — the same bargain `SleepNeedMath` documents. Two things about it will otherwise read as bugs: `minimumRRIntervals` is **load-bearing**, because `HeartRateVariabilityMath.calculateRMSSD` returns `0.0` on insufficient data and a zero RMSSD scores as *maximum* stress; and the tile renders `—` far more often than a number, because samples exist only for days the app was running with the strap connected and the export carries no R-R series at all. The full model is in `ALGORITHMS.md` §5.
- **The Stress Monitor chart follows three rules that are not styling choices.** The y-axis is **fixed at 0–3** and never auto-scaled (auto-scaling draws a calm day and a wired day as the same picture); a gap longer than `windowSeconds × 1.5` **breaks the line** rather than interpolating, because an ineligible window is unmeasured and joining across it draws a reading nobody took; and **no windows means no chart at all** — not an empty frame, not a zero line, since a flat line at zero is the strongest possible claim of calm. The fill's gradient stops come from `StressMath.lowMediumBandEdge`/`.mediumHighBandEdge` divided by the scale, so it must not type `1.0`/`2.0` itself. The fill is a `Shape` and not a `Path` built in the view: `path(in:)` receives the frame, so the stops land on the score scale — a `Path` in a `ZStack` is graded over its own bounding box and the band colours move with the data.
- **Home's collapsing rings header is a `PreferenceKey`, and it writes no `@State`.** iOS 17 has **no scroll-geometry API** — `onScrollGeometryChange` is iOS 18 and the deployment target is 17.0 — so the mechanism is `GeometryReader` → `RingsBottomKey` (the rings row's `maxY` in a named coordinate space) → `.overlayPreferenceValue`. Four things about it are load-bearing: `PreferenceKey.defaultValue` must be `static let`, not `static var` (a mutable static is a Swift 6 concurrency error), and its value is deliberately out of any real range so an unpublished frame resolves to *hidden*; the preference reports where the rings **are**, not a scroll offset, so there is no threshold constant to go stale when the top bar changes height; the transform must not write `@State`, because it runs on every scroll frame and a state write per frame invalidates the whole screen; and the `VStack` must **not** become a `LazyVStack` — a lazy stack may release the rings row once it is scrolled past, taking the preference publisher with it and hiding the header permanently. Home's content is currently **shorter than its viewport on every day this app can show** (an empty day is ~576pt against ~741pt of scroll space, and an imported day adds only a sleep row), so the page does not scroll and the header is latent (verified once by forcing overflow with a temporary bottom padding, since reverted). Do not conclude from a screenshot that it is broken; conclude that Home needs more content before it is reachable.
- **A failing migration crashes the app at launch.** `LocalDatabaseManager.init` calls `fatalError` on a migration error. Test a migration against the real dev database before trusting it; the reset is `rm ~/Library/Application\ Support/whoopsy.sqlite`. **`LocalDatabaseManager` has no path-injecting initialiser** — `init(inMemory:)` or the `~/Library/Application Support` default are the only two — and on macOS `FileManager.url(for: .applicationSupportDirectory,…)` does **not** follow a `HOME` override, so a host-side tool that writes through it lands in the developer's own dev database however the process is launched. The simulator app is unaffected (its container is separate); a host tool that must not touch the dev database has to be given one by *temporarily moving that file aside*, not by re-pointing `HOME`.
- **Day-keyed writes must be snapped to `date.startOfDay`.** `recoveries`, `sleeps` and `strains` are read back with `startOfDay` as the lookup key, and GRDB's `save` is INSERT-or-UPDATE *by primary key* — so a row written at a raw timestamp is inserted, never updated, and no keyed read can find it. `LocalDatabaseManager`'s `saveRecovery`/`saveSleep`/`saveStrain` snap centrally for this reason; keep new writers going through them.
- **A day-keyed screen must READ.** Send day selection to the repositories (`getRecovery(for:)`, `getStrain(for:)`, `getSleepSession(for:)`), which is what `RecoveryViewModel`/`SleepViewModel`/`StrainViewModel`'s `load(for:)` do; they fall through to a calculate use case only for a day that **is today and holds no measurement**. `HomeViewModel.load(for:)` is the reference implementation. The read is the point: a stored day has no raw samples to recompute from (an imported day has none by construction), so a recompute would come back as *no row at all* and blank the day the user was looking at. `RecoveryViewModel.shouldCompute` is the gate, and it tests the measurement rather than `nil` so that a placeholder row left by an older build stays a legitimate candidate to fill.
- **`getXHistory(days:)` windows back from `Date()` unless you pass `endingOn:`.** The three metric screens show a day the user picked, so they call `getRecoveryHistory(days:endingOn:)` and its siblings. Those reads bound the window at **both** ends (`>= cutoff` and `<= endingOn.endOfDay`); the upper bound was added with `endingOn`, because a window anchored on an old day would otherwise run on to the present. Pulling the whole imported range in a test is still `days: 4000`.
- **The calendar's day colours are a map, and a day absent from it means no measurement.** `HomeViewModel.monthTiers` is keyed by `startOfDay` and built by gating each row on `hasMeasurement` — never on the row existing. A legacy placeholder holds `score: 0` and reports `.red`, so a map keyed on existence would paint an unworn night a hard red, which is the same fabrication the dash convention exists to prevent, drawn in a cell instead of a ring. Two consequences worth keeping: a day *missing* from the map is drawn grey and is still **selectable** (Home legitimately opens on an empty today, so most of a fresh install has to stay reachable), and the loading test is `isLoadingMonth`, never `monthTiers.isEmpty` — a month the export never covered is empty and finished, and testing emptiness would spin forever on it.
- **The month read's window is `days: <the span between the month's own bounds>, endingOn: <the month's last day>`.** Because the window is inclusive at both ends and runs from `endingOn - days`, that pair covers exactly the month. Neither of the obvious alternatives does: `days: 30` reaches back into the previous month on a 31-day one, and `days: dayCount` pulls in the 1st of the next — either would put a neighbouring month's row in `monthTiers`, where the grid is free to tint a day nothing measured. An assertion on one month cannot see this, which is why §14's version puts a row on each side.
- **`.toolbar(_:for: .tabBar)` is unavailable on macOS, and Home is built for both.** `swift build` is this repo's edit/compile loop and the test runner links its objects, so the unguarded modifier breaks the fast path while `xcodebuild` for the simulator stays green — it reports `error: 'tabBar' is unavailable in macOS` and nothing else does. Home wraps it in a `#if os(iOS)` helper (`View.hidingTabBar(_:)`) for that reason. This is the second member of the family that also holds `#if canImport(HealthKit)` being true on the host: **a green iOS build is not a green host build, and vice versa** — run both.
- **Home's calendar is an overlay, not a `.sheet`, and the difference is load-bearing.** A sheet is a full-height card the system centres, which put the grid in the middle of a dark slab with Home invisible behind it; the calendar hangs from the top of the safe area instead, over a `0.45` black scrim so the screen behind stays legible. Home also hides the tab bar while it is up, because an overlay inside a tab **cannot cover the tab bar** — the `TabView` draws it above its content — so leaving it visible would put a live row of tabs under a modal, and a tab switch would strand `isPresentingCalendar` set and reopen the calendar on return.
- **`SleepSession`'s `Equatable` cannot compare two reads of the same night.** The struct carries `let id: UUID`, its initialiser defaults that to a fresh `UUID()`, and the synthesised `==` includes it — so two `getSleepSession(for:)` calls on one unchanged row are never equal. Compare the fields you mean.
- **SDNN and RMSSD are different quantities and never share a baseline.** Every `recovery` row carries `hrvMetric`; `RecoveryScoring` is the only place that filters history by it. Mixing them computes a z-score between two distributions and silently mis-scores every day.
- **The export's day key is `startOfDay(Wake onset)`, and that is the app's own convention.** `CalculateRecoveryUseCase` writes `date.startOfDay` and reads the sleep session *for that same date*, so a recovery row for day D comes from the night that ended on D's morning. The export's `physiological_cycles.csv` is one row per cycle, and keying those on `Cycle start` would collapse 935 rows onto 753 days — silently dropping a fifth of the history. `WhoopExportImporter` keys on the wake onset for every row that has one. Verified against the real file: 910 wake rows → 910 distinct days, zero collisions, and 933 `Day Strain` values → 931 distinct days.
- **The importer's `calendar:` parameter cannot override the database's day-key snap.** `LocalDatabaseManager.save*` snaps with the `Date.startOfDay` extension, which is `Calendar.current` and is not injectable. Handing `WhoopExportImporter` a calendar in another zone does not shift its day keys, it *splits* them — the importer computes `startOfDay` in one zone and the database re-snaps in another, so a UTC midnight lands on the previous day and every key is wrong by one. Production passes `.current`, so the two agree; a test or a new caller must too.
- **24 export cycles have a `Day Strain` but no wake onset.** They are fragments that never closed, so they become `strains`-only rows. Two of them start at 23:30 and 23:48 on a day a closed cycle already claims (2024-02-11, 2024-03-20), and their day is genuinely unknowable — so the closed cycle takes the day and the fragment defers. That is why 933 `Day Strain` values produce 931 `strains` rows, and it depends on the device zone: a fragment near midnight lands on a different date in a different zone. `Tests/WhoopsyTestRunner` §11 recomputes the expected key set rather than hardcoding it. The three day-level counts in `WhoopImportSummary` (`daysWritten`, `strainOnlyDays`, `duplicateExportRows`) are accumulated from those key sets as the walk goes, because they cannot be recovered from the per-table row totals: on this export the arithmetic shortcut for strain-only days gives 21 where the truth is 22, since one scored day carries no strain. `duplicateExportRows` exists because a skipped row has two possible causes that look identical — a day that already held data *before* the import ran, and a day an *earlier row of the same import* claimed. Only the first is `daysAlreadyRecorded`; counting the collision rows there made a fresh install report "2 already recorded locally" when nothing was.
- **A strap night's Sleep Need is computed; an imported night's is WHOOP's own, and the two must not be crossed.** `SleepNeedMath.sleepNeedSeconds(baselineSeconds:previousDayStrain:)` returns the profile's baseline plus `6.40 min × the previous day's strain`, and `AnalyzeSleepUseCase` reads that strain row from `strainRepository` at `startOfDay(morningDate) − 1 day` — the *previous* day, because `strains` is keyed on `startOfDay(wakeOnset)` and the cycle preceding the night ending on D is keyed D. Three things about it are decisions, not oversights, each with its basis in `ALGORITHMS.md` §4: the coefficient is **fitted to the bundled export** (WHOOP publishes this model's shape and none of its constants — 6.40 is the pinned-intercept least-squares slope over the 909 nights carrying a preceding strain day, and the cross-validation curve is flat from 6.4 to 7.0, so the reproducible fit is shipped over the marginally luckier one), a **`nil` strain returns the baseline exactly** rather than a plausible strain, and the **accumulated Sleep Debt term WHOOP names is deliberately absent** — a judgement, not a measurement: a fitted 7-night deficit buys 0.35 of a point (3.77 → 3.41) for a second fitted constant and seven nights of history, and WHOOP's own `Sleep debt (min)` column does no better (3.43), so there is no hidden headroom. What *was* measured as harmful is the old documented `0.20` carryover: written out, it scores 18.44 against the flat 480's 10.06. Imported nights store the export's `Sleep need (min)` verbatim, so a need *below* the 8-hour baseline exists in the database and is correct; the suite's §13 is what fails if anyone routes them through the formula. `profile.targetSleepHours` is the strap path's flat baseline — never editable, never persisted.
- **Every imported `strains` row holds WHOOP's own score, not this app's.** The export has no heart-rate series, so `StrainAccumulatorMath` has nothing to integrate and `WhoopExportImporter` stores the `Day Strain` column verbatim. This is the only place a stored strain value comes from a different algorithm, and the only way to tell is the `source` column. Zone breakdowns are empty for every imported day for the same reason — which is why `StrainDashboardView` renders "No zone data recorded."
- **WHOOP's HRV is classified as RMSSD, and that is an inference.** The export does not name the quantity in its `Heart rate variability (ms)` column. It is called RMSSD because WHOOP publishes overnight HRV as rMSSD and the observed distribution (52.5 ± 10.5 ms, range 15–99) fits that band. It matters because of the never-mix rule: the classification decides which baselines the imported days join. The claim is made in exactly one place (`WhoopExportImporter`, passed as `todayHrvMetric: .rmssd`) and its basis and falsification test are in `ALGORITHMS.md` §1.
- **Importing recomputes Recovery rather than storing WHOOP's.** The export's `Recovery score %` column is not written anywhere: the importer feeds WHOOP's *measured* inputs to `RecoveryScoring` so one formula covers all 910 imported days and every day after. Historical percentages therefore will not match the WHOOP app, which is the accepted cost of not putting two models on one chart. The same reasoning makes `SleepSession` derive its own performance rather than use the export's `Sleep performance %` column — they disagree on 457 of 910 nights.
- **HealthKit availability is a runtime question.** `HealthKit.framework` is present in the macOS SDK, so `#if canImport(HealthKit)` is **true on the host** and guards nothing. Use `HKHealthStore.isHealthDataAvailable()` (which `HealthKitStoreClient.isAvailable` does). On macOS the answer is false, so the import path can only be exercised by the fixture tests in the runner.
- **HealthKit never discloses read-permission status.** `requestAuthorization` completes `true` even when the user taps "Don't Allow", so no code can report "access granted". The import result is the only honest signal, which is what `HealthImportSummary` carries.
- **`physiological_cycles.csv` is the only bundled resource, read through `Bundle.module`.** It is the only file in `Data/Resources/` declared in `Package.swift` (`resources: [.process(...)]`); `sleeps.csv`, `journal_entries.csv` and `workouts.csv` stay on disk unbundled and are read by nothing. One file is enough because nothing reads `sleeps.csv` yet: **`Nap` exists only in `sleeps.csv`**, and its eight records need a `naps` table before they can be stored at all (see `ALGORITHMS.md` §4). Its 910 non-nap rows carry the same 910 wake onsets as the bundled file, set-for-set, so those 8 naps are its entire unique contribution. `TODO.md` §2 carries the full inventory. Never use `Bundle.main` for it: the app target's resource phase is empty and never did contain these files. **`Bundle.module` traps rather than returning `nil`** when the resource bundle itself is missing, so the lookup must stay inside the user-initiated action and never run at launch. Parse its dates with a fixed format: the export writes `2026-08-22 00:17:13`, so `ISO8601DateFormatter` returns `nil` and a parser built on it drops every row with no error.
- **`simctl launch` on an already-running app does not relaunch it, so a screenshot can show the previous build's code.** The sequence that works is `terminate` → confirm it succeeded → `install` → `launch`. Two of those steps have a silent failure mode: `terminate` exits non-zero with *"found nothing to terminate"* when the app is not running, and `install` over a running app replaces the bundle on disk while the live process keeps executing the old one — so a `launch` that merely foregrounds it renders the old view. The tell is two screenshots taken either side of a visible source change coming back **pixel-identical**, which reads exactly like a modifier that did nothing; that is what happened to `.defaultScrollAnchor`, which was working the whole time. `uninstall` is the other way to force a cold start and is **wrong here** — it drops the data container, taking the imported export with it.
- **Filenames lie.** `Data/Persistence/Repositories/SwiftDataRecoveryRepository.swift` actually declares `GRDBRecoveryRepository`. No SwiftData remains in the codebase.
- **Repositories answer from local storage and nothing else.** There are no fallback sources: `GRDBRecoveryRepository`/`GRDBSleepRepository`/`GRDBStrainRepository` take only `db:`, and a day with nothing stored returns `nil` (or an empty history) rather than a substituted row. Anything else makes "no data" indistinguishable from a measurement, which is the failure mode every no-data rule in this file exists to prevent. `RecoveryRepository.getLocalRecovery(for:)` now reads identically to `getRecovery(for:)`; it is kept as a separate name because it is what a caller *about to write* should call, and the name is the only place that intent is recorded.
- **A day that was not measured gets no row, and the same test must be on both sides of the write.** `CalculateRecoveryUseCase.execute` and `CalculateStrainUseCase.execute` return an optional and write nothing when they produced no measurement, which is how `AnalyzeSleepUseCase` has always behaved. The rule is one sentence: **a writer may persist a row only when it produced a measurement, and the test it uses must be the same test its readers use.** `RecoveryMetric.hasMeasurement` is `hrvValueMs > 0`, so the guard has to be that comparison made against the value *as it will be stored* — `CalculateRecoveryUseCase` rounds to one decimal **before** guarding, because an RMSSD below 0.05 ms passes on the raw value and is still written as `0.0`. Guarding on the interval count instead is a different test: `HeartRateVariabilityMath.calculateRMSSD` returns exactly `0.0` when `filterRRIntervals` leaves fewer than two beats, so one surviving interval used to write a `0.0` ms row that the type's own readers called unmeasured. On the reading side, `RecoveryScoring` filters placeholders out of every baseline, `HealthKitImporter` fills a day whose row is unmeasured instead of skipping it, and `RecoveryDashboardView`, `StrainDashboardView` and the Home rings render one as `—` rather than a red 0% or a confident `0.0`. A day with no *sleep* session contributes `BaselineStatisticsMath.sleepPerformancePivot` (0.70) to an otherwise-measured day — the value that shifts the score by zero. **`RecoveryMetric.hasMeasurement` and `StrainScore.hasMeasurement` are now reader tolerance, not a marker any writer sets**: rows written before this rule are still on disk holding zeros, and the gates are what keep them off the screens, the baselines and the charts. `StrainScore.hasMeasurement` is a **required** initialiser parameter with no default, deliberately: a default of `true` would let a construction site silently mark a placeholder measured, which is the exact bug the flag exists to prevent.
- **Absence is the same shape in all four metrics now, and that is the point.** Recovery, Strain, Sleep and Stress all report a day with no measurement as **no row**, with the optional as the answer. A reserved zero row is the weaker design — every reader has to remember to exclude it, and two did not (the export importer skipped a day whose strain row merely existed, so WHOOP's real `Day Strain` for it was never imported; `StrainViewModel` treated one as settled and never recomputed). An absent row cannot be mistaken for data by a reader that forgot the rule. Do not reintroduce a placeholder to make a keyed table "tell nothing from zero" — that is what the optional is for.
- **Sleep has no placeholder: an unclassifiable night is an absent row.** `AnalyzeSleepUseCase.execute(for:)` returns `SleepSession?` and returns `nil` — writing nothing — when the overnight window holds fewer than `minimumEpochSamples` (30). It previously built an eight-hour night out of literals and saved it, so a strap left on the charger was stored and scored as a full night's sleep; rows of exactly `4.2/1.8/1.6/0.4` hours in `sleeps` are that artefact. Every reader therefore takes an optional: `SleepDashboardView` and the Home ring render `—`, and `SleepViewModel.session` is `SleepSession?`. Recovery needs no special case — its sleep term falls back to the pivot above, which is a defined constant.
- **A channel the strap has no sensor for is `nil`, not a plausible constant.** `SleepSession.disturbanceCount` and `.respiratoryRate` are optional and `sleeps` stores both as nullable; the strap path has no respiratory sensor at all, and a disturbance count exists only for a night the classifier could read. A defaulted `respiratoryRate: 14.0` on every row a repository reads back, and a literal `14.4` written by `AnalyzeSleepUseCase`, are both fabrications this repo has shipped. `HealthKitImporter` is the only source of a real respiratory rate. When adding a field to a domain entity, ask which path actually produces it; a defaulted number on a stored row is a fabricated reading. **`MetricDay.respiratoryRate` and `MetricDay.sleepPerformance` are the two fields in `MetricWeek.makeDay` passed through with no gate**, and the missing gate is the design rather than an omission to tidy: every other field there tests `hasMeasurement` (and RHR also `> 0`) because its column has a reserved zero, while respiratory rate is optional on the row *and* on the slot — so the optional already is the whole rule — and sleep performance is computed on read off a classified night, so there is no column and no zero to reserve. Adding either gate would let a week chart omit a mark the row directly above it prints — the same value, read through `RecoveryMetric` for respiratory rate and through `SleepSession.sleepPerformancePercentage` for sleep performance, both without a gate. The two are excluded from `hasAnyMeasurement` for opposite reasons: the sleep-performance exclusion is **redundant** (a day with a performance necessarily has a need, which is already in the list, the same as the VO₂ estimate), while the respiratory-rate one is **load-bearing** — a night can carry a respiratory rate with no HRV, so it is the field that could make an otherwise-empty day count as measured on a chart that draws neither quantity. Sleep performance's own fabrication risk is `SleepSession.sleepPerformancePercentage`'s `guard targetSleepNeedSeconds > 0 else { return 100 }`: unreachable on stored nights, because every imported row carrying a wake onset carries a need and the strap path computes one, but pinned by an assertion rather than left as a claim.
- `Package.swift` points the executable target at `path: "app"`, but the directory on disk is `App/`. These are the same directory on macOS's case-insensitive filesystem; be consistent with existing paths when adding files.
