## A shipped migration is frozen.

GRDB records applied migration *identifiers* and does not checksum bodies, so editing `v1`'s body changes nothing on any database that already ran it — and the schema silently stays wrong. Schema changes always go in a new `registerMigration` block. The per-version inventory — what `v2`…`v11` each added — is `docs/ARCHITECTURE.md` §2.B and is not repeated here. Note `addMissingColumns(to:columns:in:)` adds **nullable, undefaulted** columns only; a NOT NULL column needs an explicit `db.alter`, which is why `source` is nullable: NULL is the honest value for a row written before the column existed. **SQLite cannot relax `NOT NULL` in place, so `v18` does the staging dance — and the rename goes staging-onto-the-old-name, never the reverse.** The sequence per column is add a nullable `"<name>_unmeasured"`, `UPDATE` it from the old column, `DROP` the old, then `ALTER TABLE … RENAME COLUMN "<name>_unmeasured" TO "<name>"`. Written the other way round — renaming the *old* name onto the staging one — the statement runs after the old column has already been dropped and fails with `SQLite error 1: no such column: "strain"`, which `LocalDatabaseManager.init` turns into a `fatalError` at launch. It is loud and it is harmless (`GRDB` runs each migration in one transaction, so nothing is recorded in `grdb_migrations` and the schema is unchanged), but it is a launch crash rather than a test failure, so verify a new migration against a copy of a real database before trusting it. The `UPDATE` is mandatory and the add must not go through `addMissingColumns`: a bare `ADD` leaves every existing row NULL, silently converting 673 measured workouts into "nothing was measured", and that helper's skip-if-present guard would make a half-applied `v18` a no-op. A `workouts` table rebuild is the wrong route for a different reason — `workout_route_points` and `workout_splits` are `onDelete: .cascade` children, and GRDB runs migrations with foreign keys deferred, so dropping the parent orphans every child without firing the cascade.

## A `[Double]` property on a `Codable` record is a JSON-encoded `.text` column, and `Array` is not a `DatabaseValueConvertible`.

`biometric_samples.rrIntervalsMs` is `[Double]?` and GRDB stores it as a String, which is why `v8` declares the column `.text`. The array can therefore only ever be a *record property* — using it as a query binding is a compile error, and `BiometricSampleRecord.rrSeries` exists as the computed `[Double]` that is safe to pass around. Computed properties are invisible to `Codable` synthesis, so adding one to a record adds no column. The same record has **no `CodingKeys`**, so its property names *are* its column names — `rrIntervalsMs`, camelCase. `v12`'s `sleeps.sleep_stages` is `[SleepStageSegment]?` in the same shape, and one detail of that encoding is worth knowing before writing a fixture or a backfill by hand: **the `Date`s inside the JSON are unix milliseconds** (`1787372263000`), not seconds and not an Apple reference date, so a plausible-looking value in the wrong unit decodes to a year far away and the night silently loses its timeline.

## The test suite is not hermetic, but only in the migration sense — §6 opens the developer's real database, and does not write rows to it.

`ios/Tests/WhoopsyTestRunner` §6 builds `DIContainer(useMockBLE: true)`, and `DIContainer.init` takes `LocalDatabaseManager.shared` — the actual `~/Library/Application Support/whoopsy.sqlite` — whose `init` runs the migrator. So **running the suite applies any pending migration to that file**, which is how `v8`, `v9`, `v10` and `v11` land on a developer's database before the app is ever launched, and it is the one thing here that mutates real state. It does **not** leave §6's rows behind: measured, a full run leaves that file byte-identical (same mtime, same size, no `-wal`), because every section that writes builds its own `LocalDatabaseManager(inMemory: true)` — that is the shape to copy, and there is no path-injecting initialiser to reach the real one with on purpose (see the gotcha below). The practical consequence is narrow and worth stating exactly: a migration added in a turn is exercised against real data by the next suite run, so a failing one `fatalError`s there rather than at app launch — and a passing run tells you nothing about whether the rows you *expect* were written, since nothing was.

## The BLE streams are multicast.

`liveTelemetryStream` and `deviceStream` each hold a dictionary of continuations keyed by `UUID`, pruned in `onTermination` and guarded by a lock (the class is `@unchecked Sendable`, and these are written from caller threads and read from the BLE queue). A second subscriber must never orphan the first: the failure is silent — no error, no gap, just a `for await` that stops receiving, which is indistinguishable from a strap that went quiet. **A stream's reader count is a fact that changes, and deleting a screen changes it**: `StreamBiometricsUseCase` is driven from `HomeViewModel.load(for:)` alone, while `deviceStream` is read by `HomeViewModel.observeDevice()` and `DeviceViewModel.load()` — **one reader, not two, since the device screens were merged** — `motionStream` by `TrackStepsUseCase` and `LiveSessionUseCase`, and `stepCounterStream` by `TrackStepsUseCase` — reader counts that move whenever a screen does. The registry is not there for a named pair of readers: the count is per-stream, and the failure it prevents is silent. A new subscriber is safe to add, but anything that *yields* must go through `yieldTelemetry`/`yieldDevice` rather than touching the dictionary. **`DeviceViewModel.load()` takes a `guard task == nil` before assigning its subscription task, and that guard is a fix rather than tidying**: it used to assign unconditionally, so a second `load()` abandoned the first `for await` *without cancelling it* and left a continuation registered in the dictionary forever — the exact silent failure this bullet describes, and reachable because `MainContainerView` builds the view model once while `.task` fires on every push.

## The reconnect is an outstanding `connect`, never a timer.

`central.connect(peripheral, options: nil)` has no timeout, stays pending across suspension, and is what lets iOS wake or relaunch the app when the strap re-advertises. A retry loop — `DispatchQueue.asyncAfter`, a periodic scan, a `Task.sleep` *in place of* calling `connect` — does the opposite: at the instant the system suspends the app it leaves **nothing** outstanding, so the strap's return wakes nobody and the reconnect waits for the user to open the app. The community reference measured that failure as a reconnection 10 h 46 m 50 s late (#1413). So `didDisconnectPeripheral` answers a drop at once, `didFailToConnect` defers to `ReconnectPolicy` — delay only when the attempt failed within `fastFailureSeconds` (2 s), because that is the strap answering "no", and floor the next attempt `retryFloorSeconds` (30 s) from the attempt's *start* — and `disconnect()` sets `intentionalDisconnect` **before** cancelling the link, because the callback can arrive on the BLE queue mid-call and an unflagged callback brings the link straight back. **A drop is never delayed**, however recently the previous attempt failed: a link that was up is not a refusal, and applying the floor to one delays every ordinary recovery by half a minute. State restoration is the other half: `CBCentralManagerOptionRestoreIdentifierKey` means a process the system killed is relaunched into `willRestoreState` (documented to run **before** `centralManagerDidUpdateState`, hence the parked peripheral), and a restored already-connected peripheral **never fires `didConnect`** — so the manager seeds the device state and calls `discoverServices(nil)` itself, which re-runs `didDiscoverCharacteristicsFor` and with it the subscription and the enables. An inherited subscription can report `isNotifying == true` while delivering nothing (the community reference #613), so re-discovery rather than inheritance is the rule. **The one known limit**: `intentionalDisconnect` is in-memory, so a background relaunch after an explicit disconnect could re-arm; persisting the intent is a change nothing has asked for yet. **A 5.0/MG is the one generation whose retries are capped**: five consecutive fast refusals (`ReconnectPolicy.refusalCap`, the community reference #747) produce `.giveUp`, because the loop that produces them is the bond handshake's; a 4.0 is left uncapped because a 4.0 that keeps refusing is more likely out of range, which is precisely the state a standing connect exists to wait out. Every non-refusal event — a drop, a slow failure, a failure with no previous attempt — resets the count, or one bad streak would cap a link that later worked.

## A connected peripheral is not a producing strap, and the keep-alive's silence window must not count time the app spent suspended.

`CBPeripheral.state == .connected` says GATT is up; it says nothing about whether the strap's producers are still armed. A disconnect, a replaced subscription, or a 5.0/MG whose pre-bond enable was refused all leave a link that reports connected and carries nothing, so **every keep-alive rule reads data, never the connection state** — a check on `state` stays green over a strap sending nothing. `lastActivityAt` advances on every non-empty notification in `didUpdateValueFor` (including the `0x2A19` battery answer, which is why that one request doubles as the probe) and on a **successful** confirmed write in `didWriteValueFor` only; a failed one is not counted because the error can be a timeout delivered after the link is already gone. The tick is 30 s; the battery read is floored at 60 s; the silent-stream re-send is 15 s on a 4.0 (the Swift 4.0 client's `WhoopBleDataWatchdog.swift`) but **60 s on the 5.0/MG**, whose heart rate has documented at-rest lulls (the community reference #580/#1414, Edge #191) and whose healthy silence a 15 s rule would mistake for a stopped producer. The re-send has a **second** 60 s floor: noticing is not poking, and without it an every-30-s tick writes every tick to a strap that is not streaming. The liveness fuse is **120 s on a 4.0 and 600 s on the 5.0/MG** for the same family reason; past it the link is bounced with `cancelPeripheralConnection`, which `didDisconnectPeripheral` sees as an involuntary drop and answers with the ordinary standing connect — discovery then re-runs and re-arms the producers. A drain suppresses both the re-send and the bounce, because a flash write is exactly when a strap goes quiet and re-arming mid-drain is the documented way to lose its type-47 records; the battery read stays safe. **The suspension trap is new and silent**: a `DispatchSourceTimer` does not fire while the app is suspended, and on resume it fires once with hours of wall time behind it — read as silence, that bounces a healthy link every time the app comes forward. Both `restartKeepAliveWindow()` (called from `rearmConnection` on `.active`, the earlier of the two) and the tick's own 90 s gap check advance the window instead. Finally, `hasSentConnectCommands` guards the re-send: a 5.0/MG whose handshake was never acknowledged must not have its enables written pre-bond, and the fuse's bounce is that link's recovery.

## A sample row's `timestamp` is an arrival instant, not a beat time.

`WhoopBLEManager` stamps `Date()` when the notification is decoded, so the column records when the app heard about the beats, not when they happened. Within a notification the intervals in `rrIntervalsMs` are adjacent beats in exact order; **across** notifications they are not, and no column distinguishes them. Anything building a beat-to-beat tachogram must therefore reconstruct beat times by cumulative sum from the intervals themselves and must not trust `timestamp` as a per-beat time. `getSamples` orders by `timestamp` with `id` as the secondary key, which recovers insertion order for ties — that is arrival order, and it is the best the schema has. **RMSSD is a successive-difference statistic and inherits the same rule**: `HeartRateVariabilityMath.calculateRMSSD(fromRuns:)` takes one run per notification and differences each on its own, and `calculateRMSSD(from:)` forwards to it as a single run. Differencing across the seam is not a rounding error — two runs of beats alternating ±40 ms pool to 58.34 ms instead of 40.0, which scores as *calmer* than the night was. `AnalyzeSleepStressUseCase` uses the per-run entry point; `AnalyzeStressUseCase` still uses `compactMap(\.rrIntervalMs)` and so still differences beats that were never adjacent, which is recorded rather than silently fixed because correcting it moves the Stress Monitor's existing numbers.

## The proprietary BLE path was unvalidated until it was first run; on one 5.0 it is now validated end to end, and the 4.0 remains spec-only.

**What changed, measured on the owner's 5.0 with the device log in hand.** The just-works bond the whole 5.0 path was gated on **completed**: `5.0/MG handshake acknowledged — the link is bonded, so the producers are being armed now.` — the `.notice` line `WhoopBLEManager.didWriteValueFor` writes, reached after the confirmed `CLIENT_HELLO` write. With it, **live heart rate** (standard `0x2A37`), **R-R intervals** and **100 Hz motion** all arrived, and the app produced its first stored strap night. That answers §7 Q6 in the affirmative for this strap on this platform, and it means the decoder, the enable sequence and the reconcile-with-the-carrying-command path are no longer designs against a reference — they have run.

**The banked drain has since run, and it works end to end on this hardware.** `SYNC HISTORY` completed with `caught up to now, 59 record(s) in 1 batch(es)`; the records logged as `type=0x2F layout=18 payload=109 B`, which is `R18` — the heart-rate walk — and `LAST SYNC` moved to the drain's own instant, so request → batch → ACK → decode → store is proven as a chain. **A multi-batch drain has since been observed, and the paragraph below was written before it.** Measured across a night disconnected, a `0x1D REBOOT_STRAP`, a post-reboot 15-minute disconnected wear, and a hard Bluetooth-off window: **the archive holds two bursts of ~60 records stamped with a months-old date, and nothing else.** Pressing sync repeatedly gives that first burst, then the second, then `0 record(s) in 1 batch(es)` however many times it is pressed. The `HISTORY_END` marker was instrumented to rule out a misread live-edge test and it is not: `headAsUnix` decodes to the drain's own instant, so the strap is genuinely saying *this is the end of what I have*. **The drain, its ACK loop, its pointer, its marker and the (now correct) RTC all work; the strap is not appending.** So the live stream is the only recording path this app has on hardware it has seen, which is what captured the first night and why that night's 5-hour gap mattered. Treat "the strap banks 14 days" as the documented design rather than a measured property of this unit, until a drain returns a record stamped after a wear. **Corrected 2026-10-24 — the strap had been appending the whole time, and the drain could not read it.** Sending `0x9A TOGGLE_PERSISTENT_R21` (`[01, 01]`) from the device page turned a strap whose every drain for weeks answered `0 record(s)` into one that returned **8,984 real `R18` records** in the first session, then `caught up to now, 422 record(s) in 9 batch(es)` — records stamped hours *before* the command was sent. So the recording was never the problem and "the strap is not appending" was an inference from an empty read, which is the mistake this paragraph should now be read as an instance of: **a `0 record(s)` drain is evidence about the read path, not about the recorder.** After the toggle a ten-minute disconnected wear banked **25 records in 2 batches** — a count from the app's completion line, not a captured frame — and a 30-minute one banked **30**, which read as sparse until **2026-10-25's capture settled it the other way**: a worn strap with Bluetooth off for 32 minutes returned **2,003 records, one per second, no gaps** (`docs/TODO.md` §7.2). Those sparse windows were the strap off the wrist — and the same capture shows the rule from the
other end: a ten-minute shower with the strap off produced a **ten-minute hole in the history**,
`newest=16:15:39` to `first=16:25:42`, inside a drain that was otherwise one record a second. Whether those sparse records are `R18`, `R21`, or a mix was never read from that drain — the archive had rolled past it — but the later captures answer it for the worn case: every record is `R18` at one a second, from `layout=18` on each batch. The flag's battery cost is unmeasured and it is sent only from the manual control, never on connect. See `docs/TODO.md` §7.2 for the full sequence and §7.3 for what this retires. **What the multi-batch drain now establishes (2026-10-24):** one session returned `412 record(s) in 8 batch(es)`, `layout=18` throughout at one record per second, batch boundaries a minute apart, ending `liveEdge=true` — so the ACK loop, the stall guard and the live-edge rule are proven across batches, not just within one. It also showed the write rate depends on the link — **~1 `R18` per second while connected**, captured; **~1 record per minute while disconnected**, inferred from a 30-record completion line and the next drain's start stamp rather than from a frame, so treat that half as an estimate until an offline drain is caught in the archive. **What it does not establish is as important as what it does.** A night is only as good as what was recorded, and on this first night the live stream caught 55% of the window (samples stop partway through the night and resume in the morning — exactly the sleep the night was supposed to measure), which is the 5.0/MG at-rest lull the keep-alive exists for, and a suspended app's 30 s tick does not fire. **The clock set does latch, but the 5.0/MG needs both payload lengths to make it do so** — measured the same day. The 8-byte `[u32 epoch LE][u32 0]` form was written `.withResponse`, acknowledged by the strap, and left the RTC at `2000-01-03 20:25`; adding the **9-byte legacy form** (`[u32 epoch][5 × 0]`, the one 4.0 firmware 41.17.x requires) moved it to `drift -0.0 h`. The readout is the **motion record's own clock field**, not `GET_CLOCK`: that reply is undocumented, answered once and then not again, and its first four bytes decode to a number that is not the RTC. `WhoopBLEManager.noteStrapClock` logs the record field once a minute, which is the only continuous view of the strap's clock and is exactly the value a drain files history by. What this does **not** establish is that a drained record's timestamp is *right*: it is now set, which was the prerequisite, and the record's absolute time is still unverified until a drain is compared against wall time. **The drain does work and must be described that way** — request, batches, ACK, pointer, marker, decode and store are all proven on this unit; what is absent is the strap's writing. Never generalise the bond, the clock or the drain result to another strap, another generation or another firmware.



The framing matches `docs/BLE_PROTOCOL.md` §2 — the 4.0 envelope's header CRC8 is over the two length bytes only, `length` is the inner record plus four, and the inner record is `[type][seq][cmd][payload…]` with the CRC32 over the whole record — and the decoder verifies both checksums on inbound frames. **An assertion whose expected value is computed by the code under test is not an assertion**: an encoder and decoder that share a mistake round-trip against each other, and a check like `crc8Val >= 0` on a `UInt8` passes for a wrong polynomial, byte order and input alike. §1 of the runner pins the four published vectors from `docs/BLE_PROTOCOL.md` §2.1 plus layout assertions derived from the format. Length-based reassembly across BLE fragments is implemented (`WhoopFrameReassembler`), so a frame spanning several notifications is caught: it owns the **boundaries** and the decoder owns **validity**, and that split is what keeps the length and checksum rules in one place — do not restate either in the reassembler. Two things about it are easy to get wrong. The buffer is **per-connection** and must be `reset()` on connect *and* disconnect, because bytes held across a reconnect are prepended to the next stream's first frame and shift every field in it. And it must never be called without a profile: with no envelope there is no boundary to reassemble against, so the manager's `guard let profile = currentProfile` is what stops a strap whose envelope this build does not know from accumulating bytes forever. **That guard now passes for the 5.0 and the MG**, which is the intended change rather than a leak — the reassembler reads the declared length at the profile's own `lengthFieldOffset`, so a 5.0 notification is framed correctly and a complete 5.0 frame reaches the decoder and validates. A 5.0's write side is a separate question from its read side and is carried by a separate field (`syncOpcodes`, beside the 4.0's `commandOpcodes`) — see the strap-selection gotcha below, which is where that distinction lives. **The hardware evidence this section once lacked now exists**, and it lives in the strap-validation gotcha above: the 5.0 bond completed, frames arrived and decoded, and a night was stored. What the reassembler's own assertions still buy is coverage a capture cannot give — every boundary, both envelopes, and the false-boundary cases — rather than the first sighting of a real frame.

## A drain has two triggers, and a strap that answers nothing is retried.

**A connection returning is not the only moment a drain is owed.** `DrainCoordinator` is called from two
places: the device stream's `.connected` arm, and the scene's `.active` phase. The second exists because
a phone that stayed connected all night **never reconnects in the morning** — so the connect trigger
never fires, and an overnight wear sits in flash until someone presses `SYNC HISTORY`. Both triggers go
through one actor for two reasons. **`isRunning` makes it single-flight**, because a second drain
request supersedes the first — the manager concludes the interrupted session as `.aborted` and neither
finishes — and two triggers firing at once is exactly that. **And it retries a silent strap** up to three
times, five seconds apart: `0 record(s) in 1 batch(es)` is the strap answering *empty*, while **zero
batches** is the strap not answering at all, which was measured on 2026-10-24 seconds after a live
session ended and again on a reconnect. One retry lives on the automatic path only; the device page's
manual `SYNC HISTORY` remains the user's own retry.

## The drain is implemented and its ACK loop is not optional — that ordering is the whole rule.

A batch that is not acknowledged is re-sent forever, so a build holding the request byte and no loop leaves a strap looping, which is worse than a command it ignores. `HistoricalDrainSession` is the loop: `HISTORY_END` is acknowledged and the session **keeps listening**, `HISTORY_COMPLETE` ends it and is **not** acknowledged, and the eight-byte continuation token sits at the same frame offsets on both generations — `inner[13:21]` under the 4.0 and payload `[6,14)` under the 5.0 are the same bytes. Termination is `HISTORY_COMPLETE`, an idle timeout whose window comes **off the profile** (8 s for the 4.0, 60 s for the 5.0/MG), or catching up to the live edge, which is **two-sided** because a strap whose RTC is wrong is wrong in both directions. **Both generations' heart-rate records are walked**: `HeartRatePayloadDecoder` reads the 5.0/MG's `R18` and the 4.0's type 24, each at its own published offsets, and `MotionPayloadDecoder` walks the motion layouts, so a banked record reaches both `stepCounts` and `biometric_samples`. **The one gap left is the clock's read-back** — `GET_CLOCK` is sent on both generations and its reply is logged raw, never parsed — so a clock set having been written is still no evidence that it latched. `docs/TODO.md` §5 carries it. **No 16-byte walk of the type-24 record belongs here**: the record's own header is 96 bytes, so such a walk reads a record-counter byte as a heart rate and writes it to `biometric_samples` — a fabricated reading of exactly the kind the absence rule forbids. The type-24 walk reads the header's fields, not chunks of it. The capture plan that would settle the rest, in cheapest-first order, is `docs/BLE_PROTOCOL.md` §7.

## A record's stamp is only a clock on the 1 Hz layouts, and R26's is not one.

**A type-47 frame is a historical record; it is not necessarily a one-second record.** `R26` — the
research reference's *Pulse Information Packet*, 88 bytes — carries its own event time in the bytes the
1 Hz layouts keep their clock in. **Measured on 2026-10-26**, the owner's 5.0 delivered
`layout=26 ... expected=8 counted=8 ... types=2F×1,30×1,31×2,32×6` with the one record stamped
`00:18:04` after a batch that had already reached `00:18:43`, and the drain logged `stalled=1`.

**That is a fuse, not a log line.** Three consecutive stalled batches end a drain as `.idleTimeout`,
so a night with a few `R26` packets would stop a drain that was advancing perfectly well and report
it as stalled. The live edge is the same field trusted the other way: an `R26` stamped *now* in a
burst after a 1 Hz record would end a drain whose backlog is still behind it. The rule is one gate —
`HistoricalDrainSession.timestampedLayouts` (18, 21 and the 4.0's 24) — applied inside
`recordTimestamp`, so both readers inherit it. **The frame still counts**: the count gate asks how
many frames a burst carried and the clock asks where the drain is, and answering the first does not
entitle a record to answer the second. §16 pins a four-burst R26 run that must not stall, an `R26`
stamped now that must not finish, and the same frame counting toward its burst.

## A Gen 5 burst declares its frame count, its membership is six types, and Gen 4's same offset is a different field.

**A `HISTORY_END` on a 5.0 carries an `expected_count` — a u32 LE at `inner[9]`, payload 6 here — and a
client that counts it wrongly makes the strap re-offer the same burst forever.** [reported] The
research reference's `PROTOCOL-GEN5.md` §8 gives the membership explicitly: count complete frames
**once each, for types 47, 48, 50, 53, 54 and 55** — 49 is the marker carrying the count, 51/52 are
the IMU stream, and revision and byte length are irrelevant. The matching negative result is `0x17` with body
`00 00` on this generation (a 4.0's is a single `00`), the burst size falls from 50 to 10 after five
consecutive failures, and fifteen is the terminal boundary the client aborts from with `0x14`.

**The trap is that the 4.0 publishes the same `inner[9]` as "a record-id / batch counter (not
echoed)".** One offset, two meanings, chosen by the envelope — so the read is gated on
`WhoopProtocolProfile.declaresBurstFrameCount`, which follows `headerChecksum` as every other
generation test here does. A validator that read that field on a 4.0 would compare a batch counter
against a frame count and refuse every burst the strap sent.

**Measured 2026-10-25: the premise holds and the mechanism does not follow.** The owner's capture,
with a per-batch histogram in place, showed bursts carrying `types=2F×45,30×2,31×2,32×8` and
`2F×30,31×2,32×40` — types 48 and 50 really do ride in bursts, so a 47-only count is short by the event
and console-log traffic. But **this app only ever sends the positive result**, so the band has never had
a count of ours to disagree with, and the re-offers in that same capture cannot be the gate reacting to
our arithmetic. What the gate actually buys is the case nobody can see today: a burst damaged in
transit is acknowledged, the strap trims past records this phone never stored, and its ring buffer is
the only copy. That is why `HistoricalDrainSession` now counts the six types and logs `expected=` /
`counted=` on every `DRAIN_BATCH` line and **still acknowledges success** — enforcement waits on one
capture showing the two agreeing on an ordinary burst, because a validator whose membership is wrong
refuses good bursts forever. §16 pins the membership set, the payload-6 offset, an agreeing burst, a
short one that is *still acknowledged*, and a 4.0 marker that reads no count at all.

**The instrumentation then answered its own question, and the answer was not the one the hypothesis
wanted.** On 2026-10-25 the owner's 5.0 returned 53 consecutive bursts with `expected == counted` on
**every one** — `2F×44,30×3,32×20` against 67, `2F×20,30×1,32×36` against 57, every `2F×60,31×2`
against 60, and the `31` pair never counted in any of them. The membership is right and the count gate
is **ruled out as the cause of the re-offers**: the strap re-sent bursts this phone had already
received, with the declared count agreeing both times, so nothing was lost — the rewind is in the
trim cursor, not in the counting.

## A protocol default implementation beats the conforming type's own method through an existential, silently.

**Found on 2026-10-24 while adding sleep provenance, and it had been hiding a dead delete.** `SleepRepository` declared `deleteSleepSession(for:)` in an extension with an empty body — "most readers of this protocol do not own storage" — while `GRDBSleepRepository` declared a real one that removed the row. Called on the concrete type the real method ran; called through `any SleepRepository`, which is how every screen holds it, the **default** ran. The sleep page's "remove a provisional night the classifier no longer stands behind" therefore never deleted anything, and nothing anywhere said so: the screen set its own `session` to `nil` and drew the absence, so the picture agreed with the intent while the row stayed on disk.

**The rule: a requirement whose body is empty is not a convenience, it is a silent override.** A default belongs on a protocol only where *every* conformer should behave identically — the `saveSleepSession(_:)` and `getSleepHistory(days:)` conveniences here, which forward to the real requirement. Where the answer differs per type, the requirement has no body and the compiler makes each one say what it means; a fixture that owns nothing answers with an empty method of its own, which is a statement rather than an inherited silence. §15's keep-versus-delete block is the assertion that would have caught it: it deletes through the same existential the page uses and reads the row back.

## A zone row's time comes from exactly one producer, and the page's grey average is measured samples only.

**Two producers can name a session's time in a heart-rate band, and a row uses one of them.** An
imported session carries WHOOP's own `HR Zone n %` block, and its time is that share of the session's
length (`WorkoutSession.zoneSeconds(_:)`). A session this app recorded carries no block at all — the
live path writes `hrZonePercents: nil` on purpose, because that column is WHOOP's producer — so its
time is `ZoneTimeMath.totals` folded from its own heart-rate samples. **Measured wins when both happen
to exist**, because it is this session's readings rather than a percentage rounded before it was
stored; a row averaging the two would be a figure from neither producer.

**The prior-session average is the same rule applied to history, and it is where the trap is.** The
grey mark on each row is the mean time in that band over the last ten sessions of the same activity —
the window `ActivityBaseline.window` already owns — and it is built **only** from `ZoneTimeMath.Totals`.
An imported prior has a percentage block and no samples, so it contributes nothing; letting its share
into the mean would mix WHOOP's producer with this app's inside one number, which is exactly the defect
`RecoveryScoring` avoids by never mixing a computed sleep need with an imported one. The mark appears
once `RecoveryScoring.minimumBaselineDays` (3) priors have samples, and never beside a row that has no
time of its own — a comparison with one side missing is withheld, not drawn.

**The date this was measured:** the page drew five dashes for every recorded session until 2026-10-24,
when a football session's own five times arrived and the fold that produced them was found to have been
written three times — in `LiveSessionAccumulator`, in `StrainDayMath`, and (about to be) in the page.
It is one function now, `ZoneTimeMath.delta`, and §4 cross-checks the completed-stream fold against the
live accumulator so a fourth transcription fails rather than agrees.

## A stored night records the rule that classified it and the input it saw, and is re-read rather than re-analysed.

**`v38` adds the other half of that sentence: the *evidence* the rule ran on.** Two signals can
evidence the same stillness — `R21` motion epochs while a phone is connected, and the accelerometer
carried by `R18` for a phone-away night, because the strap banks no `R21` in flash. Both run the same
stager, so `algorithm` is unchanged and says nothing about support; `sleeps.stillness_spine` does.
A row that recorded only the version would make a night of per-second means look identical to one of
100 Hz epochs, which is the provenance defect this whole entry exists to prevent.

**The two sources are merged window by window, and the first version chose one for the whole night.**
It read "samples only if no motion epoch exists at all", on the reasoning that motion is the stronger
signal. Measured 2026-10-27, on the night of 2026-10-26/27: the phone was connected for two evening
hours and away for the rest, so 242 `R21` epochs existed — every one of them awake — and the thirteen
hours of `R18` stillness that held the actual night was discarded. The classifier reported
`epochs=242 asleep=2` and refused a night it had all the evidence for; presence of a source in one
part of the window says nothing about the rest of it. `AnalyzeSleepUseCase.stillnessWindows` now keys
both onto `MotionEpochGrid.index` and lets `motion` overwrite `samples` where both exist, so the
choice belongs to the thirty seconds. A night the merge assembled from both is recorded as
`stillness_spine = merged` — one value per window is not enough to describe a night that straddled
them, and the row should not have to pick one. `docs/ALGORITHMS.md` §4 carries what this replaced —
an HR-only fallback and a live IMU stream, both of which the community reference's open issues
propose for straps that cannot get motion — and why neither is needed when the record is banked.

**A night is a decision, not a reading.** `sleeps` rows were classified by `AnalyzeSleepUseCase` — onset, staging, need — and until `v37` the row recorded nothing about *which* rule made it or *how much input* it was made from. That left the sleep page with one way to know whether a stored night met the current stager: recompute it, on every open, and overwrite the row. The cost was a page that waited for a full classification every time; the danger was worse. An inconclusive run over a night whose drain had not finished — no motion yet, fewer samples than an epoch — is a legitimate "no night" answer, and the old code treated it as a verdict and deleted the row.

**`v37` gives the row the same pair `v35` gave `strains`:** `algorithm` (the rule, `SleepAlgorithm.current`) and `scored_through` (the newest epoch end or sample instant the classification actually read, taken from the arrays it classified rather than re-read). The page now answers three questions in order — imported? never touch it; version matches and the analyzer can see nothing newer? read the row; otherwise? classify again. A re-classification that comes back empty **keeps** the stored night unless the row's version is one this build no longer has, which is the only case where today's rule is entitled to deny yesterday's night. §15 pins both halves: the watermark rule as a pure function, and the keep-versus-delete pair through the real page and a real database.

**"New input" means input inside the night, and the first version meant anywhere in the morning.**
`SleepReclassification.isOwed` compared the row's `scoredThrough` watermark with the newest sample in the
whole 21:00 → 10:00 read window, so every sample after waking made the stored night owed. Measured
2026-10-27: `NIGHTS … owed=true saved` twice inside two minutes with identical start and end, a full
reclassification on every foreground and every open of the sleep page — each folding tens of thousands of
samples to reproduce the same night — and each save published to Home, which redrew the ring. An hour of
awake samples cannot change a night; a night ends when the wrist starts moving. The rule now takes the
stored `endTime` and counts input inside it, or within `extensionGraceSeconds` (the classifier's own
ten-minute run) after it. **And a re-classification that reproduced the same night is no longer
published** — `execute` always writes, because advancing the watermark is what stops the next check, but
`SleepSession.drawsSame(as:)` compares what a screen draws (not `id` or `scoredThrough`, which
`Equatable` would trip on) and only a changed drawing reaches `nightUpdates`. The sleep page also stopped
clearing `week` and `sleepScore` before its reads: the page is pushed for one day and can never load two,
so the clear only blanked the chart and the ring for the length of the load.

**The grace had a blind spot: a night that ended because its data did, rather than because its wearer
woke.** Measured 2026-10-28, a night saved as 23:05–23:59 stayed a 54-minute night while seven hours of
later records arrived — the gate called all of it wake time. Two attempts to infer the difference from the
row's own instants both failed, and the capture says why: the stored watermark was **07:10** while the end
was **23:59**. The watermark is `inputEdge`, the max of the newest sample and the newest epoch, so it says
*what input the run read*, not *what could change the night* — and a night cannot grow on heart-rate-only
samples.

**The fix is to record the fact rather than infer it.** `v40` adds `sleeps.ended_at_data_edge`: the
classifier knows whether its retaining run reached the last epoch it was handed (the data edge) or stopped
before it (a detected wake), and that one boolean is the discriminator. `isOwed` then answers by record —
`true` means any newer input still belongs to the night however late it arrives, `false` takes the grace,
and `nil` (every row written before `v40`) is owed one re-classification, which stamps the verdict. Nothing
is backfilled: guessing `false` would restore exactly the bug. §15 pins all three branches, and the
`NIGHTS check day=… watermark=… end=… edge=… dataEdge=… owed=…` line puts the whole decision in
`capture.txt`.

**The lesson repeats the entry above it:** a field derived from the same inputs as the value it guards
cannot independently vouch for that value. The watermark described the night's input, and the night's end
described its output; the missing fact — *did the input stop, or did the night?* — had to be stored on its
own.

**The column names are snake_case here and camelCase on `strains`,** and that is `CodingKeys` rather than taste: `SleepRecord` declares them, so `scored_through` is the column; `StrainRecord` declares none, so `scoredThrough` is. A migration that guesses wrong creates a column nothing writes and the insert fails at launch with `no such column`.

## A worn strap banks at full rate with no phone; a strap off the wrist banks almost nothing.

**Measured 2026-10-25, and it inverted the reading this repo had been carrying.** Three early windows —
30 records over 30 minutes, 25 over ~10, 15 over 10–15 — looked like a sparse offline recorder, and the
`0x9A` flag's name (`TOGGLE_PERSISTENT_R21`) made "motion-only capture" the obvious explanation. Then a
30-minute wear with **Bluetooth off** came back from `Documents/capture.txt` as **2,003 records over 32
minutes, sixty a minute, with no gap in the stamps and `stalled=0` throughout**. The variable was never
the link: it was whether the strap was **on a wrist**. The optical engine feeds the recorder, and a strap
on a table writes almost nothing however it is paired.

**The consequence is the answer to "will it sync when I get back": yes, at full fidelity.** A strap worn
through a football match or a night with the phone in airplane mode has a complete `R18` per second
waiting in flash, and the drain returns it as one live-edge session. **The consequence for testing is
that a count proves nothing without the wear.** Every sparse figure in this repo's history was taken
without recording whether the strap was on a body — the next such test should state that first.

## A `0 record(s)` drain is evidence about the read path, not about the recorder.

**Measured 2026-10-24 on the owner's 5.0, firmware 50.42.1.0, and the reversal is the point.** For weeks every drain from that strap answered `0 record(s) in 1 batch(es)` — across a night disconnected, a reboot, a hard Bluetooth-off window and a 15-minute disconnected wear, with the link healthy and the RTC correct — and the natural reading was that the flash recorder had stopped. It had not. Sending `0x9A TOGGLE_PERSISTENT_R21` with the body `[01, 01]` (the revision-1 "persistent" form) from the device page turned the same strap into one that returned **8,984 real `R18` records** in its first drain, and the next sync completed `caught up to now, 422 record(s) in 9 batch(es)`. The drained records carried stamps from **hours before the command was sent**, so nothing was ever restarted — the history was there and the read path could not reach it, either because the flag gates the read or because sending it reset the read pointer. Which of the two is unresolved, and they differ in consequence: a gate is a setting that must be set, a pointer reset is a one-shot. Two further findings from the same run belong here. **Offline capture looks motion-only**: ten minutes disconnected and worn produced **25 records in 2 batches**, one per ~24 s, which is `R21` motion cadence and not `R18`'s one per second (~600 expected) — consistent with the opcode's name, `TOGGLE_PERSISTENT_R21`. And **`0x22 GET_DATA_RANGE` is sent and answered by nothing** on this firmware, so a `Data range:` line that never prints is not evidence of an empty buffer either. The transferable rule: an empty drain bounds what the app could read, and says nothing about what the strap wrote. Never conclude a recorder is dead from a drain alone — a successful read of even one record stamped after the wear in question is the only evidence that separates the two, and the flag's battery cost is still unmeasured, so `0x9A` is sent only from the manual control and never on connect. The full sequence is `docs/TODO.md` §7.2.

## The oxygen candidate is instrumentation, and no screen or row may read it as a measurement.

The community reference's `spo2_candidate_82` is a decompile-sourced reading of the official app's `spo2_pct`: the 5.0/MG `R18` record's **frame byte 82**, which is payload `[71]` under the 11-byte origin, with the sleep-state byte beside it at frame 81 / payload 70 and neighbours to scan at frame 74–92 / payload 63–81. It reads as a percentage **on one strap**: eight nights tracked the app at +0.99 with ~0.4 points' mean error, and byte 82 was the only offset in its window to win the specificity scan. It does **not** on another: two nights on a second device moved in the opposite direction, which is why the community reference keeps it behind instrumentation and why this app does too. **The tri-mode gate is what makes the byte legible**: 70–100 is a reading, bit 7 (`0x80`, `0xA0`) is a saturation sentinel, another sub-70 nonzero value is a diagnostic code, 0 is the awake/idle state, and 101–127 is unclassified. Printing the raw byte would turn a diagnostic into a desaturation and a sentinel into 160 %. `Spo2CandidateProbe` classifies every drained record and `Spo2CandidateAccumulator` writes at most three raw lines (value, sleep state and the nineteen neighbours) plus one summary (per-band counts, in-band mean/range, first/last stamp) to `.notice` and `Documents/spo2-candidate.txt`; **it writes no `BiometricSample.spO2Percentage`, no `recoveries.spo2_percentage` and no screen value**, and the import's stored `spo2_percentage` column stays what the official app recorded rather than anything derived here. Promotion needs **≥2 devices × ≥5 paired nights, Pearson r ≥ 0.7, MAE ≤ 1.0 points**, with byte 82 still winning the 74–92 scan on each. **The 4.0 has no path at all**: its type-24 record carries raw red/IR ADC scalars at record `[31]`/`[66]` with no wavelength labels and no AC/DC waveform, so ratio-of-ratios cannot be formed, and no `GET_SPO2` command exists on either generation. The `CaptureLog` sink is capped and rotating at ~64 KB and writes into the app's own Documents; the two `Info.plist` sharing keys expose that directory in Files and add no network path. `docs/BLE_PROTOCOL.md` §4 carries the offsets and the validation bar.

**The same rule now covers a second candidate.** The community reference names a skin-temperature `u16`
(raw ÷ 100, 5–45 °C) at "byte 73" of the same record, and the two offset conventions this codebase
already uses disagree about where that byte is: the accelerometer is *body 24* at payload 34
(`payload = 10 + body`), the oxygen candidate *frame 82* at payload 71 (`payload = frame − 11`). So
`SkinTemperatureCandidateProbe` reads **both** origins (payload 83 and payload 62), gates each on the
plausible range and logs both to `Documents/skin-temperature-candidate.txt` with the record's stamp —
it writes no sample, no row and no screen value. Picking one origin would produce a number that still
reads as a temperature; two candidates and the gate are what make the wrong one visible. One drained
night against a known reading settles it, and then the field is one line in
`HeartRatePayloadDecoder`.

## A drained record's timestamp is verified as a field and unverified as a value, and the failure files history onto a wrong day rather than onto no day.

`[7:11]` of the type-24 record is a u32 unix time, but the strap's RTC is set by `0x0A SET_CLOCK`, and the 4.0 reference's event enum carries type 13 `RTC_LOST` ("battery fully died — clock reset") — so a battery-flat strap stamps every record with a wrong offset and **nothing in the record shows it**. Check `[7:11]` against wall time per strap before trusting it; `docs/BLE_PROTOCOL.md` §7 lists that as the capture's most consequential question. **Setting the clock is a prerequisite for the drain rather than a refinement of it, because the payload length is firmware-specific and load-bearing.** `WhoopCommandFrames.setClockFrames` sends **both** 4.0 forms — 8-byte `[u32 seconds][u32 subseconds in 1/32768 s]` for newer firmware and 9-byte legacy for fw 41.17.x, which ignores the 8-byte form outright — because a wrong-length set is **acknowledged but not latched**, and a strap with an invalid RTC **stops banking sensor data to flash entirely**, surfacing as a strap that looks connected and healthy while writing nothing. Published clients disagree on the length (4, 5, 8 and 9 bytes all appear in the wild), so settle it per strap. **Sending a clock set is not checking it**: the read-back is command **11 `GET_CLOCK`** on both generations — `0x0B` under either envelope, the pair being 10/11 and not `0x92`/`0x93` — it is sent at every drain and in a 5.0/MG's connect pass, and **nothing in this app decodes the reply**, so no path may claim a clock latched. **And a *live* record never trusts the stamp at all.** `MotionPayloadDecoder.decode` keys a **live** frame — the 4.0's type 43, the 5.0/MG's packet 43 — on the **arrival instant**, and only a **banked** record (the 5.0/MG's packet 47) on the strap's own clock, because a banked record is the one thing that has no other way onto the day it was measured while a live one arrives as it is measured. That split was measured the hard way on 2026-10-20: a real 5.0 with a lost RTC stamped every live record `2000-01-03`, `TrackStepsUseCase` faithfully wrote **22,702 steps under that day**, and Home's `STEPS` tile drew `—` through the whole walk while the counter was working perfectly. The tile was never the bug; the day key was. **One opcode must never be sent and one is a deliberate exception.** `0x19 FORCE_TRIM` is a flash erase (destructive — the drain is non-destructive by design and needs no trim; issuing one to "clear the backlog" destroys history including what has not been drained) and no path in this app builds it. `0x9A TOGGLE_PERSISTENT_R21` forces the optical engine on across reboots, burning battery until a `REBOOT_STRAP` — and since 2026-10-24 it has **one manual control** on the device page's ADVANCED tab, the experiment `docs/TODO.md` §7.2 records. The byte is in neither opcode table, `WhoopCommandFrames.persistentR21` is its only builder, and §16 sweeps the tables for it — so a second caller has to come through a name that says what it does.

## A strap's advertised name is a proprietary command, not GAP's `0x2A00`.

**The reason it looks untouchable is that CoreBluetooth hides the Generic Access service from every app.** `0x1800` and `0x1801` are reserved, so no third-party iOS app can read or write Device Name — which is why the name on the device page seemed to be a thing only the WHOOP app could set. It is not GAP at all: it is a command on the proprietary surface. [reported] The community reference's command matrix gives **ID 140/141** for 5.0/MG (`[revision=1][length][name…]`, 0–15 bytes) and **ID 77/76** for 4.0 (two reserved bytes then a 16-byte NUL-terminated field), with the 5.0 table marking the 4.0 ids unsupported. **[captured] 2026-10-25: ID 140 was applied on this project's own 5.0 (firmware 50.42.1.0)** — measured from the `NAME` row, with **the advertisement lagging the write by a few minutes**. So a sent frame is still a request and not a stored name, and an immediate scan proves nothing because the phone answers from CoreBluetooth's cache: the status line says *requested* rather than *renamed* because the strap gives no acknowledgement this app can read, not because the write is believed to fail.

## Which strap is connected is a stored choice, and a guess must never override it.

`WhoopHardwareGeneration` has five cases — `whoop4`, `whoop5`, `whoop5MG`, `standardBleHR`, `simulator` — and `selectableModels` derives the three a user may pick. The choice is kept per **peripheral identifier** in `UserDefaults` (`UserDefaultsStrapModelRepository`), because a strap advertising no name arrives as `"WHOOP Strap"`, and a name heuristic — `advertisedName.contains("5") ? .whoop5 : .whoop4` — cannot tell a 5.0 from a 5.0 MG and calls an unnamed 5.0 a 4.0. The precedence rule is `WhoopBLEManager.resolvedGeneration(stored:advertisedName:)`, a **public static** taking both inputs so the suite can assert it without a `CBCentralManager` (constructing one raises a system Bluetooth prompt mid-run). Three things about the wiring are load-bearing. `refreshStrapModels()` must run **before** `startScanning()`, because `didDiscover` is a synchronous CoreBluetooth callback and cannot `await` the store. `didConnect`/`didDisconnect` go through `resolvedDevice(for:)` rather than building a bare `WhoopDevice` — whose `hardwareGeneration` defaults to `.whoop4` — so the discovery-time resolution is not silently replaced by a literal the moment the strap connects. And `WhoopBLEManager.sendCommand` is the **choke point**: it refuses to write unless `currentProfile.canTransmitCommands`, because a 4.0-framed command written to a 5.0 strap is a *different message* rather than a rejected one. **The reason is the envelope, not the type numbering**: the two references write the same eight type roles in hex and in decimal respectively, and all eight correspond exactly, so the numbering is shared and the envelope is the discriminator. **`canTransmitCommands` tests two opcode tables and not the envelope**: the read side and the write side do not have the same answer, and a guard on the envelope would permit 5.0 writes on the grounds that inbound 5.0 frames are legible — a fact about reading, not about writing. `profile(for:)` answers `nil` for `.standardBleHR` and `.simulator` only; the two tables are `commandOpcodes` (4.0) and `syncOpcodes` (5.0/MG), and the second exists because **the two generations share only part of their numbering** — `0x16`, `0x17`, `0x22`, `0x14` and `0x21` are the same byte under both envelopes, and the rest are each generation's own. Do not merge them into one table, and do not "fall back" to the 4.0 path for a generation whose table this build does not hold: a frame with a valid envelope and another generation's opcode is a *different command*, which a strap accepts and acts on.

**What no opcode table can say is whether a strap will answer, and the 5.0's obstacle is not its opcodes.** Its command characteristic refuses writes and notifies until the link is **encrypted** (`CBATTError.insufficientAuthentication` / `.insufficientEncryption`), and the bond is established by **just-works pairing** — the community reference writes the static `CLIENT_HELLO` `.withResponse`, which triggers it, and ships that path on macOS **and** iOS, so the community reference's source does **not** say macOS cannot complete the bond. The APK reading's iOS success is the weaker shape — it reuses the bond the official WHOOP app already made, via `retrieveConnectedPeripherals` — and CoreBluetooth exposes no bond state for a client to check whether it is already bonded. So the iOS write path is a bond a third-party app **can** establish; the honest remaining unknown is that the failure is silent (an unanswered `CLIENT_HELLO` drops the link with no error) and Apple cannot tell the client whether it is bonded. It must not be described as resolved further in either direction than that. `DeviceViewModel.protocolCaveat` is where that reaches a screen — on the merged page's `ADVANCED` tab: it says a *different* sentence per generation, because the 4.0's open question is unvalidatedness alone while the 5.0's has the bond on top — and one generic sentence would hide the reason a 5.0 sync is the more likely of the two to do nothing. `WhoopProtocolCatalog.supportsProprietarySync` asks `canTransmitCommands`'s question, and answers `true` for all three WHOOP models.

**The name heuristic was the weak rung, and on 2026-10-25 it was replaced from above.** A strap
advertising as `Alex WHOOP` has no digit in its name, so `advertisedName.contains("5")` called a 5.0 a
**4.0** — which is what the device page showed whenever it rendered before service discovery. The
strap answers for itself in `0x2A24`: **`5.0`**, with `WG50_r52` for the hardware revision and
`50.42.1.0` for the firmware, read from a Mac acting as a second central. So the ladder is now
**stored choice → observed service list → model string → advertised name**, the model string being the
only rung that separates a 5.0 from a 5.0 MG, and it is persisted when the user has never chosen a
model — evidence, not a guess, so writing it does not override a choice. **The picker is gone with it**:
it existed because only the owner could answer a question the hardware now answers itself.

## Column naming differs per table, and `CodingKeys` is the only thing that decides it.

`RecoveryRecord` declares `CodingKeys` mapping its properties to **snake_case** columns (`recovery_score`, `hrv_value_ms`), so a new property needs a matching case there. `StrainRecord` has **no** `CodingKeys`, so its property names *are* its column names and `strains`' columns are **camelCase** (`strainScore`, `averageHeartRate`, `hasMeasurement`). Check `pragma_table_info(<table>)` or the record's `CodingKeys` before naming a column in a migration: a wrong name raises `SQLite error 1: no such column` at launch, and a failing migration `fatalError`s, so the whole app goes with it.

## `naps` follows `workouts`, not `sleeps`, and a nap's day is its onset while a night's is its wake.

A day holds one night and can hold several naps, so `naps` is keyed on `id` with `date` an ordinary indexed column, exactly as `workouts` is — a `date` primary key would make the second nap overwrite the first. The day key is still snapped centrally by `LocalDatabaseManager.saveNap`, so a nap written at a raw 17:33 is found on its day and not on a neighbouring one. **The key itself is the opposite of the night table's**: a night is filed under the morning it ended on, a nap under the day it was *taken* on, and the difference is a whole day — measured against the bundled export, keying the eight naps on their wake onset moves the two that cross midnight (2024-02-05 22:13 → 02:34, 2024-08-26 23:48 → 02:36) onto a day nothing reads, so only six are reachable. **The `id` is the nap's own start instant as a string, never a `UUID()`** — this is the one place `SleepNap` deliberately differs from `SleepSession`, whose fresh-per-init `UUID` is why two reads of one night never compare equal. A `UUID()` here would write eight more rows on every press of the import button, since GRDB's `save` is INSERT-or-UPDATE *by primary key*. **A nap is not a night and carries no performance**: WHOOP's own `Sleep performance %` for the export's eight naps is 6–43 because its denominator is a full night's need (526–617 min) against 33–237 min of actual nap, so reading it as a performance would file a deliberate 33-minute nap as a 6% night. `SleepNap` therefore holds only its window and its asleep duration. **The three rows the sleep-performance screen gained are all ungated readings, and that is the point of them**: sleep debt and respiratory rate are optional on the row *and* on the value, and neither joins `SleepBand` — WHOOP publishes no anchor for a respiratory rate, and a running deficit is not monotone in the direction the banded rows share — so both render as plain figures in `Theme.textPrimary`. A nap is drawn as an **absent row, not a dash**, when the day has none: not napping is an ordinary answer rather than an unmeasured one.

## `receptive_inactivities` has one read and no `covering:` sibling, and its day comes from the screen rather than from its own optional time.

Every other table in this family that can be underway at a day's midnight carries a second reader — `getWorkouts(covering:)` beside `getWorkouts(for:)` — because an 86-hour fast draws a row on all five of its days. A receptive inactivity has **no end**, so it has no overlap, and a `covering:` read here would be a second way to ask one question with nothing to double-count. **The day is the one being viewed and not the one its start implies**: `started_at` is nullable and `date` is `NOT NULL`, so unlike `saveNap` — whose `date` is derivable from its start — there is nothing to derive the day *from* when no time was given at all. The invariant that removes the reconciliation is one sentence: **the start time is a time-of-day on the day being viewed**, and the picker's hour and minute are rebuilt onto the selected day's year/month/day before the write. **`v22_receptive_inactivity_note` adds a nullable, undefaulted `note`, and that column is read *and stored* — the entry's prose is the row's value *and* the input its id is derived from.** The derivation is what keeps the import idempotent: these records carry no producer id, `ReceptiveInactivity.init` declares `id: UUID = UUID()`, and GRDB's `save` is INSERT-or-UPDATE *by primary key*, so an importer calling the convenience initialiser per record appends 62 more rows on every press and reads back perfectly well while doing it. `InactivityParser.identifier(date:type:note:)` therefore computes a UUIDv5 over a pinned namespace and `"<yyyy-MM-dd>|<type>|<note>"`, and three things follow that a `UUID()` or a string id would not give: the id is reproducible outside Swift (Python's `uuid.uuid5`, which is how §21 pins two of them as literals computed independently of the code under test), it needs no change to the file or the generator, and it is a **real** UUID string — `GRDBReceptiveInactivityRepository.makeActivities` drops any stored id that will not round-trip through `UUID(uuidString:)`, so a string id would write 62 rows, read back none, and report a successful import of nothing. **The import deliberately skips no day**, on `ZeroFastingImporter`'s rule, because a derived id is disjoint from every other producer's — the cost is that re-importing recomputes the same id from the unchanged file and `save`s the file's original text back over a hand-edit, silently, which is the same asymmetry the fasts import already carries and which the button's caption states rather than leaving to be found; and because the note is an identity input, a *re-worded* entry now leaves its predecessor on the day beside it as a visible duplicate rather than an indistinguishable one. **`type` is read rather than required to be `"dream"`** — it goes through `ReceptiveInactivityCatalog.name(for:)`, so a future producer carrying `type: "meditation"` joins this path instead of needing a second one. **The `"yyyy-MM-dd"` parse is the sharpest trap in the parser**: a `DateFormatter` left on its UTC default turns `"2023-07-23"` into `2023-07-23T00:00Z`, which `Calendar.current.startOfDay` in a negative-offset zone snaps back to the **22nd** — every record a day early, silently, on a screen that looks right. It sets `locale = en_US_POSIX` and `timeZone = .current`, then re-snaps through `startOfDay`, and §21's per-row "this date is the start of its own day" assertion is what fails if either half goes.

## `workouts` breaks the day-key rule, and it must stay broken.

`recoveries`, `sleeps` and `strains` are primary-keyed on `date` snapped to `startOfDay` because a day holds one of each. A day can hold **several** workouts, so `workouts` is keyed on `id` (a UUID string) with `date` as an ordinary indexed lookup column, and `getWorkouts(for:)` returns an array rather than an optional. The snap still applies — `LocalDatabaseManager.saveWorkout` snaps `date` centrally like its `saveRecovery`/`saveSleep`/`saveStrain` siblings — so a session started at 17:33 is filed under that day. Do not "normalise" this table onto a `date` primary key; that would make a second session on one day overwrite the first. `DIContainer` wires `GRDBWorkoutRepository`; there is no in-memory workout store. **An imported session's id is derived from its own two instants rather than being a `UUID()` or a string**, and both alternatives are traps here that the naps table does not share: a fresh `UUID()` per run appends 673 more rows on every press of the import button, because GRDB's `save` is INSERT-or-UPDATE *by primary key*; and the ISO-string trick `SleepNap` uses is silently discarded, because `GRDBWorkoutRepository.makeSessions` skips any row whose id is not a UUID — so a string id writes 673 rows, reads back none, and reports a successful import of nothing.

## There are two reads over that `date` column, they answer different questions, and they must not be merged.

`getWorkouts(for:)` — `LocalDatabaseManager.getWorkouts(on:)` — is *"which day is this row filed on"* and matches the snapped key alone. `getWorkouts(covering:)` is *"which sessions were underway on this day"*: a **half-open overlap**, `date <= day.startOfDay` **and** `ended_at > day.startOfDay` as two chained filters, because this file carries no `OR` anywhere. Home's `ACTIVITIES` card asks the second, and that is the whole of the feature — an 86-hour fast draws a row on all five of its days rather than on one. The strain page's zone rows, `WorkoutZoneTime.aggregate`, `StrainViewModel.zoneBaselines` and `getWorkoutHistory` all keep asking the first. **The reason is a double count before it is a mis-key, and the mis-key is the corollary.** `WorkoutSession.zoneSeconds(_:)` scales WHOOP's share by the session's **whole** `durationSeconds`, so a covering read feeding a zone consumer would add the same measured time to *both* the day a cross-midnight workout starts on and the day it ends on — and `WorkoutZoneTime.aggregate` keys a day's whole array off `workouts.first?.startedAt.startOfDay`, which on a day a fast merely passes through is a day that is not the day on screen. `getWorkoutHistory` must stay day-keyed for a third reason: **`WhoopExportImporter.recordedWorkoutDays()` depends on it** to skip days the export must not overwrite, so a covering read there would make every day a fast passes through read as already recorded and silently drop the export's rows for it — measured, 16 of the file's 673 rows across 10 days at UTC. §20 asserts the two reads disagree on the 86-hour fast's five days (covering 5, day-key 1), which is the assertion that fails if anyone "simplifies" them back into one.

## A half-open bound wants `Date.startOfNextDay`, never `Date.endOfDay`, and the difference is one second that is invisible and load-bearing.

`endOfDay` is `23:59:59` — the last **instant** of the day, right for an inclusive bound and wrong for a half-open one. Measured against the bundled fasts, borrowing it flips **four real day-appearances whose per-day elapsed lands exactly on a zone edge** (2022-03-02, 2022-12-31 and 2023-01-16 at exactly 4 h, 2022-06-07 at exactly 16 h), drawing three of the four a zone too early. Its `?? self` fallback is a second reason not to borrow it: it would return the day's own start and fabricate an elapsed of `0`. `startOfNextDay` is `startOfDay(day) + 1 day` and **snaps first**, which is the half that matters for `elapsedSeconds(byEndOf:)` — see the `ActivityFigure` paragraph above. It is defined once and shared because two copies of `startOfDay + 1 day` drift by exactly this second and the drift is invisible; `WorkoutSession.covers(_:)` is the Domain statement of the same rule, and §20 asserts it and the SQL predicate agree on a fixture database so the rule does not live only in a query string. **The sync is that rule's second and third instance and its only *inclusive* counter-example**: `CloudSync.recoveries(from:to:)`, `RecoverySyncStore.syncRows(from:to:)` and `WorkoutSyncStore.syncWorkoutRows(from:to:)` are all half-open `[from, to)` built from `startOfNextDay`, because two chunks sharing an instant would write one day twice — while `CloudRecoveryRepository.getRecoveryHistory(days:endingOn:)` is **inclusive at both ends**, `first = last − days`, so `days: 2` names **three** days. Two conventions on purpose: a chunk boundary is a position and a screen's window is a set of days.

## The sync's two boundary predicates are different questions asked of different dates, and merging them loses days.

`SyncSettings.isCloudDay(_:)` is a *routing* predicate asked of the user's `cutoff` — is this a day the cloud owns, so should this read go to the server — while `cloudHolds(_:)` is a *provenance* one asked of `uploadedCutoff`, the boundary a transfer actually reached. Keying the second on the first is the tempting simplification and it is wrong: a phone with `keep` set holds a copy of some cloud days and not others, and a range uploaded under `delete` then re-uploaded under `keep` holds a copy of neither the days it deleted nor the ones it never had. Both use the same strict `day.startOfDay <` comparison, so the cutoff day itself stays on the phone in both readings. **`pendingWork` is a sign, not a mode** — there is no stored direction: `cutoff > uploadedCutoff` owes an upload, `<` owes a download, equal owes nothing, a `nil` `uploadedCutoff` beside a cutoff owes the whole range upward, and a `nil` cutoff is `false` for **every** day including the distant past, so the guard is an unwrap and never a comparison against `.distantPast` — the two are different instructions, one uploading nine hundred days and the other none.

## `workouts` is an aggregate of three tables on the wire, and three consequences of that are load-bearing.

The children (`workout_route_points`, `workout_splits`) ride **inside** the row, because a route has no identity outside the session that owns it — there is no `/v1/routes/{id}`, so a session read is one request and never three. **The local child tables have no `seq` column** (`WorkoutRoutePointRecord` is `(id, workout_id, latitude, longitude, timestamp, heart_rate)` and `WorkoutSplitRecord` is `(id, workout_id, elapsed, strain)`), so `getRoutePoints`/`getSplits` recover order by sorting on `timestamp`/`elapsed`, while D1's schema *does* carry `seq` and its adapter binds it from the array index — so the wire mapper must **preserve read order and must never sort**. And `saveSyncWorkoutRows` is a **replacement, not a merge**: it removes and re-inserts the children inside the same transaction as the parent, because a parent written without them would leave the stored route from an older write. **The two id policies are opposite and neither is a preference**: a *session* whose stored id will not parse as a `UUID` is **dropped**, because a session's id is its address; a route point's or split's id is part of no lookup, so it keeps its place and takes a fresh `UUID()`. That is `GRDBWorkoutRepository.makeSessions`'s rule mirrored rather than re-argued.

## The sync's chunking terminates because of an equality, and the workouts half's method names carry the resource because Swift overloads on name + labels.

`SyncWorkoutsUseCase.maximumBatchRoutePoints` is 2000 and `MAX_ROUTE_POINTS` is 2000; `maximumBatchSplits` is 200 and `MAX_SPLITS` is 200 — so **a chunk of one is always legal** and the walk cannot deadlock on a session too large to send. `batchSize` is 200 for all three resources and `maximumLookbackDays` 4000 (above which a range is refused with `.rangeTooWide` rather than attempted) — and **each resource declares its own pair rather than sharing one constant**, because the Worker does: `MAX_BATCH_STRAINS` and `MAX_STRAIN_WINDOW_DAYS` are deliberately not aliases of `MAX_BATCH_ROWS`/`MAX_WINDOW_DAYS` even though the values are equal today, so a client is told the limit for the resource it is writing and one resource's ceiling cannot silently become another's. `isSendable` is the *wire's* gate and stricter than the app's `hasMeasurement` — *will the database take it* against *is this a reading* — and it is applied **before** chunking, because `POST /batch` is one all-or-nothing transaction and a single unsendable row would fail the whole batch; what is dropped is reported in `SyncSummary.skipped`. **`StrainWireMapper.isSendable` tests both heart rates `>= 0` and must not copy recoveries' `restingHeartRate > 0` guard**: the schema declares them `.nonnegative()` precisely because an unmeasured row legitimately carries a `0`, and a `positive()` bound would refuse a row the app really holds. And **the three workouts-side store methods are `syncWorkoutRows` / `saveSyncWorkoutRows` / `deleteSyncWorkoutRows` because they have to be**: `LocalDatabaseManager` conforms to all three sync-store protocols, a signature is name + argument labels, and the row type appears in none of them — so a second `syncRows(from:to:)` is an `invalid redeclaration`. The strains half is `syncStrainRows` / `saveSyncStrainRows` / `deleteSyncStrainRows` for the same reason. `saveSyncRows(_:)` deliberately does not overload on element type.

## The two absence codes on the wire are different words, and they are read by name.

`recovery(onDay:)` translates `404` + code `no_measurement_for_day` to `nil`; `workout(id:)` translates `404` + code `not_found` to `nil`. A `nil` return is therefore **not** an error — both sources merge by one comparison rather than by a thrown error — and the codes are distinct because the absences are different shapes: a day has no measurement, an id has no row. **`strains` reuses `no_measurement_for_day` rather than minting a third word**, because its absence is the day-shaped one — but the *behaviour* behind the same code differs from recoveries', and the difference is on the wire: `hasMeasurement` rides a strain row as a **required** field, so `strain(on:)` passes a `200` through as a row **regardless of the flag** and translates only a genuine `404` into `nil`. A `kilojoules == 0` row is a legitimate measured value and must not be mistaken for an absence. `UnconfiguredCloudSync` keeps the same twenty-six methods and throws `.unreachable` from every one rather than returning `nil`, because an unreachable server is not a day without a measurement.

## `SyncKeyStore`'s read is a write on the first call, and `SyncStatusLog` keeps its two day-sets disjoint — both are `actor`s for the same class of reason.

Two concurrent first-reads that both find nothing would mint two keys and orphan a partition, so a conforming store must be single-flight across the whole read-or-mint; the protocol cannot state that as a type, so it is stated on the protocol. `SyncStatus` (`markStale`/`markUnavailable`/`clear`) is a **pair of disjoint day sets rather than a flag**, because a failed cloud read has two honest outcomes with two different sentences — a day the phone still holds a copy is drawn with a note that it may be behind, and a day deleted on the way up has nothing to draw and says a connection is needed — and a single "the cloud is down" boolean would have to pick one sentence for a window where both are true. `markStale` removes from `unavailable` before inserting into `stale` and vice versa, so a day cannot be described two ways. **Every day is snapped on the way in, and that is the protocol's contract rather than its callers'**: a screen passes the instant it is displaying, so an un-snapped read of one afternoon would be two entries and the screen would report two problems where there is one. `DIContainer` holds `syncSettings`, `syncKeyStore` and `syncStatus` as **stored properties** for that reason — one built per read would hold a set that is always empty and a Keychain read that is always the first. `SyncStatus`'s two reads have **no production caller yet and are not dead code**: the screens are the next pass and §22 drives the marking directly, which is the `ActivityDurationBar` precedent.

## `WorkoutSession`'s three measured fields are optional, and a fast is the reason.

`strain`, `averageHeartRate` and `maxHeartRate` were `NOT NULL` until `v18` made them nullable, because a Zero fast measures none of the three and there is no number that honestly stands in — a `0` reads as a measurement, which is the fabrication the absence rule forbids everywhere else in this app. **Neither initialiser defaults them**, deliberately: the four existing optionals on that type are defaulted, and a defaulted `strain` would let `LiveSessionUseCase.end()` degrade silently from "a measured strain" to "nothing measured" with no compile error. `LiveSessionUseCase.end()`'s four guards therefore became *policy* rather than type-narrowing — they are now the only thing stopping an empty session writing a row of NULLs — and `ActivityEditDraft.applying(to:)` passes all three through untouched, which is what keeps an edited fast a fast and an edited export row still `whoop_export`. **The two figures a row prints off them live in one value type**, `Presentation/DesignSystem/ActivityFigure.swift`: `strainText(for:)` returns the dash for `nil` and a real figure for a measured `0.0`, and `headlineText(for:)` returns the strain where the app measured one and the session's own **duration** where it did not — which is the `SLEEP` row's shape above it and the only figure a fast has. `ActivityFigure.dash` is the one `—` literal in the figure vocabulary and `ActivityDetailViewModel.stepsText` reads it from there. **The gate is the data and never the name**: a session *named* `Fast` that carries a strain prints the figure, and §20 asserts exactly that case, because gating the headline on `activityName` is the most likely way this gets broken later. The type's **third rule is `fastingZone(for:on:)`**, which returns the zone a fast is in or `nil` for every row that prints a figure — and it consults the *name*, which at first reading is exactly the regression the rule above warns about. It is not, and the reason is where the two sit relative to each other: **the pill occupies the slot the duration would have occupied, never the slot the strain has.** The first `guard` is that same data gate and returns `nil` the moment a sensor measured a strain, so a `Fast` carrying `7.4` still headlines `7.4` byte-identically to before, and the label is read only on the branch where nothing was measured and the duration was a fallback anyway. The key is the **name and not `source`**: `WhoopActivityCatalog.fastingName` is selectable in the edit sheet, so a hand-recorded fast carries it with no `zero_fasting` label and must still get a pill, while a fast re-labelled to something else has stopped being one — and it is the same key `ActivityGlyph.mark(for:)` resolves through, the same `ActivityName.normalised`, so the chip and the pill cannot disagree about which rows are fasts. **The third rule takes a day, `fastingZone(for:on:)`, and that parameter is a user decision rather than plumbing.** A zone is a claim about how long the body has been fasting, so on a day a multi-day fast merely passes through the honest answer is the zone it had **reached by the end of that day** — `WorkoutSession.elapsedSeconds(byEndOf:)`, cumulative from `startedAt` and clamped to `endedAt`. An 86-hour fast therefore walks `ANABOLIC → KETOSIS → KETOSIS → DEEP KETOSIS → DEEP KETOSIS` down its five days, and **that monotonicity is the tell**: the rejected alternative — the fast's overall zone on the start day and the reached zone only after it — would draw `DEEP KETOSIS` on day 1 above `KETOSIS` on day 2, a zone moving backwards down the week. **The cost is that the start day's pill changes on every multi-day fast** (151 of the 170 bundled ones): a start day has only a few hours behind it, so it now draws `ANABOLIC` or `CATABOLIC` where it drew the whole fast's zone. A **single-day** fast is untouched, because `min(endedAt, day.startOfNextDay) == endedAt` for it — so the 19 that start and end on one day keep exactly the pill they had. `elapsedSeconds(byEndOf:)` **snaps its `day` argument**, and that is load-bearing rather than defensive: `HomeDashboardView.selectedDate` is a raw `Date()` stepped by `Calendar.date(byAdding:.day,…)`, so the day it passes on first load is `today at 14:23` — and `day + 1 day` instead of `startOfDay(day) + 1 day` inflates a mid-fast day by up to 24 h while the clamp hides it entirely on a day after the fast ended, which would make the feature silently no-op on exactly the days it exists for. §20 asserts `f(day) == f(day.startOfDay)` on a day carrying `14:23:00`, because nothing else in the suite can see it. **The fourth and last rule is `fastingEndText(for:on:now:)` beside it** — the end figure a fast's time range prints, and the reason `inProgressText` (`"ACTIVE"`) is a constant on the type rather than a literal at the call site. It reads the **same two guards in the same order** as `fastingZone`, deliberately, so this app holds one definition of which rows are fasts rather than two that can drift; a session carrying a measured strain prints its own end on every day it covers, and §20 pins that pair. **Those two guards are now three readers with a split inside them, and the split is what the picker forced.** `ActivityFigure.isFast(_:)` is the whole rule — `strain == nil`, then the name — and it was extracted because the activity detail page needed a third reader of it and a third verbatim copy is how a pair becomes three that can drift. `ActivityDetailViewModel.isFast` forwards to it, so the page's layout gate and the Home row's pill cannot disagree about which rows are fasts, and both rules are now one `guard isFast(session) else { return nil }`, so §20's pinned pair is unchanged. **`isFastName(_:)` is the second reader and it is the name half alone**, because the `+` menu's picker has to know whether the name it was just handed means a fast **before any session exists to hold a strain** — the dispatch has one `String` and no `WorkoutSession`, so it cannot call `isFast` and must not re-implement the comparison. It is an extraction and not a new rule: `isFast` calls it for its second half, so the two cannot come apart, and it is `ActivityName.normalised` equality rather than `hasPrefix`/`contains` — §19 asserts a one-letter `"F"` is *not* a fast, which is the assertion that fails if anyone loosens it. **The `strain == nil` guard stays first inside `isFast`, and it is the whole reason the name is allowed to be read at all**: it is the data gate above, so a `Fast` carrying a measured strain takes the ordinary layout on both screens, and the name is consulted only on the branch where nothing was measured. Reading the name *without* that gate is correct in exactly one place, and it is `isFastName`'s own caller: a name the user picked off a catalogue is not a row, so there is no measurement for a gate to exclude. The rest of the rule is the two states the user named, stated above on the `Fast` bullet: the day's own last minute while the fast is underway, `ACTIVE` on the day it is running on now, and the fast's real end on the day it ended and on every single-day fast. Two details are load-bearing rather than stylistic. **`endOfDay` is the display value here and never a bound** — this is the one place in the app it is right to read, because what it produces is a *string*, while the comparison beside it is built on `startOfNextDay`; borrowing `endOfDay` for that comparison under-counts every day by the second that flips four real fast-days. And the `>=` rather than `>` is the half-open convention settling a fast that ends at exactly `00:00:00`: it ran to the day's last instant, so the day reads `11:59 PM` — under `>` the row would print `12:00 AM`, a clock time belonging to a day the covering read excludes and which therefore draws no row at all. `now` is a parameter and not a `Date()` read inside, for `DayBarRules`' reason: an assertion about "in progress" must not say something different tomorrow, and §20 drives one fixture under two `now` values — which is the only way to tell the fast's own state from "the card is showing today". **That state is now one function, `ActivityFigure.isInProgress(_:now:)`** — `startedAt <= now && now < endedAt`, half-open at both ends — because the fasting page's guidance line needs the fast's own state *without* the day, while this row needs it *with* one; so the comparison moved out and `fastingEndText` kept only its `DayBarRules.isToday` test beside the call. Written twice they would be two definitions of one state, and the row's `ACTIVE` and the line's tense would be free to disagree about whether the same fast had stopped.

## `Fast` is one name everywhere, and it was renamed from `Fasting` for the picker's sake.

`WhoopActivityCatalog.fastingName == "Fast"` (still first in `recoveryActivities`, still in `unpublishedNames`), and `ActivityGlyph`'s table key is `"fast"` carrying `.pair("fork.knife", "timer")` — fork first, then clock, on the user's own row spec. `ActivityGlyph` resolves the key through `ActivityName.normalised`, so the stored `"Fast"` and the picker's own entry reach one mark. A `fast` renders `FAST` through the card's existing `.textCase(.uppercase)`, and the figure that row would print is `durationSeconds.formattedCompactHoursMinutes()` — the same formatter the `SLEEP` row uses, so both rows would read `h:mm` under a word. **It draws a pill instead**: Home's row swaps that one slot for `FastingZonePill`, naming the zone the fast reached, so a fast states *what kind of fast it was* rather than how long it ran. `headlineText` is unchanged and is still computed and passed at that call site for every row, fasts included — the pill is drawn *instead of* the `Text` and not instead of the computation, so `headlineText` stays the one definition of what a row prints when it is not a pill. **The row is now drawn on every day the fast covers, not on its start day alone**, which is the user's own request — *"i want the fast to show up as an activity on home screen"* for a fast that is still in progress — and it is Home's read that changed rather than this type: `HomeViewModel.load(for:)` asks `getWorkouts(covering:)` instead of `getWorkouts(for:)`, so an 86-hour fast draws a row on all five of its days and each row's pill names the zone **that day** reached. **The time text on those days carries the day too, and this supersedes the earlier "not an `IN PROGRESS` marker" decision — the user reversed it.** The left half is unmoved: the fast's own start clock with its start weekday. The right half is `ActivityFigure.fastingEndText(for:on:)`, and it has three answers rather than one: on a day the fast merely passes through it is **that day's own last minute** — `11:59 PM`, printed with the meridiem the row's every other clock carries, so the user's `11:59` is honoured as a value rather than as a format; on the day the fast is running on **right now** it is the literal `ACTIVE`, because there is no end figure to print; and on the day it **ended**, plus every single-day fast, it stays the fast's real end clock. A fast's own end belongs to the day it ended on, so on any other day printing it would claim the fast stopped at an hour of a day the row is not about. **The override is a parameter on the shared `timeRange` helper and never a branch inside it** — passed by the one call site that has a fast, `nil` everywhere else — which is what keeps the `SLEEP` row and every measured row, the export's three cross-midnight workouts included, printing their own two clocks byte-identically. The consequence is that a long fast's covered days now differ by the **end figure** as well as by the pill — measured, **326 fast day-rows over 204 distinct days, 108 of those days carrying two or more fast rows and up to three**. **Nothing in this app can draw the `ACTIVE` branch on this machine**: all 170 bundled fasts have ended, so it is reachable only from a fixture, which is what §20 asserts it with. **The change is Home's `ACTIVITIES` card alone**: the activity detail page still prints `ACTIVITY STRAIN —` for a fast, because that `—` comes from `ActivityFigure.strainText`, which does not move.

## The export's day skip excludes fasts and hand-added sessions, and that exclusion is what makes the imports order-independent.

`WhoopExportImporter.recordedWorkoutDays()` asks whether a day already holds *any* workout, and `importWorkoutRows` refuses every row landing on one. Once fasts are in `workouts`, a fast's start day would read as already recorded and the export's rows for it would be dropped silently — measured, that is 16 of the file's 673 rows across 10 days at UTC (17 over 12 at UTC−4, since `Manual Labor` drops out), so the count is zone-dependent and the exclusion is not optional. The exclusion is one set in `Domain`, `WorkoutSession.measurementFreeSourceValues`, and it was widened when the `+` menu's `ADD ACTIVITY` row landed: a hand-added session carries `source == "manual"` and measures nothing — no strain, no heart rates, no route, no zone block, no steps — so its day must accept the export too, or adding a walk before importing the file would silently drop that day's rows and the order-independence would hold for fasts alone. `nil` is deliberately not a member: it is what `end()` writes for a session the strap watched, and that day *was* measured. The filter is **negative** (`!WorkoutSession.measurementFreeSourceValues.contains($0.source ?? "")`) and not a positive scope to `whoop_export`: scoping positively would change the rule for live sessions and let an export row be written beside a session this app recorded itself, which is exactly what "it never touches a day the app measured itself" forbids, and it would double the day's zone aggregate through `WorkoutZoneTime.aggregate` and put a second row on Home's card. Two consequences are deliberate: a day can now hold an export workout *and* a fast or a hand-added row, and Home draws both rows; and an edit survives a re-import of the export but **not** a re-import of the fasts, because the fast path deliberately does not skip a day — a fast's id is its own `FastID`, disjoint from every other producer's, so a fast write can only ever touch a fast row. A skip there would drop fasts on exactly the days the two files overlap.

## `WhoopDevice.batteryPercentage` is not optional and defaults to `100`.

`WhoopBLEManager` writes a literal `100` at discovery, so a percentage read off a strap that is not connected is a constant this app wrote down rather than a measurement it took. **The gate is `WhoopDevice.batteryReading`** — `Presentation/DesignSystem/WhoopDevice+Extensions.swift`, a `String?` that is `nil` for every state but `.connected`, and the one place the refusal of `.syncing` is argued: the dot beside that figure draws `.syncing` green, so `== .connected` and `isLinked` are two plausible gates that differ on exactly that state, and nothing here has ever seen a battery read during a drain to say which it is. **It has one rendered reader and one kept-but-unrendered one, and they draw the absent case differently, which is the whole reason the gate is an optional rather than a string**: `DeviceSettingsView.batteryText(for:)` is `device?.batteryReading ?? ActivityFigure.dash` — a `nonisolated static` over a bare `WhoopDevice`, so §14 asserts it with no view model — and the dash was right there because a labelled `BATTERY` row inside a `Form` with no value looks unfinished, while `HomeDashboardView`'s status badge draws **no figure at all** in that slot, because the user read the dash on the badge as a battery *bar* (measured off the screen: 9.7 × 1.3 pt of white at 12 pt type, which is a bar's proportions) rather than as the app's word for no reading. **That `BATTERY` row is now gone** — the user removed it along with the rest of the `Strap` section — so `batteryText(for:)` is kept **unrendered**, on the `ActivityDurationBar` precedent: the suite has no test discovery, so deleting it would drop its §14 assertions and a falling `assertions=` count would be the only trace. Do not read its presence as a screen still drawing it. **Do not "unify" the two into one string**: they agree about *when* there is a reading and differ only about how to draw its absence. **The badge's dot is a separate rule answering a separate question** — it reads `WhoopConnectionState.linkColor`, so it is green for `.connected` *and* `.syncing`, yellow for `.disconnected` (the "stale connected" state the user corrected from red) and red for `.scanning`/`.connecting`/`.error`, and the two deliberately part company on a strap the app can address whose battery it has not been told. The old Settings page's `device?.batteryPercentage ?? 0` fabricated a `0%` for an absent strap and a `100%` for a merely discovered one; that fabrication is gone rather than fixed in place. **And `.connected` alone was not enough — `batteryIsMeasured` is the second gate, added 2026-10-21 after a measured complaint.** The owner reported "green dot and 100% while not connected"; the log showed the strap genuinely linked (steps still landing), so the colour was right and the *figure* was the bug: `WhoopDevice.batteryPercentage` is not optional, defaults to `100`, and discovery writes the same literal, so a connected strap that had never answered `0x2A19` drew a confident `100%`. `batteryIsMeasured` is set only by `updating(batteryPercentage:)` — the one path a real read takes — and `batteryReading` now requires it. **The badge then drew nothing, and the user asked for a dash back** — so it draws `ActivityFigure.dash` in `Theme.textSecondary`, which answers the bar-reading complaint at its root: the muted ink is what separates *no reading* from a low battery at 12 pt, where the bright dash did not. Both screens now draw the same word for absence. The wider fix (making the field optional the way `SleepSession.respiratoryRate` is) remains open.

## Steps come from the strap and from nothing else, and `stepCounts` deliberately has no `source` column.

**A locomotion class is the strap's opinion, and the wrist gets a second one.** Measured 2026-10-26: a
morning showed **300+ steps before the wearer left the bed**. The counter path was already gating on
the strap's own class — `1` walk, `2` run — so the defect was not a missing gate but a wrong class:
in-bed movement was classified as walking, and the app believed it. `R18` body 24 now carries the
mean acceleration triplet to the counter record as well, and `StepCounterAccumulator` asks a second
question — **how many of the last thirty seconds actually moved** — before counting a locomotion
interval. A count, not a mean: one roll produces two large deltas, which drag any five-second mean
past its threshold while describing half a second of movement. A record with no accelerometer is
**not** gated, because the class rule is the documented fallback and a decode gap must not read as a
dead pedometer.

The strap's own accelerometer is the producer: a live IMU stream (`0x2B`/43) or a banked drain (47) decodes to a `MotionBatch`, `TrackStepsUseCase` accumulates it, and one day-keyed row is written. **Do not gate a step row on a provenance label** — this is the "the strap is the producer" rule, and the schema records the consequence: live and banked motion are the same measurement of the same motion from the same sensor, and a single day is routinely fed by both, so a per-row `source` could not be written honestly and `StepRepository` takes no `source` parameter. The HealthKit path is **absent at every layer** — no `.stepCount` case on `HealthQuantityMetric` (which is why steps are not in the consent prompt's `readTypes`), no `stepCount(on:)` on `HealthKitSyncing`, and no `dailyTotal` on `HealthStoreClient`. Do not restore a display-time read-through as a fallback: a day the strap did not measure would then show the phone's count instead of a dash, which is a fabricated reading of the kind every absence rule here forbids. **A day the strap did not measure has no row at all**, and a *measured* day of no walking is a real `0` — `StepCount.hasMeasurement` (`measuredSeconds > 0`) is the test that separates them and it is the same test the writer gates on. It is written **incrementally and stored**, because a day at 100 Hz × 3 axes is ~26M samples and a count computed on read would re-walk the day to redraw one tile. **`TrackStepsUseCase` is started once from `MainContainerView`'s app-level `.task` and never from `HomeViewModel.load(for:)`** — the streams are multicast, so a subscription per day-step tap would orphan or accumulate consumers and fail silently, as a `for await` that stops receiving is indistinguishable from a quiet strap. **`motionStream` now has a second reader on purpose: `LiveSessionUseCase` counts the session's own steps while `TrackStepsUseCase` counts the day's, and the registry is what makes both receive.** They are two accumulators over one stream because they answer different questions — a session's count is bookended by the session, a day's by the day — and the session's is written to `workouts.steps` while the day's stays on its own row. **The gate is `hasMeasurement`, and it must be applied on both sides of that write**: a session that saw no motion is `nil` and draws a dash, never a `0`. A session that measured motion but counted no steps is a real `0`, which is the distinction `StepCount.hasMeasurement` (`measuredSeconds > 0`) exists for. Deleting the second reader is not the way to simplify this: one continuation would let whichever registered first take every batch and leave the other's `for await` silent, and `LiveSessionUseCase` registers first, so the day's tile would simply stop advancing with nothing anywhere reporting an error.

## A local delete is a cache eviction while the destination is the API, and a writer that seeds itself from a read will resurrect the row.

`CloudStepRepository.getStepCount` is local-first **with a cloud fallback on a local miss**, and `TrackStepsUseCase.ingest` seeds its day accumulator from exactly that call. So deleting a phone's row under the `.cloud` destination does not delete it — the next read misses locally, the decorator asks D1, and the counter resumes from the database's copy. Measured 2026-10-20: a `v25` migration deleted an inflated 47k step row, and the very launch that cleared it rewrote 47,765 because `measured 965 min` came back from the server. **A local delete is a cache eviction**, not a correction; clear a day with the destination on `DEVICE STORAGE` (where `storesInCloud()` is `false` and the miss answers `nil`), or correct the database copy itself. The cloud heals on its own only once the phone is writing again — a save is a write-through mirror, so the next real count pushes the corrected row up. There is **no DELETE on the wire by design**, which is the user's own ruling and §22.7's sweep; the API's only write for a day is `PUT /v1/step-counts/{date}`.

## §6's motion layouts are frame-absolute, and the payload origin differs per generation.

`docs/BLE_PROTOCOL.md` §6's `R21`/`R10` offsets are measured from the **frame's** first byte, while `WhoopRawFrame.payload` begins at `innerOrigin + innerPrefixBytes` — **11** under the 5.0/MG envelope, **7** under the 4.0's. `MotionPayloadDecoder` subtracts that origin while keeping the spec's numbers verbatim in the code, so the two differ by eleven — an off-by-eleven in the source that is the spec's own frame-absolute basis and not a decoder error. The two layouts also **require an exact payload length** (1,229 and 1,910 — R21's 1,244 is its *frame*, and R10's 1,917 is the length the frame declares) and return `nil` otherwise, and the generation is what selects a layout — never a fallback, since the two generations share the packet-type numbering and differ in envelope and origin. Run both builds after touching this: the offsets are frame-absolute in a way that compiles identically if they are wrong. **The VO₂ MAX panel is not a HealthKit read and must not become one** — there is no `.vo2Max` case on `HealthQuantityMetric` and no member on `HealthKitSyncing`, so VO₂ max is absent from the consent prompt's `readTypes`. It prints an estimate this app computes instead: `Vo2MaxMath.heartRateRatioEstimate` (`15.3 × HRmax / HRrest`, Uth et al. 2004), derived on read inside `MetricWeek.makeDay` from the slot's own gated resting heart rate and `UserProfile.maxHeartRate`, stored nowhere. Two things about it are not negotiable: the label says `(EST.)` because it is a model's output beside three measurements, and a day that cannot produce one is `—` and never `0`. `docs/ALGORITHMS.md` §6 carries the model, the citation, the 4.7 mL·kg⁻¹·min⁻¹ (~7.8%) error bar that applies when `HRmax` is *not* measured, the measurement that rejected the day's own peak as an anchor, and why WHOOP's three-tier model is still unimplemented.

## The scoring window is the last 30 days that *have rows*, and a mean is not a baseline until the window held some.

`RecoveryScoring.baselineWindow(before:in:)` filters to the days strictly before the day and *then* takes the trailing `baselineWindowDays` (30) — slicing first takes the wrong thirty, and the input must be **oldest-first**, which is what the repositories return. **The `before:` comparison is made on the calendar day, and that is not a detail**: every row is keyed on `startOfDay`, but the two callers hand different kinds of anchor — `WhoopExportImporter` passes a snapped day key while `RecoveryViewModel.loadBaselines` passes the `Date` the screen is displaying, which is an instant and on every day this app runs is hours after midnight. Compared raw, that instant is later than the day's own midnight row, so the day fell inside its own baseline and the printed mean was taken over a different set of days than the score above it — measured on the simulator, 2026-08-17 printed an HRV baseline of 53 and a sleep-performance baseline of 80 where the strictly-before window gives 52 and 78. Both anchors are snapped inside the helper rather than at the call sites, so the contract holds for whatever a caller passes. The two definitions are not nearly the same number: measured over the bundled export, 391 of 907 comparable days have a calendar-30 window that differs from the last-30-rows window, by up to **18.03 ms**, and the worst case reaches back **172 calendar days** to fill thirty rows. A reader must fetch `baselineWindowLookbackDays` (180) back or it silently prints a baseline built from fewer days than the score above it used. It lives here rather than in the importer because the Recovery detail screen prints the same baseline its ring was scored against. **The scorer no longer substitutes a cold-start constant for an empty window.** `BaselineStatisticsMath.baseline` still has that fallback (65 ms RMSSD, 40 ms SDNN, 54 bpm), but `CalculateRecoveryUseCase` and `WhoopExportImporter` both require `minimumBaselineDays` (3) measured days before a day. The first days are stored as **measurements with no score** (`source = "measurement"`, `RecoveryMetric.hasScore == false`, the reserved `0` never drawn), so the window can build and the fourth day is the first scorable one; the ring draws `—` rather than a percentage in the meantime. `RecoveryScoring.baselines(...)` returns each mean *with the count it was taken over*, and `Baselines.displayed` withholds one below three. `score(_:)` is built on `baselines(...)`, so a screen that prints `displayed` cannot disagree with the ring above it.

## `MetricChange` draws a comparison on the *formatted* pair, not the raw one, and its verdict is three states rather than two.

A resting heart rate of 52 against a mean of 52.4 is genuinely below it, but a row printing `52` over `52` renders as `52 ▼ 52` — a row contradicting itself. The digits on screen are the whole of the evidence a reader has, so the comparison is made on the **formatted** pair: two figures that print alike *are* the same as far as the screen is concerned. That case is `.same` — `direction` is `nil` and the glyph is `circle.fill`, because a figure sitting on its average has not moved and there is no direction to point. **The middle state is the whole reason the colour cannot be read off the direction**, and `nil` is reserved for a *missing side* — a day with no measurement, a window with no baseline — never for "unchanged". Direction and verdict are separate by construction: the triangle always points the way the number went, while `higherIsBetter` turns that direction into the verdict and the verdict alone picks the colour — `Theme.recoveryGreen` / `Theme.recoveryYellow` / `Theme.recoveryRed`, so an HRV rise is green while a resting-heart-rate rise is red from one call. The type is shared by Home's four metric panels, Home's two tiles, and the four breakdown rows, so a change here moves all three. **`ActivityDelta` is its deliberate sibling and not a fourth case on it**, because a fourth verdict would have to be one of the three colours and there is no true one: strain rising against the last ten basketball sessions is neither good news nor bad, and neither is a step count rising. So the activity page's two badges carry a direction and its text, carry **no verdict**, and draw in a new `Theme.neutralDelta` token — a dedicated token rather than `textSecondary` or `bandSufficient` borrowed to mean a judgement, since neither of those means one. It borrows `MetricChange`'s one real rule and nothing else: **the comparison is made on the formatted pair**, so `4.14` against a mean of `4.1` is *unchanged* rather than a row printing `4.1 ▲ 4.1`.

## A week's baseline is a mean over measured slots, and HRV's is narrowed to one metric first.

`MetricWeek` computes four baselines from the same seven slots. Three are plain means over the slots carrying that figure, `nil` below `minimumBaselineDays` (3). HRV's is not: SDNN and RMSSD are different quantities on different scales, so it takes the **newest measured slot's metric**, averages only the days matching it, and can therefore come back `nil` in a week that has readings in it — which is the honest answer, not a baseline over a mixture. **`hrvBaselineMetric` and `hrvBaselineMs != nil` are two different conditions**, and picking the wrong one is silent: the metric names which quantity the week is *in* and is set as soon as one slot has a reading, while the mean additionally needs `minimumBaselineDays` days in it — so a two-day week is `hrvBaselineMetric == .rmssd` with `hrvBaselineMs == nil`. Anything selecting days to plot wants the metric; anything printing a mean wants the mean. `MetricDay.hrvMetric` is non-`nil` only when `hrvValueMs` is, so a slot can never name a quantity it has no reading in. VO₂ max joins the week through `MetricWeek.init`'s `maxHeartRate:` parameter instead — the one input that is not a per-day row, being the profile's assumed maximal heart rate, which is also what `CalculateStrainUseCase` builds its Karvonen zones from so the app has one definition of `HRmax` rather than two. The estimate itself is computed **inside** `makeDay` from that slot's already-gated `restingHeartRate`, which is the whole reason for the placement: the day's absence rule for a resting rate is applied once, and the VO₂ field inherits it. A caller assembling the estimate itself would have to restate the `hasMeasurement && > 0` gate, and an unmeasured row carrying a plausible `55` bpm — which is constructible, since `hasMeasurement` is `hrvValueMs > 0` — would then produce a confident estimate on a day this app calls unmeasured. **A `MetricWeek` built from one history is not a week with the other two unmeasured.** `MetricWeek.init`'s three history parameters all default to `[]`, so a caller that passes only `recovery:` gets `nil` for `strain` and `sleepNeedSeconds` on every slot — and on this type `nil` is the documented word for *nothing was measured*. `RecoveryViewModel.week` is that build one history short (the Recovery page draws five charts and the five read two histories between them: the recovery-performance bars and all three lines come out of `recovery`, since HRV, resting rate and respiratory rate are all columns on a `recoveries` row, and the sleep-performance bars need a `sleeps` row, which no column of a `recoveries` row carries), so its `strain` is "not asked for" and **a strain-plotted view handed that week would report every day of it as unmeasured**. The narrowing is per-caller, so it is carried in that property's doc comment rather than here; the fix if a view ever needs a second series is to pass the second history, not to read through the `nil`.

## Stress Monitor is a calibration, not a recovery of WHOOP's function.

WHOOP publishes the model's shape (HRV + heart rate + motion, a 14-day personal baseline, a 0–3 scale banded 1.0/2.0) and none of its constants, so every threshold in `StressMath` is this app's own and **this app's number will not agree with the WHOOP app's** — the same bargain `SleepNeedMath` documents. Two things about it will otherwise read as bugs: `minimumRRIntervals` is **load-bearing**, because `HeartRateVariabilityMath.calculateRMSSD` returns `0.0` on insufficient data and a zero RMSSD scores as *maximum* stress; and the tile renders `—` far more often than a number, because samples exist only for days the app was running with the strap connected and the export carries no R-R series at all. The full model is in `docs/ALGORITHMS.md` §5.

## A live stress window must land on the stored day's grid, and a day with no personal baseline is scored against its own preceding hours.

The live half of the Stress Monitor (`StressLiveViewModel`) scores a five-minute window while the page
is open, and three things make that the *same* measurement as the stored day rather than a lookalike.

**The grid.** `AnalyzeStressUseCase` anchors its buckets on the first sample inside the day's waking
window, so bucket starts are that instant plus whole `windowSeconds` steps — a live window cut from
`Date()` instead folds a different five minutes and draws a line whose points are not the day's. The
view model therefore takes a **stored** window's start as its anchor, which is on that grid because the
analyzer's own starts are, and steps from there.

**The reference.** The personal baseline — the previous fortnight's waking hours, one point per day —
needs `StressMath.minimumBaselineDays` (3) days that carry still windows, and it used to gate the whole
model: below three days there was no `StressDay` at all. That was wrong for a **live** monitor, and the
failure is specific rather than cosmetic — it reported the absence of *history* as an absence of
stress, and left the tile and the page dead for the first three days of wearing the strap. A
day with no personal baseline is now scored against its own preceding hours instead: each window
against the windows of the same day inside `StressMath.recentBaselineSpan` (6 h) before it, floor
`StressMath.minimumRecentWindows` (12, one hour at this cadence), strictly before the window so it
never contributes to its own reference, and over a **wall-clock span** so the same day's data always
reproduces the same scores. `StressDay.baseline` is `nil` exactly when that happened, which is how the
live page knows to rebuild each window's reference from the windows' own `features` — which is why
`StressWindow` carries them.

**The consequence, stated rather than hidden.** A recent baseline is a local reference: a day that is
uniformly elevated has no contrast within it and reads as average, and the score answers *"how does
this five minutes compare with your last few hours?"* rather than *"how does it compare with your
fortnight?"*. The page names which one it is showing, and the personal baseline takes over as soon as
three days of daytime stillness exist. Neither path opens a day with no measurable window on it: the
reference is a fact about inputs, and a day nothing measured has none.

## The Stress Monitor chart follows four rules that are not styling choices.

The mark is **one bar per five-minute window**, not a line: a window is a measurement over a span, and a polyline implied a value at every instant between two windows, including the ones nothing measured — which is why it also needed a dot at each peak to be readable. The y-axis is **fixed at 0–3** and never auto-scaled (auto-scaling draws a calm day and a wired day as the same picture); an ineligible window **draws no bar at all**, since a gap is unmeasured and a zero-height bar is the strongest possible claim of calm; and **no windows means no chart at all** — not an empty frame, not a row of zero bars. The bars' colour is `StressMath.Band.gradient`, whose stops are `lowMediumBandEdge`/`mediumHighBandEdge` divided by the scale, so the view must not type `1.0`/`2.0` itself. **The bars are a mask over one full-height `Rectangle` filled with that gradient**, never a gradient applied per bar: a `LinearGradient` on a bar is graded over that bar's own height, so a short bar and a tall one would put "high" at different heights — the same defect as a `Path` graded in a `ZStack` rather than a `Shape` receiving the frame.

## An edit is not a re-measurement: it carries every field and advances the watermark so re-classification cannot undo it, and a night has no delete.

The `SLEEP` row's page (`SleepDetailView`) — not the ring's (`SleepPerformanceView`) — has a `•••` whose `Edit` changes **only the night's two bounds** — the user's instruction was *"only
time"* — so `SleepSession.withEditedTimes` copies every other field through: the stage totals, the need,
the provenance (the save hands `saveSleepSession(_:source:)` the `whoop_export` label back, because
`hasWhoopSleepNeed` is read off exactly that string) and the stillness spine. An edit is a correction to
*when* the night ran, not a claim about how it went.

**The watermark is the half that makes the edit stick.** `shouldReclassify` re-runs a stored night when
its newest input is later than `scoredThrough`, so a row whose watermark stayed at the old end could be
re-analysed by the next foreground or drain and silently redraw the times the user just set. The copy
advances `scoredThrough` to the edit instant: the edit happened after every record the night can hold,
so the claim is honest, and only input arriving *later* — which for a finished night is nothing — can
move past it.

The span is validated where it is a rule rather than in the view: `SleepTimeEditDraft` refuses an end at
or before the start (a zero-length night divides the chart's axis by zero) and a span over 24 hours (the
row is keyed by its day, and a longer "night" would describe two). The draft's rules are asserted in the
suite; the sheet's layout is not, because nothing here has a renderer.

**The menu is `ActivityOverflowMenu.nightGroups` and the drawing is shared.** `Edit` alone, then
`Cancel` in a card of its own; a night carries no `Delete` because removing one would orphan the
day its Recovery, ring and re-classification watermark are keyed to, so the app's one destructive
control stays on the activity page. The scrim, card and row geometry live in
`OverflowMenuOverlay`, lifted out of `ActivityDetailView` when this page needed the same menu.

## A Health Monitor row counts readings, and its page bands them.

Home's **HEALTH MONITOR** card, above `My Day`, draws WHOOP's five vitals as `n/5 METRICS`. **`n` is a
count of `recoveries` fields the day actually holds** — `hrv`, `resting_heart_rate`, `respiratory_rate`,
`spO2_percentage`, `skin_temperature` — and the card says `ALL MEASURED`, not the reference's
`WITHIN RANGE`.

That wording is the rule, not a placeholder: the **row** is a count, and the reference's caption is a
*verdict* the row cannot support. The verdict lives one tap away, on `HealthMonitorView`, where
`HealthMonitorReadings` bands each figure — the mean ± one standard deviation of the last
`RecoveryScoring.baselineWindow` nights, the same window every other "typical" figure uses, with blood
oxygen on the clinical 95–100 % range instead because a personal band on a metric that barely moves calls
a normal night low. **Two surfaces, two claims**: the row says what was measured, the page says where
each figure sits, and neither says the other's sentence. Flipping the row's caption to `WITHIN RANGE`
without giving it the page's read is the change this entry exists to stop.

**The gate is presence, and the count has an honest empty answer.** A strap-classified day carries two
of the five (HRV and resting heart rate); an imported day carries all five; a day with no `recoveries`
row is `0/5`. The card draws on every day, because a monitor whose subject is *which of my vitals do I
have* can answer "none" — hiding it would leave an unmeasured day indistinguishable from a missing
feature. **Flipping the caption to `WITHIN RANGE` without building the five bands is the change this
entry exists to stop.**

## The app's copy never names the strap's maker.

On 2026-10-29 the user asked for the brand out of the interface — *"remove all 'whoop' references and
instead of 'whoop age' lets do 'whoopsy age'"* — so every **user-visible** string now says *the strap*,
*the strap maker*, *the import* or *the published guidance*, and the Healthspan dial reads
`WHOOPSY AGE`. The device page's subject is `STRAP DEVICE` and its six state words begin `STRAP`;
import errors, the export's own figure descriptions and the scan line follow the same rule.

**What deliberately still says WHOOP, and why.** Three kinds of occurrence are not copy and were left
alone: **identifiers** (`WhoopBLEManager`, `WhoopRawFrame`, `WhoopDevice`), **the persisted source
label** `whoop_export` in `sleeps.source` / `recoveries.source` — it is a stored value that the import
and the sync both read, so renaming it would orphan every row — and **`docs/` plus the code's own doc
comments**, which are the record of what the references and the filings say. `WhoopHardwareGeneration`'s
raw values are also unmoved, because `UserDefaultsStrapModelRepository` persists them; what a screen
draws is its `displayName` (`4.0`, `5.0`, `5.0 MG`, `Strap Simulator`), added for exactly that split.

**The trap:** a new user-visible string that names the maker will not fail any build or assertion. The
suite pins the two strings where a brand was load-bearing — `DeviceSettingsView.subject` and the six
distinct state words — and nothing else, so the rule is kept by reading this entry rather than by a
test.

## Home's collapsing rings header is a `PreferenceKey`, and it writes no `@State`.

iOS 17 has **no scroll-geometry API** — `onScrollGeometryChange` is iOS 18 and the deployment target is 17.0 — so the mechanism is `GeometryReader` → `RingsBottomKey` (the rings row's `maxY` in a named coordinate space) → `.overlayPreferenceValue`. Four things about it are load-bearing: `PreferenceKey.defaultValue` must be `static let`, not `static var` (a mutable static is a Swift 6 concurrency error), and its value is deliberately out of any real range so an unpublished frame resolves to *hidden*; the preference reports where the rings **are**, not a scroll offset, so there is no threshold constant to go stale when the top bar changes height; the transform must not write `@State`, because it runs on every scroll frame and a state write per frame invalidates the whole screen; and the `VStack` must **not** become a `LazyVStack` — a lazy stack may release the rings row once it is scrolled past, taking the preference publisher with it and hiding the header permanently.

## A failing migration crashes the app at launch.

`LocalDatabaseManager.init` calls `fatalError` on a migration error. Test a migration against the real dev database before trusting it; the reset is `rm ~/Library/Application\ Support/whoopsy.sqlite`. **`LocalDatabaseManager`'s path-injecting initialiser is `init(fileURL:)`**, which the pool test uses to open a real file under `tmp/`; `init(inMemory:)` and the `~/Library/Application Support` default are the other two. On macOS `FileManager.url(for: .applicationSupportDirectory,…)` does **not** follow a `HOME` override, so a host-side tool that writes through it lands in the developer's own dev database however the process is launched. The simulator app is unaffected (its container is separate); a host tool that must not touch the dev database has to be given one by *temporarily moving that file aside*, not by re-pointing `HOME`.

## Day-keyed writes must be snapped to `date.startOfDay`.

`recoveries`, `sleeps` and `strains` are read back with `startOfDay` as the lookup key, and GRDB's `save` is INSERT-or-UPDATE *by primary key* — so a row written at a raw timestamp is inserted, never updated, and no keyed read can find it. `LocalDatabaseManager`'s `saveRecovery`/`saveSleep`/`saveStrain` snap centrally for this reason; keep new writers going through them.

## A window computed by adding hours to midnight lands on the wrong clock time, and the failure is a plausible number rather than an error.

`AnalyzeSleepUseCase` read a night out of `startOfDay − 11 h` and called it "9:00 PM previous evening" in its own comment. Midnight minus eleven hours is **1 PM**, so the read window was 21 hours wide rather than 13, and every document in this repo — that comment, `SleepOnsetMath`'s header, `docs/ALGORITHMS.md` — agreed on a bound the code did not implement. The symptom is not a crash or a dash: on 2026-10-20 a real strap's quiet afternoon made the detected onset **3:33 PM**, and the sleep card reported a night from 3:33 PM to 8:38 AM — an absurd span that still looks like a sleep session. **Build a wall-clock boundary from `Calendar.date(bySettingHour:minute:second:of:)`, never by adding hours to `startOfDay`**, both because the intended value is a clock time and because hour arithmetic is wrong across a DST boundary too. `AnalyzeSleepUseCase.readWindow(for:calendar:)` is now the one definition, and §13 pins both ends plus the width. Two consequences worth carrying: the three fixtures in §13 were anchored at 2 PM *because that is where the buggy window reached*, so correcting the window turned them into samples the read never returned and the use case answered `nil` — a fixture that only fits a window its own comment contradicts is not evidence about the window. And a row computed by the bug is not corrected by fixing the bug: `SleepViewModel.load` answers from storage for a day that holds a row, so `v27` deletes today's `sleeps` row and lets the next load recompute it.

## A day-keyed screen must READ.

Send day selection to the repositories (`getRecovery(for:)`, `getStrain(for:)`, `getSleepSession(for:)`), which is what `RecoveryViewModel`/`SleepViewModel`/`StrainViewModel`'s `load(for:)` do; they fall through to a calculate use case only for a day that **is today and holds no measurement**. `HomeViewModel.load(for:)` is the reference implementation. The read is the point: a stored day has no raw samples to recompute from (an imported day has none by construction), so a recompute would come back as *no row at all* and blank the day the user was looking at. `RecoveryViewModel.shouldCompute` is the gate, and it tests the measurement rather than `nil` so that a placeholder row left by an older build stays a legitimate candidate to fill.

## `getXHistory(days:)` windows back from `Date()` unless you pass `endingOn:`.

The three metric screens show a day the user picked, so they call `getRecoveryHistory(days:endingOn:)` and its siblings. Those reads bound the window at **both** ends (`>= cutoff` and `<= endingOn.endOfDay`); the upper bound was added with `endingOn`, because a window anchored on an old day would otherwise run on to the present. Pulling the whole imported range in a test is still `days: 4000`.

## The calendar's day colours are a map, and a day absent from it means no measurement.

`HomeViewModel.monthTiers` is keyed by `startOfDay` and built by gating each row on `hasMeasurement` — never on the row existing. A legacy placeholder holds `score: 0` and reports `.red`, so a map keyed on existence would paint an unworn night a hard red, which is the same fabrication the dash convention exists to prevent, drawn in a cell instead of a ring. Two consequences worth keeping: a day *missing* from the map is drawn grey and is still **selectable** (Home legitimately opens on an empty today, so most of a fresh install has to stay reachable), and the loading test is `isLoadingMonth`, never `monthTiers.isEmpty` — a month the export never covered is empty and finished, and testing emptiness would spin forever on it.

## The month read's window is `days: <the span between the month's own bounds>, endingOn: <the month's last day>`.

Because the window is inclusive at both ends and runs from `endingOn - days`, that pair covers exactly the month. Neither of the obvious alternatives does: `days: 30` reaches back into the previous month on a 31-day one, and `days: dayCount` pulls in the 1st of the next — either would put a neighbouring month's row in `monthTiers`, where the grid is free to tint a day nothing measured. An assertion on one month cannot see this, which is why §14's version puts a row on each side.

## `.toolbar(_:for: .tabBar)` is unavailable on macOS, and Home is built for both.

`swift build` is this repo's edit/compile loop and the test runner links its objects, so the unguarded modifier breaks the fast path while `xcodebuild` for the simulator stays green — it reports `error: 'tabBar' is unavailable in macOS` and nothing else does. Home wraps it in a `#if os(iOS)` helper (`View.hidingTabBar(_:)`) for that reason. This is one member of a family that also holds `#if canImport(HealthKit)` being true on the host, `keyboardType` (→ `View.numericKeyboard(decimal:)`) and the whole of `ActivityKit`: **a green iOS build is not a green host build, and vice versa** — run both. **`fullScreenCover` is the second modifier in that family, and the one a new control is most likely to reach for**: the map cards' expand control presents `MapFullScreenView` through `View.mapExpansion(isPresented:content:)`, which is a `fullScreenCover` on iOS and a `sheet` on the Mac. The cards are compiled by `make build`, so an unguarded call breaks the fast path exactly as the tab-bar modifier does.

## It hides the tab bar only from the tab's *root* view, never from a pushed destination — and the failure is silent.

`.hidingTabBar(true)` on a view inside a `TabView` (Home, gating on its overlay and session flags) works; the same modifier on the destination a `navigationDestination` pushes **does nothing**, and the bar is drawn over the pushed screen with no error, no warning and no compiler diagnostic — it is not a first-render ordering artifact. `LiveSessionView` still carries the call because it states the intent, and that is exactly the trap — **a destination-side hiding is not load-bearing, so removing the root-side line that does the work leaves the call behind looking responsible.** Gate the root view on the same flag the `navigationDestination(isPresented:)` binding uses and the bar returns on pop for free, since SwiftUI resets that flag. The host build cannot see any of this: it is a runtime behaviour of a modifier that only exists under `#if os(iOS)`.

## A saved row is not a drawn one: a pop re-fires no `.task`, so the writer's caller has to hand the row to the screen behind it.

**Its drain-side sibling, measured 2026-10-26: a drained night is not a classified one.** A drain writes
`biometric_samples` and `motion_epochs`; `sleeps` is written only by `AnalyzeSleepUseCase`, and its only
caller was the sleep page. So a morning drain of 32,274 records ended `complete` with Home's sleep ring
still a dash, and popping back from the sleep page did not fix it — a pop re-fires no `.task`, the rule
directly above. `DrainCoordinator` now passes the range it covered to `RefreshNightsUseCase`, which
classifies the newest three days using the sleep page's own staleness test and publishes each saved
night on a stream `HomeViewModel` watches. **The range is not the input, though — today is.** The first
version derived its days from the drained range alone, and a drain whose cursor was already past the
night returns nil, so it classified nothing: the ring stayed a dash on a phone holding 31,194 records
of that very night. A foreground asks about today whether or not the strap handed it anything. **A writer this app already had is not a reader the screens
have**: the row, the stream and the subscription are three separate things and each one has to exist.


Home's `ACTIVITIES` card draws `viewModel.workouts`, and only two things refresh it: the view's `.task { … load(for: selectedDate) }`, which has already run by the time a pushed page is up and **does not re-fire when that page pops**, and `.onChange(of: selectedDate)`. A pushed page that writes a row and pops therefore leaves the row in SQLite and on no screen, and the screen behind it goes on showing yesterday's list — which reads exactly like *activities never get saved*. That was the live-session END button: `LiveSessionUseCase.end()` returns a `Summary` carrying the row it just wrote, and the button discarded it. The fast path above it had always been right, calling `HomeViewModel.updateWorkout(_:on:)` with the row `endFast()` returned, and the ordinary path now does the same: `LiveSessionView` takes a **required** `onEnded: (WorkoutSession) -> Void` and calls it after `end()` has awaited `saveWorkoutUseCase.execute(workout)` and before `dismiss()`, so Home is already drawing the row when the dismissal animation finishes.

Two things about the shape are load-bearing. **It cannot be an `onChange(of: useCase.isRunning)` on Home.** `end()` clears `isRunning` *above its first `await`*, deliberately, so the recording bar leaves the moment END is pressed rather than after a database write — which means that observer would fire before `saveWorkoutUseCase` has returned and re-read a day the row is not on yet. The callback fires after the write. And **the parameter is required rather than defaulted**, so a future call site has to decide what becomes of the row instead of inheriting a silent drop; the preview passes `{ _ in }` and says why.

`updateWorkout(_:on:)` is the right merge rather than an append: it replaces a row with the same id or adds it, then drops every row that no longer `covers(day)` and re-sorts by `startedAt`. The drop half is what keeps a session belonging to another day off the list, and §18 asserts both halves. **The absence rule is a different thing and not this bug**: `end()` deliberately writes nothing when the session captured no samples, no strain and no heart rate, so a session that measured nothing is an absent row by design rather than a row that failed to save.

**The same trap has a second shape: a writer with no caller at all.** The case above has a pushed page to blame, and this one does not — `TrackStepsUseCase` stores a new day total every second of motion while Home is already open, so there is no navigation and no user action that could hand the row across, and `load(for:)` had already read the day as empty. Home therefore held the `—` it read at launch for the whole session while `stepCounts` held a real count; switching day and back showed the figure, which is exactly what made it read as *steps are never recorded* rather than as a stale tile. The hand-off is `TrackStepsUseCase.stepUpdates`, a `nonisolated` multicast `AsyncStream<StepCount>` yielded **only after `saveStepCount` returns** — a subscriber that could see a figure the store cannot answer back is a live tile more current than the truth — and `HomeViewModel.observeSteps()` subscribes once from Home's `.task`, idempotent on `observeDevice()`'s rule because a subscription per day tap is the documented multicast failure. Two things about the reader are load-bearing: a write whose `date` is not `loadedDay` is **dropped rather than queued**, and `load(for:)` refuses to overwrite a live write it did not see — `liveStepWrites` is captured before the reads and compared after, because the store read was started first and a write landing in that window is newer than its answer. §14's `HomeStepTileTests` drives the tile with the screen already open and asserts the cross-day drop; §16's `TrackStepsUseCaseTests` asserts the published row is the stored one and that two subscribers both receive it.

## `ActivityKit` is unavailable on macOS, and the Live Activity is the family's widest member — three separate traps, none visible to `swift build`.

(1) `ActivityAttributes` is `@available(macOS, unavailable)`, so every line of `WhoopsyLiveActivityKit` and of `LiveActivityController`'s iOS branch sits inside `#if os(iOS)`; the `#else` branch declares **the same type name** so `DIContainer` holds one type with no `#if` of its own — `LocationTrackingService`'s shape. (2) **`Activity` is not `Sendable`** in the iOS 27 SDK — the swiftinterface conforms `ActivityContent` conditionally on its `State` and gives `Activity` no conformance at all — while `update`/`end` are `nonisolated async`, so every call sends the handle off the main actor and Swift 6 rejects it with *"sending 'activity' risks causing data races"*. There is no fix on this side of the boundary, so the import is `@preconcurrency import ActivityKit`; **conforming `ContentState` to `Sendable` is separately required** and is not the same fix — without it the same error names `ActivityContent` instead of `Activity`, and it too compiles on the host. (3) `ActivityConfiguration` has exactly **one** initialiser and `dynamicIsland:` is a required parameter returning a concrete `DynamicIsland` whose own initialiser requires all four of `expanded`/`compactLeading`/`compactTrailing`/`minimal` — omitting it is a compile error, not a lock-screen-only card.

## `Package.swift` points the executable at `path: "app"`, which on a case-insensitive filesystem is `App/`, and SwiftPM compiles a target's path recursively.

Widget sources under `ios/App/LiveActivity/` were therefore being compiled into the **host** executable, where `WidgetKit`'s `@main` bundle does not exist. The `WhoopsyApp` target carries `exclude: ["LiveActivity", "Map"]` for that reason, and **every new Xcode-only source directory added under `ios/App/` needs a matching entry** — the failure is a host-build error about a symbol that has nothing to do with the change. The two entries have different reasons for the same exclusion and only one of them is a `#if` away from working: `WidgetKit` exists on the host and its `@main` bundle does not, while `MapboxMaps` is an iOS-only binary artifact that could not be a dependency of this manifest at all. So `ios/App/Map/` is **the one module in this repository that neither `make build` nor `make test` nor the 2,889-assertion runner compiles** — only `make ios` sees it, and only through the Xcode target. That is why the offline card's seam is split where it is; see the offline-map gotcha below. The extension links the `WhoopsyLiveActivityKit` product and **not `Whoopsy`**, so it does not drag GRDB, CoreBluetooth and the five bundled resources (~1 MB) into a process with a hard memory budget; that is why the card's four-to-five `Theme` tokens are restated by value in `WhoopsySessionLiveActivity.swift`, and why changing one without the other is drift.

## A Live Activity outlives the process that requested it, and nothing can adopt one.

The card is system state, not app state: an app killed mid-session leaves a lock-screen card counting up from a start instant nothing is recording. This build has **no in-flight persistence and no BLE state restoration**, so a relaunch cannot resume — it can only end the card, which is `LiveSessionUseCase.endOrphanedLiveActivities()` reading `Activity<…>.activities` (not the in-process handle, which is precisely what did not survive) and running once from `MainContainerView`'s root `.task`, ordered ahead of the never-returning `trackStepsUseCase.start()`. **The timer is the one element that needs no update at all** — `Text(startedAt, style: .timer)` is drawn by the system from the wall clock in the widget's process — so a suspended app keeps a ticking clock over a frozen heart rate. `bluetooth-central` grants wake-ups rather than a background lifetime (Apple: the app is woken when a peripheral sends a value, is given around ten seconds, and "can't run forever"), so the two legitimately disagree and the timer must never be paused to hide it, nor elapsed computed from a sample count. The system removes an active activity after 8 hours and an ended one after 4, and `Activity.request` can be refused outright (`NSSupportsLiveActivities` absent, too many cards, feature off) — the catch sets `liveActivityError` and **the session keeps recording**, which is the absence rule applied to a capability.

## The route's GPS is the Live Activity's sibling: a capability seam whose `start()`/`stop()` must land on one instance, and whose four settings are each a way a route comes out wrong.

`DIContainer` holds `locationTracking` as a **stored `let`** for the same reason it holds `liveActivityController` as one — a computed property builds a fresh service per read, so the `stop()` would no-op against a manager that never started while the first kept the radio and the blue indicator up for the life of the process. Four things about `CoreLocationTrackingService` are constraints rather than preferences. **`allowsBackgroundLocationUpdates = true` is legal only while `ios/App/iOS/Info.plist`'s `UIBackgroundModes` declares `location`** — setting it without that entry raises `NSInternalInconsistencyException` at launch rather than being ignored, so the flag and the plist entry are a pair; without the mode a route stops growing the moment the screen locks, which is most of a run, so an iOS 17+ app on a pocketed phone has both. **`pausesLocationUpdatesAutomatically` defaults to `true`**, which lets CoreLocation decide the user has stopped and silently end the route at a rest stop — the session keeps running and only the route stops, so nothing on screen says anything. **`requestPermission()` must read `authorizationStatus` first and return it when it is not `.notDetermined`**: `requestWhenInUseAuthorization()` is a no-op on a settled status and iOS does not deliver `locationManagerDidChangeAuthorization` in that case, so a continuation parked unconditionally before the call is never resumed and the caller waits forever behind a prompt that never appears. And `distanceFilter` wants a few metres — zero writes a jitter cluster for a phone on a bench, and too wide cuts a run's corners. **A refused permission is the absence rule applied to a capability**: the session records on and `routeError` carries a whole authored sentence, with *denied* and *Location Services off device-wide* getting different ones because they are fixed on different screens. **The route is opt-in per session and off by default** — a toggle on `LiveSessionView`, never inferred, because this app does not classify activity type. The `(0, 0)` "not a place" rule lives on `WorkoutRoutePoint.isPlausible` and **not** in the service: the runner must not construct a `CLLocationManager`, so a rule written inside `didUpdateLocations` is a rule nothing can assert. Only `horizontalAccuracy < 0` stays there, because it is a fact about a `CLLocation`.

## The offline map is one object split into two halves, and the split is the layer rule rather than a design preference.

`USE OFFLINE MAP` — the second of `LiveSessionView`'s two map toggles, beside `USE LIVE MAP` and off by default — makes a session download a Mapbox tile region around where it started, and the activity detail page then draws the session's route on that region instead of on `MapKit`'s live tiles. The capability is therefore two protocols: **`OfflineMapServing`** in `Domain/Repositories/` is the control surface (`isSupported`, `state(for:)`, `download(regionID:latitude:longitude:onProgress:)`, `cancelDownload()`, `delete(regionID:)`) and is all `LiveSessionUseCase` may see; **`OfflineMapRendering`** in `Presentation/` adds the two drawing members — `map(route:unit:regionID:)` for a session with a path and `map(area:regionID:)` for one without — and is what can draw. `Presentation → Domain ← Data` runs one way, so a single protocol carrying either `map(...)` could not live in `Domain`, and a single one carrying `state(for:)` could not live in `Presentation`. **Two drawing members rather than one optional route**, because the two cards carry different values: a route is a path with a length and a speed, an area is a frame around the downloaded ground with neither, and folding the second into the first would make the no-route case a mode of the route card instead of its own. Both take the same `regionID` and both are resolved by the same `RouteMapRenderer.resolve(session:state:)`, so `.ready` is the only state that draws offline on either card and a failure anywhere still falls back to `MapKit`. **It is one object, not two**: `DIContainer.offlineMaps` is stored as `any OfflineMapRendering` and handed to `LiveSessionUseCase` as `any OfflineMapServing`, so there is no second instance that could disagree about which tiles are on disk. The two toggles are **a map choice, and both record the route** — the user's own correction of the first implementation, in two steps: *"those two buttons are just for which map gets used, two maps can't be used at the same time"*, then *"record route is bad wording, maybe should be 'USE LIVE MAP', they both record the route, just one is offline the other is live"*. So `USE LIVE MAP` and `USE OFFLINE MAP` are exclusive as **maps** — choosing one releases the other, and `RouteMapRenderer` draws one card — while the **route keeps running across the switch**: it starts with either and stops only when the last one goes off. The first implementation conflated the two. The live switch was labelled `RECORD ROUTE` and was the only thing that started the path, the offline switch stopped it, and turning the route on tore the downloaded region down — so a session could never hold both a path and the tiles that would draw it, and the offline route card was unreachable code on a phone. **One `CLLocationManager` is the constraint underneath**: `LocationTracking.start()` replaces the current stream rather than adding a reader, so the offline map never opens a second one — choosing it starts the route, and the region's centre is the first plausible point the route files. `routeStreamEnded` is what ends that wait when the GPS never delivers at all, rather than making a blind session sit out the ten-second timeout. `LiveSessionView` draws **one** map above END: the Mapbox card once the region is `.ready`, with the route drawn on it because both maps record one; the `MapKit` route card while the live map is the choice; and nothing while a download is merely in flight.
**The decision is the user's and is made before signal is lost** — never inferred from a connectivity check, because this app has no networking code to check with and a hiker in a dead zone cannot be asked the question once they are in one.

**A downloaded region has no geometry to read back, so the centre is persisted on the workout row — `v23`'s two columns — and that is what lets a route-less session draw anything at all.** Mapbox's `TileRegion` is an id and a tile count; there is no polygon to hand a map, which is why the download's centre and radius live in this app rather than being asked of the SDK. `workouts.offline_region_center_latitude`/`_longitude` are nullable and undefaulted (`addMissingColumns`, so a shipped migration is untouched), written by `LiveSessionUseCase.end()` from the fix the download already took, and cleared with `offlineRegionID`. They are **deliberately local-only**: a tile region belongs to one phone's tile store, so `WorkoutRecord+SyncRow` drops them on the way out and a row arriving from a sync stores `nil` — the two columns are the one place the "a fifteenth property is a compile error" rule has a named exception. **`offlineArea` requires both the region id and the centre**, so a row written before `v23` — or one from a sync — truthfully draws nothing rather than inventing a place. The area card's frame is `ActivityOfflineArea`: a box `visibleSpanFraction` (0.75) of `OfflineMapCoverage.radiusMeters` on a side, longitude widened by `1/cos(latitude)`, refused at an implausible centre or a cosine at the pole. `MapboxSetup.radiusMeters` forwards that same `radiusMeters` for the download circle, so the frame and the downloaded ground cannot drift.

**The area card is framed by a two-point `LineString`, and the line is never drawn.** `Viewport.overview(geometry:)` measures a geometry's bounding box, so two opposite corners of the region give exactly the box `ActivityOfflineArea` computed; building the corners instead would restate the framing in a second place. The `MapKit` fallback is `ActivityOfflineAreaMapView`'s own `Map(initialPosition:interactionModes: [])`, drawn whenever the renderer resolves to `.mapKit` — which is every state but `.ready`.

## The offline card keeps its drawing in `Presentation` and hands `ios/App/Map/` a single `AnyView`, and that is the whole consequence of the exclusion above.

The SDK lives outside the package in four files — `MapboxSetup`, `MapboxRouteMapView`, `MapboxAreaMapView`, `MapboxOfflineMaps` — which only the Xcode target compiles, so **the cards stayed in `Presentation` and the seam is at the picture.** `ActivityRouteMapView` and `ActivityOfflineAreaMapView` each take a `mapSurface: AnyView?` and apply the height, the clip shape and the accessibility sentence themselves, so the unverifiable module supplies one view that draws inside a frame the card has already fixed — rather than `ios/App/Map/` restating the route card's caption and its 220/48 height split, the area card's whole 220, the corner radius and either `spokenSummary`, every one of which would be checked by nothing until it was wrong on a phone. **Every file under `ios/App/Map/` is listed explicitly in `ios/Whoopsy.xcodeproj/project.pbxproj`** — the app target has no directory walk — so a new surface adds a `PBXFileReference`, a `PBXBuildFile`, a `Sources` build-phase entry and a `Map` group child, and until all four are there `make ios` fails with `cannot find '<Type>' in scope` in the module that uses it while `make build` stays green. The four numbers the surface *does* need — `lineWidth`, `startMarkerSize`, `startMarkerRingWidth`, `finishMarkerSize` — are `public static let` on `ActivityRouteMapView` so both surfaces read one definition, while the card-only constants stay `private` because a surface handed a frame never states one. `MapboxRouteMapView` repeats the card's no-interaction rule by name rather than inheriting it: `MapKit` settles it with `interactionModes: []` and Mapbox has no equivalent parameter, so every gesture is turned off individually, and `MapboxOfflineMaps` uses `GestureOptions` and **not** `.allowsHitTesting(false)` because Mapbox draws its logo and its "Improve this map" link *inside* the map view — disabling hit testing would leave the attribution present and the required link dead.

## `OfflineMapServing.state(for:)` is synchronous, and nothing about Mapbox is.

Every `TileStore` read is completion-based, so `MapboxOfflineMaps` keeps an in-memory `[String: OfflineMapState]` as the record and `prime()`s it once in `init` from `allTileRegions` — without that walk a relaunch would report `.absent` over tiles that are genuinely on disk, which is a card that silently stops being offline. Four more things about that file are constraints rather than style. **A cancelled Swift `Task` does not resume a `withCheckedContinuation`**, so the download is wrapped in `withTaskCancellationHandler` whose `onCancel` hops to the main actor and cancels the `Cancelable` — and because that cancel can land *before* the `Cancelable` is assigned, a `cancelRequested` flag is read back at exactly the point `self.inFlight = load` runs; both paths are main-actor, so the ordering is serialized, and without the flag the continuation is never resumed and the caller waits forever. **The terminal state is committed before `download` returns**, because `LiveSessionUseCase` reads `state(for:)` on the very next line and a state written a turn later reads as `.downloading`. **The style-pack load is deliberately non-fatal**: the trailhead-with-no-signal case is exactly the one where everything needed is already cached, so a failed style pack logs and returns rather than failing a region that would have worked. And **`MapboxMapsOptions.tileStoreUsageMode` is set explicitly** — a `.disabled` mode draws a blank card over tiles that are present, which is the one failure this feature cannot afford. **The safety property is the gate, not the code**: `RouteMapRenderer.resolve` draws the offline surface from `OfflineMapState.ready` alone, and every other state — `.absent`, `.downloading`, `.failed` — draws the `MapKit` card, on both the route card and the area card, because both read the one resolution, so the worst outcome of a bug anywhere in `ios/App/Map/` is the card this page drew before the feature existed and never a blank one. `.ready` is only ever set on provable completeness (`requiredResourceCount > 0 && completed >= required`), and a region that came up short is recorded `.absent` so the next open can retry.

## The Mapbox credential is two tokens with two different homes, and neither is in this tree.

The **public** `pk.…` token lives in `ios/App/Config/Whoopsy.local.xcconfig`, which is **gitignored** — untracked at the owner's request even though Mapbox's model treats a public token as embeddable. It reaches the app through the key, not by being pasted into it: that file defines `MBX_ACCESS_TOKEN`, `ios/App/iOS/Info.plist` holds `$(MBX_ACCESS_TOKEN)` under `MBXAccessToken`, and that key is the one thing `MapboxSetup.configure()` reads — Mapbox's own documented mechanism, so the token can move without the read path moving. **It is the second of two xcconfig files and that split is load-bearing rather than tidy.** `ios/App/Config/Whoopsy.xcconfig` is **tracked**, carries no token, sets `MBX_ACCESS_TOKEN` empty and ends with `#include? "Whoopsy.local.xcconfig"` — the *optional* include, skipped silently when the file is absent — and because an xcconfig assignment is last-one-wins, the include coming last is what lets the token override the empty default. The reason the token is not simply in the base file: `Whoopsy.xcconfig` is the app target's `baseConfigurationReference` on **both** Debug and Release, and `xcodebuild` treats a base configuration it cannot open as a **hard error** — `Unable to open base configuration reference file` — failing the build before a single source file compiles. A token file named there would make every fresh clone unbuildable; behind `#include?` its absence is merely unconfigured. `ios/App/Config/Whoopsy.local.xcconfig.example` is tracked so a clone knows what to create. **Two values make `configure()` return `false`**, and the first is what a fresh clone actually hits: an empty token, which the committed base file supplies on its own, and a value that is not a Mapbox public token — which is what `MapboxSetup.publicTokenPrefix` is for, accepting only `pk.` so a **secret** `sk.…` pasted into the wrong file is refused rather than shipped. A clone that has not been through `README.md` §Building therefore gets `UnavailableOfflineMaps`: the switch is never offered and the card draws `MapKit`, with no crash and nothing half-configured. **Do not "helpfully" paste a token into `Info.plist` or any other tracked file**, and do not merge the two xcconfigs or delete the committed one — those are the edits this arrangement exists to prevent. The **secret** `sk.…` token, scoped `Downloads:Read`, goes in `~/.netrc` **only** and is needed merely for SwiftPM to *resolve* the binary package — never in the repo, never in the project, never echoed into a file in the tree, `chmod 0600`. **Without it `make ios` fails at package resolution in a way that reads like a network error rather than an auth one**, which is the diagnosis to make first when that build breaks. **`configure()` must run before any Mapbox object is constructed** — `MapboxOptions.accessToken` is a `static var` that has to be set before `TileStore.default` exists, and `MapboxOfflineMaps.init` builds one immediately — which is why `WhoopsyApp.offlineMaps` gates the *construction* on `configure()`'s return rather than merely calling it. Two risks are recorded rather than resolved. The `#if canImport(MapboxMaps)` import is guarded and the call site is guarded by the same condition rather than trusted to agree with it, so a build whose package failed to resolve degrades instead of crashing. And **Mapbox Maps v11 sends telemetry**: `Sources/MapboxMaps/SwiftUI/Map.swift` calls `sendTelemetry(\.swiftUI)` and the SDK ships a `TelemetryCounter`, while the only network kill switch found (`OfflineSwitch.shared.isMapboxStackConnected`) must stay **on** for downloads to work at all — this app calls itself 100% offline and `.gitignore` calls this data de-anonymising, so locating a supported disable path is a stop-and-report step and not a tidy-up. `MapboxOptions.accessToken` / `MapboxMapsOptions.tileStore` / `.tileStoreUsageMode` are also cross-module `static var`s a Swift 6 client may diagnose; there is no alternative spelling, and the diagnostic would be loud and name its lines. **And linking MapboxMaps makes `LD_RUNPATH_SEARCH_PATHS` on the app target load-bearing, which it had never been** — measured 2026-09-29, the first launch of a build with the SDK linked died in dyld with `Library not loaded: @rpath/MapboxMaps.framework/MapboxMaps`, `termination.indicator: Library missing`. **The framework was embedded correctly and the build was green**; what was missing was the rpath. `ios/Whoopsy.xcodeproj`'s hand-written app target declared no `LD_RUNPATH_SEARCH_PATHS` at all, so neither `WhoopsyApp` nor `WhoopsyApp.debug.dylib` carried `@executable_path/Frameworks` — `otool -l <binary> | grep -A2 LC_RPATH` showed only `@executable_path`, `@loader_path` and SwiftPM's `PackageFrameworks`, while the LiveActivity appex, which *does* declare the setting, had it. Both configs now carry `LD_RUNPATH_SEARCH_PATHS = ("$(inherited)", "@executable_path/Frameworks",);`. **Nothing in this repo could have caught it**: `make build` and `make test` never compile `ios/App/Map/`, `make ios` only compiles, and the failure is at process start rather than at build time — so a Mapbox-linked build is not verified until it has been installed and launched.

## An activity's zone percentages divide by measured time, not by a sample count, and the five bands must not be made to sum to 100.

`LiveSessionAccumulator` accumulates `Σ min(5.0, Δt)` as its denominator — the same clamp `CalculateStrainUseCase` applies — so a figure computed from `samples.count / 60` is a fabricated duration of exactly the kind the deleted workout HUD shipped, and on a 1 Hz stream the two coincide, which is what makes it invisible. The five band percentages are deliberately **not** `WholePercentMath.wholePercents(ofSeconds:)`: that helper makes a column sum to exactly 100, which would claim the five zones cover the session, where time below zone 1 is a real part of it that belongs to no band — the same reason `workouts.csv`'s `HR Zone n %` block sums to at most 100 and 45 of its 673 rows read `0` in every band. **Time below zone 1 is not weightless any more, though it stays bandless**: the low-intensity band in `StrainAccumulatorMath.loadDelta` credits a heart rate above resting but below zone 1 at weight 1.0 with `zone: nil`, so it contributes *load* while contributing no *zone duration*. `strain` is `nil` until a sample arrives, `0.0` once one arrives at or below resting, and a small positive figure once one arrives above resting but below zone 1; a calorie figure is `nil` whenever no weight is on file. **Those percentages have no screen reader, and the screen's bar is not them.** The live session screen draws a *position* scale — the five bands laid end to end with a white mark where the current heart rate sits — which answers "where is the reading" rather than "where did the session's time go", so it consumes `Snapshot.bandScalePosition` and not `zonePercents`. `StrainAccumulatorMath.bandScalePosition(forHeartRate:zones:)` reads the scale's two ends off the session's own `[HeartRateZone]` table (zone 1's floor and zone 5's ceiling) rather than recomputing them from `zoneReserveFractions`, so a profile whose reserve falls under `computeZones`'s 20 bpm floor still marks against the bands it was scored on — and its clamp is the ordinary case, because a heart rate at rest is below zone 1 by construction. The three fields `zoneSeconds`, `zonePercents` and `recentHeartRates` are kept and asserted with no screen reader: they are the only observable form of the state behind the two denominator rules above, and deleting them would drop §18's assertions.


## A strength figure is this app's own definition, and a measured zone day is not compared against an imported baseline.

The strain page's card draws four rows, and **two of them were dashes for a stated reason until 2026-10-27**.
The zone rows had one producer — WHOOP's `HR Zone n %` block out of the bundled export — so a session this
app recorded itself (no block, by design) showed nothing even though the strap had recorded every beat.
The fix reuses the activity page's rule rather than writing a second one: a session's band time comes from
`ZoneTimeMath.totals` over its own samples when they exist, and from the block when they do not, measured
first. **`ActivityZoneRow`'s rule and `StrainDayActivity`'s are the same rule, and the second must not grow
a variation.**

**The comparison is the part that is easy to get wrong.** The strain page's zone baseline is a mean over
the trailing thirty days of *blocks* — that history is read as rows, and folding thirty days of samples per
page open is not affordable. Printing a measured day's figure against that mean would put two producers
under one arrow, which is the defect `ActivityZoneBaseline` refuses for the same reason. So the baseline is
withheld whenever every session behind the day's figure was measured
(`StrainDayActivity.ZoneTime.isMeasuredOnly`), and the row draws its figure with no marker rather than a
comparison it cannot stand behind.

**`STRENGTH ACTIVITY TIME` had no producer at all**, and the honest reason was that WHOOP's list marks a
subset with `^` and no public source enumerates them: the support article renders no list to a fetch and a
search finds only the definition, not the membership. So the app defines its own set — the four catalogue
entries that are unambiguously resistance training, in `WhoopActivityCatalog.strengthActivities` — and a
strength figure is **this app's**, not a reproduction of WHOOP's. Two consequences are deliberate: the
figure is a session's whole measured span rather than a subset, and a day holding a workout but no strength
session prints `0:00`, because no time spent on strength work is a reading, while the day with no workouts
at all is `nil` — the same day the whole card is absent on.
## `UserProfile` carries eleven fields and `user_profiles` stores eight of them, so every unbacked one is a number this app invented — and a body metric is the dangerous kind.

`weightKg: 75.0`, `heightCm: 178.0` and a `-28`-year birth date were initialiser defaults that no row could override, and `GRDBUserProfileRepository.getUserProfile()` returns a hardcoded `maxHeartRate: 190 / restingHeartRate: 60` when no row exists at all. A defaulted `weightKg` is the dangerous kind, because `CalculateStrainUseCase` feeds it into `StrainAccumulatorMath.estimateCalories` — so a calorie figure rests on a body the user never described. `v16_profile_weight` adds that column nullable and undefaulted — NULL is the honest value for a fact nobody supplied, exactly as `source` documents — `UserProfile.weightKg` is optional with it, and `estimateCalories` returns `nil` rather than a number when it is absent. **`v20_profile_body_fields` finishes the sweep, and it is where the rule's second half is written down.** It adds `name`, `birthDate`, `gender` and `heightCm` — all nullable, all undefaulted — and the three invented defaults go with them: `"Athlete"`, a birthday 28 years before *now* (not merely invented but **unstable**, being relative to the moment of construction, so a defaulted column would have moved at every launch), and `178.0` cm. **Those four are a different category from the weight and saying so is the point**: they are *declared* facts — the user supplies them, the user is the sensor, and they feed no model, being saved and read back onto the form and consumed by nothing else in `ios/Sources/`. The rule this app holds was never "collect nothing unread"; it is **"do not let the app invent a number"**, and a fact the user types is the opposite of an invention. `178.0` cm is the failure the rule actually names, and it is a collected field that makes it one: an invented default is worst exactly where the mockup invites the user to correct it, because that is when the app reports its own number back as theirs. The two heart rates deliberately stay non-optional and keep their defaults: they are the inputs the Karvonen zones cannot be built without, so an absent one is not an absence a screen can draw, it is a zone table that cannot be computed at all. **When adding a field to `UserProfile`, check whether a stored column backs it** — `grep -rn "<field>" ios/Sources/` for a consumer first, and add the column or leave the field out rather than letting an initialiser default divide into something. **And when adding a column to `user_profiles`, carry it through the mapper in both directions**: GRDB's `save` is INSERT-or-UPDATE over the **whole row**, so a `saveUserProfile` left carrying fewer fields than `UserProfileRecord` declares silently writes `NULL` over the rest on every save — no throw, no log, and it surfaces as a form that is empty on the second launch. §18's round trip is the assertion that sees it, and it is why the record's own doc comment points at the repository.

## `Text` prints Markdown asterisks literally unless it is handed a `LocalizedStringKey`.

A literal takes the `LocalizedStringKey` overload, which parses Markdown, but a **concatenated `String`** takes the `StringProtocol` one, which does not — so `Text("**High Sleep Stress is not measured.** WHOOP reads it from …")` renders the asterisks and any `*emphasis*` on the screen. Nothing in this repo can catch it: no test has a renderer, and a `Text`'s string is invisible to the compiler. Write emphasis as its own `Text`, an `AttributedString`, or `Text(LocalizedStringKey(…))`; never as `**…**` inside a string built with `+`.

## Home's calendar is an overlay, not a `.sheet`, and the difference is load-bearing.

It hangs from the top of the safe area over a `0.45` black scrim, so the screen behind stays legible; a `.sheet` is a full-height card the system centres and would put the grid in the middle of a dark slab with Home invisible behind it. Home also hides the tab bar while it is up, because an overlay inside a tab **cannot cover the tab bar** — the `TabView` draws it above its content — so leaving it visible would put a live row of tabs under a modal, and a tab switch would strand `isPresentingCalendar` set and reopen the calendar on return.

## `SleepSession`'s `Equatable` cannot compare two reads of the same night.

The struct carries `let id: UUID`, its initialiser defaults that to a fresh `UUID()`, and the synthesised `==` includes it — so two `getSleepSession(for:)` calls on one unchanged row are never equal. Compare the fields you mean.

## SDNN and RMSSD are different quantities and never share a baseline.

Every `recovery` row carries `hrvMetric`; `RecoveryScoring` is the only place that filters history by it. Mixing them computes a z-score between two distributions and silently mis-scores every day.

## The within-sleep stress model's baseline is drawn from prior *nights*, and reading it from days instead is the mistake that looks like success.

**It became reachable when the first real strap night landed, and its first execution crashed the sleep page.** The report is an `EXC_BREAKPOINT` in `Array._checkSubscript_mutating` two frames under `AnalyzeSleepStressUseCase.eligibleWindows(in:span:)`, called from `SleepViewModel.resolveSleepStress(for:from:)` inside `load(for:)`. The cause is a floor used as a bound: `bucketCount = Int(length / StressMath.windowSeconds)` and then `buckets[Int(offset / StressMath.windowSeconds)]`, guarded only by `offset < length`. A span that is **not** a whole number of windows — which is every span built from real sample timestamps — leaves a trailing remainder whose offsets divide to exactly `bucketCount`, one past the array. Every fixture in §15 was synthetic with a span of exactly `n × windowSeconds`, so the one shape a fixture could not produce was the one the hardware produced. The fix drops the partial window (a third of a window has no complete `stress windowSeconds` of stillness to score) rather than padding a bucket, and §15 now drives `eligibleWindows` directly with a remainder span plus an integral control.



`AnalyzeSleepStressUseCase` collapses each of the previous `StressMath.baselineDays` nights to one `(RMSSD, heart rate)` point **from that night's own in-bed span**, one bounded read per night — not one wide read over the preceding fourteen days, and not `RecoveryScoring.baselineWindow`. A day-scoped read pulls in fourteen days of *waking* samples that the model then discards, which is both the wrong population and a second filtering step that can be got wrong; the failure is silent, because a night scored against a daytime baseline is still a number in range on a card that looks right. Two consequences are load-bearing. The prior nights are **handed in** (`execute(for:priorNights:)`) rather than fetched, so the page's cards cannot describe two different night sets, and the use case takes no `SleepRepository` at all — which is what makes that structural. And the model is **unreachable on every night this machine can show**: `biometric_samples` holds no rows in any database here and the export carries no R-R series, so all 910 imported nights have none permanently; it is also unreachable for a new user with a strap, because a score is a z-score and below `StressMath.minimumBaselineDays` (3) there is nothing to draw. §13's RSA caveat applies to §15's night blocks verbatim: the fixtures are synthetic tachograms and a passing run is not evidence about a real strap.

## A fixture that pins a z-score must account for `BaselineStatisticsMath`'s coefficient-of-variation floor.

`baseline(_:fallbackMean:fallbackStdDev:)` returns `max(observedStdDev, |mean| × minimumCoefficientOfVariation)`, so a three-point history with a small spread has the *floor* as its denominator, not its own spread — a heart-rate baseline of 54/60/66 gives 6, but 58/60/62 gives 3 and not 2. Every literal downstream moves: a window built to score 2.0 scores 1.667. Real histories reach the floor easily (which is why it exists), so this is a fixture author's trap rather than a model defect — pick a spread that clears `5%` of the mean before pinning a score against it.

## The export's day key is `startOfDay(Wake onset)`, and that is the app's own convention.

`CalculateRecoveryUseCase` writes `date.startOfDay` and reads the sleep session *for that same date*, so a recovery row for day D comes from the night that ended on D's morning. The export's `physiological_cycles.csv` is one row per cycle, and keying those on `Cycle start` would collapse 935 rows onto 753 days — silently dropping a fifth of the history. `WhoopExportImporter` keys on the wake onset for every row that has one. Verified against the real file: 910 wake rows → 910 distinct days, zero collisions, and 933 `Day Strain` values → 931 distinct days.

## The importer's `calendar:` parameter cannot override the database's day-key snap.

`LocalDatabaseManager.save*` snaps with the `Date.startOfDay` extension, which is `Calendar.current` and is not injectable. Handing `WhoopExportImporter` a calendar in another zone does not shift its day keys, it *splits* them — the importer computes `startOfDay` in one zone and the database re-snaps in another, so a UTC midnight lands on the previous day and every key is wrong by one. Production passes `.current`, so the two agree; a test or a new caller must too.

## 24 export cycles have a `Day Strain` but no wake onset.

They are fragments that never closed, so they become `strains`-only rows. Two of them start at 23:30 and 23:48 on a day a closed cycle already claims (2024-02-11, 2024-03-20), and their day is genuinely unknowable — so the closed cycle takes the day and the fragment defers. That is why 933 `Day Strain` values produce 931 `strains` rows, and it depends on the device zone: a fragment near midnight lands on a different date in a different zone. `ios/Tests/WhoopsyTestRunner` §11 recomputes the expected key set rather than hardcoding it. The three day-level counts in `WhoopImportSummary` (`daysWritten`, `strainOnlyDays`, `duplicateExportRows`) are accumulated from those key sets as the walk goes, because they cannot be recovered from the per-table row totals: on this export the arithmetic shortcut for strain-only days gives 21 where the truth is 22, since one scored day carries no strain. `duplicateExportRows` exists because a skipped row has two possible causes that look identical — a day that already held data *before* the import ran, and a day an *earlier row of the same import* claimed. Only the first is `daysAlreadyRecorded`; counting the collision rows there made a fresh install report "2 already recorded locally" when nothing was.

## The need baseline is learned from prior stored needs, and learning it from achieved sleep would erase the deficit.

`SleepNeedBaselineMath.personalBaselineSeconds` inverts each prior night's stored need
(`need − clamp(strain, 0…21) × 6.40 min`) and takes the median of the last 28, once there are seven.
It deliberately does **not** learn from the hours actually slept: a person carrying a sleep deficit
sleeps less than they need, so a baseline learned from achieved sleep would drift down toward the
deficit and quietly erase the shortfall the need exists to express. The age band is only context —
the cold-start value below seven nights, a floor at the band's lower bound, and a 9.5-hour cap. A
birthday entered later can move the cold-start value and the floor for future strap nights; it does
not re-score stored needs, and imported nights keep WHOOP's `Sleep need (min)`.

## A strap night's Sleep Need is computed; an imported night's is WHOOP's own, and the two must not be crossed.

`SleepNeedMath.sleepNeedSeconds(baselineSeconds:previousDayStrain:)` returns the learned baseline plus `6.40 min × the previous day's strain`, and `AnalyzeSleepUseCase` reads that strain row from `strainRepository` at `startOfDay(morningDate) − 1 day` — the *previous* day, because `strains` is keyed on `startOfDay(wakeOnset)` and the cycle preceding the night ending on D is keyed D. Three things about it are decisions, not oversights, each with its basis in `docs/ALGORITHMS.md` §4: the coefficient is **fitted to the bundled export** (WHOOP publishes this model's shape and none of its constants — 6.40 is the pinned-intercept least-squares slope over the 909 nights carrying a preceding strain day, and the cross-validation curve is flat from 6.4 to 7.0, so the reproducible fit is shipped over the marginally luckier one), a **`nil` strain returns the baseline exactly** rather than a plausible strain, and the **accumulated Sleep Debt term WHOOP names is deliberately absent** — a judgement, not a measurement: a fitted 7-night deficit buys 0.35 of a point (3.77 → 3.41) for a second fitted constant and seven nights of history, and WHOOP's own `Sleep debt (min)` column does no better (3.43), so there is no hidden headroom. A `0.20` carryover over a 7-night deficit is measurably harmful: written out, it scores 18.44 against the flat 480's 10.06. Imported nights store the export's `Sleep need (min)` verbatim, so a need *below* the 8-hour baseline exists in the database and is correct; the suite's §13 is what fails if anyone routes them through the formula. The strap path's baseline is learned by `SleepNeedBaselineMath` from the person's prior stored needs, with the age band as cold-start/floor context; `UserProfile.targetSleepHours` is no longer read.

## The sleep detail screen's card is titled `HOURS OF SLEEP`, and that title is a figure the card prints rather than a label on the chart beneath it.

The reference's card carries the night's asleep total with the window's mean under it and draws the heart-rate trace *inside* the same card, so the screen's headline quantity is sleep and the trace is the recording sitting below it. The headline is `SleepStageRangeScoring.Summary.asleepSeconds` (`SleepSession.totalTimeAsleepSeconds`, the three sleep stages) read through `MetricChange` against `typicalAsleepSeconds`, the window's mean of it; the card prints `DURATION` further down, and the two are related by an identity a reader can check on the screen itself — **`asleep + awake = DURATION`**, the awake term being the fourth row. That identity is why the headline is the entity's own property and not a subtraction written on the view, and §15 of the suite asserts it. **The headline and the chart are gated apart, deliberately**: the figure is a *reading*, present on every imported night, while the trace is a *recording* that needs `biometric_samples` rows — so gating the figure on the chart would hide a real reading behind an absent one, which is the fabrication every absence rule in this app exists to prevent. Below the headline, `SleepTypicalRangeCard` draws the night's four stages as a share of the sleep period over a hatched remainder, with the band that share is normally in drawn as **one filled region with a dashed rule down each of its sides** — built by `SleepStageRangeScoring`, drawn by `TypicalRangeBar`, and the rules stroked by `BandEdges`, which traces two vertical lines and no closing segment. A region bounded by two rules rather than two marks because two lines say where a band's edges are while a region says the two edges bound *one span*, which is what a range is; the card's header carries a glyph of the same mark as its key to it. **The bar's own styling is measured off the reference rather than picked.** The hatch is a *dark* texture on a light ground — the reference's track reads `(60,64,68)` and its stripes `(39,43,47)` — which is why `Color.black.opacity(0.30)` over `ringTrack` reproduces its stripe to within a unit, and white over the track draws a shimmering dark band where the reference has a quiet light one. Its period and stripe width are `10.9` pt and `3.85` pt — a **1:1 duty cycle**, quoted as the horizontal run a 45° stripe makes across the scan because that is the axis `HatchShape` walks. And the share is a plain rectangle clipped to the track's shape, not a capsule: a capsule's radius is half the bar's height (`9.8` pt at the default `20`), which bulges the share's trailing edge into a semicircle and rounds the track's corners to over twice the reference's. The clip is what makes the share's leading end round and its trailing end flat in one move. **The corner radius was solved for rather than read off**, because an anti-aliased corner's last pixel or two fall below any threshold and its visible extent is therefore not its radius: the reference's profile (`3.42`, `1.71`, `0.85` pt of inset at `0`, `0.85`, `1.71` pt below the bar's top) was matched against this app's own render at a radius the file names, and the two agree at `4.5` pt. **Measure this bar on the share's leading edge** — the one edge with nothing hatched over it. The same scan across the remainder is confounded by the stripes, and in the reference the card background and its hatch stripe differ by one unit of luminance, so no threshold separates them; that image is also a 2× upscale of a ~1.17 px/pt source, so its rows quantise in pairs and one source pixel is `0.85` pt, which is the floor on every number above. **`SleepStressShareBar` is that bar's sibling and restates those three constants by value** — `stripeSpacing 10.9`, `stripeWidth 3.85`, `trackCornerRadius 4.5` — rather than extracting a shared sub-view, because the alternative was a refactor of `TypicalRangeBar` that the existing bar-layout assertions cannot see. The two bars differ in what they draw: `TypicalRangeBar` draws a share *against a range* and owns `BandEdges`; the stress row draws a share alone. So the constants are now written down twice and **changing one without the other is the drift `WholePercentMath` and this file's other extractions exist to prevent** — if the reference's stripe is ever re-measured, both files move. **WHOOP publishes no stage boundaries**, so the window and the percentile are this app's own; only two halves are reused rather than invented, `RecoveryScoring.baselineWindowDays` and `.minimumBaselineDays`, so this card and the Recovery screen cannot come to disagree about how much history a baseline needs. **The band is in percentage points of the night, not in the minutes WHOOP quotes its own REM middle-50% in** — the bar's track is a 0–100% scale, so a band in minutes could not be drawn on it. `WholePercentMath.wholePercents(ofSeconds:)` is largest-remainder because the card prints `DURATION` above the column those percentages divide, and the export stores whole minutes, so naive rounding produces a column summing to 101. The card is **absent, not empty**, on a night with no sleep period — four `0%` rows would be a picture of a night — but a *thin window* is a different state and is drawn: shares and durations are readings the night really has, so only the bands are withheld. **The heart-rate chart reads a real table** — `HoursOfSleepChartSeries` off `biometric_samples` over the night's own window, drawn by `HoursOfSleepChartView`, with a gap longer than `HoursOfSleepChartSeries.maximumGapSeconds` (300 s) breaking the line rather than interpolating across it, and a sample whose `heartRate` is `0` refused as a point rather than plotted at the axis foot. **Those types are named for the card and not for the quantity** — the series and its axis are `HoursOfSleepChart*` because they are drawn inside the `HOURS OF SLEEP` card and nowhere else, while their points stay `Point.bpm` and their labels stay `30/50/70/90`, because a `bpm` payload under a name that says hours is a name that lies about a quantity. Reaching for either half alone re-creates the mistake: `SleepHeartRateSeries` read at the call site said the card was *about* heart rate, and `Point.hours` would say a bpm is an hour. It is not a tachogram: one point per *notification*, not per beat, which is why `BiometricSample.timestamp`'s arrival-instant caveat does not bite here. The axis is **fixed at 30–110 bpm with its own gridlines** and widens in steps only to include a reading outside it, on `StressMonitorChartView`'s rule that an auto-scaled chart draws two different nights as the same picture. What is unchanged is that **no strap has ever filled that table**: `biometric_samples` holds 0 rows in every database on this machine, and the export carries no HR series at all (only a per-cycle daily average), so all 910 imported nights have none permanently and every one of them draws the chart's `No Data` state. That state sits in the chart's slot and speaks for the chart alone, because the headline above it is a real reading; a hypnogram is not a substitute for it either: `v12` now stores one for a strap night, but the export produces none (it reports stage totals and no timeline), so no night this app can show has stages to draw. So the chart is gated on strap sync, not on an algorithm, and `No Data` on an imported night is the correct output rather than a bug. **What makes it absent today is that no strap has ever been connected, not that the strap cannot produce one.** The live `0x2A37` path is implemented end to end (`WhoopBLEManager` → `BiometricSample` → `StreamBiometricsUseCase`) and yields instantaneous HR at each beat from `60000 / rr`, needing no sampling rate. And the historical drain is the stronger path: 4.0 flash records are one per second of wear with **their own absolute unix time at `[7:11]`**, so a night the app slept through is fillable with no app running (`docs/BLE_PROTOCOL.md` §5) — it is not implemented (16-byte walk through a 96-byte header, no ACK/token loop, the `RTC_LOST` wrong-day trap) and is sequenced after the screens. `docs/TODO.md` §5 carries the gap.

## A mark positioned by `.offset` inside an `overlay` must sit in an explicit `ZStack(alignment: .leading)` with an explicit full-width frame — a bare `ForEach` there is centred in a box sized to its widest sibling.

`.overlay(alignment: .leading) { ForEach { … .offset(x:) } }` lays the group out at the lane's leading edge but centres each mark *within* a box as wide as the widest one, so every narrower mark starts `(widest − thisOne) / 2` to the right of where its own offset puts it. Measured on the simulator in `SleepTimelineView`: an asleep lane whose runs were 101, 50.5 and 50.5 pt drew its two narrow runs `+25` pt right — into the gaps between them — and an awake lane of 457 and 355 pt drew its second run `+51` pt right, past the end of the asleep run it should sit under, with the last mark hanging off the card's right edge. **Nothing catches it**: every mark keeps its correct *width*, the lane keeps its correct extent, the two lanes still look like a plausible night, and a lane whose runs happen to be equal width draws correctly — so an equal-band probe and the whole test runner both see nothing wrong. `SleepNeedStackedBar` is this arrangement done right. Verify by measuring a lane's mark edges against `laneOrigin + fraction × laneWidth` on a fixture whose runs are **unequal and touch both lane edges**; do not verify it by looking at the picture.

## A `ScrollView` whose content holds nothing flexible lays out at its content's width, so a page whose only child is a fixed-size drawing needs `.frame(maxWidth: .infinity)` on the scroll view or its background paints a column.

`StrainDetailView` is one 190 pt `GaugeRingView` plus `.padding()`, so a page 222 pt wide draws `.background(Theme.backgroundDark)` as a centred column with the `UIWindow`'s black down both sides — which reads as the background being wrong without being one. Its two siblings, `RecoveryDetailView` and `SleepDetailView`, are the same shape and are safe only because their content is cards, which are themselves `.frame(maxWidth: .infinity)`, so nothing warns the next card-less page and the result reads as a deliberate dark column rather than as a layout bug. The tell in a screenshot is a pure `#000000` band at both edges; measure it rather than looking, because black beside the app's own near-black looks like a styling choice.

## The sleep-consistency chart holds two minute scales, and the bridge between them is one function that must not be inlined.

`SleepConsistencyMath.nightClockMinutes` is **noon-pivoted** — `0` is noon, `420` is 7 PM, `720` is midnight, `1140` is 7 AM — because the model measures distance *across* midnight and needs one contiguous run to do it; `Date.formattedClock(minutesOfDay:)` takes **minutes past midnight**. A night-clock value handed straight to the clock formatter prints twelve hours out and says nothing about it: `714` renders `11:54 AM` where the chart's frame means `11:54 PM`, and every pinned literal in the suite moves with it. `SleepConsistencyMath.clockMinutes(fromNightClock:)` is the only bridge and `SleepClockAxis.clockText(forNightClockMinutes:)` is its only caller — convert there rather than at a call site, which is how one of three sites drifts. That type is where the scale lives now, because two charts on the page draw against it: the consistency card's five spans and the time-in-bed card's seven. `SleepConsistencyChartLayout.clockText` forwards to it.

## The consistency card's legend says `AVG`, not `OPTIMAL`.

Nothing in this app produces a recommendation: there is no circadian-phase model and no sleep-need-derived bedtime target in any column, so the two dashed rules are the mean of the four nights the score already reads and nothing more. WHOOP's word is a claim about what the user *should* do and this app cannot make it — the same judgement that labels Home's VO₂ figure `(EST.)`. Renaming the label to match the mockup would put a claim on the screen that no code makes.

## `sleeps.respiratory_rate` and `sleeps.sleep_debt` are two-producer columns, and the model that computes one of the producers is unvalidatable.

Both are stored verbatim from the export for an imported night and computed for a strap night — `RespiratoryRateMath` and `SleepDebtMath` respectively, called from `AnalyzeSleepUseCase` and stored, not resolved on read. **Nothing but `source` distinguishes them**, exactly as `sleeps.sleep_consistency` already documents, and `nil` is the only marker for "not scored" — so a model must never be run over an imported row, and the suite re-imports the export and asserts all 910 nights still carry WHOOP's own pair. **The two producers' debts are not the same quantity, and only one of them is a term of the need printed above it.** WHOOP's need is a total that contains `need_from_sleep_debt` (the fit over the export recovers the debt at coefficient 0.98); `SleepNeedMath`'s deliberately omits any debt term (`docs/ALGORITHMS.md` §4). So `need − debt` is WHOOP's base-plus-strain on an imported night and a base requirement short by the whole deficit on a strap night, where both rows would sum to the printed total and both labels be false. **`source` is therefore read, and `SleepSession.hasWhoopSleepNeed` is what carries it**: `GRDBSleepRepository.makeSession` resolves it from `record.source`, it is `false` for a strap night and for any row written before the column existed, and `SleepNeedBreakdown.breakdown(needSeconds:debtSeconds:hasWhoopNeed:)` withholds the split on `false`. Do not gate that split on the debt being non-`nil` — every strap night has one, so that test never separated the producers. **The `SLEEP DEBT` column reaches the screen through the hours-vs-needed card's breakdown box**, not as a row of its own — so the stored value has a reader. **The `RESPIRATORY RATE` column reaches one a different way**: `CalculateRecoveryUseCase` copies it onto the `recoveries` row that `RecoveryDetailView` and its week chart read. The respiratory estimator is the one number in this app with **no ground truth anywhere**: the export carries no R-R series at all, so `biometric_samples.rrIntervalsMs` is empty in every database on this machine, and the estimator's constants come from published window lengths plus a synthetic noise measurement rather than from a fit. The suite validates its *plumbing* — a known modulation is recovered, a gapped series is refused, a below-band modulation is declined — and **not** its accuracy; do not read a passing run as evidence the strap path produces a correct breathing rate, and do not present a screenshot as evidence either, since every night this app can show was imported. `docs/ALGORITHMS.md` §4 carries the constants, the measured error bar, and the two failure modes that survive (`edgeGuardBins` covers leakage from outside the band; **folding** does not, and a 40 bpm modulation is reported as ~20).

## Every imported `strains` row holds WHOOP's own score, not this app's.

The export has no heart-rate series, so `StrainAccumulatorMath` has nothing to integrate and `WhoopExportImporter` stores the `Day Strain` column verbatim. This is the only place a stored strain value comes from a different algorithm, and the only way to tell is the `source` column. Zone breakdowns are empty for every imported day for the same reason — which is why the deleted `StrainDashboardView` drew "No zone data recorded.", a sentence that no screen says any more and that must not be re-added as a second route to a figure the strain detail page now draws off `workouts.csv`. **The strain detail page's two `HEART RATE ZONES` rows are the same kind of number from the same file and are the one place this app displays a zone**: they are WHOOP's own `HR Zone n %` out of `workouts.csv`, scaled by each workout's span and summed over the day, so they are a measurement this app reads rather than one it computes. They are not `StrainScore.zones` — that array is computed from `biometric_samples` and dropped at the write, and it exists for today alone, so drawing it would show a real figure on today and a dash on every past day. The five percentages sum to **at most** 100 (the remainder is time below zone 1, which WHOOP publishes no column for), so zones 1–3 plus 4–5 is deliberately not the workout's duration, and 45 of the file's 673 rows read `0` in every band — a **measured** `0:00`, which must not be drawn as the dash an absent block draws. A session this app recorded itself carries no zone block, so the user's rule applies to it: `nil`, and a dash. **The activity detail page is that block's second reader, and it derives a row's two figures from one number so they cannot contradict each other.** `ActivityZoneRow` computes `percent = hrZonePercents[i]` and `seconds = percent / 100 × durationSeconds` — one division of one share of one span. Two consequences follow, and both are properties of the file rather than choices. **Every one of the 3,365 `HR Zone n %` cells in `workouts.csv` is a whole number** (measured, zero fractional values), so the reference's `ZONE 1 … 0% · 0:00:12` is **unreachable here**: WHOOP computes its seconds from a finer internal share and rounds only the percent for display, while this app is handed the already-rounded percent, so `0%` implies exactly `0:00` and `1%` of a 958-second session implies `0:09`. A **fractional** percent is refused outright rather than rounded — a fraction is a value from some other producer, and rounding it would invent a reading instead of losing one. The rows draw hardest-first, and the two absences stay separate: a `nil` block is `—` on all five, while a stored `0` is a **measured** `0%` beside `0:00:00`. **The BPM boundaries are this app's and the shares are WHOOP's** — the edges come from `StrainAccumulatorMath.computeZones`, the same table the strain path scores with, which on a fresh install is the cold-start 190/60 pair, and the card says so on its face for the reason Home's VO₂ figure is labelled `(EST.)`. Zone 5's top end prints open (`177+`) rather than `177-190`, because that ceiling is the profile's nominal maximum and a strap reports a rate above it the moment a session is harder than the profile assumes. **A row's time is split for drawing at its last colon, and that split is a `nonisolated static` on the value type rather than arithmetic in the view.** `ActivityZoneRow.durationParts(_:)` divides `0:05:38` into a dim `0:05` and a bright `:38` — the reference's own emphasis, which points at the seconds because they are the part that moves — and it splits at the **last** colon so the trailing half keeps its colon and the two halves still read as one duration when they are drawn side by side. It lives on the type for this repo's standing reason: the runner has no renderer, and a rule written into a `body` is a rule nothing can assert. A string with no colon comes back whole with an empty tail, which is the dash an absent block draws.

## WHOOP's HRV is classified as RMSSD, and that is an inference.

The export does not name the quantity in its `Heart rate variability (ms)` column. It is called RMSSD because WHOOP publishes overnight HRV as rMSSD and the observed distribution (52.5 ± 10.5 ms, range 15–99) fits that band. It matters because of the never-mix rule: the classification decides which baselines the imported days join. The claim is made in exactly one place (`WhoopExportImporter`, passed as `todayHrvMetric: .rmssd`) and its basis and falsification test are in `docs/ALGORITHMS.md` §1.

## Importing recomputes Recovery rather than storing WHOOP's.

The export's `Recovery score %` column is not written anywhere: the importer feeds WHOOP's *measured* inputs to `RecoveryScoring` so one formula covers all 910 imported days and every day after. Historical percentages therefore will not match the WHOOP app, which is the accepted cost of not putting two models on one chart. The same reasoning makes `SleepSession` derive its own performance rather than use the export's `Sleep performance %` column. **Read that disagreement era by era, never over the whole file.** The export has a 137-day recording gap (2024-12-31 → 2025-05-17) and WHOOP's column is a different function either side of it: before the gap it **is** the app's expression — 423 of 451 nights exact, 28 off by one from rounding, MAE 0.062, and a fit that recovers `asleep/need` at coefficient +100.04 — while after it only 33 of 459 match, at MAE 7.05 and a worst case of 51. The whole-file count of 454 is 28 + 426 and says the opposite of the truth about the older half. Post-gap the column is a composite: predictable from these columns at MAE 3.61 but not recoverable, and its linear fit has a −32 intercept, so it is not WHOOP's formula. The column **is** parsed (`WhoopExportRow.sleepPerformancePercent`) and read by nothing; the figure on every screen is the app's own, `clamp(asleep ÷ need × 100, 0, 100)`. **Re-measure by driving that property** — the clamp is part of the answer (15 nights carry more stage time than need; dropping `min(100, …)` reports 457).

## `simctl launch` on an already-running app does not relaunch it, so a screenshot can show the previous build's code.

The sequence that works is `terminate` → confirm it succeeded → `install` → `launch` — **### Running on a simulator** above carries the commands and this bullet carries why each step is there. Two of those steps have a silent failure mode: `terminate` exits non-zero with *"found nothing to terminate"* when the app is not running, and `install` over a running app replaces the bundle on disk while the live process keeps executing the old one — so a `launch` that merely foregrounds it renders the old view. The tell is two screenshots taken either side of a visible source change coming back **pixel-identical**, which reads exactly like a modifier that did nothing. `uninstall` is the other way to force a cold start and is **wrong here** — it drops the data container, taking the imported export with it. **`make ios` does not build the bundle you install on a simulator, and this is the third way the same false green arrives.** It passes `-destination 'generic/platform=iOS'`, so it compiles and relinks into `Build/Products/Debug-iphoneos`; `Debug-iphonesimulator` is left holding whichever simulator build ran last, and `install`ing that path after a `make ios` therefore installs a bundle that does not contain the edit — with `** BUILD SUCCEEDED **` printed twice and no warning at any point. Compare the product's own mtime against the source's before believing it (`ls -la …/Debug-iphonesimulator/WhoopsyApp.app/WhoopsyApp.debug.dylib` — the ~58 KB `WhoopsyApp` stub beside it is not the code), or build the simulator explicitly, which is the only command that refreshes it and the one to use with the `rm -rf …/Debug-iphonesimulator/Whoopsy-t.build` above:

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  xcodebuild -project ios/Whoopsy.xcodeproj -scheme WhoopsyApp \
  -destination 'platform=iOS Simulator,id=55511A6D-ED4D-4405-941C-FB0DFF107662' \
```

## Repositories answer from local storage and nothing else.

There are no fallback sources: `GRDBRecoveryRepository`/`GRDBSleepRepository`/`GRDBStrainRepository` take only `db:`, and a day with nothing stored returns `nil` (or an empty history) rather than a substituted row. **The cloud decorators were the exception that proved it, and the exception is gone.** They answered a local miss from the database — unconditionally for the three history windows — so on a `.cloud` install a screen's content could depend on a request, and a Home load measured at 32–39 s on 2026-10-27 was waiting on none of it. `DIContainer` now constructs all seven with a closed read window, so their cloud branch is unreachable by construction; a fresh install is filled instead by `RestoreFromCloudUseCase`, the one deliberate pull, which runs on a launch that finds no days **or when the user presses `RESTORE`**, and writes what it finds into the phone's own tables through the sync stores. **The press is the one call this app makes outside its window** — every other request is refused between midnight and 18:00 Eastern — because the app's traffic is a schedule and a person pressing a button is not, which is why `DIContainer` builds the restore's client open and `restoreIfNeeded` keeps the window check instead. Anything else makes "no data" indistinguishable from a measurement, which is the failure mode every no-data rule in this file exists to prevent. `RecoveryRepository.getLocalRecovery(for:)` reads identically to `getRecovery(for:)`; it is kept as a separate name because it is what a caller *about to write* should call, and the name is the only place that intent is recorded.

## An estimate about the person is read from the last measured day, never from the day on screen.

**Measured 2026-10-29, on the Health tab's Whoopsy Age dial: it drew `—` on a phone holding eighty
years of history.** The rule is not about the dial. The tab asks `HealthMonitorViewModel.load(for: Date())`
— *today* — and a day with no measurement has no `recoveries` row, because this app stores no
placeholder for one. That is the absence rule working exactly as designed, and it is fatal to any figure
that reads only the day it was opened on: `Home` opens on today, and after any gap today is empty. The
estimate was computed from `getRecovery(for: today)` returning `nil`, so the risk profile was `nil`, so
there was no multiplier, so there was no age — while the same database held hundreds of measured nights
behind it.

**The fix is a second window and a printed date, in that order.** When the day holds no measurement the
view model reads back at most `healthspanLookbackDays` (365) — `endingOn: day`, so a row written after the
day on screen can never leak backwards — and takes the **last** row holding a measurement, which is the
most recent only because the repository promises oldest-first (`mostRecentMeasured(in:)` states the order
rather than trusting it: a reversed read would pick the oldest night in the window and still look
plausible). 365 rather than unbounded: past a year the profile describes someone the wearer may no longer
be, and a dash says that better than a stale number. And the card then **prints the day** — *"From your
last measured day, Aug 22, 2026"* — because a number that is right and undated is a number that reads as
today's.

**The general rule, which is why this is here and not only in `docs/PAGES.md`:** a page whose subject is
*the person* must not source its inputs from *the day the page happens to open on*. Fitness, resting rate
and step count are facts about a body; the calendar is not what they are indexed by. The tell is a screen
that dashes while the database is full — and the remedy is to ask *which day was this actually measured*,
not to fill the gap with a zero.

**Two riders, both found in the same repair.** A dash cannot say which of three different things is
missing, so `LongevityAbsence` carries the reason (no measured night / no birth date / no life table) and
the card prints the matching sentence — one of them is a field the reader can fill in immediately. And the
`BIRTHDAY` row that answer points at had existed since `v20` and drew a bare, unlabelled `—`, because its
three controls were built with `DatePicker("BIRTHDAY", …).labelsHidden()`; the field was reported as
missing by the person it belonged to, while the column behind it was collecting the value. A control whose
only name is its accessibility label is a control with no name.

## A night's evidence is rotated out by the drain that produced it, and the stillness spine's input was never validated.

**Measured 2026-10-30, on a night the app reported as its first thirty-one minutes.** The owner sent
both capture files and the two probe dumps; the `NIGHTS check` line that survived carried a stored end
hours before a watermark that had reached the following morning, with `dataEdge=false owed=false` — so
the classifier had seen the night's input and still ended the night where it did, and the gate that
re-opens a night as it grows had already decided not to. **The line that would have said *why* —
`SLEEP inputs`, with
the per-spine window counts — was gone**: `capture.txt` is capped at 64 KB and one morning drain writes
hundreds of `DRAIN_BATCH` lines, so the classifier's four lines a day rotate out behind the drain's
thousands. Two nights of logs therefore could not separate *judged awake* from *had no windows*, and the
two need opposite repairs.

**The fixes are instrumentation, deliberately, because neither the data nor the log could decide.** A
fourth capture file (`Documents/decisions.txt`) takes every `SLEEP`/`NIGHTS`/`RECOVERY` line beside the
shared one, so a decision survives the next drain — `RECOVERY` is in it because the answer to "why is my
recovery 40%?" is a pair of z-scores and their spreads, and it has the same rarity and the same enemy as a
night's verdict. `AnalyzeSleepUseCase.logStillness` prints, **per spine**, the
window count and the `p10`/median/`p90`/max of `meanMagnitudeG` against the ceiling that judges it — a
`p90` above the ceiling is a calibration fault rather than a restless night, and `n=0` next to a night
that exists is the sample spine having produced nothing at all.

**The verdict that froze it was a rule, not the data, and that rule is repaired in `stager-v2`.** A night
recorded *ended at the data edge* only when **no** epoch followed it, so a classification that overlapped
a drain — a few live epochs at the tail, the night's own records still arriving — stamped *trimmed at a
wake*. Everything after that end is then wake time by the gate's own rule, and the row never moves again.
The test is now a **hole**: evidence resuming within the onset grace is the same night continuing,
evidence resuming later means the night ended where its coverage did. A hole is self-healing — filling it
stops the answer being `true` — which is what a grace window is not, and why the gate does not go back to
churning on every foreground.

**And the third probe exists because the stillness spine's input had never been checked.**
`AccelerometerCandidateProbe` dumps `R18` body 24's three `f32` per drained record, gated on the same
0.5–2 g band `HeartRatePayloadDecoder` refuses outside, with a per-drain `in-band=` summary. The
prefix's other two probes each answered an ambiguous offset; this one answers the one that the whole
sleep classification rests on, and it was the only one never asked.

**The thread this comes from matters as much as the fix.** One earlier night was refused with a few
hundred epochs over a thirteen-hour window, its hourly curve printing only the hours at the edges; a
night in between printed every hour. A night whose stillness comes only from the connected edges is a
night whose span is the connected window — which is exactly the thirty-one-minute answer above.

row: it runs from the foreground after the night refresh, and scores a day only when the stored row says

nothing on the row could say what it had been computed from. `v39` gave `recoveries` the pair `strains`
and `sleeps` already had — `algorithm` and `scored_through`, both local-only — so `isOwed` is now two

**The clear is the part that bites, and Home had it too.** `HomeViewModel.load` nil'd `sleepScore` at its

## One serialized connection is every screen's read latency, so the store is a pool and its reads leave the actor.

**Measured 2026-10-27, from the user's report that the Recovery and Sleep pages took "a few seconds" to
fill on a phone that already held the row.** Nothing on either page computes — they read — so the wait
was not work, it was queueing, and there were two queues. `LocalDatabaseManager` held a single
`DatabaseQueue`, which serialises *every* operation the app makes, reads included: one screen's read
waits for the strain tick's whole-day fold, a drain's bulk write, or the recovery scorer's night read.
And the manager is an `actor`, so a synchronous method held its mailbox for the whole call as well — a
pool behind an actor would not have helped.

**Both halves were needed.** On disk the store is now a **`DatabasePool`** (WAL, one writer, concurrent
snapshot readers); in memory it stays a `DatabaseQueue`, because a pool has no file to open. And the
read methods are **`nonisolated`** — they touch only `dbQueue`, which is `Sendable`, the argument
`rekeyMislabelledStepDays` already recorded — so they run off the actor and a long call cannot hold the
mailbox. Writes stay isolated: SQLite has one writer anyway, and the ordering work belongs where the
mailbox is.

Two consequences to keep in mind. **A read now sees a snapshot taken when it started**, so a page that
begins reading while a writer is mid-transaction answers from before it — which is what a pool means and
is why nothing may assume two separate repository calls see one another's writes. And **the pool is the
arm every device build launches on while every host test opens an in-memory queue**, so it needed a test
of its own: §7's `LocalDatabasePoolTests` opens a real file under `tmp/`, migrates it, writes through it
and reads back. Without that block the pool would be compiled and never executed — the shape of a
migration that crashes the app at launch with a green suite.

## A day that was not measured gets no row, and the same test must be on both sides of the write.

`CalculateRecoveryUseCase.execute` and `CalculateStrainUseCase.execute` return an optional and write nothing when they produced no measurement, which is how `AnalyzeSleepUseCase` has always behaved. The rule is one sentence: **a writer may persist a row only when it produced a measurement, and the test it uses must be the same test its readers use.** `RecoveryMetric.hasMeasurement` is `hrvValueMs > 0`, so the guard has to be that comparison made against the value *as it will be stored* — `CalculateRecoveryUseCase` rounds to one decimal **before** guarding, because an RMSSD below 0.05 ms passes on the raw value and is still written as `0.0`. Guarding on the interval count instead is a different test: `HeartRateVariabilityMath.calculateRMSSD` returns exactly `0.0` when `filterRRIntervals` leaves fewer than two beats, so one surviving interval writes a `0.0` ms row that the type's own readers call unmeasured. On the reading side, `RecoveryScoring` filters placeholders out of every baseline, `HealthKitImporter` fills a day whose row is unmeasured instead of skipping it, and `RecoveryDashboardView`, `StrainDetailView` and the Home rings render one as `—` rather than a red 0% or a confident `0.0`. **That list is shorter than it was** — `StrainDashboardView` was its third name and is deleted — and it is worth knowing which of the three the `assertions=` count actually covers: the suite asserts `StrainScore.hasMeasurement`'s value directly, so the reader list is a description of the app rather than a guarantee the runner makes about it. A day with no *sleep* session contributes `BaselineStatisticsMath.sleepPerformancePivot` (0.70) to an otherwise-measured day — the value that shifts the score by zero. **`RecoveryMetric.hasMeasurement` and `StrainScore.hasMeasurement` are reader tolerance, not a marker any writer sets**: rows written before this rule are still on disk holding zeros, and the gates are what keep them off the screens, the baselines and the charts. `StrainScore.hasMeasurement` is a **required** initialiser parameter with no default, deliberately: a default of `true` would let a construction site silently mark a placeholder measured, which is the exact bug the flag exists to prevent.

## Absence is the same shape in all four metrics, and that is the point.

Recovery, Strain, Sleep and Stress all report a day with no measurement as **no row**, with the optional as the answer. A reserved zero row is the weaker design: every reader has to remember to exclude it, and a reader that forgets imports an unworn day as a real score or plots it as a measured `0.0`. An absent row cannot be mistaken for data by a reader that forgot the rule. Do not reintroduce a placeholder to make a keyed table "tell nothing from zero" — that is what the optional is for.

## The persisted and wire `sleep_performance` is the sufficiency ratio, not the ring's composite.

`SleepSession.sleepSufficiencyPercentage` is `asleep ÷ need`, and that is what `GRDBSleepRepository` writes into `sleeps.sleep_performance`, what `SleepSyncRow.sleepPerformance` sends, and what the backend's 0–100 field is bounded and documented for. The ring prints `SleepScoreScoring`'s composite instead — a local, derived figure that needs prior nights and an age. Do not repoint the column or the wire field at the composite: the backend and Recovery are calibrated on the ratio's distribution, and a future reader would silently get a different quantity under an unchanged name.

## The same `SLEEP PERFORMANCE` label means the composite on the sleep page and the ratio on the Recovery page.

The sleep detail ring and its weekly chart read `MetricDay.sleepScore`; the Recovery page's `SLEEP PERFORMANCE` row and its chart read `MetricDay.sleepSufficiency`. The user chose to keep the Recovery page pixel-identical while the ring became a composite, so the shared label now names two quantities. `docs/ALGORITHMS.md` §4 records the difference. Do not "fix" it by renaming one side or by feeding Recovery the composite — Recovery's 0.70 pivot is calibrated on the ratio.

## The sleep score renormalizes over whichever components a night has; coverage below four is not a full score.

Each of sufficiency, efficiency, restorative and timing is absent when it has no denominator, and the score is the weighted mean over the terms that remain — 85 points when timing is missing, 55 when sufficiency is. Fewer than two terms is no score at all. The `Coverage` lives on `SleepScoreScoring.Score` for the tests and a future UI; the screen deliberately adds no caption or row for it. A three-term score is a real score about less data, not a night that failed a fourth term.

## The week chart needs `MetricWeek.sleepScoreLookbackDays` (19), not 7 or 14.

Every slot's composite reads its own consistency against its four predecessors, and the oldest of the seven slots needs records from before the window — up to `SleepConsistencyMath.historyLookbackDays` (12) before it. Home therefore reads 19 days; the sleep page's 180-day read is wider, and the Recovery page's chart stays the ratio so it does not need the composite. A caller that hands `MetricWeek` only seven days still draws seven slots, but the oldest ones silently lose their timing term to the age fallback or to absence.

## The composite treats a zero need as unavailable, while the legacy sufficiency property returns 100.

`SleepSession.sleepSufficiencyPercentage` guards `targetSleepNeedSeconds > 0` with a hard `100`, which is the row's figure on such a night. `SleepScoreScoring` computes its sufficiency component from the raw durations and treats a zero need as **absent**, so the composite renormalizes instead of awarding full marks. The two are asserted together in the tests; the divergence is deliberate and is the one place the old and new figures can disagree loudly.

## Sleep has no placeholder: an unclassifiable night is an absent row.

`AnalyzeSleepUseCase.execute(for:)` returns `SleepSession?` and returns `nil` — writing nothing — in **two** cases that answer different questions: the overnight window holds fewer than `minimumEpochSamples` (30), or it holds no run of sleep long enough to count as a night (the bullet below). Rows carrying exactly `4.2/1.8/1.6/0.4` hours in `sleeps` are literals rather than measurements — a night assembled that way stores a strap left on the charger as a full night's sleep and then scores it as one. Every reader therefore takes an optional: `SleepDetailView` and the Home ring render `—`, and `SleepViewModel.session` is `SleepSession?`. **`SleepDetailView` is the reader now because it is the only screen left** — it replaced `SleepDashboardView` in this sentence when the Sleep tab was deleted, and the sleep ring and the `SLEEP` activity row both push it. Recovery needs no special case — its sleep term falls back to the pivot above, which is a defined constant.

## A strap night's span is *detected*, and the run is measured in wall time — never in epoch count.

The session's boundaries come from `SleepOnsetMath.sleepPeriod(of:)` — the first and last runs of consecutive 30-second `MotionEpoch`s that are both **quiet** (mean `|a|` < 1.05 G) and below the night's own **onset ceiling** (the lowest third's resting rate × 1.10 — a margin above a *sleeping* rate, not the stage bands' 1.25, which multiplies an awake one), whose own span reaches `minimumSleepRunSeconds` (600) — rather than from `samples.first` / `samples.last`, which are the edges of the 9 PM → 10 AM **read window** and not the night. **Motion is what makes this an onset detector rather than a heart-rate stager**: a heart rate cannot separate sleep from lying still awake, so an epoch that moved is awake even when its rate sat low. A window with no motion epochs is an absent night, not a guess — which is the case a night of no sleep presents. **The ceiling is measured from the window and the stage bands are not**, because the two answer different questions: with no profile row the stage bands' reference is a cold-start 60 bpm, and an awake evening at 69–75 then read as sleep from the 9 PM edge — while putting the bands on the measured 51 bpm collapsed deep sleep to 0.04 h. The measured rate decides *when the night began*; the profile's decides *which stage*. **The run is measured from the epochs' own `start`/`end` instants, and substituting a count of epochs breaks it**: a stride is 30 *samples*, which is 30 seconds only if the samples arrived a second apart, so at 60 s spacing one epoch spans 29 minutes and a count-based rule reads twenty minutes of unbroken sleep as "one epoch, not a night". Awake epochs *between* the two ends are WASO and stay counted; the sums are recomputed over the retained epochs so `asleep + awake == duration` still holds. **The detector cannot see quiet wakefulness, and no run length fixes that**: `accelerationMagnitude` is `|a|` in Gs so a still strap reads ≈1.0 and the awake test needs `> 1.25` G **or** `> 1.25 ×` resting HR, so an hour of lying awake reading classifies as light sleep — a sustained run by construction, which satisfies every `SO1`/`SO5`/`SO10` form alike. The trim removes movement- and HR-elevated edge time and nothing more; do not describe it as removing all time before sleep onset.

## A channel the strap has no sensor for is `nil`, not a plausible constant.

`SleepSession.disturbanceCount` and `.respiratoryRate` are optional and `sleeps` stores both as nullable, and a disturbance count exists only for a night the classifier could read. A defaulted `respiratoryRate: 14.0` handed out on every row a repository reads back, or a literal `14.4` written on the strap path, is a fabricated reading rather than a measurement. When adding a field to a domain entity, ask which path actually produces it; a defaulted number on a stored row is a fabricated reading. **`BiometricSample.accelerometerX` / `.accelerometerY` / `.accelerometerZ` are that rule's more dangerous instance, because a motion reading is not merely stored — it is thresholded.** All three are `Double?` and `accelerationMagnitude` is `Double?` with them, `nil` unless every axis is present. A defaulted `0.0` is **free fall**, which is physically unreachable on a body and lands on the *still* side of every movement threshold — a fabricated zero reading as "measured, and perfectly still". The two consumers answer the same absence in opposite directions on purpose: `AnalyzeStressUseCase` **refuses** the window, because its gate exists to assert stillness; `AnalyzeSleepUseCase` **drops** the motion test and lets heart rate decide, because its motion tests sit beside a heart-rate band that can decide alone. (The strap does have a *derived* respiratory rate since `RespiratoryRateMath` — see the gotcha below — but it is derived from the R-R series, not read off a sensor, and it is `nil` for every night that series cannot support.) **`MetricDay.respiratoryRate`, `MetricDay.sleepSufficiency`, `MetricDay.asleepSeconds`, `MetricDay.deepSleepSeconds`, `MetricDay.remSleepSeconds`, `MetricDay.sleepOnsetMinutes` and `MetricDay.sleepWakeMinutes` are the seven fields in `MetricWeek.makeDay` passed through with no gate**, and a gate must not be added: every other field there tests `hasMeasurement` (and RHR also `> 0`) because its column has a reserved zero, while respiratory rate is optional on the row *and* on the slot — so the optional already is the whole rule — and the other six are read off a classified night, so there is no column and no zero to reserve — **a night has a start and an end or it has neither**, which is the whole of why the boundary pair is a pair. The need is the one sleep field that *is* gated, on `targetSleepNeedSeconds > 0`, because that field is a denominator: a zero need is not a need of zero. Adding a gate to any of them would let a week chart omit a mark the row directly above it prints — the same value, read through `RecoveryMetric`, `SleepSession.sleepSufficiencyPercentage`, `SleepSession.totalTimeAsleepSeconds` and `SleepSession.deepSleepSeconds` / `.remSleepSeconds` respectively, none of them gated. All seven are excluded from `hasAnyMeasurement`, and the reasons differ: the sleep-performance, asleep-total, deep, REM and boundary-pair exclusions are **redundant** — all six are read off the same night as the need, which is already in the list, the same as the VO₂ estimate — while the respiratory-rate one is **load-bearing**: a night can carry a respiratory rate with no HRV, so it is the field that could make an otherwise-empty day count as measured on a chart that draws neither quantity. The deep/REM pair and the boundary pair are the fields in that list a chart *draws*, on another screen — `RESTORATIVE SLEEP (HOURS)` and `TIME IN BED`, both on the sleep detail page. The deep/REM pair are the one pair carried as a **split with no total stored beside them**: a third number between them and the figure the chart labels each column with would be free to disagree with the two bands it stacks. **The boundary pair is in the model's own noon-pivoted frame and not minutes past midnight** — `0` is noon, `420` is 7 PM, `720` is midnight — so a caller printing one goes through `SleepConsistencyMath.clockMinutes(fromNightClock:)`; see the two-scales gotcha above, which is the failure this pair's `sleep`-prefixed names exist to make visible. Sleep performance's own fabrication risk is `SleepSession.sleepSufficiencyPercentage`'s `guard targetSleepNeedSeconds > 0 else { return 100 }`: unreachable on stored nights, because every imported row carrying a wake onset carries a need and the strap path computes one, but pinned by an assertion rather than left as a claim.

## A D1 migration file must not end on a comment, and the failure does not name the file.

`backend/migrations/*.sql` is read by `readD1Migrations`, which splits each file with wrangler's `unstable_splitSqlQuery` — and that splitter attaches a comment to the statement that *follows* it. Keep every paragraph above the SQL it introduces and end the file on a `;` and nothing else. `0001_create_recoveries.sql`'s own header carries the rule for whoever copies it; this bullet is for whoever writes the next one from scratch. **The other half is the rule the app already has**: D1 records an applied migration's *identifier* and does not checksum the body, so a schema change is a new numbered file and never an edit to a shipped one — including `0001`, whose `user_id` partition column is there precisely so a later auth pass needs no row rewrite.

## The remote diagnostics path is one seam and it is metadata-only; the Sentry edge lives in the app target, not the package.

`Data/BLE/` reports protocol facts into `Diagnostics` (`Core/Logging/Diagnostics.swift`), which is a lock-guarded optional sink and names no vendor. `WhoopBLEManager` emits `connect_pass`, `drain_refused`, `drain_started`, `drain_concluded`, `standard_hr_frame`, `proprietary_frame`, `live_hr_frame`, `strap_event`, `command_response` and `historical_record` — each one-shot per link except the drain events, which are per drain. **What goes in an attribute is a count, a frame type, a sequence number, a payload length or an outcome name, and nothing else.** No heart-rate value, R-R interval, oxygen candidate or sample timestamp may be added: the sink a real build installs is a third-party network service, and the Anonymous diagnostics caption on `More → Settings` promises the toggle never uploads a biometric. The oxygen probe's raw values therefore stay in `Documents/spo2-candidate.txt` and reach no network path.

**The SDK is linked only by `Whoopsy.xcodeproj`, and the guard is what keeps the host build honest.** `ios/App/iOS/SentryDiagnostics.swift` is the only file that imports Sentry, in `#if canImport(Sentry)`. The host executable target (`path: "app"`) compiles that file — it is directly under `App/iOS/`, which is not in `Package.swift`'s `exclude:` list — and takes the `#else` arm, so `make build` and the suite compile the fallback and the SDK stays absent from `ios/Package.swift`. That is the same arrangement as `#if canImport(MapboxMaps)`, and it is why adding Sentry did not touch the suite's link globs. Measured on 2026-10-18: host build compiles `SentryDiagnostics.swift` and links clean; `make ios` resolves sentry-cocoa **9.30.2** and the product dylib carries its symbols.

**Two failures are silent, and both were checked rather than assumed.** The first: the `org-slug#code` string Sentry's onboarding hands an AI coding assistant (`whoopsy#effa32dacb`) is **not a client key** — downloading `@sentry/agent-plugin` shows it installs an editor plugin and reports setup progress — so pasting it into `WHOOPSY_SENTRY_DSN` would configure nothing, and the correct value is the project's **Settings → Client Keys (DSN)**, `https://<key>@o<org>.ingest.sentry.io/<project>`. The second: an xcconfig reads `//` as the start of a comment, exactly as it does for `WHOOPSY_API_BASE_URL`, so a DSN written with its plain scheme truncates to `https:` and `SentrySDK.start` either refuses it or installs a client that cannot send. It must be written `https:/$()/key@o….ingest.sentry.io/…`; `Whoopsy.local.xcconfig.example` carries that form and the reason.

**The toggle starts and closes the SDK rather than filtering afterwards**, because Sentry's options are fixed at `start`: re-assigning `enableLogs` after the fact changes nothing. `SentryDiagnosticsSink` is `@unchecked Sendable` behind an `NSLock` because `record` arrives on the BLE queue while `setEnabled` arrives on the main actor, and the two flags have to move together. With no DSN — every clone, since `WHOOPSY_SENTRY_DSN` expands to `""` — `install` returns without installing a sink, `Diagnostics.record` returns immediately, and no socket is opened; the toggle is then a switch with nothing behind it, which is the honest state of an unconfigured build. §16 asserts the seam itself (delivery, the empty-attribute event, the toggle, replacement and `install(nil)`); it cannot see the metadata rule, which is a property of the call sites.

## A destination is a switch and not a mode, and the only thing that removes a row is the day purge — and it deletes from the database first.

*"if a DB is selected, it doesnt purge anything, it just switches where data will be stored to."* So a write goes to this phone **and nowhere else**; the once-a-day run at 18:00 Eastern is the only uploader, because a step row is written once a second and a per-save mirror exhausted the deployment's call budget. A read answers locally and reaches the database only on a miss **inside that window**, and `SyncSettings` is one destination, the span the user drew, and the day of the last automatic run. **The whole provenance model went with the purge it existed for**: the two cutoffs, the two boundary predicates that decided which side of one a day was on, and `pendingWork`. A settings value an older build left in `UserDefaults` is **deliberately not migrated** — it is orphaned, and a migration would be a second place the old shape is still believed. §22.7 is the sweep that fails the moment a `delete` returns, on the port, on the seven stores or in a resource it no longer serves. **And a local delete is not a delete while the destination is the API — it is a cache eviction.** The next read is a local miss, the decorator reaches the database, and a writer that seeds itself from that read (`TrackStepsUseCase`) resumes from the cloud's copy: measured 2026-10-20, a repaired 47k step row came straight back on the launch that cleared it. **That last sentence is now a control rather than advice, and the order in it is the whole design.** On 2026-10-29 the same owner asked for three calibration-era days to be removed *"in cloud, those 3 days should be removed, use sync api"*, and `PurgeDaysUseCase` does exactly the two steps the failure above prescribes — the database first, then the phone — as one operation. **A failed server call aborts and deletes nothing locally**: a purge that cleared the phone and reported a server failure would produce precisely the state this entry records, so the refusal is the feature rather than an edge case. The ruling it replaced was the owner's own (*"if a DB is selected, it doesnt purge anything"*) and so is this one; what did not change is that nothing else deletes — no per-row door, no delete on a batch, nothing a sync can reach for — and §22's sweep was rewritten to say *exactly one* rather than *none*.

## A cumulative motion counter's delta is not a step, and the source byte is part of the rule.

The strap's `R18` record carries a `u16` cumulative "selected step/motion counter" at frame offset 57 — the community reference's reverse-engineering, not a capture on this project's hardware — and the only correct reading of it is a **wrap-aware difference**: `(current − previous) & 0xFFFF`. Summing the counter itself (or its low byte) explodes the total, which is the bug the community reference records as a ~24× over-count; a delta of 512 or more is a wrap or a reboot boundary rather than 512 steps and is dropped, and a delta larger than four times the interval's own seconds is a discontinuity whatever the class says. **Three fields beside it are all ways the delta lies**: the activity class at 63 (`0` still, `1` walk, `2` run — a still-classed delta is coverage with no steps), the source marker at 64 (`0x10` means 57 holds the software counter and the hardware one has moved to 61, so a delta across a switch subtracts one instrument from another and is dropped), and the timestamp, which must move forward or the record is a duplicate or an out-of-order replay and is dropped **without advancing the continuation**. **The counter is taken as one tick per step and nothing here fits a divisor**: the community reference exposes a per-user `stepTicksPerStep` whose default is 1.0, and this app has no capture to fit another, so a wrong scale is a calibration waiting for hardware rather than a bug to paper over with a constant. The one-shot `step_counter` diagnostic records the first sample of a connection for exactly that reason. `StepCounterAccumulator` owns none of the day's totals — a delta can cross midnight while today's live motion is running — so the totals live in `TrackStepsUseCase`'s ledger, and that ledger is persisted **before** the row it produces because `stepCounts` has no provenance column to split a stored total back into its two sources. Offsets and status: `docs/BLE_PROTOCOL.md` §6; the rule: `docs/ALGORITHMS.md` §7.

## A drain re-covers the window the live detector already counted, and banked motion must not feed the detector.

`MotionPayloadDecoder` accepts a banked `R21` record from a drain as readily as a live one, and a drain's `R21` motion and its `R18` counter describe **the same span** — so a step writer that read both would count every drained step twice. `TrackStepsUseCase.ingest` refuses any batch whose timestamp came off the strap (`timestampIsFromStrap`), and the counter owns all history; `RecordMotionUseCase` still consumes that batch for sleep epochs, which is why the refusal belongs to the consumer and not to the stream. **Inside a drain, the counter's coverage end is the authority**: a counter record that overtakes the live tail drops it, because those detector steps are about to be counted again — the few seconds of lag between the drain and the live edge cost their steps once and return in the next interval. **The first counter record for a day replaces that day's detector total rather than adding to it**, and the stored day seed is dropped at that moment: steps from earlier in the day that the drain does not cover are lost once, which is the migration cost of a source change and is documented rather than hidden. The rule is §7 of `docs/ALGORITHMS.md`; the assertions are §16.

## A `HISTORY_END` marker's head is the drain's clock, not its records'.

The `HISTORY_END` payload's leading `u32` decodes to the drain's own instant — on the owner's 5.0 on 2026-10-23 it was the phone's wall clock — while the five records the marker closed were stamped **`2026-08-24 12:51:13`** onward. A live-edge test that reads the marker therefore declares "caught up to now" over two months of unread backlog, ends the drain after one batch, and reports it as `caughtUpToLiveEdge`; every drain on that strap returned the same 59 records and the cursor never advanced far enough to matter. **The newest record's stamp is what decides**, from a `u32` at payload `[4]` in every historical layout this app walks, with the marker as the fallback only for a batch carrying no record. A batch whose newest record does not beat the drain's **highest** stamp is a stall, and three of those end the drain as `.idleTimeout` — without that guard a re-sending strap keeps the 60-second idle window armed forever, because its records keep arriving. The finding is `docs/BLE_PROTOCOL.md` §4's history paragraph; the rule is `HistoricalDrainSession.isAtLiveEdge`; §16 asserts both the old-drain fixture and the stall.

## The `HISTORY_END` continuation token is at payload 10, not at one frame offset shared by both generations.

The ACK that advances a drain's trim cursor must echo the eight bytes at **payload 10** — frame 17 under the 4.0 (`inner[13:21]`) and frame **21** under the 5.0 (`data[10:18]`, the community reference's hardware-verified trim). This app read the 5.0's token at payload 6, four bytes early, by reconciling the 4.0's frame offset with a `[6,14)` payload form; the result is the reference's **"Groundhog Day bug"**: the strap accepts the acknowledged write, its cursor does not move, and the drain re-sends the same batch forever. Measured on the owner's 5.0 on 2026-10-23 — two batches stamped `2026-08-24`, alternating with identical counter values (`10041` at `12:51:13`, `10222` at `12:57:42`) across every connection, while the app reported thousands of records and "caught up". **The token is payload-relative on both generations precisely because their frame origins are four bytes apart**; build the reader on `innerOrigin + innerPrefixBytes + 10` and never on a frame literal. §16 asserts the derivation for both, and `docs/BLE_PROTOCOL.md` §4's ACK paragraph carries the wire form.

The same trap has a second form: **an empty `HISTORY_END` is the end of the buffer, not the present.** The strap closes its last chunk with a marker that carries no records, and because that marker's head is the drain's clock (now), a marker-fallback on an empty batch declares a two-month-old buffer "caught up". Measured on the owner's 5.0 on 2026-10-23: the final empty marker reported `liveEdge=true` over a flash whose newest record was `2026-08-26 13:40`. The fallback is the **drain-wide highest record**; the marker is used only by a session that has seen no record at all.

## A day total computed once is a snapshot, not an integral.

`CalculateStrainUseCase` had exactly one caller — `StrainViewModel.load` — and that caller recomputed only when the day had no *measured* row. So the first time the strain page was opened, a score was written and never revisited: Home's ring read that stored row for the rest of the day, a walk taken afterwards counted for nothing until midnight, and a drain that recovered heart rate for a past day was never scored at all. **The tell is that the figure looks plausible** — a morning strain of 1.4 is a real-looking number — so the failure hides behind its own arithmetic rather than throwing. The fix is `RefreshStrainUseCase`: a process-lifetime consumer that keeps the day current and repairs the days a drain delivers. Two parts of it are the rule rather than the implementation. **The trigger is an input watermark, not a score comparison** — `strains.scoredThrough` holds the newest instant a row included, so an unchanged day costs one indexed read and no write, and a comparison against the score would have had to recompute first. And **the model that produces a day must be reachable by a writer with no screen in front of it**; a use case whose only caller is a view model is a use case whose output is frozen at the first open. §25 pins the watermark, the no-op second tick, the repair, and the refusal to touch an imported day.

## A stored metric row must record the formula that produced it, and a parameter change is a version bump.

`strains` held a score and no record of how it was computed, so a row written before the motion term existed and one written after were indistinguishable — and the day the model was retuned, nothing could say which figures would move. The fix is `StrainAlgorithm` on the row, a `strainAlgorithms` catalogue in both databases (local `v35`, D1 `0009`), and the version on the wire. **The discipline is the part that will be forgotten**: any change to a zone weight, the low-intensity band, `k_day`, the gap clamp or the motion weight table is a **new version string, a new seed row and a new enum case**, never an edit in place — an edited weight leaves every historical row claiming a formula it was not computed with, which is worse than no provenance at all. Three copies describe the same model (the enum, the seed rows, `docs/ALGORITHMS.md` §2.b) and a §25 assertion pins `StrainAlgorithm.current` against the newest catalogue row so they cannot drift; nothing, though, can catch a tune that forgets to add the case. **A synced row from an older client must not erase a stored version** — absent means *this client does not know*, not *clear it* — and a nil arriving in a sync is written as NULL only when nothing was stored. **Recovery was the last metric row without the pair, and `v39` gave it both.** A `recoveries` row could say neither which formula produced it nor what input it had seen, which is why three migrations (`v29`–`v31`) existed only to clear days by guess; now `algorithm` and `scored_through` let `RefreshRecoveryUseCase` ask *is this row current* and *has the night moved* instead. Nothing is backfilled — an older row genuinely does not know, and stamping `scorerV1` on it would be the migration making the claim the column exists to prevent.

## A survey edit that rebuilds a value drops every field it does not name.

`ActivityEditDraft.applying(to:)` rebuilt a `WorkoutSession` from a list of fields it named, and the list omitted `offlineRegionID` and `offlineRegionCenter`. Every save through `EDIT ACTIVITY` therefore wrote `nil` for both — silently wiping a downloaded offline map region on an edit that touched only a name — and the page fell back to Apple's map, which looks like a design choice rather than a deletion. **The bug is the shape, not the two fields**: a hand-written pass-through is safe only while it is exhaustive, and nothing makes it exhaustive except reading every property of the entity each time one is added. When an entity gains a field, every rebuild site is a place the field can be lost. The fix here is explicit pass-throughs for both columns, pinned in §25 with a session that carries a region through an untouched edit; the general fix is to prefer a copy-with-changes (`var` copy) over a constructor that enumerates, where the entity's shape allows it. §25 also asserts the same constructor keeps the rating.

## A sync upsert can erase a local-only user field.

`workouts.rpe` is the session rating the user typed, and it is deliberately **not on the wire** — the record→row conversion passes `nil`. The sync's write path is the same `writeWorkout` as the live one, so the first upload followed by the first download of a session would have replaced the rating with `nil`, and the user's own answer would vanish with a green build and no log line. **There is no clear path for a rating, so a `nil` in a synced row cannot mean "clear"** — it means the sender does not carry the field. `writeWorkout` therefore keeps the stored `rpe` whenever the incoming record has none, and §25 drives a rated session through `saveSyncWorkoutRows` to prove it survives while the measured fields update. The same pattern applies to any future local-only column holding user-authored data: the sync writes the columns it carries, and the ones it does not must be preserved rather than defaulted.

## A radio that is turned off does not deliver a disconnect, and the link state must be moved by the state callback.

Turning Airplane Mode on, or switching Bluetooth off, does **not** reliably produce `didDisconnectPeripheral` — when the central itself goes `.poweredOff` there is no peripheral left to disconnect, and CoreBluetooth does not promise the callback for that transition. Measured on the owner's 5.0 on 2026-10-24: the device page read *Connected* and Home's badge kept a green dot beside the last battery figure, on a phone whose radio was off, because `centralManagerDidUpdateState`'s non-poweredOn branch stopped the keep-alive and returned without touching `currentDeviceState`. **Nothing can be heard while the radio is off, so the only honest state is `.disconnected`**, and the move has to preserve everything discovery populated — `WhoopDevice.updating(connectionState:)` exists for exactly this, because a fresh `WhoopDevice(...)` would reset the hardware generation, the measured-battery flag and the DIS fields. `rearmConnection` performs the same correction on foreground, because a state callback can be missed while the app is suspended; `.resetting` is deliberately excluded as transient. The drawing follows from the state: `.disconnected` paints the dot yellow and withholds the battery, since `batteryReading` admits a figure only for `.connected`. **The same trap is why a "disconnected wear" test must confirm the radio is actually off** — the app's own stale state made an airplane-mode toggle look like a connection that simply did not drop, which is the opposite conclusion.

**Moving the state is not enough — the per-link flags go with it.** A power-off delivers no
`didDisconnectPeripheral`, so `prepareForNewLink()` never ran and every flag that describes one link
survived into the next: `hasSentConnectCommands` still true, so discovery skipped the connect pass and
the strap got **no `SET_CLOCK`, no `GET_DATA_RANGE`, no history request and no battery read** while the
screen said *connected*. The community reference reports the same shape as `#2787` on a Mac that slept overnight with
`didBond` still set on wake. The fix is on `centralManagerDidUpdateState`'s `.poweredOn` arm: when the
strap is still attached, call `prepareForNewLink()` and `discoverServices(nil)` before restarting the
keep-alive, so discovery re-runs `didDiscoverCharacteristicsFor` and the connect pass is re-sent. The
measured consequence here was a reconnect on 2026-10-24 that fired the auto-drain and drained nothing,
because the request never left — the handshake that arms it had been skipped.
