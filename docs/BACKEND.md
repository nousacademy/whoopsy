# The backend Worker

The Cloudflare Worker in `backend/` — Hono in front of D1 + R2 — and the eight resources it
carries. This is the reference for the Worker's own conventions; `CLAUDE.md` keeps only the
one-line version, because most work in this repo is on the app, not on the Worker.

`shared/openapi.json` is the contract the two halves agree on, and it is an **output** rather
than a hand-written stub — regenerate it with `npm --prefix backend run openapi`.

## The gate

**Every `/v1` request needs `Authorization: Bearer <SYNC_API_TOKEN>`, and the two paths that do not
are `GET /health` and `GET /openapi.json`.** The check is one middleware inside `createApp()`, in
`backend/src/app.ts`, and it is registered **before** `.route("/", routes)` — which is load-bearing
rather than tidy. Hono seeds a route's handler array with the wildcard middleware registered
*earlier* and runs that array in order, and every handler in this Worker returns a `Response`
without calling `next`; a gate registered after the mount would therefore sit behind them and never
run, which is an open API behind a green suite. The same file records the second half of that trap:
wildcard patterns are sorted by length descending, so a later `use("/v1/*")` would run *before* an
earlier `use("*")` whatever the registration order.

**It is a global `use("*")` with an exemption list, not a `/v1/*` prefix, and the asymmetry decides
it.** A prefix rule fails **open** — a resource mounted tomorrow at some other path is silently
public and no test reports it — while an exemption list fails **closed**: a new route is protected
by default, and a mistakenly-public one `401`s loudly on its first request. That is the same rule
`app.ts` states for `onError` and `routes/index.ts` for the validation hook. `OPEN_PATHS` is matched
with `===` on `c.req.path`, so `/health` does not exempt `/health-secret`.

**The two refusal arms are different on purpose, and the difference is the repo's caller-mistake /
Worker-bug split.** A missing, malformed or non-matching credential is a `401` in the shared
envelope, with **one message for absent and for wrong** — telling them apart is an oracle this API
has no reason to publish. A deployment whose own `SYNC_API_TOKEN` is unset, empty or shorter than
`MIN_TOKEN_LENGTH` instead **throws** and answers **`500 internal_error`**, with the detail only in
the Worker's log: that is not the caller's fault and not a state the Worker knows how to serve
under, and a `401` there would tell a human holding a curl that their credential was wrong when the
truth is that there is no secret for it to be wrong about. **An unarmed deployment is therefore a
`500`, not a `401`** — worth knowing before reading a log that says the gate is broken.

**The secret belongs to the deployment and is in no file in this repository.** Its three homes are
`backend/.dev.vars` (gitignored, for `wrangler dev`), `ios/App/Config/Whoopsy.local.xcconfig`
(gitignored, for the app) and `wrangler secret put SYNC_API_TOKEN`. It is declared
`SYNC_API_TOKEN?: string` in `src/env.ts` — **optional** because `DB` and `EXPORTS` are declared in
`wrangler.toml` and always present while a secret never is, and because testing `=== undefined`
against a `string` does not compile. **Set it before deploying**: `wrangler deploy` does not fail on
a missing one, it ships a Worker that refuses everything.

**What the gate buys is bounded and is not authentication.** It stops scanners, bots and drive-by
requests against a discoverable `*.workers.dev` hostname. The same string is compiled into the app
binary, so anyone who extracts it has the same access the owner does. There is no `accounts` table,
no registration and no revocation; `X-Whoopsy-User-Id` remains a self-declared partition name that
the Worker hashes and never stores, and the gate checks the credential **first** — a bad token
beside a malformed query is a `401` and never a `400`, because a `401` from middleware bypasses
`validationHook` entirely.

**The repo is a monorepo, and this file is about the app in it.** The SwiftPM package and `Whoopsy.xcodeproj` live under `ios/`; `backend/` is a Cloudflare Worker (Hono in front of D1 + R2) that carries **eight resources the whole way** — `biometricSamples` at `/v1/biometric-samples/{id}`, `recoveries` at `/v1/recoveries/{date}`, `workouts` at `/v1/workouts/{id}`, `strains` at `/v1/strains/{date}`, `sleeps` at `/v1/sleeps/{date}`, `stepCounts` at `/v1/step-counts/{date}`, `receptiveInactivities` at `/v1/receptive-inactivities/{id}` and `userProfiles` at `/v1/profile`, each from the route through the service and the repository into its own D1 migration — plus `GET /health` and the OpenAPI document generated from those route definitions and written to `shared/openapi.json`. **Four of the eight are date-keyed with one row per day and the other four are not**: `recoveries`, `strains`, `sleeps` and `stepCounts` are keyed on their date; `workouts` is keyed on a session id and is an aggregate of three tables on the wire; `receptiveInactivities` is keyed on an id too, for `workouts`' reason and with none of its aggregate — one table, no children, no `seq`; and `biometricSamples` is keyed on an id as well, with no children either, but it is the one resource here whose **read window is a pair of instants rather than a count of days**; and `userProfiles` is the one resource here with **no key of any kind on its path** — a profile is a singleton, so a partition holds one row or none, and its whole surface is `GET /v1/profile` and `PUT /v1/profile`, which makes it the only entry in the published document that is a resource's entire path set rather than a third of one. It is also the only mount here whose segment is **singular** (the other seven name collections) and the only resource whose service refuses nothing, so there is no `UserProfileError` beside the seven refusal classes — a rule it does have, `restingHeartRate` strictly below `maxHeartRate`, is published on the write body's `.refine()` rather than restated in a service, on the same reasoning that puts `SleepWriteSchema`'s `endsAfterItStarts` on its body alone. `biometricSamples` is the widest table in this Worker by three orders of magnitude and it is the reason the family has a window measured in seconds at all: a day of it is up to 86,400 rows, so a day-counted window would make "give me last month" a read no Worker should be asked for, and `MAX_BIOMETRIC_SAMPLE_WINDOW_SECONDS` is `604_800` — a week — in this resource's own unit rather than an alias of the four day-keyed windows' `MAX_WINDOW_DAYS`. **It is also the one adapter here that handles JSON**: `rr_intervals_ms` holds a `[Double]` as text and is published on the wire as an array of numbers rather than as the string that is secretly JSON, because a series of intervals has no interior a decoder would have to agree about — which is exactly why `sleep_stages`, whose segments carry interior `Date`s, stays an opaque blob. And **it is the one resource here whose identity is the client's derivation rather than a key this app's storage already had**: the phone's local row key is an autoincrement in that device's own SQLite that never reaches its entity, so two devices in one partition would both mint from 1 and silently overwrite each other; the wire id is therefore a client-derived string, the Worker validates the shape and publishes the requirement that it be **deterministic** — so that a replay is an upsert rather than a second row — and deliberately does not reproduce a recipe, because a server that derived an id would be a second implementation of the client's identity, free to disagree with the id the client asks for on its next read. **`receptiveInactivities` is the resource the iOS half already had and the Worker did not**, and it is the one resource whose port carries a method the Worker deliberately has no endpoint for: `ReceptiveInactivityRepository.delete(_ id: UUID)` is declared at `ios/Sources/Whoopsy/Domain/Repositories/PresentationRepositories.swift:133` while **no route in this Worker deletes anything** — `WorkoutRepository.delete(_:)` is at line 76 of that same file and has no counterpart here either, so it is a standing convention rather than an omission on this resource, and the reason a reader arriving from either port will not find a delete path to call. **`/v1/step-counts`, `/v1/receptive-inactivities` and `/v1/biometric-samples` are the three kebab-case paths, and each is the one resource whose URL, type and table are spelled differently**: the resource's own type is `StepCount` and its D1 table is `step_counts`, so `/v1/stepCounts` and `/v1/step_counts` are both plausible readings of the same resource and both name a mount that does not exist — and `biometricSamples` adds a third reading from the other side, being the only one of the three whose type is *singular* while its path is plural, so `/v1/biometric-sample` is as plausible as what is mounted. That is why the served document's path list is asserted exhaustively rather than derived from the mount table. **The mount is also where this resource teaches the rule that the two orders are different**: it is mounted first among the `/v1/*` entries because `b` sorts before `r`, while the identifier `biometricSampleRoutes` would be appended last by anyone adding a resource conventionally — and `routes/index.ts` carries that argument at the mount itself. `sleeps` is the one that looks most like a copy of a sibling and is not: it is `strains`' shape — keyed on the day, an upsert, a range read, a `POST /batch` chunk — carrying `recoveries`' absence rule, because it has no `hasMeasurement` column and therefore no second kind of row, and its day is the night's **wake** day. `stepCounts` is that shape a second time, and it is the narrowest of the seven: it copies `sleeps` and not `strains` — keyed on the day, an upsert, a range read, a `POST /batch` chunk, no stored `hasMeasurement` flag and therefore no second kind of row — while having **no `source` and no nullable column at all**. Steps have exactly one producer, the strap, and a day is routinely fed by both a live stream and a banked drain, so a per-row provenance label could not be written honestly; and `measuredSeconds` is the field that separates a measured day of no walking from a day nothing measured, which is why a default on it would publish the second as the first. `receptiveInactivities` is the one resource whose *shape* is decided by a nullable pair rather than by a flag: an entry carries a `name` and an optional `startedAt` and nothing else, because with no `endedAt` it has no span — it cannot `covers(_:)` a day, cannot be in progress and cannot aggregate into a zone block — and `note` and `startedAt` are **nullable rather than optional** on the wire, so the two absences have one spelling and `""` is refused rather than accepted as a third state. Its ordering is `date ASC, started_at ASC NULLS LAST, name ASC`, where `NULLS LAST` is the clause a naive port drops and the one this resource cannot afford to lose: SQLite sorts NULL *first* ascending and the untimed entry is the *majority* case — all 62 of the app's bundled rows are untimed — so without it every imported entry would be drawn above the timed ones on its own day. **The Worker used to be ahead of the client on the last four resources, and it no longer is.** The iOS half's `CloudSync` port covers all seven, `Data/Networking/` holds a wire mapper per resource and `Domain/Repositories/` a `*SyncStore` per table — so a sentence saying "three resources" is describing the client's sync as it was and one saying "eight" is describing what this Worker carries, and the count that is current is **seven on both sides**. **The two halves are still not equal, and the difference is one resource and one direction.** `biometricSamples` is the Worker's eighth and the client carries no part of it, because its window is measured in seconds rather than days and it takes its own control. And of the seven the client does carry, the four this loop added — `sleeps`, `stepCounts`, `receptiveInactivities` and the profile — are **upload-only in this pass**: a `SYNC` run sends them and nothing reads them back, where the three the client already carried — `recoveries`, `workouts` and `strains` — have read methods on the port and only `recoveries` has a caller, `CloudRecoveryRepository`'s local-first decorator. **`userProfiles` is the one of the four whose client half was not a copy of a sibling**, because its mapper mints the `"primary"` id the app's local row carries and converts its `.datetime` birthday column to the day key the wire publishes. `shared/openapi.json` is the contract the two agree on, and it is now an **output** rather than a hand-written stub. Paths below are written **from the repo root**, so anything naming a real file carries the `ios/` prefix; the unprefixed layer names (`Data/BLE/`, `Core/Math/`, `Presentation/DesignSystem/`, `App/DependencyInjection/`) are shorthand for paths inside `ios/Sources/Whoopsy/` and were never root-resolvable.
