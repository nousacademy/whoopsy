# The suite, section by section

What each numbered section of `ios/Tests/WhoopsyTestRunner/` asserts, in the runner's own words.
This is the **reference** for a section's blocks; `CLAUDE.md` keeps only the mechanics of building
and running the suite, plus the rules that govern adding to it.

Read a section's entry here before you edit that section. `assertions=` in the summary line is the
verdict, and a block described here that stops running is a deleted guarantee.

> **Sources.** Other people's reverse-engineering is cited here by **role**, never by project
> name — the community reference, the research reference, the APK reading and the Swift 4.0
> client. Each role resolves to one file under `docs/<project>/`
> holding that project's identity, URLs and verbatim excerpts; the table is
> [`docs/BLE_PROTOCOL.md` § Sources](BLE_PROTOCOL.md#sources).

### §21

§21 is the receptive inactivity import — `dreams.json` becoming rows on the `RECEPTIVE INACTIVITIES` card — and like §16–§20 **none of it is evidence about a strap**: it is the owner's own notes log, so what it proves is parsing, identity, storage and the one screen-level reader. ### §13's strap-side models

The same section now owns the two strap-side models, and its RSA block is built the way the models' unvalidatability requires: **synthetic tachograms, never the export**, because the export carries no R-R series to test against. ### §13's consistency block

The consistency block is built on **fixed clock times rather than elapsed offsets**, and that is not incidental: `date(byAdding: .minute,)` adds elapsed time, so on a spring-forward day "420 minutes after midnight" is 08:00 on the wall and every pinned literal would move. Its hours (22:00–23:59, 06:00–07:59) sit outside both the 02:00 gap and the 01:00 fold, so the wall clock is unambiguous all year. Four assertions carry the weight. The **recency pair** — the same total drift, recent against old, scoring 88 and 92 — fails if the weights are dropped or the sort is reversed, which a single case cannot see because a flat mean scores both arrangements alike. The **midnight assertion** (a 23:50 onset against 00:10 priors scores 91) separates circular distance from a naive minute-of-day subtraction by 91 points, since the naive form reads the pair as 1420 minutes apart and clips to the floor. The **gap assertion** — a night whose fourth prior is 10 days back is still scored — is the one that fails if anyone re-derives the four-record window by subtracting calendar days. And the **strict-before assertion** passes a night dated *after* the target alongside three real priors and requires `nil`, which is what keeps a forward-dated row from taking the heaviest weight.

### §13's export guard

Its export guard is a *property* in the same spirit as the need's, and it needs one for the same reason: a stored WHOOP consistency and a computed one are the same `Int` on the same column, so nothing but an assertion keeps either producer off the other's rows. The property that separates them is **disagreement** — the model reproduces WHOOP's figure closely but not exactly, so a column that had been recomputed rather than read would agree on every night. The suite counts the nights where the two differ by more than the model's own error bar (167 of 906 at the time of writing) and requires it to be large; a fixed count of nights would break on a device time zone that merges two day keys. **The 906 counts every night with four or more predecessors; the 891 that `docs/ALGORITHMS.md` §4 fits its constants against is the subset of those that also carry WHOOP's own column**, and the two are quoted side by side in the runner — one word, two populations, so read which one a sentence means before comparing it to another.

`LifeTableTests` pins the bundled table and the arithmetic over it: the resource decodes to exactly the country the generator fetched, a table names its publisher and edition, **the app's own integration of `q_x` agrees with the published `e_x` within 0.05 years at five ages** — the assertion that catches a dropped row, which would still produce a smooth curve — a multiplier of 1.0 is the identity, 0.5 lengthens life and 2.0 shortens it, half the hazard is *not* twice the years, and a country with no table says so rather than borrowing another's mortality. **The inverse is pinned as a round trip rather than against a printed figure**: `age(withRemainingYears:)` returns the age it was handed at 10, 30, 45 and 70 (within 0.1 y), an expectancy above the table's `e_0` clamps to 0 and one below `e_100` to 100, and a profile whose adjusted expectancy exceeds its baseline reads back **younger** than the age it started from — the direction the Healthspan dial's "years younger" line asserts, which a sign error would invert while every other assertion stayed green.

### §14's Health Monitor block (cont.)

### §14's Stress Monitor block

`StressWindowEvaluatorTests` is the block that pins the **one** definition the stored day and the live

day: it is `nil` one window short of `minimumRecentWindows` and non-`nil` at the floor, its priors are

the gate used to refuse: fourteen still windows with **no prior day at all** produce a day, carrying

The page's closing paragraph is pinned in its **three** variants — low, medium, high — because a

The gates-and-score block covers: the three gates in their order (beat count before stillness before heart rate, so a

The Stress Monitor block is also where the day's **series** is asserted, not just its aggregate. `StressDay` computes its `StressScore` from the windows it was handed rather than accepting one, so `windows.count == score.windowCount` is structural; the assertions pin that, that the windows are sorted and inside `StressMath.wakingWindow`, that the average really is their mean, and — the one that matters most — that `executeDay(for:)` and `execute(for:)` return the same figure, since `execute` is a forwarder rather than a second implementation. ### §16's advertising-name block

Beside it, §16 pins the rename's two generations and its read. `SET_ADVERTISING_NAME` is framed **140
(`0x8C`)** on a 5.0/MG — `[revision=1][length][name…]`, 0–15 bytes — and **77 (`0x4D`)** on a 4.0, two
reserved bytes then a NUL-terminated 16-byte field, so a generation that sent the other's number would
frame a different message rather than a renamed one. The clamp is asserted on a **scalar boundary**:
eight `é` are sixteen UTF-8 bytes and the clamp keeps seven, because cutting the eighth stores half a
character the strap would advertise as mojibake, and an empty name frames nothing at all. The reply
decoder is pinned against **the bytes this strap actually sent on 2026-10-25** —
`14 01 01 01 0C "Whoopsy 5.0" 00…` — which is how the reference's documented 19-byte body was found to
omit two bytes this envelope carries: the payload length in front and the result byte after the
revision. The same assertion accepts that payload with the length byte removed, and refuses a reply
whose fields do not fit, because a name decoded from the wrong offset would be printed back at the
owner as though the strap had said it.

### §16's drain-trigger block

`DrainCoordinator` is asserted through a scripted strap, because what it gets right is a **sequence**
rather than an answer. Two triggers firing together are shown to produce **one** request — the second
caller receives `nil`, which means *did nothing*, and a manager would otherwise conclude the
interrupted session as `.aborted` and finish neither. A drain answering **zero batches** (silence) is

rather than the script's fourth answer. The retry delay is injected at ten milliseconds: the real five
seconds, twice in the worst case, spent the runner's own 30-second budget and timed the full suite out
on 2026-10-25 while §16 alone passed.

### §22

§22 is the cloud sync boundary, and like §16–§21 **none of it is evidence about a server**: the runner drives a `SpyCloudSync` and `LocalDatabaseManager(inMemory: true)` and no build here carries a `WHOOPSYAPIBaseURL` — so what it proves is arithmetic, wire naming, storage and the read path's routing, and nothing about whether a request arrives. That is a statement about **this runner**, not about the deployment: the Worker is deployed and a build with both keys does reach it, which is `docs/BACKEND.md`'s evidence and `README`'s, not this section's. **It is one section and not seven, because the seven resources are one feature** — one port, one `SyncSettings`, and a walk, a chunking and a skip count written once and read by all seven — and its blocks run in the order of a run rather than the order the files were written: a span is drawn (22.1), a row is spelled on the wire (22.2), the store the phone reads through answers or degrades (22.3), the database underneath takes the row (22.4), the run walks all seven (22.5), and then the two claims the run cannot make about itself are swept over the source and the contract (22.6, 22.7). **22.1 is a pure value with no database behind it**, and it is where the feature's two questions are separated: *where does the next write go* is `destination`, a switch whose two arms are asserted off `Destination.allCases`'s `rawValue` with `device` **first because it is the default**, and *which days does a run walk* is `range`, the one control on the pane that is a transfer. Both ends of a span are asserted **on the stored value** to be snapped to their own day, and the pair is asserted half-open — a `[from, to)` covering exactly the days between them, counted on the calendar rather than as `seconds / 86_400`, because a span across a daylight-saving change is not a whole number of seconds and a seconds-derived count is off by one for part of every year. The two empty states — ends on the same day, and a pair drawn backwards — are asserted **empty rather than refused**, because a backwards pair is a user mid-edit and the gate is `isEmpty` on both readers rather than a rejection at the write, and the span is stored as one pair or not at all. **What this block used to assert is recorded rather than deleted**: `isCloudDay`, `cloudHolds`, `pendingWork`, `cutoff`, `uploadedCutoff` and `Direction` are all gone, and with them the fixture built so the two boundary predicates **disagree** — the second boundary existed to answer *what has to be fetched back after a delete*, and there is no delete. The direction is still reported; it just no longer decides the verb. **22.2's blocks are the two-names rule stated as a round trip**, and there are now **six** of them — `recoveries`, `workouts`, `sleeps`, `stepCounts`, `receptiveInactivities` and the profile — each pushing a record through its mapper and back field for field, with the DTO's keys pinned so a rename in a mapper is a failure rather than a silently different JSON. **`strains` is the one resource with no such block**: `StrainWireMapper` is the shape the other six were copied from and its round trip is asserted nowhere, which is a gap in this section rather than a claim about it. Two halves of 22.2 carry more than the round trip. The recoveries half asserts the day key from **three zones**, because a formatting defect is invisible from one — a UTC−8 device's midnight formats to the same `YYYY-MM-DD` under a UTC calendar, while a UTC+10 device's does not and the *parse* half fails in the opposite direction — and the workouts half carries the aggregate's three load-bearing rules: a route array written in a **decidedly non-sorted** order reads back in that order, which is the assertion that fails if anyone reaches for `sorted(by:)` on the way out; a session whose stored id will not parse as a `UUID` is **dropped**, while a child whose id will not parse **keeps its place with a fresh `UUID()`**; and `saveSyncWorkoutRows` is a **replacement** — a parent re-saved with one child where it had two leaves one, not three. Running through all six is the **nullable-not-optional rule**, which is why five of the encoders are hand-written: a field the schema marks `.nullable()` must reach the wire as `null` and never as an absent key, and the round trip is asserted in both directions because a reader that treats the two as one shape is a reader that invents a value. **22.3 is the read path's, and its degrade is the pair that carries it.** The decorator answers a day from this phone whenever it can, asserted with a **different figure in the database for the same day** — the only fixture that can tell a correct route from a broken one, since a decorator that always read one store and one that always read the other both answer `nil` on an empty day — and it reaches for the Worker **only under `.cloud`, only for a day the phone missed, and only once**, as a single-day read rather than a window. A fetched day is **not written to the phone**, because caching it would make this app's own table depend on which screens the user happened to open, which is the one thing the pane promises never happens. A read whose cloud half throws `.unreachable` draws the local copy and marks the day, and a later successful read **takes the mark away** — a mark that could only be written would go on claiming a day cannot be shown after it was fetched, and *not measured* is not *unreachable*. A `.rejected` and a `.malformed` are neither of them outages and both propagate: degrading over one would put this phone's number on a screen where the server was saying the request was wrong, and over the other would hide a client and a server disagreeing about the shape of a day. **Beside it, the six sibling decorators are driven for the same routing in miniature**: each of the seven resources keeps a save on the phone under **both** destinations — there is no per-save mirror any more; the daily run is the only uploader — and a missed day (or a phone with no stored profile) is fetched back once, without caching it. The once-a-day window itself is `SyncScheduleTests`: its 18:00/23:59/midnight edges, the same-day not-due rule, the next-window arithmetic, and 6 PM staying 6 PM across a spring-forward wall. **22.4 is the phone's own door into its tables**, and the assertion that carries it is that a row's bounds are half-open at **both** edges — a row at `from` in, a row at `to` out, the pair that fails if anyone borrows `endOfDay`, whose `23:59:59` would also drop a row written at midnight — with `saveSyncRows` asserted to snap the day key centrally. Its aggregate sibling says the three things a recovery row cannot: a chunk's children move with it, re-saving a parent **replaces** its children rather than stacking them, and the children are read back **through the repository** rather than counted, because `LocalDatabaseManager` exposes no row count and an orphaned route point is invisible to every reader in this app — `makeSessions` fetches children per session, so a fix whose session is gone is never read, never drawn and never noticed. **22.5 drives a whole run** against a real in-memory database and the spy, which is the pairing that catches a descriptor wired to the wrong store: a double per store would answer whatever it was asked, so a descriptor walking `sleeps` and calling `writeStrains` would pass — the real manager answers only for its own table, so the crossed wire shows up as a resource that moved zero rows while its rows sat on disk. A run with no span, or with a span whose ends are the same day, throws `.nothingToDo` **before it touches anything**, asserted against an empty call list, and a span wider than the resource's own ceiling throws `.rangeTooWide` **before the read**, so an over-wide span costs nothing rather than half a run. The engine's resources are asserted equal to the pane's list **in the pane's order**, derived one from the other rather than typed twice, because a resource the pane promises and the engine does not hold is a title over nothing and the reverse is a transfer the user cannot see. An empty span still answers **once per resource** with nothing moved and nothing skipped, which is not an error, each count named in its own unit, and the far side is never contacted. `skipped` is asserted to be counted **before** chunking and the unsendable row to still be on the phone afterwards, since `POST /batch` is one all-or-nothing transaction and the naive fix — send it and let the server refuse — costs the other day in the same request. The chunk boundary is asserted as a **union**: four hundred and fifty days cut into two hundred, two hundred and fifty, with no day in two chunks and no day dropped, which is the same half-open guarantee the store gives a range. A refusal stops the run and **what landed stays landed**, because the seven sends are not one transaction and every write on the far side is an INSERT-or-UPDATE on the row's own key. And the user's own ruling is asserted directly — *"if a DB is selected, it doesnt purge anything, it just switches where data will be stored to"*: switching the destination is **one write of the settings and no call at all**, on either arm, while the span is drawn on its own ahead of the button so that a run which fails cannot lose the range the user chose. **22.6 reads the pane's list off the contract rather than off a literal typed twice**, and it is the one claim in this section a screenshot cannot see: the enum's order is the generated contract's, which is the Worker's order because the contract is generated from its route definitions and sorted by path, so a resource the server mounted and the app forgot is a title the pane never draws and one the app invented is a title over nothing — and **neither shows up anywhere else**, because both sides keep working and each list is internally consistent. The document is **line-scanned** rather than decoded, deliberately, because every Foundation parser hands a JSON object back as a dictionary and a dictionary has no order, so the tool used to read it would discard the very property under test: twenty-three mounts, eight `/v1/` roots, with `/v1/biometric-samples` **first** because `b` sorts before `p`, so the absence of the one resource that stays on the phone is visible at the head of the list rather than hidden at the end. The three spellings each resource carries — the drawn title, the mounted path and the Worker's own name — are asserted per resource **and** pairwise distinct across all twenty-one, which is the property the per-resource comparisons cannot reach. **22.7 is the app's one delete door, and the guarantee changed shape without weakening.** It read "no door exists"; since 2026-10-29 it reads "**exactly one does, and it is the day purge**": the `CloudSync` port declares 26 methods of which exactly one is named for a removal — `purge` — and it must take `from:`/`to:` labels, because a per-row verb is what a sync would reach for to reconcile a difference; the seven `*SyncStore`s are still swept for the absence and still have none, which is the half that did not change; and the committed contract mounts **exactly four** `"delete":` operations, decoded and compared with `SyncedResource.purgeable`'s paths rather than counted, so a resource added to one side and not the other fails here. The verb set is `get, post, put, delete` and the count of operations moves 31 → 35 — a fifth delete, or a third on a resource the app does not purge, fails. This is the same assertion as before in a narrower shape: a per-row delete, a delete on a store, or a delete on an untreated resource still fails, and it now also fails if the *one* door is not the range-shaped one. **Every sweep carries a positive control**, because a file that could not be read, was truncated or is not the file the block believes it is would make every negative assertion pass while covering nothing — the runner's own `assertions=` rule — and the near-miss is asserted on purpose: `WorkoutSyncStore`'s doc comment does contain the word *delete*, which is why the sweep reads declarations and never file text. **`PurgeDaysUseCaseTests` is the removal's own block, and its decisive assertion is the negative one.** With `DEVICE STORAGE` the phone is purged and the port is never called — asserted as an empty call list, and as a report that says the database was not asked rather than reporting a zero it did not measure. With `WHOOPSY SYNC API` the port is asked **once, for the exact range**, and the report carries what it removed; and with the spy **armed to refuse**, the operation throws `PurgeDaysUseCase.Refusal` and the phone's store records **zero calls**, which is the whole design in one assertion — a local delete without the database's is the cache eviction `docs/GOTCHAS.md` records, not a delete. A reversed range and a 41-day span are refused with neither side touched, and the client's `maximumDays` is pinned at the Worker's 31 because each half must refuse on its own. The section's dispatcher is `Data/Sync/SyncSectionTests.swift`, and its tree is the only one here that mirrors a directory the app keeps for the same reason: the port, the six mappers, the decorator and both store conformances each have a file at their own path. **Its newest block is the restore, and it is the one that pins what the app no longer does.** `RestoreFromCloudUseCaseTests` drives the deliberate pull over a real in-memory database: every one of the seven resources plus the profile is asked for and written into the phone's own tables, nothing is written back to the server, and the two states in which it must ask for nothing at all — a `.device` destination, and a phone that already holds a day — are asserted with an empty call list. **The window is the block beside them, and it is split on purpose:** a closed window stops `restoreIfNeeded` before it reads anything, while the explicit `restore()` still calls and writes, because `RESTORE` is the one control exempt from the 18:00 gate and a test that refused it would pin the bug this exemption removed. ### §23

§23 is the connection lifecycle's one assertable decision, and it is deliberately a small section: **everything else in that lifecycle is a CoreBluetooth callback**, and the runner cannot raise one — constructing a `CBCentralManager` opens the system Bluetooth prompt, the same reason `WhoopBLEManager.resolvedGeneration` is a static. So the callbacks defer to `ReconnectPolicy.decision(for:previousAttemptStartedAt:now:priorRefusals:generation:)`, a value-typed function over two dates and a count, and this is its case table. **The count is the policy's own output rather than the manager's arithmetic** — the same `elapsed < fastFailureSeconds` comparison that decides the floor is what decides whether an event was a refusal — and its one generation-specific branch is the cap below. The section exists at all because the two reasons a link can end are not the same event and must not get the same answer. **A drop** — a link that was up and went away — always answers `.standingConnect`, immediately, even when the previous standing attempt had been made a tenth of a second earlier: a link that was established is not a refusal, and applying the floor to one would delay every ordinary recovery by half a minute. **A failed connect** is where the refusal floor lives: if the previous attempt began less than `fastFailureSeconds` (2 s) ago, the strap answered "no", and the step becomes `.standingConnectAfter` the remainder of `retryFloorSeconds` (30 s) measured from the attempt's *start* — so a refusal at 0.5 s waits 29.5 s and one that came back at once waits the whole 30. A failure at ten seconds is not a refusal at all and retries immediately, which is why the block pins the window's **both** ends rather than only its inside. The boundary is asserted at the exact figure — exactly 2 s retries at once — so a `<` changed to `<=` fails here rather than in a field report, and the floor is clamped at 30 so a backward clock jump cannot push the wait past it. The two constants are asserted by value, because they are the numbers the design is argued from. **The refusal cap is a 5.0/MG rule and a bond question.** Five consecutive fast refusals on `.whoop5` or `.whoop5MG` produce `.giveUp` and stop the standing connect — the community reference's `#747` — while a 4.0 is asserted uncapped at ninety-nine prior refusals, because a 4.0 that keeps refusing is far more likely to be out of range than looped on a bond and the standing connect exists to wait that out. Every event that is not a fast refusal — a drop, a slow failure, a failure with no previous attempt — resets the count to zero, and that is asserted for the same reason the boundary is: one bad streak must not cap a link that later worked. **What the section cannot show is the standing connect itself** — that an outstanding `central.connect` with no timeout survives suspension and lets iOS wake the app is a property of CoreBluetooth's documented contract, not of this app — and the callbacks that re-issue it (`didDisconnectPeripheral`, `didFailToConnect`, `willRestoreState`) carry no assertions here for the same reason. What is left is the decision, and it is the one place a future backoff change can be proven before it reaches a strap.

### §24

§24 is §23's counterpart: where the reconnect decides what to do after a link **ends**, this asserts what to do while iOS still reports it **up**. The failure it exists for is the one `CBPeripheral.state` cannot see — a GATT link that is connected while the strap's producers are not — so every input is a clock rather than a callback, and `KeepAlivePolicy.action(for:lastActivityAt:lastActivationSentAt:lastBatteryReadAt:now:isDraining:)` is a value-typed function the runner can drive with no `CBCentralManager` and no strap. **The three outputs are one tick's whole obligation**: ask for a battery reading, write the telemetry and motion enables again, or bounce the link — and the bounce supersedes the other two in the same tick, which is asserted directly rather than left to the call order. The constants are pinned by value because each is a design argument: the tick is 30 s, the battery floor 60 s, the re-send floor 60 s, and the suspension gap 90 s. **The battery read doubles as the probe** — it is the only request this app makes that the strap must answer, so it is what turns "no packet has arrived" into evidence about the link — and its floor is asserted at both sides, 59 s inside and exactly 60 s due, so a `<` changed to `<=` fails here. **The silence thresholds are the generation split's first half**: 15 s on a 4.0, which is the Swift 4.0 client's `WhoopBleDataWatchdog.swift`, and 60 s on the 5.0/MG, because those generations have documented at-rest heart-rate lulls and a 15 s rule would re-arm a producer that is merely quiet. The re-send carries a **second clock** as well — noticing is not poking, and without the 60 s floor an every-30-s tick against a never-streaming strap would write every tick; the pair is written at 60 s of silence rather than longer because 120 s is the 4.0's fuse, and a case past it asserts about a bounce rather than about the floor. **The liveness fuse is the split's second half and the reason a uniform number would be wrong in both directions**: 120 s on a 4.0 would reconnect-loop a 5.0 at rest for ten minutes if applied there, and 600 s on a 4.0 would leave a dead link dead for ten minutes; both boundaries are asserted at the exact figure and one second short. A drain suppresses the re-send and the bounce — a flash write is exactly when a strap goes quiet, and re-arming producers mid-drain is the documented way to lose its records — while the battery read stays safe, which is the one asymmetric case the block pins. Finally the block covers a backward clock jump, the same NTP correction §23's floor is clamped against: a negative silence produces no action rather than a bounce. **What it cannot show is the timer** — that a `DispatchSourceTimer` on the BLE queue fires while the app runs, and stops while it does not, is a property of the platform — nor that the strap answers any of the three actions. It asserts the decision, which is the part a change can silently break.

### §25

§25 is the Strain day model with its motion term, the refresh that keeps a day current, the formula
every row now records, and the session-RPE rating. **None of it is evidence about hardware**: the
runner writes samples and motion windows into an in-memory database or hands them to the pure model,
so what it proves is arithmetic, persistence and the refresh's decisions. It is nine blocks.

**The grid.** `MotionEpochGrid`'s floor is pinned against hand-computed constants (an instant 21 s
past a boundary lands on `1,789,999,980`, and its index is `59,666,666`), the grid is idempotent on a
boundary, the last millisecond of a window stays in it — and **the identity that matters is the
integer, not the instant**: a window written at `.2345` reads back at millisecond precision as a
different `Date`, and the assertion is that both land in the same bucket. That is the whole reason
the type exists; a `Date`-keyed dictionary would file one window twice.

**The motion weight table.** ENMO subtracts gravity and clamps at zero rather than going negative (a
negative weight would subtract load from the day), every threshold is asserted at both edges —
`0.0199`/`0.02`, `0.0499`/`0.05`, `0.0999`/`0.10`, `0.1999`/`0.20` — with the boundaries half-open, and
the covered-seconds rule is pinned at `0`, `2,999`, `3,000` and `6,000` samples so a double delivery
is clamped to one window rather than credited twice. Two products are the sanity check: a full
walking-weight window is `2 × 30 = 60`, and a half-filled running-weight window is `4 × 15 = 60`, the
latter being the assertion that a partial window grows as its batches arrive.

**The day model.** The refactor pin is a **bit-for-bit** comparison of `rawAccumulatedLoad` against a
verbatim copy of the pre-motion loop, not against a rounded score — a re-association of the floats
fails it, which a hand-computed constant would not. Then the combination: a window whose heart-rate
load beats its motion load is unchanged by the epoch (and still records the motion term), a window at
resting rate with vigorous motion takes the motion's figure and the day scores above zero, a
two-window fixture comes to **180** where adding the terms would give 220 (the double count the
partition exists to prevent), a window with no epoch adds its heart rate unchanged, no heart rate at
all returns `nil` however much motion there is, and the pathological ceiling is pinned at **345,600**
weighted seconds → **20.5**. The watermark block asserts the epoch's measured edge, not the newest
sample, so a window filling with successive batches advances it.

**The use case.** `CalculateStrainUseCase` writes `hr-motion-v2` and `device`, records a zero motion
term on a motionless day, stamps the watermark at the newest sample, and reads back repairable; a
resting day with one vigorous window stores `motionLoad == 120` and a combined load of 120. Motion
with no heart rate returns `nil` and writes nothing.

**The refresh.** Five decisions, each driven rather than assumed: a tick scores today and stamps the
algorithm; a second tick with no new input leaves a directly-overwritten sentinel score of 19.9
alone (the watermark, not a timer, is what reopens a day) and a later sample does recompute it; a
`whoop-export` row is never replaced and reports `isDeviceScored == false`; the backfill stops at the
newest imported day rather than filling the gap before it; a drain with no record stamps scores
nothing, and neither does one with a missing end; nine days of backlog score the newest seven and
leave the eighth alone; and a saved row is published on `strainUpdates` **with the stored figure**
rather than one computed for the screen.

**The provenance.** `v35`'s three columns are camelCase — the assertion that fails on `motion_load`,
which would be `no such column` at launch — and `v36` adds `workouts.rpe`. The catalogue holds three
rows with non-empty formula and parameters, every `StrainAlgorithm` case appears in it, and its newest
row is `StrainAlgorithm.current`; that last assertion is what keeps the writer, the seed rows and this
document describing one model. A row's algorithm, motion component and watermark round-trip; a synced
row stores NULL for the two local-only fields; a sync from a client with no algorithm updates the
score and keeps the stored version; and a **rating survives a synced row** while the measured fields
update. The importer's label and `StrainScore.importSource` are asserted equal, because a repair
decision turns on that string.

**The wire.** The version reaches the DTO, a DTO round-trips to an identical row, a nil sends `null`
and is still sendable, an empty string is refused rather than losing its chunk, and a cloud-read WHOOP
row arrives with its provenance and is not repairable.

**The rating.** The five buckets map to `2/4/6/8/10` with distinct short labels, a value between
buckets belongs to none (so the control draws no selection rather than misreporting the answer), the
clamp holds at both ends, and the training load is `RPE × minutes` with the rating clamped. **The
two-write order is asserted in §18**, where a real `end()` produces an unrated row and
`rate(_:for:)` then writes the rating onto the same session without disturbing what it measured —
the one property this block cannot see, because it never builds the use case.

**The edit sheet's draft.** An untouched draft is not a change; rating an unrated session is; the
write carries the rating **and the offline-map region** — the field `applying(to:)` used to drop, so
this is the assertion that fails if it is dropped again — along with the measurements and the name;
re-writing the value already held is a no-op; and a value above the scale is clamped on the write.
