# Whoopsy Architecture Guide: Clean Architecture & Local-First Design

## 1. Architectural Philosophy

**Whoopsy** is designed from the ground up as a **100% offline-first, subscription-free, privacy-preserving** iOS companion application for WHOOP® straps (Gen 4, Gen 5 and Gen 5 MG — three models, two wire formats, and the app must be told which one it is holding).

To guarantee scalability, testability, and clear separation of concerns, Whoopsy strictly enforces **Clean Architecture** (Robert C. Martin / Uncle Bob) combined with **Domain-Driven Design (DDD)** and modern Swift Concurrency (`async`/`await`, `AsyncStream`, `Sendable`).

```
+-----------------------------------------------------------------------+
|                         PRESENTATION LAYER                            |
|  - SwiftUI Views (Glassmorphism, Neon Gauges, Hypnograms)             |
|  - ViewModels (@Observable, Unidirectional Data Flow, UI State)       |
|  - 1:1 Official WHOOP Layout (Tabs: Home, Strain, Sleep, Recovery...) |
|  - Live Activity (WidgetKit extension, a second Xcode target)         |
+-----------------------------------+-----------------------------------+
                                    |
                                    v (Uses)
+-----------------------------------------------------------------------+
|                           DOMAIN LAYER                                |
|  - Entities (BiometricSample, RecoveryMetric, StrainScore, Sleep,     |
|    StressScore)                                                       |
|  - Use Cases / Interactors (CalculateRecovery, CalculateStrain,        |
|    AnalyzeSleep, AnalyzeStress, ...)                                  |
|  - Repository Interfaces (Inversion of Control Contracts)             |
+-----------------------------------+-----------------------------------+
                                    ^
                                    | (Implements Contracts)
+-----------------------------------+-----------------------------------+
|                            DATA LAYER                                 |
|  - BLE Hardware Engine (CoreBluetooth, Custom 0xAA Framing, Decoders) |
|  - Persistence (Local-First GRDB / SQLite Sandbox)                    |
|  - Mock Data Engine (Hardware-free Simulator Mode for Previews/Tests) |
|  - Adapters (HealthKit Read/Import, WHOOP Export Import, JSON/CSV Out) |
+-----------------------------------------------------------------------+
|                            CORE LAYER                                 |
|  - Signal Processing (RMSSD, SDNN, Exponential Strain Integrator,      |
|    Stress activation)                                                 |
|  - Dependency Injection Container & Logging Subsystem                 |
+-----------------------------------------------------------------------+
```

## 2. Layer Definitions & Boundaries

### A. Domain Layer (The Core)
* **Zero External Dependencies**: Does not import `UIKit`, `SwiftUI`, `CoreBluetooth`, `HealthKit`, or `GRDB`. **The one import beyond `Foundation` is `Observation`**, added with `LiveSessionUseCase`, and it is an amendment rather than a hole in the rule: what this layer must not reach for is a platform framework that binds it to a device, a database or a renderer, and `Observation` is a language-level macro that carries none of those. The alternative was putting an app-lifetime session holder in `Presentation/`, which has no precedent here. Both builds compile either way, but a *new* import in this layer is the kind of change that should be argued for rather than slipped in.
* **Entities**: Pure immutable Swift structs representing core physiological models (`BiometricSample`, `RecoveryMetric`, `HRVMetric`, `HealthImportSummary`, `WhoopImportSummary`, `StrainScore`, `StressScore`, `StressDay`, `StressWindow`, `SleepStressNight`, `MetricWeek`, `MetricDay`, `SleepSession`, `SleepNap`, `StepCount`, `UserProfile`, `WhoopDevice`, `WhoopHardwareGeneration`, `WorkoutZoneTime`, `LiveSessionActivityState`). `WorkoutZoneTime` is one day's zone time summed over that day's workouts, and it is **two fields rather than five** because the strain page draws two rows; the five percentages stay on `WorkoutSession.hrZonePercents` where the file's own resolution lives. Its two figures deliberately do **not** sum to the day's workout time — the remainder is time below zone 1, which WHOOP publishes no column for — so anything printing a total takes it from the sessions. `LiveSessionActivityState` is the live card's vocabulary, and it is one of exactly **two structurally identical copies** in this repo: the widget extension links the `WhoopsyLiveActivityKit` product and not `Whoopsy`, so a module that cannot see this type cannot share it, and `LiveActivityController` is the single place the two are mapped. It is a `Sendable` value of optionals for the usual reason — a session with no strap accepts no samples, and the card draws a dash rather than a `0.0` this app invented. `StepCount` is a day, a count and a measured span, and its `hasMeasurement` is **computed from the span** (`measuredSeconds > 0`) rather than stored as a flag — so there is one test rather than a stored copy that could disagree with the column it describes. It carries **no `source` field**, deliberately: steps have one producer, the strap, and a single day is routinely fed by both of its transports (live motion and a banked drain deliver the same measurement of the same motion from the same sensor), so a per-row provenance label could not be written honestly. A *measured* day of no walking is a real `0`; a day the strap did not measure has no row at all. `WhoopHardwareGeneration` is the one entity here that describes the *hardware* rather than the body, and it carries a deliberate shape: **five cases** — three WHOOP models plus `standardBleHR` and `simulator`, which are also real answers a discovered device can have — and a derived `selectableModels` returning the three a user may *choose* — derived rather than listed, the rule `SleepStageType.allCases` follows. A single `whoop5` case covering both the 5.0 and the 5.0 MG would collapse the one distinction that matters most, since `docs/BLE_PROTOCOL.md` §7 records that the pair may not agree with each other on the wire. `WhoopDevice` lives only in memory, so the model choice is persisted separately and per device — see `StrapModelRepository` below. `StressScore`, `StressDay` and `StressWindow` are derived on read and never stored — they are a function of `biometric_samples` and nothing else, so a persisted copy could only disagree with the samples it came from. None has a placeholder instance or a zero value: a day with no eligible window has no score and no series at all. `StressDay` is the aggregate *and* the series in one value, and it computes its `StressScore` from the windows it was handed rather than accepting one beside them — so a score describing a different day than the line beneath it is not a bug to guard against, it is unconstructible. `SleepStressNight` is that same bargain for a **night** rather than a day, and it differs in three ways worth naming: it carries its own `span` (the session's in-bed bounds, which cross midnight and are therefore not expressible as a `StressMath.wakingWindow` range within one calendar day), so a chart can never draw its windows against the day's 24-hour axis; it carries a `bands` array where **`0%` is a reading rather than a reserved placeholder**, because a night that spent none of itself highly activated really did spend none of it highly; and its `init` is **failable**, refusing an empty window list and a zero-length span, because its shares are a division and a night with nothing scored has no card rather than three zeroes over an unnamed total. `MetricWeek` and `MetricDay` are the same bargain for a *week*: the seven-day join behind Home's Strain & Recovery chart and its four metric panels, derived on read from three stored histories plus one per-week scalar (the profile's maximal heart rate, which the VO₂ estimate is computed from) and stored nowhere. The VO₂ estimate is the one field on a slot that comes off another field of *the same slot* rather than off a row — `makeDay` hoists the day's gated resting heart rate into one local and both the RHR panel and the estimate read it — so the two can never describe different days. `MetricWeek` builds its slots from the **date sequence**, not from the rows, so a day with no data is an empty slot and never a shortened array — which is what stops a gap from sliding every later point one day to the left — and it computes each panel's rolling baseline as a plain mean over the measured slots only, `nil` below `minimumBaselineDays`. It deliberately takes no `calendar:` parameter: the database snaps day keys with `Calendar.current`, so a caller passing another zone would fail to match the rows rather than shift the week. `MetricDay.deepSleepSeconds` and `.remSleepSeconds` are the type's one pair carried as a **split**, for the one chart in this app that draws a stack, and their total is left underived rather than stored beside them for the reason every duplicated quantity here is: three numbers can disagree where two parts cannot. `SleepNap` is the second entity keyed on an instant rather than a day, and the one that is deliberately **not** a `SleepSession` with a flag: a session has a need, a performance and an efficiency, all three ratios against what a *night* requires, and a nap is by definition a fraction of one — WHOOP's own eight nap rows score 6–43% on that denominator. So it carries its window and its asleep duration and nothing derived from a need it does not have. Its `id` is a `String` where `SleepSession.id` is a `UUID`, and that one difference is what makes an import idempotent: a session's fresh-per-init `UUID` means two reads of one night never compare equal, while a nap's identity comes from the row. `SleepSession.hasWhoopSleepNeed` is the entity's one field that records **provenance rather than a measurement**, and it exists because `sleeps.total_sleep_needed` is a two-producer column: WHOOP's own figure on an imported night, `SleepNeedMath`'s on a strap night, indistinguishable by value. It is set on read from `sleeps.source` and it defaults to `false` — an unknown provenance may not be spent as a known one — which is what lets a caller withhold a claim about a stored pair rather than make one. `WorkoutSession.steps` is the session's own step count, and it is **optional for a reason that is not the usual one**: the producer is live-only. A `MotionBatch` carries absolute strap time only on a banked record, and no imported session can be attributed one, so the field is `nil` on all 673 imported rows and on every session recorded before `v17` — and the page draws a dash there rather than a `0`, which is `StepCount.hasMeasurement` applied on both sides of the write.

**A metric's absence is the same shape in all four: no row, and the optional is the answer.** `CalculateRecoveryUseCase` and `CalculateStrainUseCase` return an optional and write nothing for a day they could not measure, exactly as `AnalyzeSleepUseCase` and `AnalyzeStressUseCase` do, so a day with no data is absent from its table rather than present as a reserved zero — and a reader that forgets the rule sees an empty day rather than a fabricated one. `RecoveryMetric.hasMeasurement` and `StrainScore.hasMeasurement` remain, as **reader tolerance** for placeholder rows written before this rule: they keep those rows off the screens, out of the baselines and off the charts. `MetricWeek` is the one place that encodes all four rules side by side.
* **Use Cases (Interactors)**: Single-responsibility business logic units (e.g., `CalculateRecoveryUseCase`, `CalculateStrainUseCase`, `AnalyzeSleepUseCase`, `AnalyzeStressUseCase`, `TrackStepsUseCase`, `StreamBiometricsUseCase`). `TrackStepsUseCase` is the strap's step producer and the app's only long-lived subscriber: it consumes the manager's motion stream, feeds `StepAccumulator` (see §2.D), and writes one day-keyed row per day. **It is started once from `MainContainerView`'s app-level `.task`, never from `HomeViewModel.load(for:)`** — that runs on every day-step tap, and the streams are multicast, so a subscription opened per call would either orphan the previous consumer or accumulate one per tap, and the failure is silent: a `for await` that stops receiving looks exactly like a strap that went quiet. Its own `isRunning` guard makes a second `start()` a no-op rather than a second consumer. It writes nothing until a motion batch arrives, and on every machine here no motion batch ever arrives — see the note on `biometric_samples` below. `LiveSessionUseCase` is the live session — the app's only recording path, and the only use case held as a stored `let` on `DIContainer` rather than built per screen. It is a `@MainActor @Observable` **class and not an actor**, and the reason is the one `TrackStepsUseCase` records from the other side: it must be *observed* by a screen, and a stream pulled from an actor is not a broadcast, so a second consumer silently starves — the silent `for await` failure the BLE streams are multicast to avoid. `HomeViewModel` already runs a main-actor `for await` over the same `biometric_samples` stream, so the pattern is the incumbent one rather than a new precedent. Its `start()` is idempotent behind an `isRunning` guard exactly as `TrackStepsUseCase`'s is, and **`end()` is not the mirror of it**: the guard makes a second call return `nil`, but only after the first has cleared the flag, so the view holds its own `isEnding` to keep the button from racing a save. It builds the `WorkoutSession` and saves it through `SaveWorkoutUseCase`, whose only call site this is. `RecoveryScoring` is a pure scoring helper rather than a use case, shared by the strap path, the HealthKit import and the WHOOP export import so the weights exist in exactly one place. `AnalyzeStressUseCase` is the one Analyze use case that **never writes at all** — it reads samples and returns a value, with no repository to store it in — so unlike its siblings it cannot damage a stored day, and it is safe to point at any date. It has two entry points and one evaluation: `executeDay(for:) -> StressDay?` and `execute(for:) -> StressScore?`, the latter a forwarder returning `executeDay(for:)?.score` rather than a second implementation, so the two can never disagree about whether a day has a measurement. **`AnalyzeSleepStressUseCase` is the second such use case** and follows the same rule for the same reason: it scores the window `StressMath.wakingWindow` deliberately excludes, reads `biometric_samples` and writes nothing, so it is safe on any night including every imported one. Two things about its signature are decisions. Its **prior nights are handed in** rather than fetched — `execute(for:priorNights:)` takes the same night array the page's other cards were built from, so every figure on that screen describes one set of nights and the use case cannot select a different history from the screen above it, the failure `SleepViewModel.resolveWindow` exists to prevent. And it takes **no `SleepRepository`**, which is what makes that structural rather than a convention. The span it scores is the session's own in-bed bounds, guarded by `maximumNightSpanSeconds` (16 h) and skipped rather than clamped past it — the guard is a bound on the *read*, because one export row's `Sleep onset` is literally `00:00:00`. Its baseline is drawn from prior **nights**, one bounded read per night, collapsed to one point each, below `StressMath.minimumBaselineDays` returning `nil`. Four more types live beside the use cases without being interactors, and all four are the same move — a rule lifted out of a `View`'s body because this repo's runner has no renderer and a rule written into a `body` is a rule nothing can assert. `SleepStageRangeScoring` computes a night's four stage shares against the nights before it, `SleepNeedBreakdown` splits a night's need into the parts the stored row can source, and `SleepConsistencyScoring` assembles the consistency card: the five nights as spans on the model's own clock, the two rules their average draws, and the figure over its window mean. `SleepEfficiencyScoring` takes the window mean of `SleepSession.sleepEfficiencyPercentage` for the efficiency card's comparison, and it **filters out a night with no sleep period before applying its count floor** — `SleepSession.sleepEfficiencyPercentage` guards a zero denominator by returning `100`, so a window mean that counted one would be averaging a fabricated perfect night. All four are pure, all four are `enum` namespaces over free functions, and all four are **statics rather than instance methods** for the same reason: there is no state to hold and the caller has none to give. `SleepConsistencyScoring` also owns the `SleepSession` → `SleepConsistencyMath.Night` mapping (`night(from:)`), because both the score reader and the chart need one answer to "which field is the onset" — see §2.D. Its `typicalScore(in:history:)` carries the card's one absence rule that a fixture could get wrong: a window night that neither a stored figure nor the model can score is **left out of the mean** rather than counted as a zero, since a `0%` consistency is a claim about a night and no night was measured there. `ActivityBaseline` is the activity detail page's comparison model, and it is the repo's second percentile-band value beside `SleepStageRangeScoring`: a `window(for:in:)` that takes the last **ten prior sessions of the same activity name**, strictly before the target's `startedAt` and the target excluded from its own baseline, and a `summary(for:priorSessions:)` that bands the window's durations at the 25th–75th percentile and carries the mean of each banded quantity. **The window is the last ten sessions rather than a calendar window, and that is measured rather than preferred**: `RecoveryScoring.baselineWindow` is day-keyed and an imported `WorkoutSession` has instants and no `date` keypath, and over the bundled export a 30-day window leaves 20 of 28 `Basketball` sessions with nothing to compare against where the last ten leave three. Matching is `ActivityName`'s normalisation — trimmed and case-folded — and **the abstention group is baselined like any other name**, so `Activity` and `Other` have a history rather than a special case. Everything is withheld below the forwarded `RecoveryScoring.minimumBaselineDays`, including the session count. The step mean is taken over a **second population** — the window sessions that carry a count — so an unstored history reads as an absent mean rather than as a history of stillness.
* **Repository Interfaces**: Abstract Swift protocols defining data operations (e.g., `BiometricRepository`, `RecoveryRepository`, `SleepRepository`, `NapRepository`, `WorkoutRepository`, `StepRepository`, `WhoopBLEDeviceRepository`, `StrapModelRepository`, `WhoopProtocolProviding`, `HealthKitSyncing`, `WhoopExportImporting`, `LiveActivityControlling`, `LocationTracking`). The last two are the pair that are **platform capabilities rather than data stores**, and both are `@MainActor … AnyObject, Sendable` for one reason: each holds a handle that is not `Sendable` and has no second instance — an `Activity` for the lock-screen card, a `CLLocationManager` for the GPS — so it needs an isolated home, and the `Sendable` refinement is what lets `LiveSessionUseCase` hold it as a `private nonisolated let`. Dropping either refinement is a compile error at the use case rather than a silent data race. `LiveActivityControlling` takes and returns plain `Sendable` values rather than an `Activity`, because this layer cannot import `ActivityKit` at all; `LocationTracking` yields `WorkoutRoutePoint` and takes and returns a `LocationPermission` this layer declares, so neither protocol names a platform type. **`DIContainer` must hold both implementations as stored `let`s, not computed properties**, and the second is the one that corrects the older note here. A computed property builds a fresh service per read: for `LiveActivityControlling` a second access loses the card and strands it until the system's eight-hour limit, and for `LocationTracking` the `start()` that turned the GPS on and the `stop()` that turns it off land on different objects, so the stop is a no-op against a manager that never started while the first keeps the radio and the blue indicator up for the life of the process. The note that used to sit here called the location field's computed shape harmless "for a stateless wrapper" — true about *state*, wrong about *lifecycle*, which is the pair that matters for a resource that has to be released. `LocationTracking.requestPermission()` **returns** the answer rather than only requesting it, because fire-and-forget cannot tell "the user said no" from "nothing has happened yet" — and *denied* is an answer the session records through rather than a reason to stop. `StepRepository` takes **no `source` parameter on any of its three methods**, which is the same decision `StepCount`'s missing field records from the other side: a day is routinely written by both transports, so a per-call provenance argument could not be honoured. `NapRepository` is deliberately **not** a member of `SleepRepository`: the two answer different questions about a day — one night or `nil`, against an array that is legitimately empty — and merging them would make "no nap today" and "no night recorded" the same return value.
* **`StrapModelRepository` is a preference about the user's hardware, not measured data.** It maps a peripheral identifier to the `WhoopHardwareGeneration` the user picked for that strap, and it is the app's first stored fact about the *device* rather than about a day. `WhoopProtocolProviding` is the Domain-side question the UI asks — can this build frame this generation's packets — and it is a protocol rather than a property on the enum for the reason `HealthKitSyncing` is one: whether an envelope has been implemented is a fact about the code that changes with every release, and a case on an entity would go stale in the one direction that matters (a generation claiming support it does not have). The concrete answer lives in `Data/BLE/Constants/WhoopProtocolProfile.swift`, where the byte-level table belongs.

### B. Data Layer (Infrastructure & Adapters)
* **BLE Engine**:
  - **Which strap is connected is a stored choice, and the guess is only a fallback.** `WhoopHardwareGeneration` has five cases — `whoop4`, `whoop5`, `whoop5MG`, `standardBleHR`, `simulator` — and `selectableModels` derives the three a user may choose. The choice is read from `StrapModelRepository` and wins over the name heuristic; the heuristic (`advertisedName.contains("5")`) survives only for a strap the user has never been asked about, because such a strap still has to be described as something. The precedence rule is `WhoopBLEManager.resolvedGeneration(stored:advertisedName:)`, a **static** taking both inputs so it is assertable without constructing a `CBCentralManager` — which the suite has no way to do, since constructing one raises a system Bluetooth prompt.
  - `WhoopBLEManager`: Direct interface with Apple's `CoreBluetooth`. Discovers peripherals, negotiates MTU, manages reconnects and bonding. Three things about the generation-aware path are load-bearing. `refreshStrapModels()` runs **before** `startScanning()`, because `didDiscover` is a synchronous CoreBluetooth callback and cannot `await` the store. `didConnect`/`didDisconnect` go through `resolvedDevice(for:)` rather than building a bare `WhoopDevice` — whose `hardwareGeneration` defaults to `.whoop4` — so the discovery-time resolution is not replaced by a literal the moment the strap connects. And `sendCommand` is the **choke point**: it refuses to write unless the connected strap's profile carries a command opcode set, because a 4.0-framed command written to a 5.0 strap is a *different message* rather than a rejected one — the two envelopes do not describe the same bytes, and the type numbering they share is no help in telling them apart. **It fans out three streams**, all multicast in the same shape — a `[UUID: Continuation]` dictionary pruned in `onTermination` and guarded by one lock, with a private `yield*` that is the only writer: `deviceStream` (state), `liveTelemetryStream` (the standard `0x2A37` heart rate) and `motionStream` (a decoded `MotionBatch`). A second subscriber must never orphan the first, and the failure is silent — a `for await` that stops receiving is indistinguishable from a strap that went quiet. On connect, `didDiscoverCharacteristicsFor` sends the telemetry enable and then the motion enable, in that order and both from the same callback: it fires once per connection, so a command sent per screen appearance would toggle the IMU off and on as the user moved between tabs. The motion enable is generation-agnostic at the call site — it goes through `WhoopCommandFrames.motionEnableSequence`, which routes on the envelope — so the 4.0 gets its three frames (`0x6A` `[01]`, `0x3F` `[01]`, `0x6B` `[01,01]`) and the 5.0/MG gets its two (`0x51` then `0x6A` `[1,1,0,0,0]`). **Dispatch is on the envelope rather than on which opcode table happens to be non-`nil`**, because the envelope is what a builder must match to produce a valid frame; a router reading one table would agree with the envelope today and disagree the moment a generation carries both, and the failure is silent — a frame with a valid envelope and another generation's opcode is a *different command*, which a strap accepts and acts on. Every function there is **total**: a generation this build cannot write to gets `nil` or an empty array rather than a partial sequence, because half an enable sequence leaves a strap in a state nothing describes.
  - `WhoopProtocolProfile`: the value describing how to frame and parse for one generation — envelope, header-checksum algorithm and **its input**, where the length field and the header checksum sit, the inner record's origin, the packet-type numbering, and **the opcode set that generation transmits**. `profile(for:)` answers `nil` for `.standardBleHR` and `.simulator` only; `.whoop4`, `.whoop5` and `.whoop5MG` all have one. **There are two opcode tables rather than one, and they are separate types**: `commandOpcodes: CommandOpcodes?` for the 4.0 and `syncOpcodes: SyncOpcodes?` for the 5.0/MG, each populated for its own generation and `nil` for the other. The split is not decoration — the two generations genuinely share only part of their numbering (`0x16`, `0x17`, `0x22`, `0x14` and `0x21` are the same byte under both envelopes; the rest are each generation's own), and a single table would invite a builder to reach across for a byte that means something else. `canTransmitCommands` is `commandOpcodes != nil || syncOpcodes != nil` — **true for all three WHOOP models now** — and it is what the builders and `WhoopBLEManager.sendCommand` consult. It is deliberately **not** the envelope: this app validates inbound 5.0 frames, so an envelope guard would have started permitting 5.0 writes the moment the decoder learned to read them, which would have been right about nothing and wrong about why. What `canTransmitCommands` does **not** say is that a strap will answer. The 5.0's command characteristic needs an authenticated SMP bond, which noop reports macOS cannot complete and which **no reference establishes a third-party iOS app can create either** (`docs/BLE_PROTOCOL.md` §7 Q6) — so this is a barrier for every platform this app targets rather than a macOS-only one, and it stays open rather than softened into a permission. `DeviceDetailViewModel.protocolCaveat` is where that reaches a screen, and it says a different sentence per generation because the two have different open questions rather than the same one twice. `WhoopProtocolCatalog.supportsProprietarySync` asks `canTransmitCommands`'s question, since a drain is a loop of writes.
  - The two size helpers on that profile are the whole of why one decoder body serves both envelopes: `innerByteCount(declaredLength:)` is `declaredLength - checksumTrailerBytes` and `frameByteCount(declaredLength:)` is `innerOrigin + declaredLength`. 4.0's documented `length + 4` and 5.0's documented `declLength + 8` are that one rule written two ways, so neither the decoder nor the reassembler contains an `if generation`.
  - `WhoopPacketEncoder`: builds the four transmitted frames (`pingCommand`, `hapticAlarmCommand`, `enableLiveTelemetry`, `requestHistoricalSync`), each a function of a profile and each returning `nil` rather than a frame when the profile carries no opcode set — so the four opcodes are read off `profile.commandOpcodes` rather than typed as literals at the call sites. The 4.0 envelope it writes is `SOF | len u16 LE | crc8 | type | seq | cmd | payload | crc32`, with the CRC8 over **the two length bytes only** and the CRC32 over the inner record. **An encoder and a decoder that share a mistake round-trip against each other**, which is why the suite's assertions must use the published vectors rather than this code's own arithmetic. `WhoopCommandSequence` supplies the inner `seq`.
  - `WhoopPacketEncoder5`: the **5.0/MG** builder, and a separate type rather than a parameter on the one above — which is what that type's own doc comment said would happen, because the two envelopes differ in the length field's offset, in the header checksum's polynomial *and its input*, in where the inner record starts, in the two header bytes nobody has explained, and in every opcode they transmit. A single builder handling both would be a builder whose every line is a `switch`, and the one thing a wrong guess costs is a frame that is not rejected but is a **different message**. Its gate is `fiveEnvelopeOpcodes`, the counterpart of the 4.0's `fourEnvelopeOpcodes`: each builder consults its own table, so a 4.0 profile handed to this file gets `nil` rather than 4.0 opcodes under a 5.0 envelope. Two details are pinned rather than computed. `reservedHeaderBytes` (`00 01`) is the one field in either envelope this build does not understand — `docs/BLE_PROTOCOL.md` §2 names the two bytes and does not specify them, and the CRC16 covers them, so they are literals copied from the published frames; a zero constant would assert the field is empty and a derived value would assert this app knows what it means, and neither is true. And the hello's payload is one byte (`0x01`) copied from §2.1's published frame on the same footing. The builder's own arithmetic is checked before it returns: `frame.count == frameByteCount(declaredLength:)` is the identity the decoder relies on, so a frame whose arithmetic disagrees with the profile is refused rather than handed back.
  - `WhoopCommandFrames`: the generation-agnostic command surface — **the one place a caller asks for a frame without knowing which envelope will carry it** — and the reason the manager's enable call site is generation-agnostic. Dispatch is on `profile.headerChecksum`, not on which opcode table is non-`nil`: the envelope is what a builder must match to produce a valid frame, so it is the field that decides, and it is also the field the builders themselves guard on. Every function is **total** — a generation this build cannot write to gets `nil` or an empty array rather than a partial sequence. `setClockFrames` is the one entry that can return **two** frames for one generation and one for the other: the 4.0 takes an 8-byte newer-firmware form and a 9-byte legacy form and **both are sent**, because a wrong-length set is acknowledged but not latched and each is a no-op on the other's firmware, while the 5.0 takes one form (`0x92`). Its `clockReadBack` answers `nil` for the 4.0 — **neither reference gives that generation a clock get** — rather than sending something else, and **issuing the 5.0's read-back is not the same as checking it**: nothing in this app decodes the reply, so no path may claim a clock latched.
  - `WhoopPacketDecoder`: validates a proprietary frame and hands it up **undecoded** as a `WhoopRawFrame` (generation, type, seq, cmd, payload). Four checks, in order: start of frame, declared length, header checksum over the format's own bytes, and CRC32 over `frame[innerOrigin ..< length]`. A frame that fails any of them produces nothing and logs why — **a rejected frame is silence, not an error the caller can act on**. **No proprietary payload decoder belongs here.** There is no live-telemetry and no battery proprietary type in the spec, and the historical record's layout is the one `docs/BLE_PROTOCOL.md` §4 gives a **96-byte** header — so a 16-byte chunk walk reads a byte of the record counter as a heart rate. Raw frames are also the shape the pending capture needs. `decodeStandardHeartRate` is untouched: the SIG `0x2A37` profile is not a WHOOP envelope and remains the one heart-rate producer on this path that is implemented end to end.
  - `WhoopFrameReassembler`: rebuilds a frame that arrives split across notifications, which every record this app wants does — a notification carries at most `MTU − 3` bytes against a 5.0/MG type-47 `R21` record of 1244 and a 4.0 live IMU stream near 1.9 KB. It owns **boundaries and not validity**: it finds a start of frame, reads the declared length at the profile's own `lengthFieldOffset`, holds bytes until that many have arrived, and hands the candidate to `WhoopPacketDecoder`, whose checksums are the only thing that decides whether those bytes were a frame. A candidate the decoder refuses is treated as a payload byte that looked like a boundary, and the scan resumes one byte later, so a lost notification costs bytes and never a reading. Duplicating the length or checksum rules here is the drift the arrangement exists to prevent. Two properties are load-bearing: a boundary declaring more than `maximumFrameBytes` (4096) is skipped rather than waited on, which bounds the buffer without a trim rule, and the buffer is **per-connection** — `WhoopBLEManager` resets it on both connect and disconnect, because bytes held across a reconnect would be prepended to the next stream's first frame and shift every field in it.
  - `MotionPayloadDecoder`: the one payload decoder that survived the deletion below, because its layout is the one `docs/BLE_PROTOCOL.md` §6 specifies rather than one this app invented. It walks two layouts — `R10` for the 4.0's live `0x2B`, `R21` for the 5.0/MG's type 43 and 47 — and dispatches on the frame's **generation**, not by trying one and falling back: the two generations share the packet-numbering (so the type byte cannot discriminate) and differ in envelope and origin, which is exactly the per-generation difference that must not collapse into a fallback. Both layouts **require an exact payload length** (1910 and 1244) and return `nil` rather than walking off their own end, and §6's offsets are **frame-absolute**, so the decoder subtracts the profile's `innerOrigin + innerPrefixBytes` — 7 under the 4.0, 11 under the 5.0 — while the spec's own numbers stay verbatim in the code. It emits a `MotionBatch`, and the two generations differ in one field that the batch makes explicit rather than implied: `timestampIsFromStrap` is `true` for `R21`, which carries the strap's own unix stamp at frame 15 with its 1/32768 s fraction at 19, and `false` for `R10`, which carries no clock and therefore takes the arrival instant — the one place the two generations key a day differently.
  - `HistoricalDrainSession`: the state machine that makes a flash drain terminate, and the reason the drain's request byte was withheld until it existed. `WhoopFrameReassembler`'s shape — a `Sendable` struct with `mutating func accept(_:) -> DrainAction` — and its rule is `docs/BLE_PROTOCOL.md` §4's: records stream as one type punctuated by metadata whose sub-type sits at `inner[2]`, and the three sub-types are three different actions rather than three names for one. `HISTORY_START` is ignored; **`HISTORY_END` is acknowledged and then the session keeps listening**; `HISTORY_COMPLETE` stops the session and is **not** acknowledged. The asymmetry is the whole point — a batch that is not acknowledged is re-sent forever, so a build holding this loop is required before the request may be sent at all, and a build holding no loop is better off sending nothing. The continuation token is eight bytes and **lives at the same frame offsets on both generations** — `inner[13:21]` under the 4.0 and payload `[6,14)` under the 5.0 are the same eight frame bytes — which is what lets one session serve both envelopes, and the offset is derived rather than restated per generation so the two cannot drift. A marker too short to carry a token is still a batch and still gets no acknowledgement, because a padded token would be eight invented bytes sent to a strap that would read them as a cursor. Termination is `HISTORY_COMPLETE`, an idle timeout, or catching up to the live edge, and the idle window is read off the profile rather than passed in — **8 s for the 4.0 and 60 s for the 5.0/MG** — so a caller cannot pair one generation's window with another's drain. The live edge is **two-sided** (a batch stamped within five seconds either side of the phone's clock ends the drain) because a strap whose RTC is wrong is wrong in both directions, and a one-sided window on a fast strap would end the drain early and silently lose everything behind it.
  - `WhoopMockBLEManager`: High-fidelity hardware simulator generating realistic physiological variations for UI development and unit testing without requiring physical hardware.

It is nullable and undefaulted, and that is the whole point of it: `UserProfile` carries ten fields while `user_profiles` stores three, so every unbacked one is an initialiser default no row can override — and `weightKg`'s `75.0` is divided into by `CalculateStrainUseCase`'s calorie estimate. NULL is the honest value for a fact nobody supplied, exactly as `source` documents, and it is what makes the absence reachable — an unset weight produces **no** calorie figure rather than a plausible one. A failing migration calls `fatalError` in `init`, so it crashes at launch rather than at the query.
  - `UserDefaultsStrapModelRepository` is the one repository in `Data/Persistence/` that is **not** GRDB, and the choice is deliberate rather than lazy: it stores the per-device model choice as a `[peripheralUUID: rawValue]` dictionary under a single `UserDefaults` key, beside `UserDefaultsAppPreferencesRepository`, which is the shape this repo already keeps its non-measured settings in. Two reasons not to make it a migrated table. A failing migration `fatalError`s the app at launch, so a migration is a large hammer for a preference; and the value is a statement about the user's *hardware* rather than a measurement, which is exactly the distinction that puts everything else in this file on the `source` column's side of the line. The consequence to accept knowingly: a peripheral identifier survives launches but not a reinstall, so a reinstall loses the mapping and falls back to the heuristic until the picker is used again.
  - `source` records which writer produced a row: `whoop_export` for a bulk import, `NULL` for a row the app measured itself through the strap or HealthKit. It has one reader, and it is `GRDBSleepRepository.makeSession`, which resolves it into `SleepSession.hasWhoopSleepNeed` — the fact that separates WHOOP's own `Sleep need (min)` from one `SleepNeedMath` computed, since both are stored on the same column and nothing in the two numbers tells them apart. The mapper is where it is resolved because the mapper is where the column exists at all, and every value that is not the importer's own label (a strap night's `NULL`, a row written before the column) resolves to *not known to be WHOOP's*: the answer that withholds a claim rather than making one.
  - `workouts` deliberately **breaks the day-key rule** the other metric tables follow. `recoveries`, `sleeps` and `strains` are primary-keyed on `date` snapped to `startOfDay`, because a day holds one of each; a day can hold several workouts, so `workouts` is keyed on `id` (a UUID string) with `date` as an ordinary indexed lookup column. `WorkoutRoutePointRecord` and `WorkoutSplitRecord` are separate tables keyed on their own `id` and bound to the session by a `workout_id` foreign key, fetched per workout rather than joined — a join would multiply the session row by its route points. The records live in `Data/Persistence/Models/WorkoutRecord.swift` as one file because the three are one aggregate.
  - `GRDBWorkoutRepository` is what makes a recorded workout survive the launch that recorded it. **`makeSessions` skips any row whose `id` is not a UUID**, which is a constraint on every writer rather than a lenient read: `WorkoutRecord.id` is a UUID string, so a row keyed on anything else — the string-instant trick `SleepNap` uses — reads back as *no workout at all*, silently, with the insert having succeeded. An imported workout's id is therefore **derived from its own two instants** rather than fresh, which is what makes re-importing the same file update 673 rows instead of appending 673 more: GRDB's `save` is INSERT-or-UPDATE *by primary key*.
  - Repositories implement domain protocols to convert GRDB records into immutable domain models, and they **answer from local storage only** — there are no fallback sources. A stored row maps to a model without inventing values: a column the strap never filled in becomes `nil` on the model, never a plausible constant, so "not measured" stays distinguishable from a measurement all the way to the screen.
  - History reads state the day their window **ends** on: `getRecoveryHistory(days:endingOn:)` and its `sleeps`/`strains` siblings, with `endingOn` defaulting to now for the scoring baselines and the JSON exporter. The end is a parameter rather than an assumption of `Date()` because the metric screens show a day the user picked, and a window anchored on *now* cannot describe it. The reads bound the top of the window too (`<= endingOn.endOfDay`) — without it, a window anchored on an old day runs on to the present. `WorkoutRepository.getWorkoutHistory(days:endingOn:)` is the same read on a table that is not day-keyed, and it is what the strain page's zone baseline is taken over: several workouts share a day, so its caller collapses the result to one figure per day before the window is taken, and `Dictionary(grouping:)` does not preserve order — the series must be sorted oldest-first before it is handed to `baselineWindow`, or the trailing thirty are not the trailing thirty.

  - `WhoopExportParser`: Reads WHOOP's export files into `WhoopExportRow` values — a plain `Sendable` struct of optionals, with no GRDB types and no decisions. Nothing about what an empty cell *means* is decided here, and a row whose date or timezone cannot be parsed **throws** rather than being skipped silently. **One row type, three entry points**, because the three files the app reads share their date and heart-rate columns: `parseCycles` reads `physiological_cycles.csv` against `requiredColumns` (`Cycle start time`, `Cycle timezone`, `Wake onset`), `parseNaps` reads `sleeps.csv` and additionally requires the `Nap` column, and `parseWorkouts` reads `workouts.csv` against a `workoutColumns` set of its own (`Cycle start time`, `Cycle timezone`, `Workout start time`, `Workout end time`) since that file carries no `Wake onset` at all. **Each entry point requires the column that tells its file apart**, which is what makes pointing one at another file's file raise `missingColumns` rather than reading the whole file, finding none of what it wanted, and reporting a successful import of nothing. `parseNaps` goes on to filter to `isNap == true`, since 910 of `sleeps.csv`'s rows are nights the cycle file already owns; `parseWorkouts` deliberately does **not** filter, because all 673 of its rows are workouts — including the 45 whose five zone percentages are all zero, which are real low-intensity sessions rather than absences. **One field is read without being required, and it is the only one.** `text(_:)` returns `nil` for a column that is absent *and* for a cell that is empty — the two the `flag(_:)` reader deliberately separates, because `parseNaps` filters on it — and `activityName` is read that way because a name has a natural absence where a heart rate does not: a file without the column imports and every row falls back, rather than throwing on a column that carries no measurement. `workoutColumns` is unchanged for that reason, and it is the set a row must carry to *be* a workout rather than every column the file is read for.

It day-keys on `startOfDay(Wake onset)`, scores each night through `RecoveryScoring` against the preceding 30 imported days — the window is `RecoveryScoring.baselineWindow(before:in:)`, shared with every other reader rather than owned here, because the Recovery detail screen prints the same baseline its score was computed from — and takes Strain verbatim because the export holds no heart-rate series. Days with an existing measurement are skipped, so the import is idempotent. **It reads three files through one button.** `importBundledExport()` takes the naps out of `sleeps.csv` and the workouts out of `workouts.csv` first and folds both counts into the same summary, so More → Settings' import is one action over one export; a build whose bundle lacks either side file imports none of those rows and reports `0` for them rather than failing, because the cycle file is the one the app asked for and the other two are side files. Each side path keys, writes and reports separately — `napsWritten` and `workoutsWritten` are deliberately **not** added to `daysWritten`, since a nap is not a day and neither is a workout, and adding either would make the summary claim history it did not import. **The workouts path is the only producer of `workouts` rows**, and its ids are **derived from the two instants** rather than fresh: `GRDBWorkoutRepository.makeSessions` skips any row whose `id` is not a UUID, so the string-key trick `SleepNap` uses would be silently discarded here, while a fresh `UUID()` would write 673 more rows on every press because GRDB's `save` is INSERT-or-UPDATE *by primary key*. * **Services**: The platform-specific implementations behind a Domain protocol, each written as **two branches under one type name** in a single file so the layer above contains no `#if` of its own — `LocationTrackingService` is the older one and `LiveActivityController` copies its shape.
  - `CoreLocationTrackingService` is the GPS behind `LocationTracking`, and **every one of its settings is a way a route comes out wrong rather than a preference.** `distanceFilter` at 5 m: at zero a phone on a bench writes a jitter cluster, and set wide a run's corners are cut. `activityType = .fitness` is what tells CoreLocation to expect human locomotion rather than a drive. `pausesLocationUpdatesAutomatically` defaults to `true`, which lets the system decide the user has stopped and silently end the route at a rest stop — the failure is invisible, because the session keeps running and only the route stops growing. `desiredAccuracy` stays `kCLLocationAccuracyBest` rather than `BestForNavigation`, which is for turn-by-turn and buys precision no route drawing can show. **`allowsBackgroundLocationUpdates` is legal only once `App/iOS/Info.plist`'s `UIBackgroundModes` declares `location`** — setting it without that entry raises `NSInternalInconsistencyException` at launch rather than being ignored, so the flag and the plist entry are a pair and neither is optional; without the mode a route stops growing the moment the screen locks, which is most of a run. `showsBackgroundLocationIndicator` is the counterpart that keeps the delivery honest once it continues off screen. Two implementation details are load-bearing. The manager is built **lazily in `activeManager` rather than in `init`**, because `DIContainer.init` is `nonisolated` and a `CLLocationManager` cannot be constructed or configured off the main actor — the same problem `LiveActivityController` solves by giving its handle a default of `nil`, except here the object itself is what cannot exist yet. And `requestPermission()` **reads `authorizationStatus` first and returns it when it is not `.notDetermined`**: `requestWhenInUseAuthorization()` is a no-op on a settled status and iOS does not deliver `locationManagerDidChangeAuthorization` in that case, so a continuation parked unconditionally before the call is never resumed and the caller waits forever behind a prompt that never appears. The `#else` branch reports `.authorized` and yields nothing, and it is **unread rather than wrong** — the host cannot present `LiveSessionView` and the runner injects its own spy — so it is not a model to copy. `PreviewLocationTrackingService` is the SwiftUI previews' GPS: a short closed loop in lower Manhattan, delivered at once.
  - The `horizontalAccuracy < 0` filter — CoreLocation's own "this coordinate is not valid" signal — stays in the service, because it is a fact about a `CLLocation`. The `0, 0` rejection does **not**: it lives on `WorkoutRoutePoint.isPlausible` (§2.A), because the runner has no `CLLocationManager` and must not build one, so a rule written inside `didUpdateLocations` would be a rule nothing can assert.
  - `LiveActivityController` is the lock-screen card, and it is the widest instance of the "a green iOS build says nothing about the host one" family. Three separate things about it are invisible to `swift build`, because the whole iOS branch is compiled only for iOS: `ActivityAttributes` is `@available(macOS, unavailable)`; **`Activity` is not `Sendable`** in the iOS 27 SDK while `update`/`end` are `nonisolated async`, so every call sends the handle off the main actor and Swift 6 rejects it outright — the import is `@preconcurrency import ActivityKit`, and `WhoopsySessionAttributes.ContentState` separately conforms to `Sendable` for the `ActivityContent` half of the same diagnostic; and `ActivityConfiguration` has exactly one initialiser whose `dynamicIsland:` parameter is required. `isSupported` is `true` here and `false` in the `#else` branch, so nothing above branches on `os` — and it is deliberately **not** `ActivityAuthorizationInfo().areActivitiesEnabled`, which is a runtime refusal that arrives through `start` throwing rather than through a flag a caller has to remember. `endOrphans()` reads `Activity<…>.activities` rather than the in-process handle, because the case it exists for is precisely the one where `self` did not survive.
  - **The widget extension is a second SwiftPM product and a second Xcode target.** `WhoopsyLiveActivityKit` holds the `ActivityAttributes` and is linked by the extension *and* by `Whoopsy` (from `#if os(iOS)` code only, so the edge is inert on the host); the extension links the Kit and **not `Whoopsy`**, which keeps GRDB, CoreBluetooth and the three bundled CSVs out of a process with a hard memory budget — and is why the card restates a handful of `Theme` tokens by value. The `.appex` is embedded by a `PBXCopyFilesBuildPhase` with `dstSubfolderSpec = 13`, the target carries `SKIP_INSTALL = YES` and `GENERATE_INFOPLIST_FILE = NO`, and widget-ness is carried by `NSExtensionPointIdentifier = com.apple.widgetkit-extension` in `App/LiveActivity/Info.plist` rather than by a product type. The extension is listed **explicitly in `WhoopsyApp.xcscheme`'s build action** and not left to the app target's dependency, because a scheme's build action is what Xcode actually builds — reachable only through `dependencies`, it is built by `xcodebuild` and not by a Cmd-B in the GUI.

### C. Presentation Layer (SwiftUI + MVVM + Design System)
* **Declarative SwiftUI**: Optimized for iOS 17+ with smooth 120Hz ProMotion animations, dark-mode-first aesthetic, glowing gauges, and live ECG-style sparklines.
* **ViewModels**: Annotated with `@Observable`, accepting Use Cases via constructor injection. They emit discrete UI states (`Idle`, `Connecting`, `Streaming`, `Error`).
* **1:1 Official WHOOP App Layout Structure**:
  - `MainContainerView.swift`: Bottom navigation tab bar routing container. **It builds one view model per screen and never shares one between two screens**, which is what lets Home's pushed `SleepDetailView`, `RecoveryDetailView` and `StrainDetailView` each hold their own day without moving the tab behind them.   The five week charts share a **frame** and nothing else, and the split is `WeekChartAxis`: the seven-column geometry (`columnWidth`, `x(slot:columnWidth:)`), the highlighted anchor column filled with `Theme.ringTrack` at `anchorFillOpacity`, and the weekday-over-day-of-month date strip with its chipped bold anchor day. It exists because five copies of a date label are five chances to label a column with the wrong day, and the charts sit directly above and below each other so a disagreement would be visible. Everything that differs stays in the chart: bars against a line, a fixed scale against a fitted one, a tier colour against a flat one, gridlines against none. `StrainRecoveryChartView` deliberately does **not** use it — its geometry has gutters for two labelled axes and its private `Scale` honours `rect.minX`, so it is a genuinely different frame rather than a copy, and it is documented as such inside `WeekChartAxis` rather than left implicit.

  `WeekLineChartView` draws the page's three **auto-fitted y-axes**, and the trade is explicit. `FittedAxis` rounds a set of values out to bounds that are multiples of a step chosen from a fixed ladder (1, 2, 5, 10, 20, 25, 50, 100, …) so the gridlines land on values a reader can name — an HRV week of 32…67 becomes 30…70 at step 10 with lines at 40/50/60, the reference resting-heart-rate week of 49…66 becomes 45…70 at step 5 with lines at 50/55/60/65, and the reference respiratory-rate week of 14.8…16.5 becomes 14…17 at step 1 with lines at 15/16 — and it widens a zero-span range rather than dividing by it. The doctrine it bends is the **fixed-scale** one (`CLAUDE.md`, the Stress Monitor): an auto-scaled axis draws a calm day and a wired day as the same picture. The distinction is that the rule is about *unlabelled* shapes, where height is the whole of the evidence; this chart labels **every** point with its value, so the axis is a guide and the reading is stated. None of the three quantities has a usable fixed scale, from opposite directions: HRV's absolute magnitude is meaningless without the person's own baseline and has no natural ceiling, and a resting heart rate and a respiratory rate *do* have physiological floors and ceilings but a week of either spans a couple of units, so any fixed axis wide enough to hold every person flattens every week into a straight line. So the alternatives are a fabricated ceiling or a fitted axis, and the labels are what make the fitted one honest. **The resolution those labels print at is not this type's business** — a ladder that rounds milliseconds out to tens must round breaths out to single units, and the type only ever sees numbers — so it lives on `WeekLineSeries.valueDecimals`, where the chart's labels and the card's spoken sentence both read it and cannot state the same day differently. Remove the labels and it becomes exactly the chart the fixed-scale rule forbids, which is why the two ship together and why a run of one point still draws its label.

  `WeekLineChartView` is **one view for all three series**, and `WeekLineSeries` is **one type with three named initialisers**, because the three cards are the same drawing around a different selection rule — and, for one of them, a different resolution. They differ in which days plot and how finely their numbers read, and both are the initialiser's business — the caller hands the series in already built, narrowed or not — so everything downstream is shared: the same fitted axis, the same hollow points, the same value labels over them, the same seven columns and date strip. Three copies of a chart would be three chances for one of them to drift, and neither difference would show up as a compile error. The two whole-number quantities (`hrvWeek`, `restingHeartRateWeek`) print at `valueDecimals == 0`, because that is the resolution their columns are stored at; `respiratoryRateWeek` prints at 1, because a week of breaths spans about two units and a whole-number label would render the reference week's six distinct days as six `15`s. The selection rules differ too: the HRV initialiser is the only one that narrows, since it is the only one whose column holds two incomparable quantities. The series is a type rather than code in the view's body for the reason `DayBarRules` is one: the runner has no renderer, so a rule written into a `View` is a rule nothing can assert.

  The three initialisers answer "which days plot" differently, and that is the whole of the difference between the cards bar one resolution. `init?(restingHeartRateWeek:)` and `init?(respiratoryRateWeek:)` take **every** day carrying a reading: each of those is one quantity in one unit, so nothing is narrowed, and the assertion that keeps this honest is that a week giving the HRV line three points gives the resting-rate one five. `init?(hrvWeek:)` cannot, and applies the **never-mix rule** to the chart — it narrows to `MetricWeek.hrvBaselineMetric`, the newest measured slot's quantity, so a week holding both SDNN and RMSSD plots only one of them and *fewer than seven points* even though the dropped days were measured. All three then split the points into `runs` of adjacent slots so the line **breaks** at a gap. A gap is either an unmeasured day or — for HRV — a day measured in the other quantity, and a segment drawn across either would be read as a value for days this line has no reading in; a run of one draws its dot and no segment. That is the rule `StrainRecoveryChartView` and `StressMonitorChartView` already follow. The resolver that differs is `valueDecimals`, on the same type and for the same reason as the selection rule: `restingHeartRateWeek` and `hrvWeek` print whole because their columns are stored whole, and `respiratoryRateWeek` prints to a tenth because a week of breaths spans about two units — the reference week's six distinct days all render as `15` at zero decimals. All three lines and their hollow points are drawn in `Theme.weekLine`, one token for the three of them: every other blue in `Theme` already means a sleep stage, a ring or a tier, and borrowing one would invite a reader to compare two things this app has decided not to put on one axis. The shared token is also a deliberate statement that here the **colour does not carry quantity identity** — on the bars above it does, since the bar's colour *is* the recovery tier, but on these three the card's own label and its own axis say which quantity is plotted, so colouring them apart would imply a relationship between a millisecond count, a beat rate and a breathing rate that does not exist. **The page carries no chrome above the ring at all**: no `DashboardHeader` and no `DayNavigationBar`, for one reason — the page is one night's reading against one trailing window, and a title or a stepper above it is furniture that either restates what the reader just tapped or invites them to page the day out from under the figures. The no-data state survives the header's removal in the gauge's own label, which reads "No data" on a day with no measurement. **`RecoveryDetailView`'s day is handed in and fixed** — `private let date`, a plain `let` rather than a `@State`, because nothing can change it: the Recovery tab passes `Date()` and Home's ring pushes the day on screen. It is the one day-keyed screen without a stepper, and the consequence is worth stating plainly: on an install whose history is all imported, the Recovery *tab* opens on today, which is past the export's end, and shows a dash with no way to page back. Every past day is still reachable through the ring, which is the route that exists for this. Two things in the app this was modelled on are deliberately not drawn, and the reason is in the view's own doc comment: the WHOOP wordmark (another company's brand, in the one position on a screen that says whose app it is — which is now simply empty rather than holding a substitute) and the `i` button beside the ring (no destination — the affordance rule below).

  `WeekBarChartView` is **one view for both of the page's bar charts**, and `WeekBarSeries` is **one type with two named initialisers** — the arrangement the lines already have, adopted one chart later for the same reason. And its sync section is where the two generations' **different** open questions reach a screen, because one generic sentence for both would hide the reason a 5.0 sync is the more likely of the two to do nothing — which is the one thing that caption exists to say. The 4.0's caveat is unvalidatedness alone: the envelope matches two independent references and its checksums are pinned by published vectors, but no frame it builds has been seen by a strap. The 5.0's carries a second and more specific blocker — the command characteristic's authenticated SMP bond, `docs/BLE_PROTOCOL.md` §7 Q6, which nothing in this project establishes is completable from a third-party iOS app. `DeviceDetailViewModel.protocolCaveat` holds both sentences and switches on the model; `supportsSync` reads `WhoopProtocolCatalog.supportsProprietarySync`, which is now `true` for all three WHOOP models and `false` for `.standardBleHR` and `.simulator`. **What that caption may not do is imply a strap has answered** — it states what is unproven, and the caveat moves only with a capture that proves it. Its connection and battery rows follow Home's badge rule exactly: a dash, never a number, unless the strap is connected, because `WhoopDevice.batteryPercentage` is a literal `100` written at discovery. **The battery readout the user asked for lives here as a page template, not as a measurement** — the placeholder is the badge's own icon, and this page is where a real figure would land once a command that reports one exists.
  - `Settings/`: Data privacy toggles, local SQLite backup exports, and UI configuration options. Hosts the one-shot WHOOP-export import button — the only entry point to `WhoopExportImporter`.
* **Day selection**: `DayNavigationBar` (in `Presentation/DesignSystem/`) is the one day stepper, shared by **Home, Strain and Sleep** — and deliberately not by Recovery, which is handed a fixed day instead (see the `Recovery/` row above; its four rows describe one night against one trailing window, and paging away would leave the window explaining a day no longer on screen). Each of the three owns a **private** `selectedDate` — deliberately independent, so paging one tab does not move another — and each loads that day by **reading** it through its repositories. **The calculate use cases are unreachable for a past day, and the reason is the read rather than the write**: a stored day has no raw samples to recompute from — an imported day has none by construction — so a recompute comes back as **no row at all** and blanks the day on screen. (On a strap day that did hold samples the same call would recompute over a stored row, since neither use case checks what is already there; both return `nil` and write nothing when they measured nothing, which is what keeps the imported case safe.) Two of the bar's three behaviours are rules about the **date** rather than about data, so they hold wherever it is drawn and live in `DayBarRules`: the centre reads `TODAY` when the day is today, and the forward chevron stops there — a day that has not happened is empty everywhere, and leaving the clamp to the screens that happen to pass a calendar would give the app two day steppers that disagree about the future. `DayBarRules` also takes `now` as a parameter, which is what lets the runner assert both rules without a renderer and without a clock (`Domain`, and therefore a `Color`-free helper, cannot be where they live — they are a `Presentation` rule about a label).
* **DesignSystem**: Reusable design tokens, glassmorphic card containers, the shared `DayNavigationBar` day stepper, the month calendar (`MonthGrid` + `Components/MonthCalendarView`), and signature neon color palettes (Recovery Green/Yellow/Red, Strain orange-red scales). All colours are tokens in `Theme.swift` — including the Home surfaces (`homeBackground`, `homeCard`, `ringTrack`, `sleepPerformance`, `strainRing`), — **never inline one**, since a screen-local literal is exactly what a token replaces. Two of the tokens are a **pair rather than a colour**, and both are drawn on the sleep detail page's last two cards: `bandMarkFill`/`bandMarkEdge` are the region and the two dashed rules of a typical-range band, and `bandMarkEdge` has a second reader — the consistency chart's two average rules, which are the same mark turned ninety degrees, so the app has one dashed rule and not two that can drift. `bandMarkFill` deliberately has no second reader: a region bounded by two rules is a span, while the consistency chart's two rules are two independent values with nothing between them to fill. `sleepConsistencyBar`/`sleepConsistencyPriorBar` are that chart's two bar colours — the night and the four nights it was read against — kept off the page's `sleepPerformance` blue because that token encodes *how much* was slept and this chart encodes *when*, and off `ringTrack` because that is the app's "nothing was measured" grey and these are five measured nights. The three `bandPoor`/`bandSufficient`/`bandOptimal` tokens are the **sleep** band scale, not the recovery tiers: this scale's middle colour is a neutral grey rather than a warning yellow, because "Sufficient" is not a caution — and `Components/SleepBandBar.swift` draws the three-segment position bar that lights one of them, over `SleepBand.allCases` so a fourth band could not be drawn without appearing there. Unlike `HeartRateZoneBar` and `HypnogramChartView` it deliberately carries **no `GeometryReader`**: those two draw a distribution whose segments are proportional to a quantity, while this one draws a *position* on a fixed three-step scale, so its segments are equal by definition. `Components/MetricChange.swift` is the one definition of a **comparison between a figure and the value it is read against** — which way it moved, and whether that movement is good news — shared by Home's four metric panels, Home's two tiles, and the Recovery breakdown's four rows. Sharing it is the one-rule-one-definition discipline applied to a component, and the two decisions it holds are exactly the two a copy drifts on. **Direction and verdict are separate by construction**: the triangle always points the way the number went, while `higherIsBetter` turns that direction into a verdict and the verdict alone picks the colour — so an HRV rise is green while a resting-heart-rate rise is red, from one call. Three further rules are worth knowing because each produces a wrong marker that looks plausible. The verdict has **three states**, not two: green better, yellow the same, red worse — and the middle one is why the colour is not derivable from the direction, since a figure equal to its average has no direction at all. `direction` is therefore optional, and `nil` there means *unchanged* and draws `circle.fill` rather than a triangle. The comparison is made on the **formatted** pair, not the raw one (a resting rate of 52 against a mean of 52.4 is genuinely below it, but both print as `52`, and a row reading `52 ▼ 52` contradicts itself). And a `nil` **`MetricChange`** — no marker at all, just the mean — is reserved for a missing side: a day with no measurement, or a window too thin for a baseline. That is a different absence from `.same`, and one the screen renders differently. Two more components live here for the same reason `MetricChange` does. `Components/MetricHeadline.swift` is the big figure over its comparison — the night's hours of sleep, or the need card's percentage, against the window's mean — and `Components/CardNotch.swift` is the caret drawn on a card's top edge to point it at whatever it explains. Both have two callers, so neither belongs inside a screen. The notch in particular is a `Shape` rather than an `Image` so it takes the fill of the surface it is attached to and cannot come to be drawn in a colour that surface is not; its two callers fill it differently, which is exactly what a shape buys. `ActivityGlyph.swift` is the third member of the one-mapping family the two `+Extensions` files began, and the first that maps a **string to a drawing** rather than a value to a colour: `ActivityGlyph.symbol(for:)` is the single table turning a workout's own `Activity name` into the SF Symbol its row draws in Home's `ACTIVITIES` card, keyed lowercased and trimmed so a future export that re-cases a name still lands. It is a named type with a function rather than an extension on `String` — an extension would put an SF Symbol on every string in the app — and it lives here rather than inline in a `View`'s body for `DayBarRules`' reason: the runner has no renderer, and **a wrong symbol name is not an error**, so a typo draws an empty chip and nothing else sees it. Two properties the type cannot enforce and that its callers must: a symbol has to exist on the **deployment target** (iOS 17.0, so the iOS-18 `figure.ice.skating` and `figure.indoor.*` names draw nothing here), and `Activity` / `Other` deliberately take the `figure.run` fallback, because WHOOP's two words for an activity it did not categorise are not activities and giving them a glyph would claim a distinction the file does not make.
* **The month calendar is Home's, and it is opt-in on the shared bar.** `DayNavigationBar` takes an optional `onTitleTap`, and Home is the only caller that passes one; where it is `nil` the centre stays the plain `Text` it always was, because a title that looks tappable and has nowhere to go reads as broken — the same rule that keeps `CUSTOMIZE` and the ACTIVITIES expand icon off the screen. Opening it is an **overlay**, not a `.sheet`: a sheet is a full-height card the system centres, which left the grid floating in a dark slab with the app's own screen invisible behind it, whereas the calendar is a small bounded thing that reads as one only when it hangs from the top of the safe area with the day it is choosing between still legible under a partial (`0.45` black) scrim. Home hides the tab bar while it is up — an overlay inside a tab cannot cover the bar, and a live row of tabs under a modal both looks wrong and lets a tab switch strand the calendar open. `MonthGrid` is a pure value that derives the weekday header and the leading blanks from **one** `firstWeekday` rotation so the two cannot drift, and `MonthCalendarView` is dumb: values in, closures out.
* **Home's `+` opens the second overlay on that screen, and it is the calendar's shape rather than a `Menu`.** `ActivityMenu` in `Presentation/DesignSystem/` holds the two rows as data — `Entry`, a symbol, a title and an `Action` case and no closure — for `DayBarRules`' reason: the runner has no renderer, and a row written into a `View`'s body is a row nothing can assert. **`ADD ACTIVITY` is inert and `START ACTIVITY` pushes `LiveSessionView`**, and an `Action` case rather than a `() -> Void` is what keeps the older guarantee intact: a closure stored in a static list cannot be asserted, cannot be `Equatable` and can capture anything, whereas a case names the one thing the row does, §18 asserts which row carries it, and `HomeDashboardView`'s switch is exhaustive — so a third action is a compile error at the one call site rather than a silent no-op. **The `+` itself is drawn on every day; the day decides which rows the card holds.** `ActivityMenu.entries(on:)` forwards to `DayBarRules.isToday` and withholds `START ACTIVITY` off today, leaving `ADD ACTIVITY` — so the header carries no condition, and the button and its `ActivityMenuAnchorKey` anchor are unconditional together rather than gated as a pair. That is also why the withheld thing is a row and not the button: `ADD ACTIVITY`'s import path is bound to a file the user supplies and not to a day, so no other day has a reason to withhold it, and a `+` that vanished on every day but one would take it along. It is a named policy rather than a comparison in the `body` for the same reason the rows are data: the runner has no renderer, and a rule written into a view is a rule nothing asserts. `isToday` rather than the shorter `!isFuture` is the load-bearing half, and it is invisible on today — the two agree on today and on tomorrow and part company on every past day, which is the case the rule exists for and the one §14 asserts. Two things separate this overlay from the calendar's. It is anchored to the `+` by `ActivityMenuAnchorKey`, a `PreferenceKey` reading the button's frame in `HomeDashboardView.scrollSpace` and consumed by `.overlayPreferenceValue` — the same mechanism as `RingsBottomKey` and under the same two rules (`static let` default, and no `@State` written by the transform, which runs on every scroll frame) — rather than by a `padding(.top, N)` constant, because the button's y moves with the top bar's height and a fixed number would silently stop matching. And `overlayPreferenceValue` is a different modifier from the plain `.overlay` the calendar uses, so the two stack rather than replace one another; they cannot be open at once, since either scrim covers the anchor that opens the other. The two share one `.hidingTabBar(isPresentingCalendar || isPresentingActivityMenu || isPresentingLiveSession)` call rather than two or three — the flag list is the whole of Home's tab-bar policy, and more than one `toolbar(_:for: .tabBar)` modifier for one placement resolves by an ordering rule not worth relying on. Both overlays are hand-rolled `ZStack`s, which is the deliberate choice and not an omission: the app contains no `Menu`, `.popover`, `.confirmationDialog`, `.contextMenu` or `presentationDetents` anywhere.
* **`LiveSessionView` is a pushed page whose state outlives the push, which is the one thing that separates it from every other screen here.** It owns no `NavigationStack` and no view model — the first is the shape `RecoveryDetailView`/`SleepDetailView`/`StrainDetailView` share, and the second is the feature: the session is `LiveSessionUseCase`, held by `DIContainer` and handed down from `MainContainerView`, so **backing out of the screen does not stop the recording** and re-entering it shows the accumulated figures because `snapshot` belongs to the use case. There is deliberately **no `.onDisappear { end() }`**: adding one would end every session the moment a reader looked away, which is the opposite of what the screen is for. **The heart-rate block is one element and not two**: `LiveHeartRateView` draws a `HEART RATE` section label over a large left-aligned reading with its `BPM` unit, and directly beneath it the five reserve bands as a single scale carrying a white mark at that reading's position — the figure is *what* the heart rate is and the scale is *where it falls*, and the two are read together or not at all. Splitting them into a reading card and a separate zones card was wrong in both directions: the figure arrived with no scale to read it against, and the scale was filled with the session's time-in-band, a different quantity answering a question nobody had asked. So the scale is a **position** scale — its five segments never move, because a segment's width is that band's share of the *reserve*, which the profile fixes, and only the mark travels — and `HeartRateBandScaleView`'s five names come off `StrainAccumulatorMath.zoneReserveBandLabels`, derived from the same array the band edges are, because a label typed into a `View`'s `body` is a rule the runner cannot see. The mark is `Snapshot.bandScalePosition`, resolved by `LiveSessionAccumulator` from the session's own zone table rather than rebuilt here, and it is `nil` exactly when the reading is: **the absence is not a mark at zero**, since a worn strap at rest legitimately draws at the scale's left edge and parking an unheard-from session there would state the two as one thing. `Snapshot.isOnBody` drives a status line **below** the scale — kept, and not decoration, because it is the only element there that separates a reading from a worn strap from one from a strap sitting on a table, and its two states read `LIVE TELEMETRY` and `STRAP OFF BODY`. The page's own `awaitingHeartRateBlock` draws the same label, the same 40 pt slot with a dash in it and the same scale with no mark at all, so the block does not reflow when the first sample lands. `LiveSessionAccumulator.Snapshot.recentHeartRates` is where a view-owned buffer would have made the loss visible, and it lives on the snapshot rather than in the view's `@State` so it survives a reader backing out and returning — **it currently has no screen reader**, which is a state rather than a design. The tab bar is hidden for it by **Home's** `.hidingTabBar`, not by the `.hidingTabBar(true)` the page itself carries — measured on the simulator, a `.toolbar(.hidden, for: .tabBar)` declared on a pushed destination does nothing and leaves the bar drawn over the session, hiding its `END` button, so the destination-side call states the intent while the root-side line does the work; the two must move together, and the gotcha in `CLAUDE.md` carries the measurement. The timer is `Text(_:style: .timer)`, system-rendered, so it ticks with no update of any kind — which is why elapsed time is never computed from a sample count, and why the timer and the figures can legitimately disagree while the app is suspended. This is also the app's only writer of `workouts` rows and its only `SaveWorkoutUseCase` call site. Three fields on that session are deliberate. `source` and `hrZonePercents` are `nil` — the second because that column is documented as WHOOP's own `HR Zone n %` block out of `workouts.csv`, and writing this app's computed zones into it is the two-producer defect the `source` column exists to prevent. `activityName` is **set**, to WHOOP's own abstention word `Activity`: a name is a label and not a measurement, this app records a session without classifying it, and WHOOP answers that same case with a word rather than an absence — its classifier abstains rather than guessing and its export writes exactly `Activity` on 197 rows. `ActivityGlyph` deliberately holds no entry for the string, so the `ACTIVITIES` row takes the `figure.run` fallback exactly as it did when the field was `nil`, and no screen moved. **The session's zone percentages are drawn nowhere, and the bar above is not them.** A distribution of a session's time and a position on a scale are different quantities with different shapes, so `Snapshot.zoneSeconds` and `Snapshot.zonePercents` are kept and asserted with **no screen reader** — they are the only observable form of the accumulator's zone state and therefore the only thing holding its two denominator rules. **The page draws no card chrome anywhere below the ring**: the heart-rate block and the three figures under it sit straight on the background, separated by hairline rules rather than each sitting in a card of its own, which is the reference's arrangement. **The `AVG HR` / `MAX HR` / `CALORIES` tiles draw a glyph, then the name, then the figure**, and the glyph carries the tint while the name stays neutral — Home's `activityRow` shape, where a workout's symbol is `Theme.strainRing` and a night's is `Theme.sleepPerformance`. The two heart tiles take `Theme.livePulseCyan`, this page's own heart-rate colour, and `CALORIES` takes `Theme.strainRing`, which is the colour the same figure is drawn in on Home and is *why* it is that colour — the number comes out of `StrainAccumulatorMath`, the strain model, and not out of a calorie model this app does not have. An unmeasured tile dims its glyph and its name together, and withholds the unit beside the dash, so `— KCAL` never appears. **The route card is the page's one control, and it is opt-in per session.** A `Toggle` labelled `RECORD ROUTE` sits below the three tiles and above `END`, bound not to `@State` but to the use case, because permission is async and a `Toggle` needs a synchronous setter — the binding's setter hands `setRouteRecording(_:)` to a `Task`. It is **off by default**: not every session is outdoors, and the session screen is the one place the app could try to infer that, which the standing ruling forbids it from doing. Its refusal note mirrors the live-activity note in the same slot shape, and it is the absence rule applied to a capability — a user who declines location gets a sentence explaining that the *route* is missing, while the session records on: **a route that cannot be recorded is a missing route, not a missing session.** The two refusals are deliberately two sentences rather than one, because a permission this app was denied is fixed in a per-app setting while Location Services switched off device-wide is not, and a single message would send the user to the wrong screen. **The route has no screen reader**: `workout_route_points` is written and read back by the repository, and nothing draws it — the map is a later change waiting on a mockup, so the toggle is currently the whole of the feature's visible surface.
* **`ProfileDashboardView` is the app's only screen that collects a body metric, and it is behind More rather than a tab.** It is a fourth `NavigationLink` on `MoreView`'s own `NavigationStack`, beside Coach, Device and Settings. It edits exactly three fields, and the reason is the standing rule that a control with no consumer is omitted rather than added as decoration: **weight** feeds `StrainAccumulatorMath.estimateCalories`, and the two heart rates are the inputs `StrainAccumulatorMath.computeZones` cannot build the Karvonen bands without. `heightCm`, `birthDate`, `name` and `baselineHrvRmssd` are on the entity and have no reader anywhere in `Sources/`, so they are not collected. `ProfileDraft` is the parsing and formatting, lifted out of the view model for `DayBarRules`' reason — the runner has no renderer, and a rule in a `body` is a rule nothing can assert — so §18 drives the text field's whole grammar (blank, `"75"`, `" 75.5 "`, and the comma decimal separator a European keyboard produces) as a value. An **empty weight field is the user saying they have not supplied one**, not a request to store zero: the save writes `nil`, the calorie figure stays a dash, and the status line says so rather than reporting a success the screen contradicts.
* **Two ring components, deliberately.** `GaugeRingView` draws an angular gradient, an outer glow, and its label *inside* the ring; Strain, Sleep and Recovery depend on that look. Its per-caller styling is a set of **defaulted** parameters — `ringColor`, `lineWidth`, `size`, and since the sleep detail page a `labelColor`, and since the live session a `labelScale` and a `labelFirst` — so a screen can restyle its own ring without the other two moving; that page is the one caller that passes a label colour, and the one whose label carries a line break, while `LiveSessionView` is the one caller that passes a label scale, because `ACTIVITY STRAIN` is the longest label any ring here prints and at the shared `0.09` it is wider than the chord it sits on, and the one caller that also passes `labelFirst`, because its reference names the quantity *above* its figure where every other ring here puts the figure first. **That overflow is measured rather than seen, and nothing in this repo can catch it**: on a 190 pt ring with an 18 pt line the inner edge is at radius 86, the label's lower edge sits `dy` below the ring's centre, and the chord there is `sqrt(86² − dy²)` — 151.8 pt, against 159.9 pt of text, so the word crosses the stroke by 4.1 pt at each end with every build and the whole suite green. Short labels are nowhere near the limit (`STRAIN` is 76 pt), which is why this is a parameter for the length of one screen's word rather than a corrected default. **`labelFirst` relieves that same constraint rather than adding to it**: the chord is widest at the ring's centre line, so moving a label up from the bottom of the stack can only widen the chord it must fit inside, and a caller that has already narrowed its label is simply given more room. `MetricRingView` is the flat counterpart Home's mockup calls for — neutral track, value centred, label beneath — and is a sibling rather than a mode of `GaugeRingView`, so restyling one screen does not move three. `MetricRingView` takes its value as an **optional** `String?`: a caller passing a dash cannot also pass a fill, so the ring cannot contradict itself. It also takes `showsLabel` (defaulted `true`, so the three existing call sites do not move), which Home's collapsed header sets to `false` — its label font is fixed at 10pt rather than scaled from `size`, so at 40pt the words would be wider than the rings and would decide the header's height.
* **The Recovery ring's colour is the day's tier**, not a fixed green — green 67–100, yellow 34–66, red 0–33, so a 20% morning reads red on Home exactly as it does on the Recovery tab. The boundaries live in one place, `RecoveryMetric.RecoveryState`'s three `Range<Int>` constants (`greenRange`, `yellowRange`, `redRange`), which `init(score:)` is built from; `RecoveryMetric.state` forwards to it and `GenerateCoachInsightsUseCase` reads it rather than comparing against `67` itself. Those constants are `public` because a **view** now has to print them: the calendar's key reads `<34%`, `34% - 66%` and `>66%` off the ranges (`RecoveryTierLegend.entries`) instead of typing the numbers a second time. Note the two ends are different bounds — `<34%` is yellow's *lower* bound and `>66%` is its *upper*, `greenRange.lowerBound - 1` — which is the off-by-one a hardcoded key would have shipped. `RecoveryState.color` (`Presentation/DesignSystem/RecoveryState+Extensions.swift`) is the single mapping from tier to token, used by Home's ring and by the Recovery tab's gauge, HRV card and trend chart. It is a `Presentation` extension rather than a property on the enum because `Domain` imports only `Foundation` and cannot name a `Color`. No fill is drawn for an unmeasured day, so a legacy `score: 0` placeholder never reaches the screen as a red 0%. `StressMath.Band.color` (`StressBand+Extensions.swift`) is the same shape for the Stress Monitor's three bands, and exists for the one-mapping rule: the tile's label and the chart's fill must not be two definitions. `StressMath.Band.gradient` is that file's second export and the third instance of the same rule — two charts now fill under a stress trace, the day's `StressMonitorChartView` and the night's `SleepStressChartView`, and a divergence between their fills would not be a styling difference: it would put "high" at a different score on two screens that both label their axis 0–3. It is on `Band` rather than on `Theme` because its stops are `StressMath`'s band edges divided by `StressMath.maximumScore` — the same two numbers `band(forScore:)` branches at — so neither chart types `1.0` or `2.0`.
* **Home navigates from six places, and five of them are pushes on the `NavigationStack` it already owns** — the **recovery ring**, which pushes `RecoveryDetailView` seeded with the day on screen; the **sleep ring** and the **strain ring**, which push `SleepDetailView` and `StrainDetailView` on the same terms; the **status badge**, which pushes `DeviceDetailView`; and each row of the **ACTIVITIES card**, which pushes `ActivityDetailView` for that session. The sixth is the day bar's title, which opens the month calendar and is an **overlay rather than a push**. **Only the workout rows are wrapped, and the SLEEP row is deliberately left inert** — it is drawn by the same helper from a `SleepSession`, and a sleep row has no workout behind it, so wrapping the helper rather than its call site would give that row a destination that does not exist. The badge is the only element on Home that is about the *strap* rather than about the day, which is what makes it the honest way in — and wrapping it in a link required care in two places that a screenshot would not reveal: the `batteryText` dash gate had to survive untouched, and the accessibility label had to move onto the link with a hint rather than being left on the inner `HStack`, which would have announced a battery percentage as a button with no indication of where it leads. Everything else the mockup draws is still omitted: `CUSTOMIZE`, the pencil, the ACTIVITIES expand icon, the chevrons beside the rings and the STRESS MONITOR tile. A control that looks tappable and is not reads as broken; the day-bar title is honest because it has somewhere to go, and on the other three screens `onTitleTap` is `nil` so its label is not a button at all. **The rings push rather than switching to their tabs, and that is a data decision rather than a styling one**: `RecoveryDashboardView`, `SleepDashboardView` and `StrainDashboardView` each keep a private `selectedDate` seeded to `Date()`, so a tab switch would show *today*, and today is past the export's end — the reader would tap an 87% ring on an imported day and land on "No data recorded". Each pushed copy is seeded with Home's own `selectedDate` and owns its day from there, so Home's day does not move underneath it, which is the same independence the tabs already have; **each therefore has a second view model built in `MainContainerView`**, because sharing one would let the pushed copy move the tab's day. **The pushed copies do not page, where their tabs do**, and all three share that reasoning: `RecoveryDetailView`'s own doc comment makes the argument and the other two follow it — these pages are one day's reading against one trailing window, so a stepper would invite the reader to page away from the figure they just asked *why* about, and the comparison at the foot would then be describing a window with no visible top. **The STRESS MONITOR tile is the one element on this row still inert**, for that same reason rather than a different one: it has no detail page to push, and the three rings are the shape to copy when it gets one. The chevrons stay omitted: a chevron on one of three otherwise identical rings would say the other two are broken. Two `RecoveryViewModel`s exist for the same reason two days exist — sharing one would let paging the pushed copy move the tab's day.

### D. Core Layer (Cross-Cutting Utilities)
* **Math & Signal Processing**: Robust mathematical engines for Heart Rate Variability (RMSSD/SDNN), Borg-scale exponential Strain integration, rolling baseline statistics, the Sleep Need model, daytime Stress activation, and the VO₂ max estimate.
  - `LiveSessionAccumulator`: a running session's Strain, heart rates and calories, accumulated **incrementally from the live sample stream** rather than re-derived by re-walking it — `StepAccumulator`'s reason, and the same reason it is a plain `Sendable` struct in `Core/Math` that the runner can drive with no database, no device and no renderer. It is deliberately **not** `CalculateStrainUseCase`: that type reads a whole calendar day out of `BiometricRepository`, rebuilds the zones from `UserProfileRepository` on every call and writes a `strains` row, so calling it per sample would hammer SQLite, write a row keyed on an instant rather than `startOfDay`, and measure a different population from the one on screen. It reuses `StrainAccumulatorMath`'s own functions, so no zone weight and no `k` is restated — but **two of its conventions fork from the day model on purpose, and both are recorded in the type**. The first sample's duration is `1.0` s, the constant `CalculateStrainUseCase` writes for `i == 0`, rather than a difference against the session start, so the live figure and a recomputed day figure differ by at most that one term. And the calorie term divides by `Σ min(5.0, Δt)` rather than by `samples.count / 60` — a fabricated duration: on a 1 Hz stream the two coincide, and where they diverge the measured span is the honest one. `strain` is `Double?` — `nil` until a sample arrives, `0.0` once one arrives that never reached zone 1 — which is `StrainScore.hasMeasurement`'s own distinction. Its zone percentages are **not** `WholePercentMath`'s: those five bands divide by measured time and time below zone 1 belongs to no band, so a column forced to sum to 100 would claim the five zones cover the session. `bandScalePosition` is the one of its fields the session screen actually draws — where the latest reading sits on the five bands laid end to end, as a `0…1` fraction, resolved here from the session's own zone table so the mark is placed on the same scale the session was scored against, and `nil` exactly when `latestHeartRate` is. `zoneSeconds`, `zonePercents` and `recentHeartRates` are a bounded buffer and two aggregates with **no screen reader at present** — kept, and asserted, because they are session state rather than screen state: they live here rather than in a view's `@State` so a reader backing out and returning finds the session as they left it, which is the user's stated requirement, and a screen that draws any of them again reads it with no change to this type.
  - `SleepNeedMath`: the sleep a night required, as `baseline + 6.40 min × the previous day's Strain`. The coefficient is **fitted to the bundled export** rather than cited, because WHOOP publishes this model's shape and none of its constants; the type's own doc comment carries the fit, the 5-fold cross-validation, and the three WHOOP inputs the model deliberately omits. Accumulated Sleep Debt, naps and Sleep Stress are named WHOOP inputs that are *not* implemented — each with its basis in `docs/ALGORITHMS.md` §4.
  - `StressMath`: daytime physiological activation on WHOOP's published 0–3 scale. WHOOP publishes this model's inputs, its 14-day baseline window and its band edges, and **not** the mapping between them — so every constant in the type is this app's own, calibrated to reproduce the described behaviour, and this app's number will not agree with the WHOOP app's. Same bargain as `SleepNeedMath`; the whole model is in `docs/ALGORITHMS.md` §5. It also owns `wakingWindow(on:calendar:)`, because the chart is not its only consumer: the chart has to know which hours the model *can* score, so it can shade them rather than draw them as calm. It has **two consumers over two different windows** — `AnalyzeStressUseCase` over the waking day and `AnalyzeSleepStressUseCase` over a night's in-bed span — which is why every constant it owns is read by name from both rather than restated, including the band edges the two charts' shared `Band.gradient` is stopped on.
  - `WholePercentMath`: how a set of durations becomes a column of whole percents, by **largest remainder**. It exists because a printed column that sums to 101 is a column a reader can catch by adding it up, while the same column printed by naive rounding looks entirely ordinary — the export stores whole minutes and the exact shares land on fractions, so an eight-hour night split `4.2 / 1.8 / 1.6 / 0.4` hours rounds to `53 + 23 + 20 + 5 = 101`. Two cards print such a column — the sleep detail screen's typical-range bars and its within-sleep stress rows.
  - `SleepConsistencyMath`: how closely a night's **timing** matches the nights before it, on a 0–100% scale, from the recency-weighted circular boundary shift against the four prior records. Like `SleepNeedMath` its constants are **fitted to the bundled export** rather than cited, and like it the fit and its error are carried in the type's own doc comment. Three things about it are decisions rather than details: it defines its own nested `Night` value type instead of taking a `SleepSession`, because `Core/Math` does not name `Domain` entities (`StressMath` takes a `Double` and returns its own `Band` for the same reason) — so the `SleepSession` → `Night` mapping lives in `SleepConsistencyScoring.night(from:)`, one definition shared by the score reader and the chart; it returns `nil` below four priors rather than rendering a partial score, which is the gate `SleepNeedMath` and `BaselineStatisticsMath` apply to insufficient history; and it carries **two** model outputs rather than one — `consistency(for:history:)` is the figure, and `typicalBoundaries(for:history:)` is the recency-weighted **circular** mean of the same four priors' onsets and wakes, which the consistency card draws as its two dashed rules. `circularMean` is where that clock arithmetic lives, and its degenerate-input guard is on the resultant's length rather than on the components being zero, because a true cancellation is not zero in floating point. `clockMinutes(fromNightClock:)` is the inverse of `nightClockMinutes`, for the three callers that print a night-clock minute as a time of day. The model is in `docs/ALGORITHMS.md` §4.
  - `RespiratoryRateMath`: the breathing rate a night's own beats carry, by respiratory sinus arrhythmia — respiration modulates the R-R interval, so a peak in the tachogram's 0.1–0.4 Hz band **is** the rate. This is the first signal processing in the repo (no FFT, no vDSP, no resampling anywhere else) and the only `Core/Math` type whose input is a **time series** rather than values: it takes `[BiometricSample]`, which is why it also owns `usablePackets`/`contiguousRuns`/`isContiguous` — the rule that decides whether two BLE notifications' beats may be chained at all, built on the SIG characteristic's own meaning (a packet's R-R field carries the intervals since the previous notification, so the seam is `dt − span` of the *later* packet). It returns `Double?` and never `0.0`, and unlike the fitted models above it has **no ground truth in this app at all** — the export carries no R-R series — so its constants are derived from published window lengths and its threshold from a synthetic noise measurement. `docs/ALGORITHMS.md` §4 carries the contiguity rule, every constant with its basis, and what it cannot be validated against.
  - `SleepDebtMath`: the running sleep deficit WHOOP names, as a **lagged** accumulation — the export's own column correlates 0.891 with the *prior* night's shortfall against 0.506 with its own, so a night's debt sums the shortfalls strictly before it and never its own. Fitted to the bundled export like `SleepNeedMath` and `SleepConsistencyMath`, and carrying its fit table in the type's own doc comment. Three things about it are decisions rather than details: it defines its own nested `Night`, for the same `Core/Math`-does-not-name-`Domain` reason `SleepConsistencyMath` does; it is written as a **closed form over an explicit sort rather than as a walk**, because a recurrence has loop-carried state and reading the export in its own newest-first file order moves MAE from 8.31 to 22.69; and it **may legitimately return `0`**, uniquely among the numbers this app computes, since WHOOP's own column bottoms out at zero — `nil` is the word for *not scored*. `docs/ALGORITHMS.md` §4 carries the formula, the constants, the fit table and the recorded negative result on a repayment term.
  - `SleepOnsetMath`: where a night begins and ends, from the classified epochs themselves — onset is the start of the first run of consecutive non-`awake` epochs whose own **wall-clock** span reaches ten minutes, wake the end of the last such run, and no qualifying run means no night at all. **A session's first and last sample are the edges of the read window (9 PM → 10 AM, *when the strap might have been worn*) and not of the night** — a strap put on at 7 PM would report a night beginning at 7 PM. It follows the `Core/Math` convention exactly — a locally-defined nested `Epoch` rather than a `SleepStageSegment`, for the same reason `SleepDebtMath.Night` and `RespiratoryRateMath.BeatPacket` exist — and its one constant is **cited** (`SO1`/`SO5`/`SO10`, the actigraphy convention, with Busa et al. 2022 finding the choice moves no sleep variable) rather than fitted. `docs/ALGORITHMS.md` §4 carries the rule, the citation, and the quiet-wakefulness blind spot that no run length can fix.
  - `Vo2MaxMath`: the one model here whose constant is **cited rather than fitted** — the Heart Rate Ratio Method, `15.3 × HRmax / HRrest` (Uth, Sørensen, Overgaard & Pedersen 2004), called `heartRateRatioEstimate(maxHeartRate:restingHeartRate:)`. That makes it the mirror image of the two above: they reproduce a model whose constants WHOOP withholds, and this one implements a published constant against a proprietary model it declines to reimplement. Its caller is `Domain/Entities/MetricWeek.swift`, **not** a screen: the estimate is computed per day inside `makeDay` from that day's already-gated resting heart rate, so it is derived on read, stored nowhere, and cannot disagree with the RHR panel beside it. `StressScore` and `StressWindow` name `StressMath` the same way: **`Domain` importing only `Foundation` is a rule about *frameworks*, not about the module's own layers.** `docs/ALGORITHMS.md` §6 carries the citation, the constant's derivation, the error bar that applies because this app's `HRmax` is assumed rather than measured, and the measurement that rejected the day's own observed peak as the anchor.
  - `StepDetectionMath`: the pedometer, and the one model here whose **input is a waveform** rather than a statistic — three 100 Hz accelerometer axes in g. It removes a per-axis trailing gravity mean, judges the magnitude of what is left against an adaptive level with a floor, and enforces a refractory interval. Its nested `Sample` carries `xG`/`yG`/`zG` rather than a pre-computed magnitude, so the caller cannot hand it a magnitude from a different gravity treatment than the one the detector uses. Following the convention above, it names no `Domain` type — `MotionBatch` is a `Domain` entity, so the mapping lives in the caller. WHOOP publishes no step model, so nothing here is cited or fitted against anything this app can see: the band and the interval ceiling are conventional figures and the two fitted constants are this app's own, which the type's doc comment says in `SleepNeedMath`'s voice. `docs/ALGORITHMS.md` §7 carries the rule and the constants.
  - `StepAccumulator`: the incremental driver over `StepDetectionMath.Detector`, and it is incremental for a measured reason rather than an aesthetic one — a full day at 100 Hz × 3 axes is **≈26 million samples**, so a detector run on read would re-walk a day's motion to redraw one tile. It holds the filter state, the last accepted peak and the running count, and it carries a `baselineStepCount`/`measuredSeconds` seed so a process that starts at noon continues the morning's count instead of restarting it. Its `accept` **refuses outright** a batch whose axes disagree in length, an empty batch, or a non-positive sample interval, contributing no steps *and no measured time* — truncating to the shortest axis would count a partial stride as a whole one and hide the defect, and counting samples at an assumed spacing would invent the time they cover. `reset()` clears the detector and keeps the baseline, because the day's stored count is not this process's to drop: crossing midnight means building a new accumulator, which is why the baseline is a `let`.
* **Formatting and Logging**: `Core/Extensions/` holds the two files that turn stored values into the strings the screens print, and they are here rather than on the views because a duration is printed on more than one screen and two formatters that agree today are a bug that fires later. `Double+Extensions` carries `formattedOneDecimal`, `formattedHoursMinutes`, `formattedCompactHoursMinutes` and `formattedSignedCompactHoursMinutes` — the last is the compact form with a leading `+`, which exists because a comparison column needs the sign shown rather than left to the sign of the number, and `rounded(toPlaces:)` beside them. `Date+Extensions` carries the time, short-date and weekday abbreviations the day bars and chart strips print, plus `formattedClock(minutesOfDay:)` — the one place minutes past midnight become a clock string. It prints a whole hour as `"7 PM"` and a minute as `"7:56 AM"`, and that asymmetry is a rule rather than an accident: a **tick** on a whole-hour axis is a time of night and three characters of `:00` five times down a gutter is noise, while a **mean** lands on a minute and dropping its minutes would print a figure the model did not produce. Midnight is `"12 AM"` rather than `"0 AM"`, and a negative or past-a-day count wraps rather than printing a negative hour. `Core/Logging/AppLogger.swift` is the app's `os.log` wrapper and the sole reason `Core` imports anything beyond `Foundation`.
* **Dependency Injection**: `DIContainer` for clean, modular wiring and testing overrides. The strap-model work added two wires and both are constructor-injected like everything else below the container: `strapModelRepository` (`UserDefaultsStrapModelRepository`) goes into `WhoopBLEManager`, because resolution happens inside a synchronous CoreBluetooth callback, and `protocolCatalog` (the `WhoopProtocolProviding` conformance over `WhoopProtocolProfile`) goes into `DeviceDetailViewModel`, which is the only thing that has to answer "can this build speak that strap" before the user picks. `DIContainer.preview` and `DIContainer(useMockBLE: true)` take the same two; there is no mock variant of either, because neither has anything to fake — one is a `UserDefaults` dictionary and the other is a pure function of the generation. `analyzeSleepStressUseCase` is wired the same way and takes one dependency for a reason worth naming: `biometricRepository` only. It is deliberately given **no `sleepRepository`**, because the prior nights it scores against are handed in by the caller, and leaving the repository out is what makes that structural rather than a convention — a use case that could fetch its own history could describe a different night set from the cards above it.
* **`DeviceDetailViewModel` is built in `MainContainerView`, not inside the `NavigationLink`'s destination closure.** That closure is re-evaluated on every push, so a view model constructed in it would be a fresh one every time — losing the device subscription each push and starting another.

All three sources write the **same** day-keyed rows through the same repositories, so a day has one
recovery row regardless of which source produced it. `RecoveryScoring` is the meeting point: it owns
the z-score weights, and the metric filter that keeps an SDNN day and an RMSSD day out of each
other's baselines. Each importer only fills days that have no local measurement, so a strap-recorded
day is never overwritten by an imported one.

The two stress branches are the diagram's two **read-only** producers of a derived value, and they
are the only ones: each reads `biometric_samples` on demand and returns a value with no repository to
store it in, which is why neither can damage a stored day and both are safe to point at any date. They
differ in exactly one input — `AnalyzeStressUseCase` reads the day's waking window
(`StressMath.wakingWindow`, 06:00–22:00) and `AnalyzeSleepStressUseCase` the night's own in-bed span,
which crosses midnight and is not a range within any calendar day. The night model's baseline comes
from prior **nights**, one bounded read per night, because a night's beats are not a day's.

`[LiveSessionUseCase]` is the diagram's **fourth consumer of the sample stream and its only live one**, and it is the branch that writes from a screen. Everything else in this diagram is a day-scoped read or a bulk import; this one is fed by the same `AsyncStream<BiometricSample>` that `CalculateStrainUseCase` reads, accumulates as the samples arrive, and produces a `workouts` row only when the user ends the session — which is why the row's day key is `startOfDay` of the session's *start* rather than of any sample, and why a session left running overnight still files under the day it began. **It is the diagram's only box with a second input**, and it is a platform capability rather than a data source: `LocationTracking` yields `WorkoutRoutePoint`s into the same use case while the screen's route toggle is on, each stamped with the reading in force at that moment, and they ride out on the row `END` already writes — so the route needs no new edge to the database and no new writer, which is why the drawing shows it as an arrow into the box rather than a second column. The toggle is **off by default and opt-in per session**: not every session is outdoors, and this app does not classify activity type, so it cannot infer that. Three things about the branch are deliberate and none is visible in the drawing. It has a **second output, and it leaves the app entirely**: `LiveSessionUseCase`'s updates go out through `LiveActivityControlling` to an iOS Live Activity, so the lock-screen card is a data-flow destination that no repository and no table is involved in — the widget extension is a second process that reads nothing from this database and cannot, which is the whole reason it links the Kit product rather than `Whoopsy`. **The route is a third destination and a table-backed one**, unlike the card: it reaches `workout_route_points` through `SaveWorkoutUseCase`, which delete-then-inserts the points inside the same transaction as the row, and it has no screen reader at all — the map is a later change. And it is the only branch here that is **not** idempotent by day: every other writer in this diagram skips a day that already has a measurement, while two sessions on one afternoon legitimately produce two rows, because `workouts` is `id`-keyed. Its accumulator forks from `CalculateStrainUseCase` in exactly two places — the first sample's duration and the calorie denominator — and both are in §2.D.

The third input is unlike the other two in two ways that the diagram does not show. It is **not a
sync**: it reads files that shipped inside the app and runs once, when the user asks (Settings), so
there is no availability question and no background path. And it is the only source whose Strain is
not computed here — the export holds one row per day and no heart-rate series, so
`WhoopExportImporter` stores WHOOP's finished score rather than integrating one. See `docs/ALGORITHMS.md`
§2.

**One row type reads all three files, and the diagram's third column is one parser and one importer
for that reason.** `physiological_cycles.csv` is the one the button is about and the only one whose
absence is an error; `sleeps.csv` contributes the export's eight naps and `workouts.csv` its 673
workouts, and either being unbundled costs the import those rows and nothing else. The three files
share their date, timezone and heart-rate columns, so they parse into one `WhoopExportRow`, and the
importer walks each file's rows the same way. What comes out the far end is therefore **five** row
types: `recoveries`, `sleeps` and `strains` off the cycle file, each keyed on `startOfDay(Wake
onset)`; `naps` off `sleeps.csv`, keyed on the nap's own onset, since a day holds one night and can
hold several naps; and `workouts` off `workouts.csv`, keyed on a derived id rather than a date,
since a day can hold several of those too. `naps` and `workouts` are the two tables whose rows are
not one-per-day, and both are written through the same repositories the strap path uses —
`GRDBNapRepository` and `GRDBWorkoutRepository`.

Two edges in the diagram are narrower than they read, in the same direction. `[WhoopPacketDecoder]` emits a `BiometricSample` only on the **standard** `0x2A37` heart-rate characteristic, which remains the only producer that reaches `biometric_samples`. Its proprietary branch validates the envelope and hands up a `WhoopRawFrame`, and the consumers of that are **motion only**: the frames reach `MotionPayloadDecoder` and a decoded `MotionBatch` reaches `TrackStepsUseCase`, so the strap's proprietary input now produces `stepCounts` rows and **not** heart-rate rows. No proprietary record is parsed for heart rate, so the historical **heart-rate** drain is still work in `docs/TODO.md` §5 rather than a path on this diagram. **The drain itself is not missing from it** — a banked motion record (type 47) arrives through this same decoder and this same `MotionBatch`, which is the whole reason the shared core is shared: `HistoricalDrainSession` owns the batch structure (which `HISTORY_END` to acknowledge, which `HISTORY_COMPLETE` ends it) and the motion decoder owns the payload, so the app cannot have two ideas about what a batch is. What the drain does *not* yet have is a reader for the type-24 record's own 96-byte header, which is the same gap stated above from the other side. And the motion edge is **unexercised**: no strap has been connected to this machine, so no `MotionBatch` has ever been produced here and `stepCounts` is empty in every database.

Two paths in the diagram deliberately **do not** touch the database. The VO₂ estimate is derived on
read from two values that *are* stored — the day's resting heart rate on its `recoveries` row and the
profile's maximal heart rate — so it needs no column of its own and a persisted copy could only ever
be a second number that disagrees with its own inputs (see `docs/ALGORITHMS.md` §6, which carries the
model, its citation and its error bar; WHOOP's own three-tier model is still the one this app
declines to implement). Steps are stored rather than derived — a **measured** day-keyed row, because
the strap produces the sum itself off its own motion stream rather than the phone's pedometer
producing it on demand — the count is accumulated incrementally and stored, since a day's motion is
~26M samples and cannot be re-walked to redraw one tile (`docs/ALGORITHMS.md` §7). And
`AnalyzeStressUseCase` is derived on read from `biometric_samples`: it answers from a table but
writes nothing, which is what makes it safe to point at any date — the calculate use cases are not,
because they overwrite. All three keep the day-keyed tables holding only what was measured once.

## 4. Testing & Verification Strategy

1. **Domain Tests**: Test business rules, Recovery z-score computations, and Strain algorithms in complete isolation with zero mocks.
2. **Decoder Tests**: Verify binary packet parsing against raw hex fixture dumps with various CRC edge cases and corrupted frames. The assertions that carry the weight are the **published known-answer vectors** from `docs/BLE_PROTOCOL.md` §2.1 — a CRC checked against its own implementation is not a check — one assertion of that shape passes for a wrong polynomial, byte order and input alike. The corruption cases are built by mutating a **well-formed frame the encoder produced** (a bad SOF, a bad header checksum, a bad payload checksum, a truncated frame, a frame that lies about its length), so each rejection is a one-byte difference from a frame that was accepted. The generation-resolution rule is asserted as a pure function of its two inputs, `WhoopBLEManager.resolvedGeneration(stored:advertisedName:)`, because a `CBCentralManager` cannot be constructed in a test run — doing so raises a system Bluetooth prompt.
3. **Repository Tests**: Validate GRDB persistence and query operations against `LocalDatabaseManager(inMemory: true)`.
4. **Import Tests**: Drive `HealthKitImporter` with a fixture `HealthStoreClient` and an in-memory database, asserting day attribution, that a day without a reading stores no row, and that a repeated import does not duplicate rows. No device and no HealthKit entitlement are needed. `WhoopExportImporter` is driven the same way against the **real** bundled CSV read by path, asserting the day keys it derives (recomputed independently from the parsed rows), the minutes-to-seconds conversions, and that a second run writes nothing.
5. **ViewModel Tests**: Ensure state transitions and UI updates respond predictably to use case streams.
